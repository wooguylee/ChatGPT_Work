### 설치 및 사용

```bash

```

- 추가 요구사항: **Python 환경 + Playwright 및 브라우저 런타임**이 필요하다.

**평가:** UI Agent가 “코드를 보고 상상해서 클릭”하는 패턴에서 벗어나 실제 화면을 보고 행동하도록 만드는 점이 좋다. 다만 Playwright/browser dependency가 준비되지 않은 환경에서는 첫 실행 비용이 있다.

**평가:** 설치 후 바로 적용할 수 있고 결과를 `docker build`로 곧바로 검증할 수 있어 Codex 개발 workflow에 붙이기 쉽다. 단, Alpine/distroless가 항상 정답은 아니므로 native dependency가 많은 프로젝트에서는 호환성 검증이 필요하다.

- 품질 점수 / 보안 점수: **SkillsMP에서 미제공**

### 무엇을 해결하나

한 Agent가 설계부터 구현·리뷰까지 혼자 하면 처음 세운 가정에 계속 끌려갈 수 있다. 이 Skill은 사용자가 명시적으로 `consult`를 요청했을 때 Claude Code를 **도구 권한 없는 독립적인 second opinion**으로 호출해 architecture, naming, API lifecycle, trade-off, hidden coupling, rollback 위험 등을 비판적으로 검토하게 한다. 중요한 점은 Claude가 구현권을 넘겨받지 않고, **주 Agent가 계속 소유권을 가진 채 방향 검토와 사후 리뷰 두 번의 파동으로 활용**한다는 것이다.

### 설치 및 사용

```bash
npx skills add https://github.com/EpicenterHQ/epicenter --skill consult-claude
```

Skill이 사용하는 핵심 consultation 형태:

```bash
claude -p "$prompt" --no-session-persistence --tools "" --effort high
```

- 추가 요구사항: **Claude Code CLI 설치 및 인증**
- `--tools ""`로 외부 도구 사용을 막고, `--no-session-persistence`로 일회성 리뷰 세션을 만든다.
- API Key를 직접 Skill에 넣는 구조라기보다 로컬 Claude Code 인증을 사용한다.

**Agent에게 줄 예시**

> 이 OAuth 세션 저장 구조를 구현하기 전에 Claude를 한 번 consult해서 hidden coupling과 rollback 위험을 찾아줘. 현재 설계와 관련 diff만 넘기고, 파일 수정 권한은 주지 마.

**평가:** 서로 다른 모델을 “합의 생성기”가 아니라 **독립 reviewer**로 쓰는 패턴이 실무적으로 매우 건강하다. 반면 Claude Code 구독/인증이 추가로 필요하고, 너무 자주 호출하면 비용과 latency가 늘어난다.

### 인기 및 트렌드 지표

- 24시간 설치 증가 / 누적 설치 / 좋아요: **확인되지 않음**
- 품질 점수 / 보안 점수: **SkillsMP에서 미제공**

### 무엇을 해결하나

Codex worker를 여러 개 띄우는 것만으로는 서로가 무엇을 끝냈는지, 어디서 막혔는지, 어떤 dependency를 넘겨야 하는지 공유하기 어렵다. `agent-relay`는 **실시간 message bus, DM, channel, 상태 메시지와 ACK/STATUS/BLOCKED/DONE 프로토콜**을 붙여 multi-agent 실행을 작은 팀처럼 운영하게 한다. 첫 활성화에서 setup script가 Codex 설정에 Relay MCP와 hooks를 연결해, 단순 prompt fan-out보다 한 단계 높은 **상태 있는 협업 orchestration**을 만든다.

### 설치 및 사용

```bash
npx skills add https://github.com/AgentWorkforce/relay --skill agent-relay
```

- 첫 활성화 시 `scripts/setup.sh`가 실행되어 `.codex/config.toml`에 Agent Relay MCP server를 추가하고 hooks 및 worker 설정을 구성하는 흐름이 문서화되어 있다.
- workspace 연결에는 `RELAY_WORKSPACE_KEY` 또는 legacy `RELAY_API_KEY`를 사용할 수 있고, 새 workspace 생성 흐름도 제공된다.
- 추가 요구사항: **Agent Relay MCP/네트워크 서비스**, workspace credential, Codex config/hook 변경.
- credential은 Agent 대화나 로그에 출력하지 않는 것이 중요하다.

**Agent에게 줄 예시**

> 인증/DB/테스트를 3개 Codex worker로 나눠. Agent Relay로 workspace를 만들고 worker마다 ACK → STATUS → DONE 프로토콜을 써서 서로 의존성을 공유하게 해.

**평가:** multi-agent가 실제 개발팀처럼 서로 상태를 전달하게 만드는 방향은 앞으로 중요해질 가능성이 높다. 다만 외부 coordination service와 credential, MCP/hook 설정이 추가되므로 단일 Agent 작업에는 오버헤드가 크다.

### 무엇을 해결하나

Skill이 많아질수록 “설치는 됐는데 실제로 좋은 Skill인가?”, “prompt와 references가 너무 커 토큰을 낭비하지 않나?”, “고친 뒤 정말 좋아졌나?”를 평가하는 도구가 필요해진다. `plugin-eval`은 **정적 분석 → 토큰 budget 설명 → starter benchmark 생성 → 실제 `codex exec`를 격리된 임시 workspace에서 실행 → 결과 비교**를 하나의 workflow로 묶는다. 즉 Skill 자체를 만드는 단계에서 한 걸음 나아가, **Skill을 테스트·측정·회귀검증하는 evaluation layer**를 제공한다.

### 설치 및 사용

요구사항은 **Node.js >= 20**이다. 현재 package가 `private: true`라 public npm 설치보다 local checkout이 기준이다.

```bash
git clone https://github.com/openai/plugins.git
cd plugins/plugins/plugin-eval
npm link
plugin-eval --help
```

전역 link 없이도 실행할 수 있다.

```bash
node ./scripts/plugin-eval.js analyze ./skills/plugin-eval --format markdown
```

주요 command:

```bash
plugin-eval start <path> --request "Evaluate this skill." --format markdown
plugin-eval analyze <path> --format markdown
plugin-eval explain-budget <path> --format markdown
plugin-eval init-benchmark <path>
plugin-eval benchmark <path>
```

- `analyze`, `explain-budget`, `measurement-plan`은 deterministic local workflow다.
- `benchmark`는 실제 **`codex exec` session**을 isolated temp workspace에서 돌리고 `.plugin-eval/runs/` 아래에 artifact를 남긴다.
- benchmark config는 실행 전에 검토해야 하며, 신뢰할 수 없는 prompt/target을 그대로 실행하지 않는 것이 좋다.
- Codex plugin mode로 쓸 때는 `.codex-plugin/plugin.json`과 marketplace 기반 discovery를 사용하며, 설치 후 `$plugin-eval ...` 형태의 자연어 진입점이 제공된다.

**Agent에게 줄 예시**

> 이 `~/.codex/skills/my-skill`을 plugin-eval로 분석해. 가장 큰 품질 문제 3개와 토큰 예산을 보여주고, benchmark까지 돌리기 전에 우선 고칠 것만 정리해.

**평가:** Skill 생태계가 커질수록 “Skill을 평가하는 Skill”은 CI/test와 비슷한 기반 계층이 된다. 아직 public npm 한 줄 설치가 아니라 local checkout/marketplace 구성이 필요한 점은 진입장벽이다.

### 🏆 오늘의 Top Pick

**`plugin-eval`** — 단순히 Agent에게 새 능력을 하나 더 붙이는 Skill이 아니라, 앞으로 늘어날 Skill/Plugin 자체를 **정적 분석·토큰 비용·실제 benchmark로 검증하는 품질 관리 계층**을 제공한다는 점에서 기술적 가치와 생태계 파급력이 가장 크다. 특히 OpenAI 공식 `openai/plugins` 안에서 Codex의 plugin/skill 평가 흐름을 실제 CLI와 연결했다는 점이 중요하다.

### ⚡ Codex에서 바로 써볼 만한 것

**`multi-stage-dockerfile`** — `npx skills add ... --skill multi-stage-dockerfile` 한 번으로 붙일 수 있고 별도 MCP/API Key가 필요하지 않으며, 기존 프로젝트의 Dockerfile 하나만 줘도 바로 생산적인 결과를 얻기 쉽다. 결과물을 `docker build`와 이미지 크기/실행 계정으로 즉시 검증할 수 있어 적용→검증 루프가 짧다.

### 오늘 보이는 Skill 생태계 흐름

오늘 후보들의 공통점은 **“prompt 템플릿”에서 “실행 가능한 운영 프로토콜”로 이동**하고 있다는 점이다. Playwright로 실제 UI를 관찰하고, 다른 모델을 독립 reviewer로 부르고, multi-agent 사이에 상태 메시지를 주고받고, PR 운영 규칙을 Skill로 고정하며, 나아가 Skill 자체를 benchmark한다. 앞으로 Agent Skill의 가치는 문장이 얼마나 그럴듯한지보다 **외부 도구와의 결합, 검증 가능한 실행 루프, 권한·보안 경계, 재현 가능한 평가**에 의해 더 크게 갈릴 가능성이 높다.
