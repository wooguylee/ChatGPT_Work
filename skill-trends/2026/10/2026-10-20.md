## 1. eval-suite-planner

**평가 목적·책임자·판정 기준을 실제 워크북에 연결하기**

- 출처: Microsoft 공식 eval-guide
- 태그: 평가 설계 · RAG · 품질 기준 · 워크북 · 채점기 검증
- 난이도: 중급. 실제 템플릿과 업무 기준, 검토 담당자를 준비해야 한다.

### 무엇을 해주나

에이전트 설명을 받아 정확성·근거성 같은 Capability 평가와 거절·민감정보·프롬프트 인젝션 같은 Trust & Safety 평가를 구분한다. 위험도, 담당자, 통과 기준, 정답 출처, 재평가 주기를 평가 계획 워크북에 채운다. 프롬프트형·RAG형·도구 실행형에 따라 범위를 달리하며, 단순 FAQ 에이전트에 불필요한 도구 호출 검사를 붙이지 않도록 한다. [SKILL.md](https://github.com/microsoft/eval-guide/blob/7a22a8957ced79a35fd7b4634fd5b5eac56c308e/skills/eval-suite-planner/SKILL.md)

Capability는 초기 출시 최소 기준과 이후 회귀·개선 추세를, T&S는 절대 통과 기준을 중심으로 계획한다. 특히 LLM 채점자를 사람의 라벨로 검증할 계획, 정답이 의존하는 정책·지식 원문의 변경 관계를 남기는 점이 유용하다. 문서가 바뀌었는데 예전 정답만 고집하는 평가를 찾아내는 준비 단계다. 실제 통과 기준·위험도·담당자 결정은 사람이 확인해야 한다. [워크북 계약](https://github.com/microsoft/eval-guide/blob/7a22a8957ced79a35fd7b4634fd5b5eac56c308e/skills/eval-guide/eval-suite-template.md)

### 실전 프롬프트

“eval-suite-planner로 첨부한 빈 평가 템플릿을 복사해 사내 IT 도움말 에이전트의 평가 계획을 만들어줘. 승인된 도움말 문서에서만 답하고 계정 변경은 직접 실행하지 않는 에이전트야. 정확성·근거성·범위 밖 질문·민감정보·프롬프트 인젝션을 나누고, 정답 출처·검토 담당자·출시 기준·회귀 주기·채점기 검증 계획을 기록해줘. 모르는 값은 TBD로 남겨줘. 원본 양식과 기존 파일은 덮어쓰지 말고 실제 테스트 실행 없이 새 XLSX와 HTML만 만들어줘.”

### 설치·주의

**실제 빈 Eval Suite Planning & Logging Template가 필요하다.** 없으면 요청해야 하며 Markdown 명세를 보고 임의 양식을 만들어서는 안 된다. 시트·열·머리글·스타일·유효성 검사를 보존하고 기존 셀·행만 채운다. Run Log의 실제 결과 칸은 비워 둔다.

산출물은 양식을 보존한 XLSX와 별도 정적 HTML 리뷰 페이지다. 워크북이 기준 문서이며 HTML 체크 항목이 XLSX에 자동 반영되는 구조는 아니다. 이 정적 페이지는 네트워크 호출·외부 라이브러리 없이 동작하도록 명세되어 있다. 문서 생성·검토 완료를 평가 통과로 표현하지 않는다. [HTML 리뷰 명세](https://github.com/microsoft/eval-guide/blob/7a22a8957ced79a35fd7b4634fd5b5eac56c308e/skills/eval-guide/plan-review-page.md)

## 2. eval-generator

**평가 계획을 질문·기대 답·근거가 연결된 사례로 바꾸기**

- 출처: Microsoft 공식 eval-guide
- 태그: 테스트 데이터 · CSV · 다중 턴 · 회귀 테스트 · manifest
- 난이도: 중급. 기대 답과 rubric을 검토할 도메인 담당자가 필요하다.

### 무엇을 해주나

계획 워크북의 평가 세트를 구체적인 질문과 기대 답변으로 변환한다. 단일 응답은 가져오기용 CSV, 다중 턴은 대화 테스트를 구성할 blueprint로 만든다. 평가 방법·기준·출처·담당자·회귀 대상 여부는 별도 manifest에 남겨 CSV에서 잃기 쉬운 맥락을 보존한다. 계획 없이 업무 설명만 받는 fallback도 있지만 이때 생성되는 최소 6–8개 사례는 충분한 커버리지나 통계적 신뢰를 보증하지 않는다. [SKILL.md](https://github.com/microsoft/eval-guide/blob/7a22a8957ced79a35fd7b4634fd5b5eac56c308e/skills/eval-generator/SKILL.md)

정상·예외·공격성 입력을 포함하고 Capability와 T&S를 별도 세트로 유지한다. 검토 중 기대 답의 사실 부분에는 [VERIFY]를 붙이고, 여러 턴에서는 앞선 맥락이 유지되어야 하는 지점과 취약한 턴을 표시한다. 단순히 질문을 늘리기보다 “이 사례로 어떤 실패를 발견하려는가”를 설명하는 산출물이 장점이다.

### 실전 프롬프트

“eval-generator로 평가 계획 워크북과 가림 처리한 기존 실패 사례를 테스트 초안으로 바꿔줘. 단일 응답은 세트별 Question·Expected response 두 열 CSV, 평가 방법·기준·출처·검토자는 별도 manifest에 기록해줘. 적절한 거절의 성공 조건은 Custom rubric으로 정의해줘. 확인되지 않은 사실은 [VERIFY]로 표시하고 내가 원문으로 검증하기 전에는 확정 답변으로 내보내지 마. 여러 턴 문제 해결 흐름은 별도 blueprint로 만들고 실제 에이전트 호출·업로드는 하지 마.”

### 설치·주의

원문은 최종 내보내기에서 [VERIFY]를 제거한다. **표시가 사라진 것과 사실 검증이 끝난 것은 다르다.** 사람의 확인 기록을 남기고, 검증되지 않은 기대 답을 정답 세트에 섞지 않는다. 임의의 정책·금액·기한을 모델이 채우게 하지 않는 것이 중요하다.

단일 응답 CSV 두 열에는 평가 방법을 넣지 않는다. 가져온 뒤 사용하는 제품 화면에서 방법·rubric·예상 도구 등을 설정해야 한다. 원문의 “7개 방법”, conversation의 Capability use 지원, 거절에 대한 General quality 활용은 현재 공식 표와 차이가 있어 아래 공통 호환성 항목을 함께 적용한다. blueprint도 그 자체로 대화형 평가를 실행한 결과가 아니다. [현재 평가 방법](https://learn.microsoft.com/en-us/microsoft-copilot-studio/analytics-agent-evaluation-overview) · [현재 CSV 가져오기](https://learn.microsoft.com/en-us/microsoft-copilot-studio/analytics-agent-evaluation-create)

## 3. eval-result-interpreter

**평균 점수 뒤의 세트별 실패와 판정 근거 읽기**

- 출처: Microsoft 공식 eval-guide
- 태그: 결과 분석 · 회귀 비교 · 평가 기준 · 실패 분류 · 출시 검토
- 난이도: 중급. 결과·manifest·원본 응답과 채점기 검증 기록을 함께 읽어야 한다.

### 무엇을 해주나

평가 결과 CSV와 manifest를 받아 SHIP·ITERATE·BLOCK 권고, 실패 원인 분류, 수정 우선순위를 구조화한다. 전체 평균보다 세트별 hard gate를 먼저 확인하고, 실제 응답이 틀렸는지 정답·rubric·채점 방식이 틀렸는지 구분하도록 한다. 첫 결과를 빠르게 정리하는 역할이며, 상세한 후속 진단은 다음 triage 스킬과 이어진다. [SKILL.md](https://github.com/microsoft/eval-guide/blob/7a22a8957ced79a35fd7b4634fd5b5eac56c308e/skills/eval-result-interpreter/SKILL.md)

권장 조치를 “무엇을 수정 → 무엇을 다시 실행 → 어떤 결과를 기대”로 연결하고, 두 실행이 있으면 통과 유지·개선·회귀·지속 실패를 구분한다. CSV 설명만으로 원인이 불명확하면 Activity map 같은 추가 근거를 보도록 한다. 이 지도는 관찰 가능한 도구·토픽·입출력 기록이며 모델의 모든 내부 사고를 보여주는 것으로 설명하면 안 된다. [현재 결과·비교 안내](https://learn.microsoft.com/en-us/microsoft-copilot-studio/analytics-agent-evaluation-results)

### 실전 프롬프트

“eval-result-interpreter를 참고해 가림 처리한 변경 전후 결과 CSV, manifest, 채점기 검증 기록을 읽기 전용으로 비교해줘. 승인된 hard gate를 우선하고 Capability와 T&S를 나눠줘. Invalid·Error·인프라 장애·미채점을 Pass/Fail과 구분하고 분모 처리도 설명해줘. 원본 응답과 근거가 충분한 경우에만 실패 원인을 확정해줘. 기준·자료가 없으면 판정을 보류하고, 수정안 세 가지와 회귀 재실행 범위만 제시해줘. 설정 변경·실행·배포는 하지 마.”

### 설치·주의

manifest가 없으면 원문은 파일명·질문에서 gate와 목표를 추정할 수 있게 한다. 출시 판단에는 승인된 기준을 제공하고, 자료가 없을 때는 추정 판정 대신 필요한 자료를 먼저 정리하는 편이 안전하다. SHIP은 분석 권고이며 실제 배포 승인이나 커버리지 보증이 아니다.

“±5%는 정상”, “100%면 너무 쉬운 평가” 같은 표현은 일반적인 통계 법칙이 아니다. 표본 수·반복 실행·세트 구성·채점기 변동을 함께 봐야 한다. 원문의 Pass/Fail 중심 요약에는 Invalid·Error·미확인 상태를 별도 집계하도록 보완한다. 현재 standard harness 결과 보존 기간은 89일로 안내되므로, 장기 비교가 필요하면 권한과 보존 정책에 맞춰 원본 결과·에이전트/세트 버전을 함께 보관한다. [결과 보존·내보내기 안내](https://learn.microsoft.com/en-us/microsoft-copilot-studio/analytics-agent-evaluation-results)

## 4. eval-triage-and-improvement

**실패 원인을 수정·재검증 계획으로 연결하기**

- 출처: Microsoft 공식 eval-guide

- 태그: `평가 디버깅` `회귀 분석` `Copilot Studio` `휴먼 리뷰`
- 난이도: 중상급. 실행 결과뿐 아니라 실제 응답, 원문, 설정 변경 내역을 읽을 수 있어야 한다.
- 추천 대상: 첫 결과 해석을 마쳤지만 무엇을 고쳐야 할지 불명확하거나, 수정 후에도 같은 실패가 반복되는 팀.

### 무엇을 해주나

실패 사례를 대화식으로 조사하고, 원인·담당자·수정 위치·재검증 방법이 연결된 보고서를 만든다. 먼저 지식 소스의 색인 상태, 커넥터 오류, 인증, 평가한 에이전트 버전부터 확인한다. 이후 기대 답안의 노후화나 채점 기준 오류 같은 ‘평가 설정 문제’를 점검하고, 실제 에이전트 품질 문제를 분리한다. 여러 턴의 대화에서는 최초로 잘못된 판단이 발생한 턴을 찾고 이후의 연쇄 실패를 묶는다. [검토한 SKILL.md](https://github.com/microsoft/eval-guide/blob/7a22a8957ced79a35fd7b4634fd5b5eac56c308e/skills/eval-triage-and-improvement/SKILL.md)

앞의 result-interpreter와 진단 체계가 겹친다. 독립 실행도 가능하지만, 함께 사용할 때는 기존 해석 보고서와 동일 버전의 결과를 이어받고 설정·실행 로그를 추가하는 편이 낫다. 예를 들어 ‘잘못된 도구 호출’이라는 발견에서 시작해 도구 설명의 중복, 매개변수 정의, 백엔드 오류 중 어디를 조사할지 좁히는 데 쓴다. 판단의 근거가 없는 부분은 추가 확인 목록으로 남긴다.

### 실전 프롬프트

“eval-triage-and-improvement로 앞서 만든 결과 해석 보고서, 같은 에이전트 버전의 평가 결과, 실패 사례 5개, 최신 정책 원문, 도구 호출 로그와 최근 설정 변경 내역을 첨부한다. 기존 판정은 가설로 취급하고 사례별로 평가 설정 문제와 에이전트 품질 문제를 확인해 줘. 각 항목에 확인된 증거, 부족한 증거, 담당자, 최소 수정안, 영향받는 회귀 테스트를 적어 줘. 다중 턴 사례는 최초 오류 턴을 찾아줘. 설정 수정·재실행·배포·합격 기준 변경은 하지 말고 검토용 계획만 만들어 줘.”

### 설치·주의

- 원문 스킬은 실패를 두 가지 상위 범주 중 하나로 분류하도록 강하게 요구하지만, 참조 플레이북은 복합 원인과 ‘미분류’를 허용한다. 증거가 부족하면 억지로 단정하지 말고 잠정 분류와 필요한 로그를 남기는 것이 안전하다. [진단 의사결정 트리](https://github.com/microsoft/triage-and-improvement-playbook/blob/a4fe20e46c4a50b6860cbdf2529e3ea6b6110faf/triage-decision-tree.md)
- 스킬에 나오는 ‘핵심 턴 수정 후 후속 실패의 40–60% 해소’, 실행 간 변동 폭 등의 수치를 보장치나 통계적 검정으로 쓰면 안 된다. 한 번의 실행만으로 우연한 실패와 회귀를 확정하기도 어렵다.
- 플랫폼 한계를 이유로 합격 기준을 낮추는 제안은 위험 수용 책임자의 검토가 필요하다. 프롬프트 변경은 다른 평가 항목을 악화시킬 수 있으므로, 수정 범위에 맞는 회귀 검증을 계획한다. [수정안과 재실행 범위 안내](https://github.com/microsoft/triage-and-improvement-playbook/blob/a4fe20e46c4a50b6860cbdf2529e3ea6b6110faf/remediation-mapping.md)
- 참조하는 상세 플레이북 파일들은 별도 Microsoft 저장소에 있다. eval-guide만 설치하면 그 상대 경로가 로컬에 존재한다고 가정하면 안 된다.

## 5. eval-faq

**평가 질문을 관련 공식 문서로 연결하기**

- 출처: Microsoft 공식 eval-guide

- 태그: `평가 방법론` `문서 탐색` `채점 기준` `LLM-as-judge`
- 난이도: 초중급. 답변의 수치와 제품 제약을 검증할 기본 지식이 필요하다.
- 추천 대상: 평가 방법 선택, 사람과 AI 채점의 불일치, 다중 턴 평가 등을 빠르게 정리하려는 실무자. 출처 탐색용으로 조건부 추천한다.

### 무엇을 해주나

질문 주제별 URL 표를 이용해 관련 자료를 먼저 읽고, 보통 3–5문장으로 실무적인 답을 만든다. Microsoft 자료를 우선하며 채점기 종류, 데이터셋 설계, 비결정성, 도구 호출, 루브릭 보정 등을 다룬다. 필요할 때 다른 평가 스킬 하나를 제안한다. 장문의 평가 설계나 결과 분석에 들어가기 전, 어떤 문서를 읽고 무엇을 결정해야 하는지 좁히는 데 유용하다. [검토한 SKILL.md](https://github.com/microsoft/eval-guide/blob/7a22a8957ced79a35fd7b4634fd5b5eac56c308e/skills/eval-faq/SKILL.md)

특히 채점기 검증 질문에 활용할 만하다. 정답의 의미를 비교할지, 필수 문구를 확인할지, 도메인별 기준을 적용할지 구분하고, 사람이 독립적으로 채점한 사례와 비교하는 절차를 요청할 수 있다. Microsoft의 루브릭 안내도 사람이 AI 점수를 보기 전에 판단하고, 관찰 가능한 기준과 다양한 사례를 사용하도록 권한다. [루브릭 보정 권장사항](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/kit-rubrics-best-practices)

### 실전 프롬프트

“eval-faq로 사내 정책 문서에 근거해 답하는 RAG 에이전트를 평가하려 한다. 의미가 같으면 통과해야 하는 답변, 반드시 포함해야 하는 문구, 별도 판단이 필요한 업무 규칙에 각각 어떤 평가 방법이 적합한지 설명해 줘. 현재 Microsoft 공식 문서를 먼저 확인하고 5문장 이내로 답해 줘. 마지막에 출처 링크와 사람이 채점한 사례로 검증할 다음 단계 하나를 포함해 줘. 문서 조회가 실패하면 그 사실을 밝히고, 내장 지식의 수치·제품 제약을 최신 사실처럼 단정하지 마.”

### 설치·주의

- 내장 지식은 최신 문서와 차이가 있다. 예를 들어 스킬은 평가 방법을 7개로 적지만, 확인한 현재 standard harness 문서에는 Content safety를 포함한 8개가 나온다. 제품 기능과 지원 평가 유형은 실제 사용하는 환경과 현재 문서를 우선한다. [현재 평가 방법 안내](https://learn.microsoft.com/en-us/microsoft-copilot-studio/analytics-agent-evaluation-overview)
- 수치 오류도 발견했다. 스킬은 성공률 70%, 10회에서 pass@10을 약 97%라고 설명한다. 각 시도가 독립이고 성공 확률이 같다는 가정이면 ‘한 번 이상 성공’은 약 99.9994%, ‘모두 성공’은 약 2.82%다. 실제 시도가 서로 연관되어 있으면 이 단순 계산을 그대로 적용할 수 없다.
- 조회 실패 시 내장 지식으로 계속 답하는 설계다. ‘평가 사례 수’, ‘허용 변동 폭’, ‘출시 가능 점수’처럼 맥락에 따라 달라지는 숫자는 출처와 가정을 확인해야 한다. 짧고 단정적인 답변 형식 자체가 검증을 대신해 주지는 않는다.

### 현재 Copilot Studio와 원문의 차이

현재 **standard harness**용 공식 평가 방법 표에는 **8가지**가 있다. 원문의 7가지 안내와 달리 Content safety가 포함되며, **Tool use는 single response 전용**이다. General quality는 올바른 거절도 abstention 기준에서 낮게 평가할 수 있으므로, 거절 성공을 판단할 때는 기대 행동을 명시한 Custom 기준을 검토한다. 안전성 평가 통과는 모든 상황의 안전 보증이 아니다. [현재 평가 방법](https://learn.microsoft.com/en-us/microsoft-copilot-studio/analytics-agent-evaluation-overview)

standard harness의 단일 응답 CSV는 Question·Expected response 순서의 두 열, 최대 100개 질문·질문당 공백 포함 1,000자 안내와 일치한다. 그러나 방법은 현재 UI에서 추가·설정하며, 원문의 “행마다 방법을 지정”을 유일한 현행 UI 절차로 복사하지 않는다. [현재 단일 응답 가져오기](https://learn.microsoft.com/en-us/microsoft-copilot-studio/analytics-agent-evaluation-create)

반면 **GitHub Copilot harness 기반 새 에이전트의 preview**는 별도 문서다. 현재 지원하는 평가 방법은 General quality뿐이며 기대 답변과의 비교는 수행하지 않는다. conversation 데이터를 사용하며, CSV는 화면의 템플릿을 받고 최대 5MB 조건을 확인한다. standard harness의 8가지 방법·두 열/100개 조건을 이 화면에 그대로 적용하면 안 된다. 설치 도구인 GitHub Copilot과 Copilot Studio 에이전트의 harness 구분도 별개다. [preview 평가 개요](https://learn.microsoft.com/en-us/microsoft-copilot-studio/agents-experience/analytics-agent-evaluation-intro) · [preview 테스트 세트](https://learn.microsoft.com/en-us/microsoft-copilot-studio/agents-experience/analytics-agent-evaluation-create)

같은 저장소 내부에도 동기화 차이가 있다. canonical playbook의 **Step 6은 채점기 검증, Step 7은 기준 실행과 실패 진단**인데 README·interpreter·triage·FAQ에는 Step 6을 baseline으로 부르는 표현이 남아 있다. 번호를 따라 자동 실행하기보다 최신 본문 의미와 채점기 검증 기록을 우선한다. [canonical playbook](https://github.com/microsoft/eval-guide/blob/7a22a8957ced79a35fd7b4634fd5b5eac56c308e/skills/eval-guide/playbook.md)

### 문서 생성과 실제 실행은 다른 단계다

계획·CSV·진단 보고서가 생겨도 실제 평가가 수행된 것은 아니다. live agent 연결·실제 질문 전송·도구 호출·테스트 세트 업로드·설정 변경·배포에는 별도의 실행 범위와 승인이 필요하다. 실제 평가는 연결 계정으로 지식·도구에 접근할 수 있고 비용을 소비할 수 있으므로, 가림 처리한 데이터·테스트 계정·비운영 자원과 예산부터 확인한다. 결과나 질문에 업무 기밀·개인정보가 있으면 모델 제공자·공유 대상·보존 위치도 확인한다. [프로필·연결 설정](https://learn.microsoft.com/en-us/microsoft-copilot-studio/analytics-agent-evaluation-create) · [preview 평가·크레딧 안내](https://learn.microsoft.com/en-us/microsoft-copilot-studio/agents-experience/analytics-agent-evaluation-intro)

동봉 eval-runner.js를 Copilot Studio 평가와 동등한 실행기로 가정하지 않는다. 코드 검토에서 다음 차이를 확인했다.

- 두 열 CSV에는 testing_method가 없어 실행기는 **General quality로 기본 처리**한다. 별도 manifest의 평가 방법·hard gate·목표를 자동 적용하지 않는다.
- LLM 채점은 Anthropic API에 질문·기대 답·실제 답을 보낸다. 모델 ID가 claude-sonnet-4-20250514로 고정되어 있으며, 이 모델의 현재 가용성이나 실행 결과는 검증하지 않았다. 키가 없으면 해당 채점은 N/A가 된다.
- N/A도 전체 건수의 분모에 남고, 에이전트 호출 오류는 답변 문자열로 들어간다. 단순 성공률을 품질 실패율로 곧장 해석하지 않는다.
- CSV parser는 먼저 줄 단위로 나누므로 인용된 셀 내부의 개행을 온전히 처리하지 못한다. 문서의 CSV 계약과 실제 실행기 입력 검증을 따로 점검해야 한다.

이 관찰은 정적 소스 검토이며 실행 재현이나 제품 전체의 결함 판정은 아니다. 오늘의 추천 경로는 **실행기를 자동 가동하는 것보다 설계·자료·결과의 읽기 전용 검토**다. [실행기 원문](https://github.com/microsoft/eval-guide/blob/7a22a8957ced79a35fd7b4634fd5b5eac56c308e/skills/eval-guide/scripts/eval-runner.js)

대시보드도 승인 보안 장치로 확대 해석하지 않는다. standalone planner의 정적 HTML과 별도 serve.py의 legacy --serve 경로는 다르다. 후자는 선택 포트의 기존 프로세스를 종료할 수 있으며, 이전 feedback 파일의 confirmed 상태를 새 세션인지 확인하지 않고 읽을 수 있다. 실제 사용자 확인은 새 산출물·현재 실행 범위에 연결해 받아야 한다. 이 서버는 이번에 실행하지 않았다. [대시보드 구현](https://github.com/microsoft/eval-guide/blob/7a22a8957ced79a35fd7b4634fd5b5eac56c308e/skills/eval-guide/dashboard/serve.py)

## 오늘의 적용 순서

1. 현재 사용 중인 harness·버전·자료를 확인하고, planner로 평가 세트·담당자·채점기 검증 계획을 정한다.
2. generator로 소수의 대표·경계 사례를 만들되, 기대 답의 근거와 검토자를 먼저 확인한다.
3. 허가된 환경에서 실제 실행한 결과에만 interpreter를 적용한다. 미실행·오류·N/A·자료 부족을 보존한다.
4. triage로 작은 수정 가설을 검증하고, 변경 전후 동일한 테스트 세트·환경에서 회귀를 비교한다. FAQ는 필요한 개념의 출처를 찾는 보조 수단으로 쓴다.

위 순서는 다섯 후보를 함께 활용하는 제안이다. SHIP 문구나 높은 통과율은 배포 승인·규제 적합성 인증·미검사 영역의 안전 보증을 대신하지 않는다.

가림 처리한 기존 결과·manifest·채점기 검증 기록을 놓고 세트별 실패·자료 누락·추가 확인 목록을 정리하는 것부터 시작할 수 있다. gate나 담당자 결정을 추정하지 않고 “판정 보류”를 허용한다. 이 제안은 작업 방식에 대한 것이며, 해당 플러그인의 Codex 설치·실행 호환성을 검증했다는 뜻은 아니다.

### 오늘 보이는 공통 흐름

다섯 후보는 평가를 점수 하나보다 **설계 근거 → 사례와 메타데이터 → 실행 결과 → 원인 확인 → 회귀 검증**의 연결로 다룬다. 동시에 한 저장소 안에서도 문서·UI·실행기 계약이 달라질 수 있음을 보여준다. 스킬은 절차를 시작하는 데 도움을 주지만 최신 제품 문서·실제 데이터·사람의 판단을 생략하게 해주는 인증서는 아니다. 이는 오늘 후보에 대한 편집적 해석이며 생태계 전체의 시장 추세를 입증하지 않는다.
