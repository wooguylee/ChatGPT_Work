## 1. wiki-qa

**코드베이스 질문에 실제 파일과 줄 근거를 붙여 답하기**

- 출처: Microsoft 공식 저장소의 deep-wiki 플러그인
- 태그: 코드 Q&A · 저장소 탐색 · 근거 인용 · 호출 흐름 · 아키텍처
- 난이도: 초중급. 구체적인 질문으로 시작하기 쉽지만 동적 호출과 외부 의존성은 따로 확인해야 한다.
- SKILL metadata 버전: **1.0.0**, MIT.

### 무엇을 해주나

원격 저장소 주소 또는 로컬 전용 여부를 확인하고, 질문과 관련된 소스를 검색·읽어 답변을 작성한다. 질문 언어에 맞춰 답하고 파일·줄 인용과 핵심 파일 목록을 포함하도록 한다. 구조·데이터 흐름·관계 질문에는 Mermaid 다이어그램을 요구한다. 별도의 전체 위키를 먼저 생성하는 단계는 없다. [SKILL.md](https://github.com/microsoft/skills/blob/8850874f66fb4d905bfcfcb923a18883bb70d1cd/.github/plugins/deep-wiki/skills/wiki-qa/SKILL.md)

“인증 검사는 어디서 하나?”, “캐시가 언제 무효화되나?”, “이 설정을 바꾸면 어떤 경로가 달라지나?” 같은 질문에 맞는다. 기존 documentation-lookup의 외부 문서 검색, agents-md의 에이전트 지침 작성과 구분되는 **현재 저장소 내부 설명**이 핵심이다. 소스에 근거가 부족하면 부족하다고 밝히고 더 읽을 파일을 제안하도록 한다.

### 실전 프롬프트

“wiki-qa로 이 저장소에서 사용자 권한을 확인하는 위치와 실패 시 처리 흐름을 한국어로 설명해줘. 분석 커밋과 현재 checkout을 먼저 확인하고 실제 소스의 호출 경로를 추적해줘. 핵심 파일·줄 근거와 흐름도 하나를 붙여줘. 확인하지 못한 호출과 런타임 동작은 구분하고, 파일 수정·설치·테스트 실행·외부 요청·비밀값 출력은 하지 마.”

### 설치·주의

공식 명령 진입점은 `/deep-wiki:ask 질문`이다. 두 wiki 스킬 폴더에는 각각 SKILL.md만 있고 별도 검색 인덱서·RAG 서버·검증 실행기가 없다. 실제 결과는 호스트의 파일 접근·검색 능력과 모델의 검토에 의존한다. “추측하지 말라”는 원문 지시는 정확도 보증이 아니다. [ask 명령](https://github.com/microsoft/skills/blob/8850874f66fb4d905bfcfcb923a18883bb70d1cd/.github/plugins/deep-wiki/commands/ask.md)

정적 소스에서 보이는 경로와 운영 환경에서 실제로 실행되는 경로를 구분한다. 외부 라이브러리 내부·다른 저장소의 서비스·실시간 환경 설정을 읽지 못했다면 그 부분은 미확인으로 남긴다. 소스 인용이 있어도 인용 줄이 주장 전체를 뒷받침하는지 다시 확인해야 한다. 설치 경로와 두 wiki 스킬에 공통인 브랜치 인용 주의점은 아래에 정리했다.

## 2. wiki-onboarding

**같은 코드베이스를 신규 기여자·시니어·리더·PM에게 맞춰 설명하기**

- 출처: Microsoft 공식 저장소의 deep-wiki 플러그인

- SKILL metadata 버전: **1.0.0**, MIT.

### 무엇을 해주나

onboarding/ 아래 허브와 네 역할별 가이드를 만들도록 지시한다. 신규 기여자에게는 환경 설정·첫 작업·테스트·디버깅, Staff Engineer에게는 아키텍처·데이터·실패 경로, 엔지니어링 리더에게는 기능·의존성·위험, PM에게는 사용자 여정·기능 범위·제약을 설명한다. 빌드 파일로 주 언어를 감지하고 코드 위치 인용·경로 검증·Mermaid 렌더링 확인을 요구한다. [SKILL.md](https://github.com/microsoft/skills/blob/8850874f66fb4d905bfcfcb923a18883bb70d1cd/.github/plugins/deep-wiki/skills/wiki-onboarding/SKILL.md)

문서 변경 동기화 자체보다 **독자가 무엇부터 읽고 이해해야 하는지**를 정리하는 데 가치가 있다. 개발자가 합류하거나 팀이 프로젝트를 인수할 때, 기술 README 하나에 모든 설명을 몰아넣지 않고 읽기 경로를 나눌 수 있다. 기대 효과는 소스 구조를 바탕으로 한 활용 평가이며 실제 온보딩 시간 단축을 측정한 결과는 아니다.

### 실전 프롬프트

“wiki-onboarding으로 이 저장소의 한국어 온보딩 초안을 새 docs-review/onboarding/에 작성해줘. 네 역할별 가이드와 허브를 만들되 각 가이드는 핵심 내용 중심으로 150줄 이내로 제한해줘. 분석 커밋과 확인한 파일·줄을 적고, 담당자·비용·실측 성능·SLA·로드맵·설계 결정 이유에 근거가 없으면 확인 필요로 남겨줘. 기존 파일·코드는 수정하지 말고 설치·테스트·빌드·배포 명령은 제안만 해줘. 비밀값·개인정보 복사와 커밋·게시도 하지 마.”

### 설치·주의

공식 명령은 `/deep-wiki:onboard`다. 원문 기본 분량은 네 가이드 합계 **2,600~5,300줄**, 최소 다이어그램은 합계 **16개**로 크다. 이는 지시된 목표 분량이며 품질·실행시간 보장이 아니다. 작은 저장소에서는 위 예시처럼 분량을 줄이거나 당장 필요한 독자 범위를 정하는 편이 실용적이다. [onboard 명령](https://github.com/microsoft/skills/blob/8850874f66fb4d905bfcfcb923a18883bb70d1cd/.github/plugins/deep-wiki/commands/onboard.md)

코드만으로 실제 운영 비용·현재 SLA·담당자·로드맵·기술 선택 당시의 의도를 알아낼 수는 없다. 특히 원문이 이런 항목을 요구하므로 **미확인 항목을 추정으로 채우지 않는 조건**이 중요하다. 기여자 가이드는 Python/JavaScript 경험자를 가정하므로 독자 배경도 맞춘다. 코드가 존재한다는 사실을 운영 배포·제품 공개 상태로 바꾸어 표현하지 않는다.

문서 작성, 명령 실행, Mermaid 렌더링, 사이트 게시·주기적 갱신은 각각 별도 단계다. 스킬이 검증을 지시하더라도 이번 조사에서 생성 문서나 실행 명령을 시험한 것은 아니다. 기존 가이드를 보존하고 검토용 새 폴더에서 시작하기 좋다.

## 3. pydantic-models-py

**생성·부분 수정·응답·저장용 모델을 분리해 API 계약을 명확히 하기**

- 출처: Microsoft 공식 저장소의 azure-sdk-python 묶음
- 태그: Python · Pydantic v2 · API 스키마 · 부분 수정 · 데이터 검증
- 난이도: 초중급. Python 타입과 JSON 직렬화·API 요청/응답의 차이를 이해해야 한다.
- SKILL metadata 버전: **1.0.0**, MIT. 이 이름의 Azure 묶음에 들어 있지만 Pydantic 패턴 자체에 Azure 계정은 필요하지 않다.

### 무엇을 해주나

공통 필드를 Base에 두고 Create, Update, 응답, InDB 모델을 구분하는 패턴과 템플릿을 제공한다. 클라이언트가 보낼 값과 서버가 부여할 ID·작성자·시각을 나누고, snake_case 속성과 camelCase API 필드의 연결을 정리하는 데 유용하다. 모델 파일·내보내기·프런트엔드 타입을 함께 맞추도록 안내한다. [SKILL.md](https://github.com/microsoft/skills/blob/8850874f66fb4d905bfcfcb923a18883bb70d1cd/.github/plugins/azure-sdk-python/skills/pydantic-models-py/SKILL.md) · [동봉 템플릿](https://github.com/microsoft/skills/blob/8850874f66fb4d905bfcfcb923a18883bb70d1cd/.github/plugins/azure-sdk-python/skills/pydantic-models-py/assets/template.py)

별도 참고 자료는 field/model validator, JSON-safe 직렬화, 부분 수정, JSON Schema와 v2 방식의 검증을 추가 점검하도록 한다. 응답 클래스는 설명에서 Response라고 부르지만 실제 템플릿은 ResourceName 자체를 응답 클래스로 사용한다. 파일 경로와 클래스 이름은 기존 프로젝트에 맞춰야 한다. [참고 자료](https://github.com/microsoft/skills/blob/8850874f66fb4d905bfcfcb923a18883bb70d1cd/.github/plugins/azure-sdk-python/skills/pydantic-models-py/references/capabilities.md)

### 실전 프롬프트

“pydantic-models-py로 우리 프로젝트의 Task 생성·부분 수정·응답 스키마 초안을 검토해줘. 설치된 Pydantic 버전을 먼저 확인하고, 필드 생략과 명시적 null, snake_case 입력과 camelCase 출력, 서버 전용 필드를 구분해줘. 빈 이름·너무 긴 문자열·누락·null·추가 필드·출력 필터에 대한 테스트 사례를 제안해줘. 기존 API 계약 변경·의존성 설치·DB 쓰기·외부 전송은 하지 마.”

### 설치·주의

**Update의 Optional 필드는 ‘생략 가능’과 ‘null 허용’을 함께 만든다.** 템플릿의 name은 null을 받을 수 있지만 생성·응답의 name은 문자열이다. 부분 수정 시 `model_dump(exclude_unset=True)`는 보내지 않은 필드를 제외하며, 명시적으로 보낸 null은 남는다. 서비스 계층에서 필드별 삭제·초기화 허용 여부를 정해야 한다. `exclude_none=True`로 모두 지우면 사용자가 의도한 null 수정도 사라질 수 있다. [Pydantic 직렬화](https://docs.pydantic.dev/latest/concepts/serialization/) · [FastAPI 부분 수정](https://fastapi.tiangolo.com/tutorial/body-updates/)

원문의 `populate_by_name=True`는 v2.11+ 공식 문서에서 새 코드에 권장되지 않는다. 해당 버전에서는 `validate_by_name=True`와 `validate_by_alias=True`를 검토하되 프로젝트의 지원 버전부터 확인한다. 입력 alias를 허용해도 `model_dump()`의 출력 alias가 자동으로 켜지는 것은 아니다. `by_alias=True` 또는 지원 버전의 `serialize_by_alias` 설정과 실제 HTTP 응답을 따로 검증한다. [현행 ConfigDict](https://docs.pydantic.dev/latest/api/config/) · [Alias 규칙](https://docs.pydantic.dev/latest/concepts/alias/)

템플릿의 InDB에는 Cosmos DB용 doc_type이 들어간다. 이를 모든 데이터베이스에 필요한 필드로 복사할 이유는 없다. 모델 검증은 사용자·테넌트의 접근 권한 검사를 대신하지 않으며, 공개 응답에는 승인된 필드만 포함하도록 별도 계약을 둔다. 템플릿을 그대로 배포하는 것보다 프로젝트의 필드 경계를 검토하는 용도로 먼저 쓰기 좋다.
## 4. gws-workflow-standup-report

- 출처: googleworkspace/cli
- 태그: Google Calendar · Google Tasks · 업무 브리핑 · 생산성 · 읽기 중심
- 난이도: 초중급. 인증된 환경에서는 간단하지만 조회 범위·시간대·오류를 읽어야 한다.
- SKILL metadata 버전: **0.22.5**, Apache-2.0.

### 무엇을 해주나

기본 캘린더의 오늘 일정과 기본 Google Tasks 목록의 미완료 작업을 한 결과로 묶는다. 일정 제목·시작·종료, 작업 제목·예정일, 반환 개수·기준 날짜를 읽고 에이전트가 짧은 브리핑을 만들기 좋다. 기존 agenda 스킬보다 Tasks를 함께 읽는 점이 추가된다. helper 자체가 어제 성과·오늘 우선순위·장애물을 추론해 완성된 스탠드업 문장을 만드는 것은 아니다. [SKILL.md](https://github.com/googleworkspace/cli/blob/a3768d0e82ad83cca2da97724e46bea4ff0e6dbd/skills/gws-workflow-standup-report/SKILL.md)

확인한 기본 사용 형식은 다음과 같다. 아래는 실행 결과가 아닌 사용 안내다.

```text
gws workflow +standup-report
gws workflow +standup-report --format table
```

### 실전 프롬프트

“이미 인증된 환경에서 gws-workflow-standup-report로 오늘 일정과 기본 Tasks 목록의 미완료 작업을 읽어 정리해줘. 결과의 날짜·시간대가 Asia/Seoul의 오늘과 맞는지 확인하고, 조회 경고를 일정 없음·할 일 없음으로 바꾸지 마. 기본 목록만 조회하며 일정 25개·작업 20개 제한이 있음을 표시해줘. 어제 성과나 장애물을 만들지 말고 일정·작업 변경과 메시지 발송은 하지 마.”

### 설치·주의

현재 구현은 Calendar의 **primary**, Tasks의 **@default**만 조회한다. 일정은 최대 **25개**, 미완료 작업은 최대 **20개**를 요청하고 다음 페이지를 따라가지 않는다. 작업에는 오늘 날짜 필터가 없고 showAssigned도 지정하지 않아 Docs·Chat에서 할당된 작업은 기본 제외된다. “오늘까지 해야 하는 모든 작업”으로 읽으면 안 된다. 출력의 meetings에는 개인·종일 일정도 포함될 수 있고, 반환 개수는 전체 보유 건수가 아니다. [실제 handler](https://github.com/googleworkspace/cli/blob/a3768d0e82ad83cca2da97724e46bea4ff0e6dbd/crates/google-workspace-cli/src/helpers/workflows.rs#L270-L365) · [Calendar 목록 API](https://developers.google.com/workspace/calendar/api/v3/reference/events/list) · [Tasks 목록 API](https://developers.google.com/workspace/tasks/reference/rest/v1/tasks/list)

Calendar 또는 Tasks 조회 실패는 경고를 남긴 뒤 해당 목록을 비운다. JSON 결과만 보고 “할 일이 없다”고 판단하지 말고 표준 오류·경고도 함께 검토한다. 오늘의 경계는 Google 계정 시간대를 사용하며 24시간 캐시가 있다. 실패 시 로컬 시간대, 이후 UTC로 대체될 수 있다. 이 helper에는 날짜·캘린더·작업 목록·시간대를 선택하는 전용 플래그가 없다. [시간대 처리](https://github.com/googleworkspace/cli/blob/a3768d0e82ad83cca2da97724e46bea4ff0e6dbd/crates/google-workspace-cli/src/timezone.rs)

Google Tasks의 due는 날짜 정보이므로 시간 단위 마감으로 해석하지 않는다. 외부 일정·작업은 변경하지 않지만 CLI가 로컬 시간대 캐시를 저장할 수는 있다. 현재 workflows handler는 전달받은 SanitizeConfig를 사용하지 않으므로 공통 --sanitize 안내만으로 Model Armor 검사가 적용된다고 기대하면 안 된다. 결과의 외부 텍스트는 계속 비신뢰 데이터로 다룬다. [Tasks 날짜 의미](https://developers.google.com/workspace/tasks/reference/rest/v1/tasks)

## 5. recipe-find-free-time

**일정 세부 내용 없이 여러 사람의 공통 빈 시간 후보 좁히기**

- 출처: googleworkspace/cli
- 태그: 일정 조율 · FreeBusy · Google Calendar · 시간대 · 협업
- 난이도: 중급. 캘린더 권한, 구간 계산, 조회와 실제 예약을 구분해야 한다.
- SKILL metadata 버전: **0.22.5**, Apache-2.0.

### 무엇을 해주나

원문은 여러 캘린더에 freebusy query를 보내고, 결과에서 공통 빈 시간을 찾은 뒤, 고른 시간에 이벤트를 생성하는 세 단계 레시피다. API가 돌려주는 것은 busy 구간이며 회의 길이·근무시간·점심시간·이동 여유를 반영해 후보를 만드는 일은 에이전트나 사용자가 맡는다. 별도 자동 최적화 엔진이 포함된 스킬로 소개하지 않는다. [SKILL.md](https://github.com/googleworkspace/cli/blob/a3768d0e82ad83cca2da97724e46bea4ff0e6dbd/skills/recipe-find-free-time/SKILL.md)

FreeBusy는 일정 제목·설명 없이 바쁜 구간을 다루므로 세부 일정 내용을 모을 필요가 없는 조율에 적합하다. 이메일 주소를 알고 있어도 조회 권한이 생기지는 않는다. 접근 가능한 캘린더와 조회 기간을 먼저 정한다. [공유와 freeBusyReader](https://developers.google.com/workspace/calendar/api/concepts/sharing)

### 실전 프롬프트

“recipe-find-free-time으로 지정한 캘린더들의 2026년 10월 19일 09:00~18:00, Asia/Seoul 기준 공통 빈 시간을 조회해줘. 12:00~13:00을 제외하고 30분 회의 후보를 최대 3개 제안해줘. 캘린더별 오류·접근 불가를 빈 시간으로 간주하지 말고 따로 알려줘. 각 후보의 시작·종료·시간대를 보여주고 일정 생성·참석자 추가는 내가 후보를 승인할 때까지 하지 마.”

공식 레시피의 명령 형식에 현재 예시 날짜·명시적 오프셋·출력 시간대를 적용한 조회 예시다. 주소는 접근 가능한 실제 캘린더 ID로 교체해야 하며 이번 조사에서 실행하지 않았다.

```text
gws schema calendar.freebusy.query
gws calendar freebusy query --json '{"timeMin":"2026-10-19T09:00:00+09:00","timeMax":"2026-10-19T18:00:00+09:00","timeZone":"Asia/Seoul","items":[{"id":"user1@example.com"},{"id":"user2@example.com"}]}'
```

### 설치·주의

**레시피 전체는 읽기 전용이 아니다.** 마지막 +insert는 실제 이벤트를 만들고 참석자를 추가한다. 후보 조회와 확정·초대 승인을 분리한다. 조회 시에는 적절한 FreeBusy/읽기 권한을 사용하고, 일정 쓰기 권한까지 자동으로 넓히지 않는다. [gws-calendar 지침](https://github.com/googleworkspace/cli/blob/a3768d0e82ad83cca2da97724e46bea4ff0e6dbd/skills/gws-calendar/SKILL.md)

FreeBusy 응답의 캘린더·그룹별 errors를 먼저 확인한다. 비어 있는 busy 배열만 보고 종일 가능하다고 판단하면 접근 실패를 놓칠 수 있다. busy의 시작은 포함·끝은 제외이며 응답 시간대를 생략하면 UTC다. 한 번에 확장 가능한 캘린더는 최대 50개, 그룹 확장 한도는 최대 100명이다. 근무시간·선호·버퍼는 별도 조건으로 계산해야 한다. [공식 FreeBusy 스키마](https://developers.google.com/workspace/calendar/api/v3/reference/freebusy/query)

원본 예시는 2024년 날짜를 쓰고 이벤트 생성 start/end에 오프셋이 없다. 현재 +insert 구현은 문자열을 dateTime에 넣으며 별도 timeZone을 추가하지 않는다. Calendar API는 별도 timeZone이 없으면 dateTime의 오프셋을 요구하므로, 나중에 승인받아 생성할 때도 +09:00 또는 Z 등을 명시해야 한다. [insert 요청 구현](https://github.com/googleworkspace/cli/blob/a3768d0e82ad83cca2da97724e46bea4ff0e6dbd/crates/google-workspace-cli/src/helpers/calendar.rs#L422-L465) · [이벤트 생성 스키마](https://developers.google.com/workspace/calendar/api/v3/reference/events/insert)

비어 있다는 결과가 참석 의사나 최종 예약을 보장하지는 않는다. 조회 이후 변경 가능성을 고려해 확정 직전에 다시 확인하는 것이 운영상 권고다.
