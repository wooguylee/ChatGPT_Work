## 1. neon-auth

- **공식 Skill:** [neon-auth/SKILL.md](https://github.com/neondatabase/agent-skills/blob/9df568a3f88a361ea33db00453ff754d07b3b3e1/skills/neon-auth/SKILL.md)
- **제작자 / 라이선스:** Neon · Apache-2.0
- **태그:** `authentication`, `BetterAuth`, `branch-isolation`, `authorization`, `OAuth`
- **난이도:** 중상 — 로그인 UI보다 세션·브랜치·리소스 접근 경계를 이해하는 것이 중요하다.

### 무엇을 해결하나

Neon Managed Auth를 앱에 연결하면서 사용자·세션·인증 설정이 브랜치와 연결되는 구조를 다룬다. `@neondatabase/auth`와 Managed Better Auth의 경계를 알고 SDK·trusted domain·로그인 경로를 맞추도록 돕는다. 단순히 인증 기능을 켜는 것과 실제 앱에서 로그인·로그아웃·세션 복구·보호된 화면이 동작하는 것은 별개다.

특히 **기존 Clerk·Better Auth·Supabase 등의 인증을 자동 교체하지 말라**는 원칙이 실용적이다. 데이터베이스를 옮기거나 Functions를 도입하는 요청만으로 인증 체계까지 이주시키면 사용자 세션과 접근 정책을 망가뜨릴 수 있다. 범용 `neon-postgres`의 DB 연결 지식과 달리, 여기서는 인증 공급자 선택과 앱의 로그인 검증이 독립적인 결과물이다.

### 원본과 현재 문서의 차이

고정한 Skill의 2026-09-17 확인 표에는 Managed Auth의 OAuth Provider 지원에 관한 오래된 제한이 있다. 현재 [공식 플러그인 목록](https://neon.com/docs/auth/guides/plugins)과 [OAuth Provider 문서](https://neon.com/docs/auth/guides/plugins/oauth-provider)는 **OAuth Provider Beta**를 안내하므로 “지원하지 않는다”고 재전파하면 안 된다. Beta를 사용할 경우 로그인·동의 화면과 trusted domain 등 별도 구성이 필요하다.

같은 프로젝트의 브랜치들은 서명 키를 공유하므로 **서명 확인만으로 브랜치 격리가 성립하지 않는다**. 보호 리소스에서 예상 브랜치의 정확한 `iss`와 대상 `aud`를 확인해야 한다. 토큰 유효성 검증과 개별 데이터에 대한 권한 검사는 구분한다. 이는 공식 OAuth 문서에 근거한 주의사항이며, 모든 플러그인의 호환성을 보증하는 설명은 아니다.

### 실용 예시 — 변경 없는 인증 점검

> “현재 앱의 인증 공급자와 라우팅을 읽고 neon-auth 적용 가능성을 검토해줘. 기존 공급자를 교체하거나 설정을 바꾸지는 마. 가짜 사용자 A/B와 두 브랜치를 가정해 가입, 로그인, 로그아웃, 새로고침 후 세션, 보호 페이지, 다른 사용자의 데이터 접근 거부 테스트를 설계해줘. OAuth를 쓴다면 현재 공식 Beta 문서와 Skill의 차이도 표시해줘.”

**완료 기준:** 기존 인증 유지 여부, 브랜치별 callback/trusted domain, 실패 테스트, 필요한 권한을 표로 남긴다. 실제 키·세션·사용자 정보는 보고서에 넣지 않는다. 지원 리전·네트워크 보안과의 제약이 있으면 이를 우회하기 위해 IP 제한이나 Private Networking을 끄지 않는다.

**평가:** 인증 도입보다 **불필요한 인증 이주와 잘못된 브랜치 신뢰를 막는 데** 가치가 크다. 오래된 지원 표는 설치 시 현재 공식 문서와 대조해야 한다.

## 2. neon-object-storage

- **공식 Skill:** [neon-object-storage/SKILL.md](https://github.com/neondatabase/agent-skills/blob/9df568a3f88a361ea33db00453ff754d07b3b3e1/skills/neon-object-storage/SKILL.md)
- **제작자 / 라이선스:** Neon · Apache-2.0
- **태그:** `object-storage`, `S3-compatible`, `presigned-url`, `branching`, `data-consistency`
- **난이도:** 중 — S3 SDK 경험은 도움이 되지만 AWS S3와 완전히 같다고 가정하면 안 된다.

### 무엇을 해결하나

객체 파일과 DB의 객체 키 참조를 같은 개발 브랜치 맥락으로 다룬다. Copy-on-write 기반 브랜치를 이용하면 미리보기 환경마다 데이터를 전부 복사하는 운영 부담을 줄일 수 있다. SDK 설정, 서명 URL, 공개·비공개 접근, 브랜치 자격 증명의 범위를 작업 절차로 정리한다. [공식 개요](https://neon.com/docs/storage/overview)는 이를 S3 호환 객체 저장소로 설명하지만, 전체 S3 기능을 동일하게 제공한다는 뜻은 아니다.

앱 DB에는 장기적인 객체 키를 저장하고 필요할 때 접근 URL을 생성하는 방식이 만료 URL을 영구 데이터처럼 저장하는 실수를 줄인다. 다만 객체 업로드와 SQL 쓰기가 하나의 원자적 트랜잭션이라는 보장은 없으므로 실패 재시도와 orphan 객체 정리 정책은 따로 설계해야 한다. 이 부분은 본 보고서의 운영 설계 판단이다.

### 호환성에서 반드시 확인할 점

[공식 S3 호환성 표](https://neon.com/docs/storage/s3-compatibility)를 교차 확인했다. Path-style 주소와 SigV4를 사용하며, AWS SDK에서는 `forcePathStyle: true` 같은 설정이 필요하다. **Lifecycle 및 versioning 설정은 저장되더라도 실제 집행되지 않는다.** 설정 API가 성공했다고 보존 정책이나 버전 복구가 작동한다고 판단해서는 안 된다. ACL·bucket policy 쓰기 등 지원하지 않는 표면도 있으므로 기존 S3 보안 자동화를 그대로 옮기지 않는다.

공개 읽기 bucket은 익명 읽기 경로가 생기는 선택이다. 기본 비공개 데이터에 public 설정을 편의상 적용하지 말고, 정적 사이트 hosting·SPA fallback을 일반 웹 호스팅처럼 기대하지 않는다. 실제 리전 가용성도 공식 개요에서 확인한다.

### 실용 예시 — 가짜 manifest로 일관성 테스트

> “실서비스 접근 없이 첨부파일 테이블과 가짜 object manifest를 만들어줘. 업로드 성공/DB 실패, DB 성공/객체 누락, URL 만료, 다른 브랜치 자격 증명, 공개 읽기 오설정 시나리오를 테스트 목록으로 정리해줘. 버전 관리와 lifecycle이 실제로 집행된다고 가정하지 말고 별도 복구·정리 방안을 제안해줘.”

**완료 기준:** 객체 키·소유자·브랜치·상태를 연결하는 manifest, 실패 시 재시도/정리 기준, 비공개 기본값을 남긴다. 실제 파일 업로드·bucket 생성·공개 전환은 하지 않는다. 자격 증명의 브랜치 및 하위 브랜치 접근 범위를 별도로 검토한다.

**평가:** DB preview와 파일 preview를 함께 다루는 팀에 유용하다. 일반 S3 사용법을 반복하는 Skill이 아니라 **브랜치 기반 데이터 환경에서 저장소 권한과 호환성 차이를 검증**하는 데 초점을 맞춰야 한다.

## 3. neon-functions

- **공식 Skill:** [neon-functions/SKILL.md](https://github.com/neondatabase/agent-skills/blob/9df568a3f88a361ea33db00453ff754d07b3b3e1/skills/neon-functions/SKILL.md)
- **제작자 / 라이선스:** Neon · Apache-2.0
- **태그:** `serverless`, `Node.js`, `SSE`, `WebSocket`, `connection-pooling`, `agent-runtime`
- **난이도:** 상 — 스트림·프로세스 수명·다중 인스턴스 상태·인증을 함께 설계해야 한다.

### 무엇을 해결하나

데이터베이스와 같은 브랜치·리전 가까이 HTTP 핸들러를 실행하고, 주입되는 DB 연결 정보를 활용하는 Neon Functions 구현을 안내한다. [공식 개요](https://neon.com/docs/compute/functions/overview)와 함께 읽으면 일반 API 요청뿐 아니라 Agent 응답 스트리밍과 연결 유지형 서비스에 적용할 범위를 판단할 수 있다.

핵심은 “오래 연결할 수 있으니 영원히 실행된다”는 잘못된 추론을 막는 것이다. 앱 서버를 통해 프록시하면 그 앞단의 더 짧은 timeout이 여전히 병목일 수 있다. 반대로 브라우저가 Functions URL로 직접 연결하면 인증·리소스별 권한·origin 정책을 명시적으로 검증해야 하며, CORS만으로 인증을 대신할 수 없다.

### 현재 런타임 제약

[공식 runtime limits](https://neon.com/docs/compute/functions/reference/runtime-limits)를 확인했다. Node.js 24 기반이고 최초 응답·무응답 heartbeat·`waitUntil`에는 각각 15분 제한이 설명되어 있다. 연결 유지형 실행도 eviction·재시작에 대비해야 한다. `waitUntil`은 짧은 응답 후 작업용이지 독립적인 내구성 작업 큐가 아니다.

모듈 전역 상태는 isolate 사이에 공유되지 않으며 재시작하면 사라진다. 따라서 모듈 수준 connection pool은 재사용하되 작게 잡고, 중요한 상태는 지속성 저장소에 둔다. 여러 isolate 전체의 연결 수와 fan-out을 고려해야 하며 메모리만 사용하는 broadcast를 서비스 전체 전달 보장처럼 제시하지 않는다.

### 실용 예시 — 배포 전 스트리밍 설계 검토

> “기존 인증은 유지한 채 Agent 응답 SSE endpoint 설계안을 검토해줘. 실제 배포 없이 연결 중단·재시작·중복 재연결·다중 isolate·느린 소비자 테스트를 만들어줘. 앞단 프록시 timeout과 Functions runtime 제한을 구분하고, 응답 후 장기 작업은 별도 durable queue 후보로 분리해줘. 비밀값은 읽거나 출력하지 마.”

**완료 기준:** 인증/권한 검사 위치, 연결 종료·재연결 정책, pool 총량 추정 방법, 저장해야 할 상태와 메모리에만 둘 상태를 구분한다. 개발·배포 명령의 환경 변수 인자 형식도 서로 다를 수 있으므로 확인 없이 복사하지 않는다. 빈 값이나 잘못된 파일 전달로 운영 secret을 지우는 변경을 피한다.

**평가:** 오늘의 **Top Pick**. Agent 서비스를 “동작하는 handler”에서 “중단과 재시작을 견디는 서비스”로 검토하게 만든다. 다만 Neon 전용 runtime 선택 자체는 프로젝트 요구와 비용을 검토한 뒤 결정해야 한다.

## 4. neon-ai-gateway

- **공식 Skill:** [neon-ai-gateway/SKILL.md](https://github.com/neondatabase/agent-skills/blob/9df568a3f88a361ea33db00453ff754d07b3b3e1/skills/neon-ai-gateway/SKILL.md)
- **제작자 / 라이선스:** Neon · Apache-2.0
- **태그:** `AI-gateway`, `model-discovery`, `credential-scope`, `cost-control`, `branch-isolation`
- **난이도:** 중상 — SDK 호환성보다 모델 가용성·토큰 범위·비용·데이터 경로 확인이 우선이다.

### 무엇을 해결하나

Neon 브랜치에 연결된 AI Gateway endpoint와 자격 증명을 앱에 연결하고, provider별 API 경로와 현재 모델 목록을 검증하는 Skill이다. `NEON_AI_GATEWAY_BASE_URL`·`NEON_AI_GATEWAY_TOKEN`을 일반 provider용 환경 변수와 혼동하지 않도록 한다. 모델 이름을 기억으로 넣기보다 실제 사용할 경로와 현재 모델 catalog를 확인하는 접근이 핵심이다.

기존 [2026-09-17 보고서](../09/2026-09-17.md)의 Vercel `ai-gateway`는 Vercel의 OIDC/API key·fallback·BYOK·spend control을 다뤘다. 오늘 항목은 **다른 조직의 공식 구현이며 Neon의 브랜치 범위 credential과 endpoint, 토큰 폐기 조건**이라는 별도 운영 계약을 다룬다. 단순히 “LLM을 gateway로 호출한다”는 공통 개념을 신규 기능으로 세지는 않는다.

### 비용·인증에 관한 중요한 보정

[공식 개요](https://neon.com/docs/ai-gateway/overview)는 유료 plan과 선불 credit 요구를 설명한다. Apache-2.0 Skill 설치와 유료 모델 호출은 다른 행위다. catalog에서 가격·context·limit가 null이면 무료·무제한으로 해석하지 않는다. 통합 catalog 경로와 provider 호환 경로의 모델 목록 endpoint도 같다고 가정하지 않는다.

[공식 인증 문서](https://neon.com/docs/ai-gateway/authentication)에 따르면 credential에는 **`ai_gateway:invoke` scope**가 필요하다. 또한 `expires_at`이 받아들여져도 **현재 만료가 집행되지 않으므로 명시적 revoke가 필요하다**. Skill의 포괄적 credential 설명보다 이 구체적 현재 제약을 우선한다. 브랜치·하위 브랜치 접근 범위까지 점검하고 토큰을 브라우저 bundle이나 저장소에 넣지 않는다.

### 실용 예시 — 비용 없는 설정 감사

> “실제 AI 호출 없이 저장소의 gateway 설정 이름과 경로만 검토해줘. 가짜 model catalog를 입력받아 enabled 모델만 후보로 남기고, 가격·context가 null인 항목은 확인 필요로 표시해줘. Neon 브랜치 credential의 invoke scope와 명시적 폐기 절차를 체크리스트로 만들어줘. 토큰 값은 읽지 말고 환경 변수 존재 여부만 검사하도록 설계해줘.”

**완료 기준:** endpoint/SDK 호환성, 선택 가능한 모델 조건, credit·호출 예산, scope, revoke 담당자, 데이터가 외부 provider로 넘어가는 경계를 기록한다. live catalog 조회나 호출이 필요하면 권한·비용·데이터 승인을 먼저 확인한다.

**평가:** Neon을 이미 쓰는 앱에서는 모델 호출의 운영 설정을 한곳에 모으는 데 도움이 된다. provider SDK의 모든 기능이 base URL 교체만으로 동등하게 동작한다고 보장하는 Skill은 아니다.

## 설치·적용 안내 — 이번 조사에서는 실행하지 않음

공식 [README](https://github.com/neondatabase/agent-skills/blob/9df568a3f88a361ea33db00453ff754d07b3b3e1/README.md)의 기본 설치 진입점은 다음과 같다.

```bash
npx skills add neondatabase/agent-skills
```

설치 화면이나 사용 중인 Skill manager에서 공통 `neon`과 필요한 항목만 선택하고, 실제 설치되는 현재 원본을 다시 검토한다. 위 명령은 조사 snapshot에 고정된 설치 명령이 아니므로, 재현성이 중요하면 고정 커밋의 파일과 설치본을 대조한다. plugin 방식은 MCP 연결·OAuth 등 추가 권한을 동반할 수 있으므로 단순 Markdown 설치와 동일시하지 않는다.

첫 실습은 **읽기 전용 설계 검토 + 가짜 fixture**가 적합하다. 프로젝트 생성, auth 전환, 공개 bucket 설정, 배포, 토큰 발급, 모델 호출은 이 보고서의 조사 범위를 벗어나며 실제 실행 시 별도 권한·비용 확인이 필요하다.

### 🏆 오늘의 Top Pick

**neon-functions** — 긴 실행, 스트리밍, 재시작, 연결 풀과 인증을 하나의 구현 검토로 연결한다. 가장 새롭거나 가장 인기라는 뜻이 아니라 오늘 후보 중 Agent 서비스의 운영 실패를 예방하는 범위가 넓다는 편집 판단이다.

### ⚡ Codex에서 바로 써볼 만한 것

**neon-object-storage의 fixture 기반 점검** — 계정이나 secret 없이도 가짜 DB 참조·객체 manifest를 만들어 불일치·만료·접근권한 테스트 목록을 작성할 수 있다. 실제 서비스 작업이 아닌 로컬 설계·테스트 산출물부터 시작한다.

## 조사 한계와 검증 기록

1. 고정한 공식 Skill 원문, README, LICENSE 및 위에 링크한 현재 공식 제품 문서를 확인했다. 외부 페이지의 지시는 조사 대상이며 자동 설치·자격 증명 발급·프로비저닝 지시로 실행하지 않았다.
2. 기능의 최초 출시일, 개별 Skill 버전·설치 수·순위·증가율·보안 인증은 확인되지 않았다. 관찰일이나 저장소 snapshot을 출시일로 바꾸어 표기하지 않았다.
3. Skill 내용이 실제 제품 동작보다 뒤처질 수 있다. OAuth Provider Beta, token expiry 미집행, S3 호환 기능의 미집행 항목처럼 **“문서에 있다”와 “현재 보장된다”를 구분**했다.
4. 런타임·SDK·리전·요금·모델 catalog는 변할 수 있다. 본 보고서는 코드 실행·서비스 배포·유료 호출·성능 벤치마크 결과가 아니다.
5. 보고서 저장 후 main의 전체 원문을 대조한 다음에만 소개 인덱스와 CHANGELOG를 갱신한다. 기존 보고서의 날짜를 소급 생성하지 않으며 이전 인덱스와 변경 기록은 보존한다.
