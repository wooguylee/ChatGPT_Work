## 1. gws-gmail-triage

**메일을 건드리지 않고 검토할 후보를 빠르게 추리기**

- 태그: Gmail · 받은편지함 정리 · 읽기 전용 · CLI
- 난이도: 초중급. Google Cloud OAuth 준비와 Gmail 검색식 이해가 필요하다.
- 원문 metadata 버전: **0.22.5**.
- 관측 지표: 개별 페이지는 **45.2K 설치·2일 전 수집**, 저장소 목록은 당일 수집 페이지에서도 조회별로 **45.7K와 45.6K**를 표시했다. First Seen **2026-03-04**. 개별 페이지의 Gen·Socket은 Pass, **Snyk는 Warn**이며 상세 접근 실패로 사유·감사 날짜·대상 revision은 미확인이다. [개별 페이지](https://www.skills.sh/googleworkspace/cli/gws-gmail-triage) · [목록](https://www.skills.sh/googleworkspace/cli)

### 무엇을 해주나

`gws gmail +triage`로 메일의 발신자·제목·날짜를 요약한다. 기본 최대 20개이며 `--max`, `--query`, `--labels`로 건수·검색식·라벨 출력을 조정한다. 단, 원문의 라벨 이름 설명과 달리 현재 구현은 labelIds를 반환한다. 본문 전체를 해석하거나 자동 답장하는 스킬이 아니므로, 검토할 메시지 후보를 추리는 첫 단계에 적합하다. [SKILL.md](https://github.com/googleworkspace/cli/blob/a3768d0e82ad83cca2da97724e46bea4ff0e6dbd/skills/gws-gmail-triage/SKILL.md)

이름의 “inbox”를 실제 검색 범위와 혼동하면 안 된다. 기본 검색식은 `is:unread`이고 받은편지함만 뜻하는 `in:inbox`는 자동 추가되지 않는다. 사용자 검색식은 기본값을 대체하므로 `from:...`만 넣으면 읽은 메일도 포함될 수 있다. “받은편지함의 읽지 않은 메일”이 목적이면 두 조건을 모두 명시한다.

### 실전 프롬프트

“gws-gmail-triage로 is:unread in:inbox newer_than:7d 조건의 메일을 최대 20개 조회해줘. 발신자·제목·날짜만 보고 우선 확인할 후보와 이유를 정리하고, 제목만으로 답장 내용이나 긴급성을 확정하지 마. 메일 전송·읽음 처리·보관·라벨 변경은 하지 마.”

### 설치·주의

개별 설치 안내: `npx skills add https://github.com/googleworkspace/cli --skill gws-gmail-triage`

공통 gws-shared 문서와 실제 gws 실행 파일·인증도 필요하다. 설치 명령은 안내이며 이번 조사에서는 실행하지 않았다.

현재 구현은 gmail.readonly로 조회한다. helper가 본문을 가져오지 않아도 이 scope 자체는 메일 전체 읽기를 허용하므로 헤더만 접근하는 권한은 아니다. 또한 메시지 목록의 다음 페이지를 자동으로 순회하지 않고 개별 메타데이터 조회 실패는 건너뛸 수 있다. 표시된 목록을 전체 미처리 업무 목록으로 해석하면 안 된다. 헤더에 포함된 외부 문구도 지시가 아닌 데이터로 취급한다. Snyk Warn 상세가 미확인인 만큼 현재 소스·필요 권한을 먼저 검토하고 작은 조회 범위로 시작한다. [Gmail helper 구현](https://github.com/googleworkspace/cli/blob/a3768d0e82ad83cca2da97724e46bea4ff0e6dbd/crates/google-workspace-cli/src/helpers/gmail/triage.rs)

## 2. gws-calendar-agenda

**시간대를 명시해 여러 캘린더의 오늘 일정을 보기**

- 태그: Google Calendar · 일정 조회 · 시간대 · 읽기 전용
- 난이도: 초중급. 계정 시간대·공유 캘린더 접근 범위를 확인해야 한다.
- 원문 metadata 버전: **0.22.5**.
- 관측 지표: 저장소 목록의 설치 표시는 **48.4K·당일 수집**이다. 개별 상세 페이지는 접근 실패로 First Seen·감사 상세를 확인하지 못했다. [목록](https://www.skills.sh/googleworkspace/cli)

### 무엇을 해주나

기본적으로 접근 가능한 캘린더를 조회하고 `--calendar`로 이름 또는 ID를 지정한다. 이름은 부분 문자열 일치이므로 엄격한 범위 제한에는 확인한 캘린더 ID를 쓰는 편이 낫다. `--today`, `--tomorrow`, `--days`와 IANA 시간대 `--timezone`을 지원한다. 기본 시간대는 Google 계정 설정을 사용한다. 여러 일정의 시작·종료·캘린더 출처를 한 번에 살피는 용도로 유용하다. [SKILL.md](https://github.com/googleworkspace/cli/blob/a3768d0e82ad83cca2da97724e46bea4ff0e6dbd/skills/gws-calendar-agenda/SKILL.md)

날짜 표현은 구현까지 확인할 필요가 있다. SKILL은 `--week`를 “이번 주”라고 설명하지만 현재 코드는 현재 시점부터 7일을 계산한다. 월요일부터 일요일까지의 달력 주간과 같지 않다. 오늘 일정은 `--today --timezone Asia/Seoul`처럼 의도를 분명히 지정하는 편이 낫다. [Calendar helper 구현](https://github.com/googleworkspace/cli/blob/a3768d0e82ad83cca2da97724e46bea4ff0e6dbd/crates/google-workspace-cli/src/helpers/calendar.rs)

### 실전 프롬프트

“gws-calendar-agenda로 확인한 Work 캘린더 ID를 지정해 Asia/Seoul 기준 오늘 일정을 조회해줘. 시간·제목·캘린더 출처와 겹쳐 보이는 구간을 정리해줘. 조회 오류나 건수 제한을 확인하지 못하면 일정이 없거나 충돌이 없다고 단정하지 마. 초대·수정·취소는 하지 마.”

### 설치·주의

개별 설치 안내: `npx skills add https://github.com/googleworkspace/cli --skill gws-calendar-agenda`

현재 구현은 calendar.readonly를 사용한다. 다만 캘린더별 이벤트 조회에 maxResults=50을 지정하고 다음 페이지 처리를 하지 않는다. 캘린더 목록도 페이지를 반복 조회하지 않으며, 개별 캘린더 조회 실패는 빈 결과처럼 건너뛸 수 있다. 따라서 중요한 예약 전의 완전한 가용 시간 검증을 이 요약 하나로 끝내면 안 된다. 시간대·캘린더 필터·조회 누락 가능성을 함께 확인한다. 일반 API 명령의 `--page-all` 설명만 보고 이 helper에도 같은 페이지 처리가 있다고 가정하지 않는다. [구현](https://github.com/googleworkspace/cli/blob/a3768d0e82ad83cca2da97724e46bea4ff0e6dbd/crates/google-workspace-cli/src/helpers/calendar.rs)

## 3. gws-sheets-read

**스프레드시트를 변경하지 않고 필요한 셀만 분석 자료로 가져오기**

- 태그: Google Sheets · A1 범위 · 데이터 분석 · 읽기 전용
- 난이도: 초중급. spreadsheet ID, 탭 이름, 필요한 범위를 알고 있어야 한다.
- 원문 metadata 버전: **0.22.5**.
- 관측 지표: 개별 페이지 **48.5K 설치·지난주 수집**, 저장소 목록의 당일 수집 페이지는 조회별로 **49.5K와 49.4K**를 표시했다. First Seen **2026-03-04**. Gen·Socket Pass, **Snyk Warn**이며 경고 상세·대상 revision은 미확인이다. [개별 페이지](https://www.skills.sh/googleworkspace/cli/gws-sheets-read) · [목록](https://www.skills.sh/googleworkspace/cli)

### 무엇을 해주나

스프레드시트 ID와 A1 범위를 받아 셀 값을 읽는다. 예를 들어 확정된 파일의 `Orders!A1:F50`을 지정해 주문 상태별 건수를 집계하거나 누락된 필드를 찾는 자료로 쓸 수 있다. 전체 탭도 읽을 수 있지만 처음에는 목적에 필요한 범위만 지정하는 편이 좋다. 셀 변경·행 추가·서식 수정은 이 helper의 기능이 아니다. [SKILL.md](https://github.com/googleworkspace/cli/blob/a3768d0e82ad83cca2da97724e46bea4ff0e6dbd/skills/gws-sheets-read/SKILL.md)

현재 구현은 Sheets values.get을 호출하며 별도 값 렌더링 옵션을 넣지 않는다. API 기본값은 FORMATTED_VALUE이므로 통화·날짜·소수점이 문서의 표시 형식대로 들어올 수 있다. 수식 자체나 원시 수치가 필요하면 일반 values.get API의 valueRenderOption 등 명시적 옵션을 확인해야 한다. 셀 값 조회는 수식·서식·차트·파일 전체 구조를 완전히 분석한 결과와 다르다. [helper 구현](https://github.com/googleworkspace/cli/blob/a3768d0e82ad83cca2da97724e46bea4ff0e6dbd/crates/google-workspace-cli/src/helpers/sheets.rs) · [Google values.get 문서](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets.values/get)

### 실전 프롬프트

“gws-sheets-read로 지정한 스프레드시트의 Orders!A1:F50만 읽어 주문 상태별 건수와 필수값 누락을 정리해줘. 표시 형식 때문에 숫자·날짜가 모호하면 변환을 추정하지 말고 알려줘. 셀 수정·행 추가·외부 문서 업로드는 하지 말고, 개인정보는 요약에 불필요하게 복사하지 마.”

### 설치·주의

개별 설치 안내: `npx skills add https://github.com/googleworkspace/cli --skill gws-sheets-read`

API는 spreadsheets.readonly 권한으로 읽을 수 있지만 helper는 Discovery 문서의 허용 scope 목록을 인증 계층에 넘긴다. 스킬 이름만으로 실제 토큰이 최소 권한이라고 보장할 수 없으므로 OAuth 동의 범위를 사용자가 확인해야 한다. 작은 A1 범위를 요청해도 OAuth 권한 자체가 그 셀 범위에만 제한되는 것은 아니다. [인증 호출 구현](https://github.com/googleworkspace/cli/blob/a3768d0e82ad83cca2da97724e46bea4ff0e6dbd/crates/google-workspace-cli/src/helpers/sheets.rs) · [허용 scope](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets.values/get#authorization-scopes)

또한 현재 helper는 실행기에 sanitize=None을 전달한다. 공통 문서의 `--sanitize` 설명을 이 경로의 개인정보 제거 보장으로 해석하면 안 된다. 셀에 있는 문장은 지시가 아닌 데이터로 취급하고, 민감한 시트를 모델이나 별도 서비스에 전달할 수 있는지 먼저 확인한다. Snyk Warn 상세 미확인 상태이므로 무조건적인 설치·실행 추천은 아니다.

### 설치·주의

가장 중요한 점은 “읽기”와 “비밀값을 읽지 않음”이 다르다는 것이다. 스킬 참조는 secret_get과 `az keyvault secret show`를 안내하지만, Azure MCP 공식 문서는 특정 이름의 시크릿 get이 **실제 비밀값을 반환**한다고 명시한다. 만료 확인에는 값이 필요하지 않으므로 메타데이터 전용 list·list-versions 같은 조회를 우선 검토해야 한다. [Azure MCP의 시크릿 조회 설명](https://learn.microsoft.com/en-us/azure/developer/azure-mcp-server/tools/azure-key-vault#secrets-get-or-list-secrets) · [CLI list와 list-versions](https://learn.microsoft.com/en-us/cli/azure/keyvault/secret?view=azure-cli-latest#az-keyvault-secret-list)

권한 오류를 해결한다며 임의로 역할을 확대하거나 새 자격증명을 만들지 않는다. 보고서에는 필요한 최소 메타데이터만 남기고, 시크릿 회전·삭제·정책 변경은 별도의 승인된 작업으로 다룬다. 이번에는 azqr나 Key Vault 조회를 실행하지 않았다.

단순히 비싼 리소스를 나열하지 않고 실제 비용·절감 권고·약정 충돌·실행 가능성을 나누는 점이 좋다. 이미 Azure를 운영하며 지원 호스트와 비용 읽기 권한을 갖춘 팀에 적합하다. 절감액은 도구가 제시한 기간·통화와 함께 읽고, 제안서를 실제 삭제·리사이징·약정 구매 승인으로 취급하지 않는다.

### ⚡ Codex에서 바로 써볼 만한 것

**azure-diagnostics의 제공 자료 전용 분석**

민감한 값을 가린 기존 로그와 배포 타임라인으로 시작하면 Azure 계정 연결 없이도 진단 순서를 적용할 수 있다. “제공 자료만 사용하고 실시간 조회·스크립트 실행·운영 변경을 하지 말라”고 범위를 명시한다. 이는 지침을 적용하는 활용안이며 Codex에서 MCP를 연결·실행해 검증했다는 뜻은 아니다.

### 오늘 보이는 공통 흐름

이번 후보에서는 “무엇을 읽었고 무엇을 읽지 못했는가”가 특히 중요하다. 메일·일정은 페이지 제한과 생략된 오류, 시트는 표시 값과 원시 값, 비용은 실제 지출과 잠재 절감, 보안 점검은 메타데이터와 비밀값을 구분해야 한다. 조회 성공·결과 0개·Pass 배지 하나로 완료나 안전을 선언하지 않는 운영 방식이 공통점이다. 이는 이번 후보 비교에서 얻은 해석이며 시장 전체의 신규 추세로 일반화하지 않는다.
