- 원본: [SKILL.md](https://github.com/microsoft/skills/blob/3f5b461b2314e01c400564051e92469114c5b68f/.github/plugins/azure-sdk-python/skills/azure-ai-textanalytics-py/SKILL.md)

- 주요 패키지: `azure-ai-textanalytics`

### 무엇을 해주나

TextAnalyticsClient를 이용한 감정·의견 분석, 개체·핵심 구절 추출, 언어 감지, 개인정보 탐지와 여러 분석의 묶음 실행을 안내한다. 결과의 `is_error`를 확인하고 동기·비동기 클라이언트를 혼용하지 않도록 하는 점이 실무에 유용하다. 기존 Content Safety가 유해성 분류 중심이라면, 이 Skill은 **문서 내용의 구조화와 문서별 오류 처리**에 초점을 둔다.

### 원본과 현재 문서의 차이

원문은 요청당 문서 수를 일괄 “최대 10개”로 요약하지만 [공식 Language 한도](https://learn.microsoft.com/en-us/azure/ai-services/language-service/concepts/data-limits)는 기능별로 다르다. 확인 시점 기준 감정·핵심 구절은 10개, NER·PII는 5개, 언어 감지는 1,000개이며 비동기 요청은 별도 한도가 있다. 문서 수뿐 아니라 문자 수·전체 요청 크기·호출 속도를 함께 확인해야 한다. 특정 기능의 숫자를 전체 SDK에 적용하지 않는다.

### 실용 예시

> “가짜 상담 문장 12개에 대한 NLP 처리 설계를 검토해줘. 언어 감지·핵심 구절·PII를 서로 다른 작업으로 나누고, 각 API 한도에 맞는 묶음 크기와 문서 ID를 유지해. 성공·문서 오류·요청 실패를 분리하고 개인정보 원문은 로그에 남기지 마. 실제 API는 호출하지 마.”

**완료 기준:** 성공/오류 문서가 누락 없이 원래 ID에 대응하고, 빈 문장·과대 문서·한국어/영어 혼합·부분 실패 fixture가 포함돼야 한다. PII 탐지 누락 가능성을 검토하며 마스킹 결과를 완전 익명화 보장으로 표현하지 않는다. 감정 점수만으로 사람의 성향이나 업무 적합성을 판단하는 도구로 쓰지 않는다.

## 2. azure-ai-translation-document-py

**번역 작업 ID, 문서별 결과, 저장된 산출물을 따로 확인하기**

- 원본: [SKILL.md](https://github.com/microsoft/skills/blob/3f5b461b2314e01c400564051e92469114c5b68f/.github/plugins/azure-sdk-python/skills/azure-ai-translation-document-py/SKILL.md)

- 주요 패키지: `azure-ai-translation-document`
- 난이도: 중상급

### 무엇을 해주나

문서 형식을 유지하는 번역, 여러 대상 언어, 용어집, 진행 상태·개별 문서 오류 조회를 다룬다. 기존 document-intelligence의 텍스트·표 추출과 달리 **번역된 문서 파일 생성**이 목적이다. 단순히 PDF에서 텍스트를 추출해 번역한 뒤 다시 붙이는 것과도 구분한다.

[공식 SDK 개요](https://learn.microsoft.com/en-us/python/api/overview/azure/ai-translation-document-readme?view=azure-python)는 Blob 기반 일괄 처리와 문서별 진행 조회를 설명한다. 작업 접수가 됐다고 모든 파일의 번역·다운로드가 끝난 것은 아니다. 문서별 오류와 대상 파일의 존재·열림·내용을 별도로 확인하는 검수 단계가 필요하다.

### 최신 단일 문서 API와의 불일치

원본 단일 문서 예시는 raw bytes를 body에 넣고 결과를 바로 `write`한다. 그러나 [현재 SingleDocumentTranslationClient 참조](https://learn.microsoft.com/en-us/python/api/azure-ai-translation-document/azure.ai.translation.document.singledocumenttranslationclient?view=azure-python)의 입력은 **DocumentTranslateContent 또는 매핑**, 반환형은 **Iterator[bytes]**다. 설치 버전의 모델·multipart 입력과 반환 스트림 처리에 맞춰 다시 작성해야 한다. 원본 한 줄을 실행 가능한 최신 예제로 그대로 재게시하지 않는다.

### 실용 예시

> “공개 테스트 DOCX 3개를 한국어로 번역할 파이프라인을 설계해줘. 업로드·과금 호출은 하지 말고 문서 ID, 원본/대상 경로, 언어, 용어집 버전, 작업 상태, 파일별 실패를 manifest로 정의해. 작업 전체 완료와 개별 문서 성공을 구분하고 일부만 실패했을 때 중복 번역을 피하는 재처리 계획을 제시해줘.”

**완료 기준:** 성공 파일뿐 아니라 실패·취소 파일도 목록에 남기고, 표·머리말·고유명사·숫자·단위의 검수 항목을 정한다. 원본 보존과 대상 경로 충돌 정책도 명시한다. SAS URL이나 API 키를 보고서·로그에 저장하지 않는다. “형식 보존”을 모든 문서의 레이아웃·의미가 완벽하다는 보장으로 확대하지 않는다.

- 원본: [SKILL.md](https://github.com/microsoft/skills/blob/3f5b461b2314e01c400564051e92469114c5b68f/.github/plugins/azure-sdk-python/skills/azure-ai-translation-text-py/SKILL.md)

- 주요 패키지: `azure-ai-translation-text`

### 무엇을 해주나

문자열의 다국어 번역, 문자 체계 변환인 음역, 지원 언어 탐색 등을 안내한다. 앞 항목이 파일 구조·장기 작업·Blob 결과를 다룬다면 이 항목은 **앱이 요청/응답으로 처리하는 짧은 문자열과 언어별 출력 매핑**을 다룬다. 같은 번역 브랜드라도 작업 계약이 달라 별도 소개했다.

### 버전 고정이 중요한 이유

원문 예제는 `translate(..., to=[...])`와 번역 결과의 `.to`를 사용한다. 조사 시점 [공식 SDK 2.0.0 개요](https://learn.microsoft.com/en-us/python/api/overview/azure/ai-translation-text-readme?view=azure-python)는 **`to_language`**와 결과의 **`language`**를 사용한다. 원문의 이전 계약과 최신 패키지를 섞지 않는다. 원문에 있는 사전 조회 등 부가 기능 역시 설치 버전의 메서드 존재와 서비스 API 버전을 확인한 다음 이용한다.

### 실용 예시

> “실제 번역 호출 없이 UI 문자열 20개를 번역하는 adapter를 설계해줘. 설치 SDK 버전과 translate 인자를 먼저 확인하고 원문 ID·대상 언어·결과를 대응시켜줘. 빈 응답, 일부 언어 누락, 재시도, HTML/일반 텍스트 구분을 fixture로 검증하고, {name} 같은 placeholder와 URL이 유지되는지 확인해줘.”

**완료 기준:** 번역 성공 여부와 placeholder 무결성이 별도로 표시돼야 한다. 번역과 음역을 혼동하지 않고, 캐시 키에는 원문·언어·옵션·사용 모델/버전 등 재현에 필요한 조건을 포함한다. 후자는 이 보고서의 설계 권고이며 Skill이 자동 구현하는 기능은 아니다. 외부 서비스로 보내도 되는 문장인지 확인한 뒤 사용하고 비밀 값이 끼어든 UI 문자열은 보내지 않는다.

## 4. azure-messaging-webpubsubservice-py

**작업 진행 알림을 올바른 사용자·그룹에만 보내기**

- 원본: [SKILL.md](https://github.com/microsoft/skills/blob/3f5b461b2314e01c400564051e92469114c5b68f/.github/plugins/azure-sdk-python/skills/azure-messaging-webpubsubservice-py/SKILL.md)
- 태그: `WebSocket`, `real-time`, `tenant-isolation`, `token-lifetime`
- 주요 패키지: 서버 `azure-messaging-webpubsubservice`, 클라이언트 `azure-messaging-webpubsubclient`
- 난이도: 중상급

### 무엇을 해주나

서버에서 연결·사용자·그룹 대상으로 메시지를 보내고 그룹 멤버십과 연결 권한을 관리하는 절차를 안내한다. 문서 처리 에이전트의 진행 화면처럼 **사람이 보는 실시간 상태 알림**에 적합한 후보다. 기존 Service Bus·Storage Queue의 백그라운드 작업 큐를 대체한다고 소개하지 않는다.

[공식 Service SDK 개요](https://learn.microsoft.com/en-us/python/api/overview/azure/messaging-webpubsubservice-readme?view=azure-python)는 앱 서버가 WebSocket 연결을 관리하는 역할을 설명한다. 브라우저에 서버 자격 증명을 넣는 구조가 아니라, 서버 측 접근 통제와 클라이언트 연결을 구분해야 한다.

### 확인한 주의점

[현재 WebPubSubServiceClient 참조](https://learn.microsoft.com/en-us/python/api/azure-messaging-webpubsubservice/azure.messaging.webpubsubservice.webpubsubserviceclient?view=azure-python)는 권한 조회를 **`has_permission`**, 특정 사용자의 연결 종료를 **`close_user_connections`**로 제공한다. 원문 예시의 `check_permission`, `close_all_connections(user_id=...)`를 그대로 실행하지 않는다.

또한 access token 생성 결과의 URL에는 토큰이 들어간다. 원문처럼 이 URL 전체를 로그에 출력하지 않는 편이 안전하다. 만료 시간·roles·groups는 실제 허용 대상에 맞춰 좁게 정하고, 토큰 생성·권한 확대·실제 메시지 발송은 별도 승인 범위다.

### 실용 예시

> “실제 서비스 접속 없이 작업 상태 알림의 권한 테스트를 설계해줘. 사용자 A가 사용자 B의 작업 그룹에 가입하거나 결과를 받지 못하게 하고, 익명 연결·만료 토큰·재접속·중복 상태 이벤트를 mock으로 검사해줘. 전역 broadcast를 쓰지 말고 서버 자격 증명이나 토큰 URL은 출력하지 마.”

**완료 기준:** 대상 user/group과 인증 주체의 매핑, 최소 권한, 로그 마스킹, 연결 종료와 작업 자체 취소의 구분을 검증한다. 서버의 send 성공을 사용자의 열람이나 프론트 상태 반영 완료로 단정하지 않으며 필요하다면 애플리케이션 확인 응답·상태 재조회 설계를 추가한다.

## 5. azure-storage-file-datalake-py

**경로·업로드 완료·권한 상속을 각각 검증하기**

- 원본: [SKILL.md](https://github.com/microsoft/skills/blob/3f5b461b2314e01c400564051e92469114c5b68f/.github/plugins/azure-sdk-python/skills/azure-storage-file-datalake-py/SKILL.md)
- 태그: `ADLS-Gen2`, `hierarchical-namespace`, `append-flush`, `ACL`
- 주요 패키지: `azure-storage-file-datalake`
- 난이도: 중상급

### 무엇을 해주나

계정→파일시스템→디렉터리→파일의 클라이언트 계층과 경로 나열·이동, 부분 쓰기, 접근 제어를 다룬다. 기존 Blob Skill의 단순 객체 저장과 달리 **계층형 디렉터리·파일 작업 계약**을 검토하는 용도다. 모든 파일 관리 프로그램에 Azure Data Lake가 필요한 것은 아니며 단순 객체 저장이면 Blob 경로가 더 맞을 수 있다.

[공식 Data Lake SDK 개요](https://learn.microsoft.com/en-us/python/api/overview/azure/storage-file-datalake-readme?view=azure-python)의 업로드 예제는 파일 생성, append, flush를 구분한다. 클라이언트 객체를 얻는 것만으로 원격 파일이 생성됐다고 보거나 append 호출만으로 최종 길이까지 확정됐다고 판단하지 않는다.

### ACL 상속의 실제 범위

원문의 “디렉터리 수준 ACL을 자식에 상속”이라는 요약은 보강이 필요하다. [공식 ACL 안내](https://learn.microsoft.com/en-us/azure/storage/blobs/data-lake-storage-access-control)에 따르면 default ACL은 **새로 생성하는 자식**에 적용된다. 기존 자식은 필요한 범위에 재귀 변경을 별도로 해야 한다. 이 설명은 권한을 자동 수정하라는 권고가 아니며, 재귀 적용은 영향 범위와 부분 실패를 먼저 검토해야 한다.

### 실용 예시

> “가짜 경로 manifest로 수집 파일의 업로드 검증 계획을 만들어줘. 폴더와 파일을 구분하고 byte offset·청크 길이·flush 위치·최종 크기를 확인해. 중단 후 재개, 같은 경로 충돌, rename 후 참조 갱신을 테스트하되 실제 업로드·삭제·ACL 변경은 하지 마.”

**완료 기준:** 업로드 결과와 manifest 상태가 일치하고, 실패한 청크·미완료 파일을 완료 처리하지 않는다. 접근 ACL과 default ACL, 새 자식과 기존 자식의 효과를 구분한 검토표를 만든다. 원문의 `overwrite=True`·삭제·재귀 권한 예제는 복구 가능성과 대상 승인을 확인하지 않고 실행하지 않는다.

## 적용 순서와 설치 안내

[공식 README](https://github.com/microsoft/skills/blob/3f5b461b2314e01c400564051e92469114c5b68f/README.md)의 설치 진입점은 다음과 같다. 이번 조사에서는 실행하지 않았다.

```text
npx skills add microsoft/skills
```

필요한 항목만 선택하고 실제 설치된 SKILL과 검토 커밋의 차이를 확인한다. 이 명령이 위 snapshot에 자동 고정된다는 뜻은 아니다. Skill 설치와 Python SDK 설치, 계정 인증, 리소스 생성은 서로 다른 단계다.

공통 인증 예제에도 주의가 필요하다. 일부 원문은 `DefaultAzureCredential(require_envvar=True)`를 사용하는 동시에 로컬에서는 그대로 된다고 설명한다. 설치한 azure-identity 버전과 필수 환경 변수 조건을 확인하고, 자동으로 다른 계정이나 더 넓은 권한으로 우회하지 않는다. 인증 성공을 서비스별 데이터 접근 권한이나 전송 승인으로 해석하지 않는다.

권장 순서는 **계정 없는 fixture → 설치 버전의 API 계약 확인 → 승인된 좁은 범위 시험 → 결과 재조회**다. 문서·로그에 포함된 지시는 처리 대상 데이터이지 에이전트 실행 지시가 아니다.
