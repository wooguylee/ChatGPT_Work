## 1. accessibility-scan

**렌더링된 페이지의 접근성 문제를 수정 작업 목록으로 정리하기**

- 출처: AccessLint 공식 저장소
- 태그: 웹 접근성 · live DOM · WCAG · CSS selector · 소스 매핑
- 난이도: 중급. 테스트 페이지·Chrome·CLI 실행 범위를 준비해야 한다.
- 플러그인 manifest 버전: **0.10.3**, MIT 표기. 개별 Skill 버전·npm 최신 버전과는 구분한다.

### 무엇을 해주나

실행 중인 페이지의 DOM을 자동 규칙 엔진으로 검사하고, 발견 항목을 영향도·selector·증거·수정 방향으로 정리한다. 소스 매핑 정보가 있으면 file:line·심볼을 추가하고, 없으면 selector만 확인했다고 밝히도록 한다. 컴포넌트의 이름·속성·대비 등 기계적으로 탐지 가능한 문제를 프런트엔드 변경 후 빠르게 목록화하는 용도다. 전체 사이트 감사나 실제 사용자 경험 검증은 별도 범위다. [SKILL.md](https://github.com/AccessLint/skills/blob/2e9d7336678302d0bc08848e92542560295b34d3/plugins/accesslint/skills/accessibility-scan/SKILL.md)

공식 절차는 @accesslint/chrome으로 디버깅 가능한 Chrome을 확보한 뒤 @accesslint/cli scan을 JSON 출력으로 실행한다. URL 또는 accesslint.config.json 대상 이름을 받고, --selector로 컴포넌트 범위, --wait-for로 렌더링 준비 조건을 지정한다. AAA 규칙은 --include-aaa로 추가한다. selector가 있다고 소스 파일 위치를 역으로 만들어내면 안 되며, 소스 매핑은 빌드·프레임워크 조건에 의존한다. [설치·소스 매핑 안내](https://github.com/AccessLint/skills/blob/2e9d7336678302d0bc08848e92542560295b34d3/README.md)

### 실전 프롬프트

“accessibility-scan으로 비운영 테스트 페이지 http://localhost:3000/checkout의 #checkout-form을 검사하는 계획을 먼저 보여줘. 이미 설치된 도구·실행 버전과 브라우저를 확인하고 #checkout-ready 이후의 상태를 대상으로 해줘. 실행을 승인하면 selector·증거·수정 제안만 정리하고 소스 위치가 없으면 추정하지 마. 실제 결제·폼 제출·파일 수정·결과 외부 업로드는 하지 마.”

### 설치·주의

자동 검사 0건은 해당 엔진·대상·시점에서 발견한 문제가 없다는 뜻이다. 키보드 경로, 화면 읽기 프로그램의 실제 발화, 페이지 밖 상태와 사이트 전체 적합성을 보증하지 않는다. 원문은 locate·don't edit를 중심으로 하지만 뒤에 수정 후 재실행 안내도 있으므로 **조회만 원하는지 코드 수정까지 원하는지**를 요청에 명시한다.

스킬의 명령은 @latest를 사용한다. 문서 커밋을 고정해도 실행 패키지·Chrome·페이지 상태가 고정되지는 않는다. 설치·실행 버전을 별도로 기록한다. 현재 CLI 구현은 설치된 core 패키지의 IIFE를 읽어 CDP로 live DOM에 실행한다. 과거 변경 기록의 CDN 로딩 설명을 최신 구현에 그대로 적용하지 않았다. [엔진 로딩](https://github.com/AccessLint/accesslint/blob/a839ea727447410e8282c3d1da83fc893b42901a/cli/src/iife-source.ts) · [CDP 실행](https://github.com/AccessLint/accesslint/blob/a839ea727447410e8282c3d1da83fc893b42901a/cli/src/cdp.ts)

소스 파일을 고치지 않더라도 패키지 실행·브라우저 시작·페이지 요청과 결과 수집은 발생한다. 결과에는 HTML·이름·URL·소스 위치가 포함될 수 있어 민감한 페이지는 출력·공유 범위를 확인해야 한다. teardown의 stop --all은 관리되는 Chrome 작업의 종료 범위를 검토한 뒤 사용한다. 병렬 작업을 무심코 종료하지 않는다. [결과 필드 구현](https://github.com/AccessLint/accesslint/blob/a839ea727447410e8282c3d1da83fc893b42901a/cli/src/cdp-audit.ts)

## 2. accessibility-inspect

**자동 검사로 결론 내릴 수 없는 상호작용과 미확인 영역 기록하기**

- 출처: AccessLint 공식 저장소
- 태그: 키보드 · 포커스 · 접근성 트리 · 리플로 · 증거 수준
- 난이도: 중급. 실제 조작·관찰 사실과 사람이 판단할 부분을 나누어야 한다.
- 플러그인 manifest 버전: **0.10.3**, MIT 표기.

### 무엇을 해주나

한 페이지의 키보드 이동, 포커스, 커스텀 위젯 상태, 확대·리플로, 폼 오류 등을 브라우저 MCP로 확인한다. 핵심은 결과의 심각도와 근거 수준을 별도로 적는 방식이다. ●는 재현 가능한 조작·DOM·접근성 트리 사실, ◐는 증거가 있지만 사람 판단이 필요한 항목, ○는 실제 보조공학·사용자 경험 확인이 필요한 항목이다. [SKILL.md](https://github.com/AccessLint/skills/blob/2e9d7336678302d0bc08848e92542560295b34d3/plugins/accesslint/skills/accessibility-inspect/SKILL.md)

검사하지 않은 기준은 not exercised·undetermined로 남긴다. scan 결과가 제공되면 엔진이 맡은 기준을 먼저 구분해 중복 조작을 줄인다. “검사 생략”이 “통과”로 보이는 보고서를 피하려는 절차가 유용하다. 이는 보고 방법의 장점이며 모델 판정의 정확성 인증은 아니다. [공통 방법론](https://github.com/AccessLint/skills/blob/2e9d7336678302d0bc08848e92542560295b34d3/plugins/accesslint/skills/shared/methodology.md)

### 실전 프롬프트

“테스트용 예약 페이지의 날짜 선택기를 accessibility-inspect로 점검해줘. 승인한 테스트 계정·더미 데이터만 쓰고 실제 Tab·Esc·화살표 입력으로 조작을 확인해줘. 관찰 사실과 사람 확인이 필요한 판단을 분리하고 미실행 기준도 남겨줘. 화면 읽기 프로그램의 발화를 추정하지 마. 예약 제출·운영 데이터 변경·스크린샷 외부 공유는 하지 말고, 제출이나 스크립트 주입이 필요한 검사는 먼저 별도로 알려줘.”

### 설치·주의

Chrome DevTools·Playwright·Puppeteer 같은 브라우저 MCP가 필요하다. 없는 경우 정적 확인만 하고 나머지는 미확인으로 넘긴다. 기본 모드는 페이지에 필요한 영역 위주이고 --deep은 해당 영역의 상세 절차를 요청한다. 접근성 트리와 aria-live 속성을 읽는 것만으로 NVDA·JAWS·VoiceOver에서 실제 안내가 전달됐다고 판단하지 않는다. scripted focus()도 실제 키 이벤트 처리를 대신하지 못한다.

상세 체크포인트에는 두 가지 해석 주의점이 있다. CSS zoom은 브라우저 확대의 근사치이므로 사람 확인 영역으로 남긴다. 또한 2.5.8을 24×24 CSS px 바운딩 박스로 단순화했지만 W3C에는 간격·동등 컨트롤·인라인·브라우저 기본 컨트롤·필수 표현 예외가 있다. 작은 버튼이라는 사실만으로 즉시 WCAG 실패를 확정하지 않는다. 표의 체크리스트는 실제 기준·예외와 대조해야 한다. [체크포인트](https://github.com/AccessLint/skills/blob/2e9d7336678302d0bc08848e92542560295b34d3/plugins/accesslint/skills/accessibility-inspect/references/checkpoints.md) · [W3C 2.5.8 설명](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)

이 스킬은 소스 수정을 목적으로 하지 않아도 **읽기 전용 작업은 아니다**. 클릭·입력·잘못된 폼 제출·스크립트 실행·CSS 조정을 지시할 수 있다. 비운영 환경과 더미 데이터에서 시작하고, 실제 제출·예약·게시가 필요한 흐름은 별도로 승인한다. 스냅샷·스크린샷의 업무 정보도 관리한다. 커스텀 combobox·grid·drag-and-drop·live region 등은 원문 자체가 휴리스틱이 불안정한 패턴으로 분류한다.

## 3. playwright-best-practices-for-agents

**브라우저에서 본 동작을 유지보수 가능한 회귀 테스트로 남기기**

- 출처: Checkly 공식 문서 저장소
- 태그: Playwright Test · locator · assertion · 테스트 격리 · flaky test
- 난이도: 중급. 테스트 설정·데이터·인증 상태와 패키지 버전을 함께 검토해야 한다.
- 개별 SKILL frontmatter 버전은 없다. Skill 문서에 적용되는 별도 라이선스는 확인되지 않았다.

### 무엇을 해주나

@playwright/test 기반 TypeScript·JavaScript 테스트 작성·리뷰 규칙을 제공한다. SKILL.md에서 locator, assertion, 인증, 네트워크 mock, 테스트 데이터, CI 등 23개 참조 문서로 연결하고 필요한 주제만 읽게 한다. 이미 소개한 playwright-cli가 브라우저 조작 도구 중심이었다면, 이 스킬은 **그 조작을 어떤 독립적인 테스트와 실패 근거로 남길지**에 초점을 맞춘다. 독립 playwright 자동화 라이브러리 전용 지침은 아니다. [SKILL.md](https://github.com/checkly/docs/blob/a9b8db5e2e3d0c440867bff191269ded3e321df0/skills/playwright-best-practices-for-agents/SKILL.md)

사용자 관점 role·label locator, 자동 재시도 assertion, 고정 sleep 대신 상태 확인, 테스트별 격리와 실패 로그 우선 검토가 핵심이다. 반복 실패를 retry 증가로 덮기보다 locator·기대 상태·공유 데이터의 원인을 찾도록 돕는다. 이런 원칙은 Playwright 공식 권장 사항과 대체로 일치한다. 다만 아래의 오류·구버전 안내 때문에 공식 문서와 대조하는 보조 자료로 추천한다. [locator 지침](https://github.com/checkly/docs/blob/a9b8db5e2e3d0c440867bff191269ded3e321df0/skills/playwright-best-practices-for-agents/references/locators.md) · [flakiness 지침](https://github.com/checkly/docs/blob/a9b8db5e2e3d0c440867bff191269ded3e321df0/skills/playwright-best-practices-for-agents/references/flakiness.md) · [Playwright 권장 사항](https://playwright.dev/docs/best-practices)

### 실전 프롬프트

“playwright-best-practices-for-agents를 참고해 tests/checkout.spec.ts·관련 설정·기존 실패 로그를 읽기 전용으로 리뷰해줘. 필요한 references만 읽고 locator·고정 대기·assertion·공유 상태 문제를 파일 위치와 근거로 정리해줘. 설치된 Playwright 버전의 공식 문서와 대조하고 차이가 있으면 설명해줘. 설치·업데이트·테스트 실행·파일 수정은 하지 말고 최소 수정안을 제시해줘. 결제나 운영 데이터 변경 가능성이 있는 테스트를 따로 표시하고 인증 상태·토큰·고객 정보는 출력하지 마.”

### 설치·주의

waiting.md는 click이 Editable까지 포함한 다섯 actionability 검사를 모두 수행한다고 설명하지만, 공식 표에서 click의 Editable 검사는 제외된다. 세부 API 설명을 그대로 복사하지 않는다. [원문 waiting.md](https://github.com/checkly/docs/blob/a9b8db5e2e3d0c440867bff191269ded3e321df0/skills/playwright-best-practices-for-agents/references/waiting.md) · [공식 actionability 표](https://playwright.dev/docs/actionability)

별도 @playwright/cli 설치 안내도 현행 환경과 대조해야 한다. Playwright 1.62부터 agent CLI가 번들되어 npx playwright cli로 실행할 수 있다. 최신 버전으로 자동 변경하기보다 기존 lockfile·패키지 버전·지원 명령을 먼저 확인한다. 원문의 “에이전트가 GUI를 사용할 수 없다”는 문장은 그 워크플로의 가정이며 모든 호스트의 능력을 뜻하지 않는다. [1.62 릴리스 노트](https://playwright.dev/docs/release-notes#version-162)

## 4. zustand-store-ts

**상태·액션·구독 범위를 분리하는 TypeScript 스토어 초안**

- 출처: Microsoft 공식 저장소의 azure-sdk-typescript 묶음
- 태그: React · Zustand · TypeScript · 상태 관리 · 선택적 구독
- 난이도: 초중급. 기존 상태 구조와 비동기 작업·구독 수명을 이해해야 한다.
- SKILL metadata 버전: **1.0.0**, MIT. 이 두 프런트엔드 스킬의 기본 패턴에는 Azure 계정이 필요하지 않다.

### 무엇을 해주나

상태와 액션의 타입을 분리하고, 개별 selector로 필요한 값만 구독하는 스토어 구조를 제공한다. 동봉 템플릿에는 목록·선택 ID·로딩·오류 상태, 추가·삭제·초기화와 비동기 로딩 골격이 있다. React 바깥에서 특정 상태 변화에 반응하는 subscribeWithSelector 사용 예도 포함한다. 전역 상태를 통째로 구독하던 화면을 작은 구독 단위로 검토하거나, 에이전트가 생성한 스토어의 일관성을 점검하는 데 유용하다. [SKILL.md](https://github.com/microsoft/skills/blob/8850874f66fb4d905bfcfcb923a18883bb70d1cd/.github/plugins/azure-sdk-typescript/skills/zustand-store-ts/SKILL.md) · [템플릿](https://github.com/microsoft/skills/blob/8850874f66fb4d905bfcfcb923a18883bb70d1cd/.github/plugins/azure-sdk-typescript/skills/zustand-store-ts/assets/template.ts)

기존 react-patterns의 넓은 컴포넌트 설계보다 **하나의 스토어 계약과 구독 방식**에 집중한다. 다만 원문의 “항상 subscribeWithSelector 사용”은 이 스킬의 설계 규칙이다. React hook의 기본 selector 사용에 그 middleware가 반드시 필요한 것은 아니다. middleware는 외부 subscribe에 selector 기반 구독을 추가하는 역할로 이해한다. [Zustand create](https://zustand.docs.pmnd.rs/reference/apis/create) · [subscribeWithSelector](https://zustand.docs.pmnd.rs/reference/middlewares/subscribe-with-selector)

### 실전 프롬프트

“zustand-store-ts로 제공한 프로젝트의 Task 스토어를 검토해줘. 현재 Zustand 버전과 기존 상태 계약을 먼저 확인하고 State·Actions·selector를 정리해줘. Item은 id가 있는 명시적 타입으로 제안하고, 삭제 시 선택 해제·초기화·로딩 실패·중복 요청·늦은 응답 테스트를 목록으로 작성해줘. 외부 구독의 해제 위치도 확인해줘. 지금은 파일 수정·패키지 설치·실제 API 호출·데이터 저장 없이 검토안만 보여줘.”

### 설치·주의

템플릿은 완성된 데이터 계층이 아니다. items는 unknown[]이고 removeItem은 id가 있다고 타입 단언한다. loadItems는 실제 fetch가 주석으로 남아 있으며 빈 배열을 넣는다. 도메인 타입·런타임 입력 검증·API 오류 처리·동시 요청 정책은 프로젝트에서 구현해야 한다. 특히 실제 fetch를 연결한 뒤 요청 두 개의 완료 순서가 뒤집히거나 reset 이후 늦은 응답이 도착하는 경우는 추가 테스트 대상이다.

Zustand의 set은 기본적으로 얕게 병합한다. 템플릿의 reset은 선언된 초기 상태 필드를 복원하며 액션을 남기는 형태다. 중첩 객체를 직접 변경해도 자동으로 안전하게 추적되는 것은 아니므로 불변 갱신과 초기 상태 참조의 취급을 확인한다. v5에서 매번 새 객체·배열을 반환하는 selector는 무한 갱신을 일으킬 수 있어 개별 selector 또는 적절한 useShallow를 검토한다. selector 분리만으로 실제 렌더링 성능 개선을 측정한 것은 아니다. [상태 갱신](https://zustand.docs.pmnd.rs/learn/guides/updating-state.html) · [useShallow와 안정된 반환값](https://zustand.docs.pmnd.rs/reference/hooks/use-shallow)

## 5. react-flow-node-ts

**시각적 워크플로 편집기의 커스텀 노드를 타입부터 연결하기**

- 출처: Microsoft 공식 저장소의 azure-sdk-typescript 묶음
- 태그: React Flow · 노드 편집기 · TypeScript · 시각적 워크플로 · Zustand
- 난이도: 중급. 노드 데이터·핸들·캔버스 이벤트·저장소 갱신을 함께 맞춰야 한다.
- SKILL metadata 버전: **1.0.0**, MIT.

### 무엇을 해주나

React Flow의 커스텀 노드 컴포넌트와 데이터 타입 템플릿을 제공한다. memo·useCallback, 입력·출력 Handle, 선택된 편집 모드의 NodeResizer와 Zustand 액션 연결을 설명하고, 타입 union·기본값·nodeTypes·메뉴 등록까지 통합 순서를 정리한다. RAG 단계, 도구 호출, 조건 분기 등을 시각적으로 배치하는 에이전트 워크플로 UI의 출발점으로 활용할 수 있다. 해당 활용은 편집적 제안이며 실행 엔진·에이전트 오케스트레이터까지 제공하는 스킬은 아니다. [SKILL.md](https://github.com/microsoft/skills/blob/8850874f66fb4d905bfcfcb923a18883bb70d1cd/.github/plugins/azure-sdk-typescript/skills/react-flow-node-ts/SKILL.md) · [컴포넌트 템플릿](https://github.com/microsoft/skills/blob/8850874f66fb4d905bfcfcb923a18883bb70d1cd/.github/plugins/azure-sdk-typescript/skills/react-flow-node-ts/assets/template.tsx) · [타입 템플릿](https://github.com/microsoft/skills/blob/8850874f66fb4d905bfcfcb923a18883bb70d1cd/.github/plugins/azure-sdk-typescript/skills/react-flow-node-ts/assets/types.template.ts)

기본 구조는 @xyflow/react의 Node·NodeProps와 맞지만, useAppStore·updateNode·canvasMode·cn·CSS 변수·AddBlockMenu·ConnectMenu는 프로젝트에 존재해야 하는 가정이다. 파일 경로도 원본 프로젝트 구조에 맞춘 예시다. 템플릿을 복사한 사실만으로 새 프로젝트에서 컴파일·동작한다고 판단하지 않는다. [현행 NodeProps](https://reactflow.dev/api-reference/types/node-props)

### 실전 프롬프트

“react-flow-node-ts로 우리 테스트용 워크플로 편집기의 ToolNode 초안을 검토해줘. 설치된 @xyflow/react 버전과 store API를 먼저 확인하고, 노드 타입·nodeTypes·핸들·제목 편집을 연결하는 변경안을 제시해줘. 입력의 접근 가능한 이름·nodrag, 읽기 모드의 연결·이동·삭제 정책, 중복 핸들 ID와 키보드 조작을 점검해줘. 기존 디자인 토큰을 사용하고 코드는 아직 수정하지 마. 도구 실행·API 호출·워크플로 게시·배포는 하지 마.”

### 설치·주의

동봉 제목 input에는 label·aria-label과 nodrag가 없다. React Flow 공식 가이드는 input에 label과 nodrag를 사용하고, utility 문서는 nodrag가 입력 조작을 노드 드래그·선택 동작과 분리한다고 설명한다. 실제 앱에 맞는 접근 가능한 이름과 동작을 추가·검증해야 한다. nodeTypes는 컴포넌트 밖에서 안정된 객체로 두는 공식 패턴도 함께 확인한다. [커스텀 노드 가이드](https://reactflow.dev/learn/customization/custom-nodes) · [상호작용 CSS 클래스](https://reactflow.dev/learn/customization/utility-classes)

원본의 editing 조건은 제목 입력과 크기 조절 UI를 제어한다. 두 Handle에는 같은 조건의 isConnectable 설정이 없고 Handle 기본값은 true다. 따라서 이것만으로 캔버스 전체가 읽기 전용이 되었다고 간주하지 않는다. 상위 ReactFlow·노드 설정·저장 API의 연결·이동·삭제 정책을 함께 확인해야 하며, 클라이언트 UI 제한은 서버 권한 검사를 대신하지 않는다. 여러 동일 종류 핸들을 추가할 때는 각 id와 edge의 sourceHandle/targetHandle 연결도 구분한다. [Handle API](https://reactflow.dev/api-reference/components/handle) · [다중 핸들 예제](https://reactflow.dev/learn/advanced-use/computing-flows)
