[공식 SKILL.md](https://github.com/trailofbits/skills/blob/8e54050ae63c2f62224c35b1616efe71865b4777/plugins/static-analysis/skills/codeql/SKILL.md)

## 2. sarif-parsing

**기존 검사 결과의 심각도와 중복을 근거 있게 정리하기**

- 출처: Trail of Bits 공식
- 태그: SARIF · 보안 결과 처리 · 기준선 비교 · CI/CD
- 난이도: 중급. JSON 구조와 사용 중인 스캐너의 결과 의미를 읽을 수 있어야 한다.
- 확인한 지표: skills.sh 설치 수는 최초 조회 **5.5K·3일 전 수집**, 재조회 **5.6K·당일 수집**으로 달랐다. First Seen은 **2026-01-19**, 세 감사기관은 Pass 표시다. 캐시 관측값을 성장률로 해석하지 않는다. 감사 상세·대상 revision은 확인하지 못했다. [상세 페이지](https://www.skills.sh/trailofbits/skills/sarif-parsing)

### 무엇을 해주나

CodeQL·Semgrep 등이 이미 생성한 SARIF 파일을 읽고 정리한다. 여러 결과 파일의 집계, 규칙·파일별 필터링, 중복 제거, 기준 실행과의 비교, 형식 변환 및 CI 게이트 구성을 돕는다. 새 취약점 스캔이나 소스 코드 직접 분석은 담당하지 않는다. [공식 SKILL.md](https://github.com/trailofbits/skills/blob/8e54050ae63c2f62224c35b1616efe71865b4777/plugins/static-analysis/skills/sarif-parsing/SKILL.md)

실무적 강점은 결과의 level이 비어 있는 경우를 다룬다는 점이다. 결과가 규칙의 기본 level을 상속할 수 있으므로 result.level만 필터링하면 경고를 놓칠 수 있다. 제공된 jq 예제와 Python 도우미는 ruleIndex 또는 ruleId로 규칙을 찾아 상속값을 처리한다. 빠른 탐색에는 jq, 반복 작업에는 표준 라이브러리 기반 sarif_helpers.py를 활용할 수 있다. [jq 예제](https://github.com/trailofbits/skills/blob/8e54050ae63c2f62224c35b1616efe71865b4777/plugins/static-analysis/skills/sarif-parsing/resources/jq-queries.md) · [Python 도우미](https://github.com/trailofbits/skills/blob/8e54050ae63c2f62224c35b1616efe71865b4777/plugins/static-analysis/skills/sarif-parsing/resources/sarif_helpers.py)

SARIF level의 error·warning·note와 규칙의 security-severity 수치 점수는 구분해야 한다. error를 곧바로 “고위험 보안 취약점”으로 읽으면 안 된다. 도우미의 Finding 객체는 level을 추출하므로 보안 점수 기반 보고서에는 해당 규칙 속성을 별도로 읽는 처리가 필요하다. [GitHub 공식 SARIF 설명](https://docs.github.com/en/code-security/reference/code-scanning/sarif-files/sarif-support#reportingdescriptor-object)

### 실전 프롬프트

“baseline.sarif와 current.sarif를 sarif-parsing으로 비교해줘. 먼저 구조를 검증하고 규칙에서 상속되는 level과 security-severity 점수를 별도 열로 정리해줘. 도구·규칙 네임스페이스, fingerprint 종류, 저장소 상대 경로를 고려해 신규·유지·사라진 경고를 구분하고, 불확실한 중복은 합치지 말고 표시해줘. 원본은 보존하고 외부 업로드 없이 결과를 작성해줘.”

### 설치·주의

개별 설치 안내: `npx skills add https://github.com/trailofbits/skills --skill sarif-parsing`

동봉 도우미는 완전한 SARIF 구현이 아니다. invocation의 ruleConfigurationOverrides는 처리하지 않는다. 중복 키에도 도구 이름이 포함되지 않으며, 입력 fingerprint 사전에서 첫 값을 선택하므로 여러 도구·규칙·fingerprint 종류를 섞을 때 서로 다른 경고가 합쳐질 수 있다. 원본을 보존하고 도구·규칙별로 먼저 분리해 비교하는 편이 안전하다. [구현 확인](https://github.com/trailofbits/skills/blob/8e54050ae63c2f62224c35b1616efe71865b4777/plugins/static-analysis/skills/sarif-parsing/resources/sarif_helpers.py)

전체 경로를 사용하는 fallback 식별자는 디렉터리가 다른 동명 파일을 구분하지만, 실행 환경별 절대경로 차이는 자동으로 같아지지 않는다. 저장소 상대 경로를 정리하고 줄 번호·도구 버전·검사 범위 변화도 확인해야 한다. 비교 결과에서 경고가 사라졌다는 사실만으로 취약점 수정이 입증되지는 않는다. 외부 웹 validator나 GitHub 업로드 예제를 사용하면 코드 경로·메시지 등 SARIF에 들어 있는 정보가 전송될 수 있으므로 로컬 검증부터 시작한다.

## 3. document-api-endpoint

**Sentry API 문서와 실제 응답 타입을 맞추는 실무 지침**

- 출처: Sentry 공식
- 태그: API 문서화 · OpenAPI · Python 타입 · drf-spectacular
- 난이도: 중상급~고급. Sentry 코드베이스와 DRF 구조를 읽을 수 있어야 한다.
- 추천 대상: Sentry 백엔드 기여자, API 스키마·타입 불일치를 다루는 개발자
- 확인한 지표: skills.sh 설치 **391**, First Seen **2026-06-04**, 세 감사기관 Pass. 웹 도구의 캐시 표시는 **2개월 전**이다. 최신 순위나 현재 revision의 안전성 인증으로 해석하지 않는다. [skills.sh](https://www.skills.sh/getsentry/skills/document-api-endpoint)

### 무엇을 해주나

엔드포인트의 선언된 스키마와 실제 응답이 어긋나는 문제를 점검한다. 클래스·메서드의 @extend_schema, 요청 매개변수, 응답 TypedDict, 예제를 함께 살핀다. Sentry의 기존 매개변수와 응답 타입을 재사용하고 담당 팀도 명시하도록 안내한다. Sentry 코드베이스의 규칙과 마이그레이션 경험을 압축한 작업 가이드이므로 다른 DRF 프로젝트에는 경로·명령·공개 상태 규칙을 조정해야 한다. [공식 SKILL.md](https://github.com/getsentry/skills/blob/d18b7aa8ba878354e5c348310230e652f7690f9c/skills/document-api-endpoint/SKILL.md)

유용한 부분은 null과 필드 부재를 구분한다는 점이다. 항상 존재하지만 값이 비어 있을 수 있는 필드와 특정 expand 조건에서만 나타나는 필드를 다르게 표현한다. 직렬화 코드의 선언만 믿지 않고 실제 응답의 ID·숫자·중첩 필드 타입까지 비교하도록 한다. 적절한 공통 타입이 없는 외부 서비스 응답은 새로운 복제 타입을 섣불리 만들지 않도록 경계한다.

레거시 문서를 옮길 때는 같은 URL 경로의 일부 HTTP 메서드만 전환하면 기존 문서의 다른 메서드가 사라질 수 있다. 원문은 해당 경로 전체를 함께 이전하고 기존 JSON과 참조를 정리하도록 요구한다. 문서 빌드, API 예제 검증, 관련 pytest, 변경 파일 검사까지 확인 절차에 포함한다. [마이그레이션·검증 원문](https://github.com/getsentry/skills/blob/d18b7aa8ba878354e5c348310230e652f7690f9c/skills/document-api-endpoint/SKILL.md)

### 실전 프롬프트

“document-api-endpoint를 사용해 이 Sentry 엔드포인트의 스키마와 응답 타입 불일치를 점검해 줘. 기존 공통 타입을 우선 재사용하고, 같은 경로의 레거시 HTTP 메서드도 확인해 줘. PUBLIC 승격은 하지 말고 변경안과 필요한 검증을 먼저 제시해 줘.”

### 설치·주의

개별 설치 안내: `npx skills add https://github.com/getsentry/skills --skill document-api-endpoint`

PUBLIC 승격은 선택적인 별도 작업이다. 문서 작성 요청만으로 공개 상태를 바꾸지 말고 대상 메서드와 범위를 먼저 정해야 한다. 실제 응답 확인에는 승인된 인증 환경과 비밀정보 처리 원칙이 필요하다. 토큰을 문서·로그에 복사하지 않고 허용된 대상만 조회한다. 문서 변경이 SDK·MCP에 반영되는 시점도 하위 스키마 재생성 이후다. 이번에는 실제 빌드나 라이브 API 호출을 하지 않았다. 세 감사 상세의 날짜·대상 revision·세부 근거는 접근 실패로 확인하지 못했다.

## 4. gh-review-requests

**팀과 관련된 읽지 않은 GitHub 리뷰 요청 추리기**

- 출처: Sentry 공식
- 태그: GitHub · 리뷰 요청 · 팀 협업 · CLI
- 난이도: 초중급~중급. 인증·팀 권한과 조회 오류를 구분해야 한다.
- 확인한 지표: skills.sh 설치 수는 최초 조회 **4.1K·2일 전 수집**, 재조회 **3.8K·3주 전 수집**으로 달랐다. First Seen은 **2026-02-20**, Gen Agent Trust Hub·Socket Pass, **Snyk Warn** 표시다. 현재 단일 값이나 감소 추세로 해석하지 않는다. 경고 상세·감사 날짜·대상 revision은 확인하지 못했다. [skills.sh](https://www.skills.sh/getsentry/skills/gh-review-requests)

### 무엇을 해주나

읽지 않은 GitHub 알림 중 review_requested에 해당하는 항목을 가져오고, 아직 열려 있는 미병합 PR만 남긴다. 지정 팀에 리뷰가 요청됐거나 작성자가 지정 팀의 구성원인 PR을 골라 제목·링크·작성자·포함 이유를 보여준다. 인증된 gh와 uv가 필요하며, 번들 스크립트는 Python 3.12 이상을 요구한다. 여러 팀은 쉼표로 구분해 지정할 수 있다. [공식 SKILL.md](https://github.com/getsentry/skills/blob/d18b7aa8ba878354e5c348310230e652f7690f9c/skills/gh-review-requests/SKILL.md)

조회의 출발점은 알림이다. 이미 읽은 요청이나 review_requested 알림이 없는 PR까지 찾는 전체 리뷰 백로그 검색은 아니다. 결과 0개를 “검토할 PR이 전혀 없음”으로 해석하면 안 된다.

조직 범위에도 주의해야 한다. --org는 팀원·팀 정보 조회에 사용되지만 알림은 사용자 전체 범위에서 가져온다. 이후 PR 저장소의 조직을 비교하지 않고 요청 팀의 슬러그만 비교한다. 따라서 --org getsentry를 넣어도 getsentry 저장소로만 제한되지 않는다. 다른 조직의 동일 슬러그 팀이나 지정 팀원이 다른 조직에 작성한 PR이 섞일 수 있다. 특정 조직만 원한다면 결과의 저장소 소유자를 별도로 확인해야 한다. [검토한 스크립트](https://github.com/getsentry/skills/blob/d18b7aa8ba878354e5c348310230e652f7690f9c/skills/gh-review-requests/scripts/fetch_review_requests.py)

### 실전 프롬프트

“gh-review-requests로 ORG의 TEAM 관련 읽지 않은 리뷰 요청을 찾아 줘. 각 PR의 포함 이유를 표시하고, 저장소 소유자가 ORG인 항목만 최종 목록에 남겨 줘. API 오류와 조회 범위 한계도 알려 줘. 리뷰 제출이나 알림 상태 변경은 하지 마.”

### 설치·주의

개별 설치 안내: `npx skills add https://github.com/getsentry/skills --skill gh-review-requests`

원문의 기본 조직은 getsentry이므로 자신의 조직·팀을 명시한다. 현재 코드에는 고정된 건수·문자열 절단 상한이 없으며 팀원 목록과 알림에는 페이지네이션이 적용된다. API 오류는 표준 오류에 출력한 뒤 빈 목록이나 객체로 처리하므로, 인증·권한·네트워크 실패로 결과가 빠질 수 있다. 결과 JSON뿐 아니라 오류 출력도 함께 확인해야 한다. 스크립트 자체는 조회 호출만 하며 리뷰 제출·병합·알림 읽음 처리를 하지 않는다. [스크립트](https://github.com/getsentry/skills/blob/d18b7aa8ba878354e5c348310230e652f7690f9c/skills/gh-review-requests/scripts/fetch_review_requests.py)

Snyk Warn의 사유를 확인하지 못했으므로 무조건적인 실행 추천은 아니다. 도입 전에 현재 코드와 경고 상세, 필요한 GitHub 권한을 검토한다. 읽기 작업에 필요하지 않은 권한을 추가하지 않는다.

## 5. pr-writer

**전체 변경을 읽고 검토자에게 필요한 PR 설명 만들기**

- 출처: Sentry 공식
- 태그: PR 작성 · GitHub · 개발 문서 · 코드 리뷰
- 난이도: 초급~중급
- 확인한 지표: skills.sh 설치 **4.4K**, First Seen **2026-03-05**, Gen Agent Trust Hub·Socket Pass, **Snyk Warn**. 웹 도구는 **전일 수집**으로 표시했다. 감사 경고 원인·날짜·현재 revision과의 일치 여부는 확인하지 못했다. [skills.sh](https://www.skills.sh/getsentry/skills/pr-writer)

### 무엇을 해주나

현재 브랜치·작업 트리·기존 PR·기준 브랜치·커밋·전체 diff를 확인한 뒤 PR 제목과 본문을 작성한다. 최신 커밋만 요약하지 않고 PR 전체가 무엇을 바꾸는지 설명한다. 기존 PR은 해당 PR의 baseRefName을 기준으로 판단하고 새 PR은 저장소 기본 브랜치를 사용한다. 제목에는 feat·fix·docs 등 지정된 유형을 쓰며 외부 계약이 깨지는 변경에만 !를 붙이도록 한다. [공식 SKILL.md](https://github.com/getsentry/skills/blob/d18b7aa8ba878354e5c348310230e652f7690f9c/skills/pr-writer/SKILL.md)

본문은 동작의 변화와 검토에 필요한 맥락을 우선한다. 작은 변경은 짧은 문단으로 끝내고 호환성·마이그레이션·운영 위험이 있는 경우에만 필요한 설명을 추가한다. 전후 예시, 작은 흐름도, 스크린샷, 검토 순서도 도움이 될 때만 사용한다. 기본 Summary·Test Plan 틀이나 CI 로그를 자동으로 채우지 않는다는 점이 특징이다. 동봉 평가 안내도 제목 형식, 간결함, 불필요한 템플릿·검증 덤프 배제를 확인한다. 이는 평가 설계의 확인이며 이번에 평가를 실행했다는 뜻은 아니다. [평가 안내](https://github.com/getsentry/skills/blob/d18b7aa8ba878354e5c348310230e652f7690f9c/skills/pr-writer/EVAL.md)

### 실전 프롬프트

“pr-writer로 현재 브랜치 전체 diff를 읽고 PR 제목과 본문 초안만 작성해 줘. GitHub PR을 생성하거나 수정하지 말고 커밋·push도 하지 마. 동작 변화와 검토 위험만 간결하게 설명하고 확인되지 않은 이슈 번호와 개인정보는 넣지 마.”

### 설치·주의

개별 설치 안내: `npx skills add https://github.com/getsentry/skills --skill pr-writer`

원문에는 새 draft PR을 만드는 gh pr create와 기존 제목·본문을 갱신하는 PATCH 명령이 있다. SPEC은 후속 커밋이 검토 기대를 바꾸면 별도 PR 수정 요청 없이 갱신하도록도 명시한다. 초안만 필요하다면 GitHub PR을 생성·수정하지 말라는 범위를 명시해야 한다. 실제 게시 권한은 사용자의 요청과 실행 환경의 승인 정책으로 판단한다. [동작 명세](https://github.com/getsentry/skills/blob/d18b7aa8ba878354e5c348310230e652f7690f9c/skills/pr-writer/SPEC.md)

고객·조직 이름, 이메일, 지원 티켓 내용, 비밀정보, 개인정보를 본문에 넣지 않도록 금지한다. 이슈 번호도 확인된 근거가 있어야 한다. Fixes는 PR 병합 시 이슈를 닫을 수 있고 Refs는 연결용이라는 차이를 검토해야 한다. 간결한 PR 설명은 실제 테스트의 생략이나 실패 은폐를 뜻하지 않는다. Snyk Warn 상세가 미확인인 상태이므로 우선 코드·문서를 검토하고 초안 전용 범위로 사용한다.
