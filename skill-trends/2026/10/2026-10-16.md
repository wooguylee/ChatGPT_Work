## 1. provider-docs

**Provider 구현과 Registry 문서가 따로 바뀌는 문제 줄이기**

- 출처: HashiCorp 공식
- 태그: Terraform · Provider 개발 · 문서 생성 · Schema · Registry
- 난이도: 중상급. Go 기반 Provider와 tfplugindocs 설정을 읽을 수 있어야 한다.
- 현행 상태: active. SKILL frontmatter에 개별 버전 번호는 없다.

### 무엇을 해주나

변경된 Provider 설정·리소스·데이터 소스 등을 정확한 문서 대상에 연결하고, 스키마의 설명을 먼저 고친 뒤 템플릿·예제·생성 결과를 맞춘다. required/optional/computed 의미와 실제 기본값, 구현되지 않은 필드의 문서화를 점검하는 데 유용하다. 문서를 코드 변경과 같은 PR에서 검토하도록 유도한다. [SKILL.md](https://github.com/hashicorp/agent-skills/blob/f706481af9b8fedb66de909f6243ad29601afa0c/plugins/terraform/skills/provider-docs/SKILL.md) · [참고 문서](https://github.com/hashicorp/agent-skills/blob/f706481af9b8fedb66de909f6243ad29601afa0c/plugins/terraform/skills/provider-docs/references/hashicorp-provider-docs.md)

**현행 원문을 그대로 복사하면 안 되는 부분이 있다.** Skill과 참고 문서는 docs/ 아래의 .md.tmpl 경로를 제안하지만, 현재 tfplugindocs 기본값은 템플릿 입력이 templates/, 생성 결과가 docs/다. 실제 저장소의 --website-source-dir·--rendered-website-dir 설정과 버전을 먼저 확인해야 한다. 사용자 설정이 없는 프로젝트에서 두 디렉터리를 혼동하면 템플릿이 반영되지 않을 수 있다. [tfplugindocs의 옵션·표준 경로](https://github.com/hashicorp/terraform-plugin-docs/blob/1bb6e1ede585dc316f2fed63b76fc4ed62f217d1/README.md)

### 실전 프롬프트

“provider-docs로 이번 Provider 스키마 변경과 문서를 대조해줘. 먼저 저장소의 generator 버전과 템플릿 입력·출력 경로를 확인하고, 필드 설명·기본값·필수 여부의 불일치를 정리해줘. 문서 수정안과 검증 명령만 제시해줘. go generate 실행, 릴리스 태그 생성, Registry 게시와 인프라 변경은 하지 마.”

### 설치·주의

개별 설치 안내: `npx skills add hashicorp/agent-skills/plugins/terraform/skills/provider-docs`

tfplugindocs는 단순 Markdown 변환만 하는 도구가 아니다. 기본 흐름에서 Provider를 빌드하고 Terraform CLI로 스키마를 조회하며, Terraform이 없으면 다운로드할 수 있다. 승인된 스키마 JSON을 --providers-schema로 제공하면 Provider 빌드·Terraform CLI 호출을 생략하는 경로가 있다. go generate ./...는 저장소의 다른 생성 명령도 실행할 수 있으므로 먼저 지시문을 검토한다. generate/validate 결과와 실제 렌더링·예제의 의미를 따로 검증하고, 문서 초안을 릴리스 승인으로 취급하지 않는다. [도구 동작과 검증 범위](https://github.com/hashicorp/terraform-plugin-docs/blob/1bb6e1ede585dc316f2fed63b76fc4ed62f217d1/README.md)

## 2. provider-test-patterns

**Provider의 생성·변경·가져오기·외부 삭제를 서로 다른 검증으로 다루기**

- 출처: HashiCorp 공식
- 태그: Terraform · Acceptance Test · Go · StateCheck · 회귀 테스트
- 난이도: 고급. Plugin Framework와 실제 API 수명주기 이해가 필요하다.
- 현행 상태·버전: active, **0.0.1**.

### 무엇을 해주나

terraform-plugin-testing의 TestCase/TestStep, ConfigStateChecks, plan checks, 단계 간 값 비교를 연결한다. 기본 생성과 변경, import 후 상태 일치, 외부에서 삭제된 자원의 복구, 잘못된 입력, 회귀 버그를 각각 검증하도록 안내한다. “테스트가 실행됐다”보다 “어떤 동작을 확인했는가”를 명확하게 만드는 스킬이다. [SKILL.md](https://github.com/hashicorp/agent-skills/blob/f706481af9b8fedb66de909f6243ad29601afa0c/plugins/terraform/skills/provider-test-patterns/SKILL.md) · [검사 참고 문서](https://github.com/hashicorp/agent-skills/blob/f706481af9b8fedb66de909f6243ad29601afa0c/plugins/terraform/skills/provider-test-patterns/references/checks.md)

일반적인 acceptance 흐름에는 plan·apply·refresh·최종 plan과 마지막 destroy가 포함된다. 후속 plan이 비어 있다는 사실은 그 시나리오의 기본 일관성 신호이며, 실제 API 값·중요 속성·import·오류 처리까지 모두 맞다는 뜻은 아니다. 회귀 검사는 수정 전 실패와 수정 후 통과를 분리해 증거를 남긴다. 기존에 소개한 terraform-test가 HCL 테스트 작성 중심이라면, 이번 스킬은 **Provider 구현자가 Go로 작성하는 acceptance test**에 초점을 둔다. [공식 testing patterns](https://developer.hashicorp.com/terraform/plugin/testing/testing-patterns)

### 실전 프롬프트

“provider-test-patterns로 이 Provider의 변경 diff를 읽고 테스트 누락을 찾아줘. create/update/import/disappears 시나리오, 상태 값과 실제 API 값, CheckDestroy를 구분해 Go 테스트 초안을 만들어줘. 기존 helper의 모듈 경로 처리도 확인해줘. 지금은 테스트 실행·API 호출·실제 리소스 생성·삭제와 sweeper 실행을 하지 마.”

### 설치·주의

개별 설치 안내: `npx skills add hashicorp/agent-skills/plugins/terraform/skills/provider-test-patterns`

Acceptance test는 실제 자원을 만들고 비용을 발생시키며 삭제할 수 있다. 전용 계정·범위·비용 한도·정리 계획을 먼저 정한다. 동봉 State lookup 예제는 RootModule.Resources만 순회하므로 중첩 module 대상에는 그대로 충분하지 않다. 예제 함수를 복사하는 것과 프로젝트에 맞게 검증하는 것은 다르다.

Sweeper 참조는 test-acc 접두어로 삭제 대상을 고르고 개별 삭제 실패를 로그로 남긴 뒤 nil을 반환하는 예제를 제시한다. 접두어만으로 소유권을 확정하거나 종료 코드만으로 정리 완료를 판단하지 말고, 계정·태그·정확한 대상과 사후 조회를 추가한다. 파괴적 정리 명령은 이번 보고서의 바로 실행할 명령으로 제시하지 않는다. [Sweeper 예제](https://github.com/hashicorp/agent-skills/blob/f706481af9b8fedb66de909f6243ad29601afa0c/plugins/terraform/skills/provider-test-patterns/references/sweepers.md) · [공식 안내](https://developer.hashicorp.com/terraform/plugin/testing/acceptance-tests/sweepers)

## 3. provider-ephemeral-resources

**짧게 쓰는 비밀값을 Terraform plan·state에 남기지 않는 Provider 설계**

- 출처: HashiCorp 공식
- 태그: Terraform · Ephemeral Resource · 비밀값 수명주기 · Open/Renew/Close
- 난이도: 고급. 비밀값 전달·API 만료·폐기 동작과 Provider 구현을 함께 설계해야 한다.
- 현행 상태·버전: active, **0.0.1**. 개별 라이선스 MPL-2.0.

### 무엇을 해주나

단기 토큰·임시 비밀번호·인증서처럼 계속 저장할 필요가 없는 값을 ephemeral resource로 제공하는 방법을 정리한다. 필수 Open과 선택 Renew/Close, 스키마·Provider 등록, 갱신·폐기용 Private 데이터 전달을 다룬다. Terraform 1.10 이상에서 ephemeral resource를 지원하며, 값의 사용 위치도 허용된 ephemeral context로 제한된다. [SKILL.md](https://github.com/hashicorp/agent-skills/blob/f706481af9b8fedb66de909f6243ad29601afa0c/plugins/terraform/skills/provider-ephemeral-resources/SKILL.md) · [공식 개요](https://developer.hashicorp.com/terraform/plugin/framework/ephemeral-resources)

Renew는 이미 제공한 값의 수명을 연장할 수 있지만 새로운 결과값을 반환하지 못한다. 갱신할 때 토큰 자체가 바뀌는 API라면 이 방식에 맞는지 별도 설계가 필요하다. Close도 상위 서비스가 실제 폐기를 지원할 때만 의미가 있으며, 종료 처리 실패·프로세스 중단까지 포함해 TTL과 정리 전략을 검토해야 한다. write-only argument를 전달 대상으로 쓰는 경우에는 **Terraform 1.11 이상**이라는 별도 조건이 있다. [Renew](https://developer.hashicorp.com/terraform/plugin/framework/ephemeral-resources/renew) · [Close](https://developer.hashicorp.com/terraform/plugin/framework/ephemeral-resources/close) · [Write-only 조건](https://developer.hashicorp.com/terraform/plugin/framework/resources/write-only-arguments)

### 실전 프롬프트

“provider-ephemeral-resources로 이 가상 토큰 API의 Provider 설계를 검토해줘. Open/Renew/Close 계약, 갱신 시 값 변경 여부, Private에 둘 lease 식별자, Terraform 최소 버전, 로그·진단 메시지의 비밀값 노출 경로를 표로 정리해줘. 더미 값만 쓰는 테스트 초안까지 만들고 실제 자격증명 발급·저장·전송·회수와 API 호출은 하지 마.”

### 설치·주의

개별 설치 안내: `npx skills add hashicorp/agent-skills/plugins/terraform/skills/provider-ephemeral-resources`

plan/state 비저장 보장은 로그·오류 메시지·상위 서비스·다른 프로그램의 저장까지 막는다는 뜻이 아니다. Sensitive 표시는 출력 가림에 도움이 되지만 전체 비밀 관리 정책을 대신하지 않는다. lease ID도 권한을 가진 handle일 수 있으므로 필요 이상 노출하지 않는다.

특히 함께 안내되는 **echoprovider 테스트는 ephemeral 값을 일반 리소스의 state에 복사해 검사**한다. 실제 운영 비밀값을 넣으면 스킬의 비저장 목표와 어긋나는 테스트 산출물이 생길 수 있다. 더미·폐기 가능한 테스트 값을 사용하고 state·로그·CI artifact 수명도 관리한다. 여러 테스트 단계에서는 기존 echo 리소스가 이전 상태를 보존하므로 단계별 새 인스턴스를 써야 한다. [테스트 참조](https://github.com/hashicorp/agent-skills/blob/f706481af9b8fedb66de909f6243ad29601afa0c/plugins/terraform/skills/provider-test-patterns/references/ephemeral.md) · [공식 echo 동작](https://developer.hashicorp.com/terraform/plugin/testing/acceptance-tests/ephemeral-resources)

## 4. azure-kusto

**스키마를 먼저 확인한 뒤 로그·텔레메트리 질문을 KQL로 풀기**

- 출처: Microsoft 공식
- 태그: Azure · ADX · KQL · 로그 분석 · 시계열
- 난이도: 중급. 데이터베이스 권한과 시간·열·집계 단위를 이해해야 한다.
- 원문 버전: **1.2.2**, MIT.

### 무엇을 해주나

Azure Data Explorer의 클러스터·데이터베이스를 찾고 테이블 스키마를 확인한 뒤 조회·집계·시계열·상관관계 분석을 진행한다. 예를 들어 응답시간을 5분 단위로 묶어 평균과 p50·p95·p99를 비교할 수 있다. 테이블 위치가 불명확할 때는 허가된 후보 데이터베이스의 메타데이터를 확인한 뒤 “없음”을 판단하도록 안내한다. [SKILL.md](https://github.com/microsoft/azure-skills/blob/d1736f313f7a5259006325d8c9dbce046ed128c0/.github/plugins/azure-skills/skills/azure-kusto/SKILL.md)

결과가 비어 있다는 것과 테이블이 없다는 것은 다르다. 시간 필터·테이블명·권한·수집 지연을 함께 검토해야 한다. KQL의 render는 표시 힌트이므로 실제 차트 지원은 클라이언트에 달려 있다. 원문의 workspace() 교차 조회 예시는 Azure Monitor 맥락이어서 모든 ADX 연결에 그대로 복사할 예제로 소개하지 않는다.

### 실전 프롬프트

“azure-kusto로 승인한 구독·ADX 클러스터·데이터베이스의 Telemetry 스키마부터 확인해줘. 최근 24시간 응답시간을 5분 단위로 집계하고 p50·p95·p99 추이를 설명해줘. 조회 범위·시간대·실패·잘린 결과를 밝혀줘. 원문 로그·개인정보를 불필요하게 출력하지 말고 함수 생성·정책 변경·데이터 쓰기는 하지 마.”

### 설치·주의

Azure 리소스 목록을 보는 ARM Reader와 ADX 데이터 조회 권한은 별개다. 일반 조회용 Database Viewer 권한도 RestrictedViewAccess가 적용된 테이블의 접근을 자동 보장하지 않는다. 조회 실패를 해결하려고 임의로 권한을 늘리지 않는다. [ADX 권한](https://learn.microsoft.com/en-us/kusto/access-control/role-based-access-control?view=azure-data-explorer)

공식 Azure MCP 문서의 ADX 조회 작업은 읽기 전용으로 표시되어 있지만, 스킬의 권장사항에는 저장 함수·materialized view·보존 정책도 등장한다. 이들은 별도 변경 작업이다. 도구명과 인자도 실행 환경의 스키마를 확인한다. 현재 문서는 일부 작업에서 클러스터 URI 또는 클러스터명+구독을 선택하도록 설명하므로 Skill의 인자 표를 그대로 고정하지 않는다. 전체 플러그인의 권한은 아래 공통 주의를 따른다. [Azure MCP ADX 도구](https://learn.microsoft.com/en-us/azure/developer/azure-mcp-server/tools/azure-data-explorer)

## 5. azure-resource-visualizer

- 원문 버전: **1.2.3**, MIT.

### 무엇을 해주나

[SKILL.md](https://github.com/microsoft/azure-skills/blob/d1736f313f7a5259006325d8c9dbce046ed128c0/.github/plugins/azure-skills/skills/azure-resource-visualizer/SKILL.md)

[문서 템플릿](https://github.com/microsoft/azure-skills/blob/d1736f313f7a5259006325d8c9dbce046ed128c0/skills/azure-resource-visualizer/assets/template-architecture.md) · [Resource Graph 참조](https://github.com/microsoft/azure-skills/blob/d1736f313f7a5259006325d8c9dbce046ed128c0/skills/azure-resource-visualizer/references/azure-resource-graph.md)

### 실전 프롬프트

“azure-resource-visualizer로 승인한 구독의 지정 리소스 그룹을 조회하고 로컬 아키텍처 문서 초안을 만들어줘. 검증된 연결만 그림에 표시하고, 다른 그룹의 의존성·권한으로 보이지 않는 부분·관측 시각을 따로 적어줘. 시크릿·키·연결 문자열의 실제 값을 조회하거나 문서에 넣지 말고 외부 게시·업로드와 Azure 변경은 하지 마.”

### 설치·주의

스킬은 Azure 자원을 수정·삭제하지 않는 분석으로 명시하지만 로컬 Markdown 파일은 작성한다. 기존 문서 덮어쓰기 여부를 확인하고 Mermaid를 지원하는 환경에서 실제 렌더링을 검증한다. 50개를 넘는 복잡한 그룹은 계층별 여러 그림으로 나누도록 제안한다.

원문은 비밀값 대신 의미 있는 자리표시자를 쓰도록 하지만 **결과에서 가리는 것과 처음부터 비밀값을 조회하지 않는 것은 다르다.** 관계를 조사한다며 연결 문자열·앱 설정·Key Vault 값을 광범위하게 읽지 않도록 메타데이터 중심으로 범위를 제한한다. 리소스 이름·내부 주소·구성만으로도 민감할 수 있으므로 문서 생성과 공유 승인은 분리한다. 권한으로 보이지 않는 자원·그룹 밖 의존성이 있으면 완전한 지도라고 표현하지 않는다.

## 6. azure-resource-lookup

**여러 구독의 자산·태그·상태를 범위가 드러나는 목록으로 찾기**

- 출처: Microsoft 공식
- 태그: Azure · 자산 인벤토리 · Resource Graph · KQL · 태그 점검
- 난이도: 초중급. 구독 선택과 페이지·권한 범위 확인이 필요하다.
- 원문 버전: **1.2.3**, MIT.

### 무엇을 해주나

VM·웹 앱·스토리지·Container Apps 등 자원을 구독·리소스 그룹·유형·태그로 찾는다. 전용 MCP 조회 도구가 충분하면 우선 사용하고, 여러 종류를 묶는 검색에는 Azure Resource Graph(ARG)를 활용한다. 태그가 빠진 자원이나 미연결 디스크를 점검 후보로 모으는 데 적합하다. [SKILL.md](https://github.com/microsoft/azure-skills/blob/d1736f313f7a5259006325d8c9dbce046ed128c0/.github/plugins/azure-skills/skills/azure-resource-lookup/SKILL.md) · [쿼리 참조](https://github.com/microsoft/azure-skills/blob/d1736f313f7a5259006325d8c9dbce046ed128c0/.github/plugins/azure-skills/skills/azure-resource-lookup/references/azure-resource-graph.md)

azure-kusto가 애플리케이션 로그·텔레메트리 데이터를 다룬다면 ARG는 Azure 자원 메타데이터를 검색한다. 둘 다 KQL 계열을 쓰지만 ARG는 지원 언어가 부분집합이다. 이미 소개한 cost-optimization과도 구분한다. 인벤토리에서 미연결이라는 사실을 발견한 것만으로 미사용·삭제 가능·절감액을 확정할 수 없다.

### 실전 프롬프트

“azure-resource-lookup으로 승인한 두 구독의 App Service와 Container Apps를 찾아 이름·유형·리전·리소스 그룹·Environment 태그를 정리해줘. 태그 누락을 별도 표시하고 조회 범위, 권한 제한, 결과 건수와 페이지 완료 여부를 밝혀줘. 비용 추정·삭제·설정 변경은 하지 마.”

### 설치·주의

CLI 경로는 resource-graph 확장이 필요하다. 스킬의 도구별 지원 표는 설치한 MCP 버전에 따라 달라질 수 있으므로 실제 사용 가능한 조회 도구를 먼저 확인한다. 명령 생성이 끝났다고 조회까지 완료된 것은 아니다.

ARG는 권한이 있는 자원만 반환하며 접근 가능한 범위가 부분적일 때 결과만 보고 이를 알아차리기 어려울 수 있다. 인덱싱 지연이 있어 방금 변경된 상태나 실시간 장애를 확정하는 용도로 쓰지 않는다. --first는 반환 건수 제한이며 구독을 제한하는 --subscriptions와 역할이 다르다. 큰 환경에서는 실제 구독 범위와 페이지네이션·잘림을 모두 검증해야 한다. [공식 ARG 개요](https://learn.microsoft.com/en-us/azure/governance/resource-graph/overview)
