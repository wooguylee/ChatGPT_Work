동봉 formatter는 공백을 한 줄로 정규화하고 기본 4,000자 제한을 검사한다. **이는 formatter의 기본값이지 모든 호스트의 현행 제품 한도를 독립 검증한 값은 아니다.** 설치한 호스트의 도움말에서 명령 지원·중단 동작을 확인한다. 또한 종료 조건 탐지는 영어 `blocked` 또는 숫자+turns/minutes 등의 정규식이다. 한국어로 적절한 중단 조건을 써도 경고가 날 수 있고, 영어 단어만 있어도 실제 종료 논리가 적절한지는 판정하지 못한다. [formatter 구현](https://github.com/trailofbits/skills/blob/main/plugins/goal-prompt/skills/goal-prompt/scripts/format_goal_prompt.py)

성공 조건들은 함께 만족하도록 구성하되, 별도의 막힘 보고·중단 조건은 성공과 구분한다. 작업 목표 초안 작성이 자율 실행·코드 수정·외부 게시의 승인으로 이어지는 것은 아니다. 긴 요구사항은 별도 문서를 참조하게 하되 그 파일의 존재와 내용을 먼저 확인한다.

## 4. mutation-testing

- 제작: Trail of Bits · 확인 버전: 1.9.2
- 난이도: 중급. 결과를 읽는 일은 비교적 가볍지만 새 캠페인은 테스트 실행 환경과 시간 예산이 필요하다.
- 태그: 테스트 품질, 변이 테스트, 회귀 방지, mewt, muton

의도적으로 바꾼 코드가 기존 테스트를 통과했을 때, 그 이유를 분석하는 스킬이다. mewt·muton 캠페인 설정, 완료된 결과의 보고서 작성, 취약하게 테스트된 원본 코드의 버그 조사라는 세 경로를 제공한다. 설정 단계에서는 실제 대상 파일과 테스트 시간을 확인하고 예상 소요 시간을 계산한다. 결과 분석에서는 살아남은 변이마다 소스와 테스트를 읽어 동등한 변이, 실제 테스트 공백, 증거가 부족한 항목을 나눈다. [공식 설명](https://github.com/trailofbits/skills/blob/main/plugins/mutation-testing/README.md)

예를 들어 unsigned 정수의 `x > 0`을 `x != 0`으로 바꾸면 관찰 가능한 동작이 같을 수 있다. 반면 `x >= 0`으로 바꾸면 0에서 결과가 달라진다. 단순 생존 개수보다 타입·경계값·도달 가능성을 확인하는 것이 이 스킬의 핵심이다. 보고서는 누락된 assertion과 입력을 제안하며, 분석 경로 자체가 테스트 코드를 구현하지는 않는다. [분석 절차](https://github.com/trailofbits/skills/blob/main/plugins/mutation-testing/skills/mutation-testing/workflows/analyzing-results.md), [동등성 확인 기준](https://github.com/trailofbits/skills/blob/main/plugins/mutation-testing/skills/mutation-testing/references/equivalent-mutants.md)

활용 장면: 커버리지가 높아도 인증·정산 로직의 assertion이 충분한지 의심될 때, 이미 확보한 mutation 결과를 다음 테스트 작업 목록으로 바꾸는 데 적합하다. 저장된 결과·해당 소스·테스트가 있다면 mewt나 muton 설치 없이 분석할 수 있다. 새 캠페인에는 별도 실행 도구와 정상 동작하는 테스트가 필요하며 예제는 mewt 4.x 기준이다. [요구사항](https://github.com/trailofbits/skills/blob/main/plugins/mutation-testing/README.md)

**Agent 활용 예시**

“mutation-testing으로 제공한 mutations.json과 해당 리비전의 소스·테스트를 분석해 줘. 각 survivor를 동등함·테스트 공백·미해결로 나누고 근거와 필요한 경계값/assertion을 적어 줘. timeout·skip을 별도 집계하고 비율의 분모를 밝혀 줘. 기존 파일 수정, 새 캠페인 실행, 도구 설치, 저장 결과 삭제는 하지 말고 mutation-testing-report.md만 만들어 줘.”

주의할 점: survivor는 원본 코드의 취약점 확정이 아니다. mutation 연산자의 등급도 실제 제품 위험도와 같지 않다. Timeout은 결론 불가이며, 높은 kill rate만으로 전체 테스트의 적절성을 보증할 수 없다. 설정 변경 후 사용하는 purge는 기존 결과를 삭제하므로 보존 여부를 먼저 확인해야 한다. [스킬 원문](https://github.com/trailofbits/skills/blob/main/plugins/mutation-testing/skills/mutation-testing/SKILL.md), [설정 절차](https://github.com/trailofbits/skills/blob/main/plugins/mutation-testing/skills/mutation-testing/workflows/configuration.md)

## 5. fp-check

- 제작: Trail of Bits 저장소, 플러그인 작성자 Maciej Domanski · 확인 버전: 1.0.5
- 난이도: 고급. 위협 모델, 데이터 흐름, 공격자 통제 범위와 실행 환경을 함께 읽어야 한다.
- 태그: 오탐 검증, 보안 리뷰, 데이터 흐름, 위협 모델, 증거 기반 판정

이미 제기된 보안 의심 항목이 실제 취약점인지 확인하는 스킬이다. 먼저 주장·원인·트리거·영향·위협 모델을 다시 정리한 뒤, 명확한 단일 컴포넌트 문제는 Standard, 여러 컴포넌트·경쟁 상태·모호한 논리 문제는 Deep 경로로 보낸다. 두 경로 모두 데이터 흐름, 공격자 통제, 실제 영향, PoC, 반대 근거를 검토하고 최종적으로 6개 게이트를 평가한다. 새로운 버그를 무작정 찾거나 일반 스타일 리뷰를 하는 용도와는 구분된다. [스킬 원문](https://github.com/trailofbits/skills/blob/main/plugins/fp-check/skills/fp-check/SKILL.md)

Standard는 의사코드 PoC를 요구하되 실행 가능한 PoC는 선택 사항이다. Deep은 의존성이 있는 검증 단계를 추적하며 데이터 흐름·악용 가능성·PoC 작업을 전용 에이전트로 나눌 수 있다. 겉으로 위험해 보이는 연산만 보고 판단하지 않고 앞선 입력 검증, 실제 호출 경로, 타입 범위, 운영 환경의 방어를 확인한다. 반대로 확인하지 않은 방어 장치를 상상해서 진짜 문제를 기각하는 것도 경계한다. [Standard 절차](https://github.com/trailofbits/skills/blob/main/plugins/fp-check/skills/fp-check/references/standard-verification.md), [Deep 절차](https://github.com/trailofbits/skills/blob/main/plugins/fp-check/skills/fp-check/references/deep-verification.md)

활용 장면: 정적 분석기나 AI 리뷰가 제기한 특정 경고를 이슈로 승격하기 전, 보고서의 주장과 실제 소스를 대조하는 데 적합하다. 코드 조각만 주기보다 해당 리비전, 호출자, 검증 함수, 관련 테스트, 적용 환경을 함께 제공해야 효과적이다. 전체 Claude 플러그인에는 검증의 누락을 확인하는 Stop·SubagentStop 프롬프트 hook도 포함되어 있다. [구성요소](https://github.com/trailofbits/skills/blob/main/plugins/fp-check/README.md)

**Agent 활용 예시**

“fp-check로 finding-17.md의 길이 검사 우회 주장을 이 로컬 소스에서 검증해 줘. 주장과 위협 모델을 먼저 정리하고 입력부터 문제 연산까지 호출·검증 경로를 파일:행 근거로 추적해 줘. Standard와 Deep 중 필요한 경로를 선택하고 6개 게이트의 근거를 보여 줘. 아직 실행하지 않은 PoC를 실행 증거로 표현하지 말고, 자료 부족과 반증을 구별해 줘. 이 단계에서는 파일 변경이나 외부 대상 테스트 없이 분석과 의사코드 PoC만 작성해 줘.”

주의할 점: 공식 게이트 형식은 모두 통과하면 TRUE POSITIVE, 하나라도 실패하면 FALSE POSITIVE라는 이진 판정이다. 따라서 독자는 “공격 경로를 반증했다”와 “확인할 자료가 모자랐다”를 별도로 읽어야 한다. 실행되지 않은 의사코드 PoC나 자동 hook은 런타임 검증의 대체물이 아니다. 메모리·정수·논리·동시성·주입·DoS 등 문제 종류별 요구사항도 함께 확인해야 한다. [게이트와 판정 형식](https://github.com/trailofbits/skills/blob/main/plugins/fp-check/skills/fp-check/references/gate-reviews.md), [버그 종류별 검증](https://github.com/trailofbits/skills/blob/main/plugins/fp-check/skills/fp-check/references/bug-class-verification.md)

### 설치 및 사용

설치: 마켓플레이스 등록 후 `/plugin install fp-check@trailofbits`. 개별 스킬은 `npx skills add https://github.com/trailofbits/skills --skill fp-check`. 에이전트·hook까지 포함하는 전체 플러그인과 개별 스킬 설치의 제공 범위를 동일하게 보지 말아야 한다. ## 6. post-patch-validation

- 제작: Trail of Bits 저장소, 플러그인 작성자 Scott Arciszewski · 확인 버전: 0.2.2
- 난이도: 고급. 취약점의 원인, 고정된 두 리비전, 실행 가능한 테스트 환경이 필요하다.
- 태그: 보안 패치, 재현성, 회귀 테스트, 증거 보존, AI 코드 검증

이미 만들어진 보안 패치가 원래 문제를 해결하고 주변 동작도 보존하는지 검사한다. 취약한 base와 패치된 입력을 고정하고 별도 Git worktree에서 실행하며, 검증용 계획과 실제 assertion·stdout·stderr를 남긴다. 체크는 정상 대조군, 원본 재현, 독립적인 근본원인 변형, 기존 동작, 비보안 회귀, 인접 보안 문제, 기존 테스트 모음의 7종이 필요하다. `result.json`과 `report.md`에서 입증된 실패와 검증 공백을 각각 확인할 수 있다. [스킬 원문](https://github.com/trailofbits/skills/blob/main/plugins/post-patch-validation/skills/post-patch-validation/SKILL.md)

중요한 설계는 “실패했다”는 종료 코드만으로 취약점 재현을 인정하지 않는다는 것이다. 원본·변형 체크는 안전 조건을 검사하기 직전에 실행 도달 표식을 출력해야 하며, base와 patch에서 같은 보안 조건을 검사한다. 의존성 누락이나 잘못된 테스트 코드의 실패를 성공적인 재현으로 오해하지 않도록 돕는다. `source`, `build`, `runtime` 증거 수준도 구분한다. [증거 모델](https://github.com/trailofbits/skills/blob/main/plugins/post-patch-validation/skills/post-patch-validation/references/evidence-model.md)

활용 장면: AI가 만든 수정안이나 upstream 보안 패치를 병합하기 전에, 같은 원인의 다른 진입점과 기존 정상 동작까지 확인할 때 유용하다. Git 2.36+, Python 3.11+, uv, 대상 프로젝트의 빌드·테스트 의존성이 필요하다. 원격·운영 시스템 대상이 아니며 로컬 코드 실행 허가가 전제다. Claude Code에는 `/post-patch-validation:validate-patch` 동적 워크플로도 있지만 별도 활성화와 사전 입력이 필요하다. [설치·요구사항](https://github.com/trailofbits/skills/blob/main/plugins/post-patch-validation/README.md)

**Agent 활용 예시**

“내 로컬 저장소의 base <취약 SHA>와 patch <수정 SHA>, findings.md를 post-patch-validation으로 검증해 줘. 전용 비밀정보 없는 컨테이너 안에서 해당 저장소의 코드·테스트 실행을 허가해. 7종 체크를 포함한 고정 계획을 먼저 검증하고, 원본과 독립 변형은 실제 안전 assertion에 도달했는지 확인해 줘. 원본 작업 트리와 패치를 수정하지 말고, 실행 로그·증거 수준·findings·gaps를 모두 보존해 줘. 병합은 하지 말고 사람 검토용 결과를 제출해 줘.”

주의할 점: `complete`는 필요한 증거가 모였다는 뜻이며 모든 검사가 통과했다는 뜻은 아니다. `incomplete`에도 유효한 실패가 함께 들어갈 수 있다. 제공한 검사가 전부 통과해도 누락된 경로까지 안전하다고 증명하지 않으며 사람 검토가 항상 필요하다. worktree와 증거 디렉터리 분리는 OS 보안 샌드박스가 아니다. 체크는 호출자의 권한으로 실행되므로 신뢰하지 않는 테스트는 별도 컨테이너·OS 격리에서 실행해야 한다. [결과 해석과 안전 경계](https://github.com/trailofbits/skills/blob/main/plugins/post-patch-validation/README.md)

설치: `/plugin marketplace add trailofbits/skills` 다음 `/plugin install post-patch-validation@trailofbits`. 개별 스킬은 `npx skills add https://github.com/trailofbits/skills --skill post-patch-validation`. 개별 스킬 설치와 Claude 전용 동적 워크플로 제공 범위는 구분해야 한다.
