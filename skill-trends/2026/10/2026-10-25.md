## 1. azure-cosmos-py

**에이전트 작업 상태를 JSON 문서로 저장할 때, ID와 partition key를 함께 설계하게 돕는 Skill.**

- 조직 / 라이선스: Microsoft / MIT
- 대상 패키지: `azure-cosmos`
- 태그: `agent-state` `nosql` `partition-key` `query-design`
- 난이도: 중급
- 원문: [SKILL.md](https://github.com/microsoft/skills/blob/2130750147dee0311215099ddf36647ba1e0f006/.github/plugins/azure-sdk-python/skills/azure-cosmos-py/SKILL.md)

### 무엇을 해주나

CosmosClient에서 database·container로 접근하는 구조, 문서 CRUD, 매개변수 쿼리, partition key, sync/async 사용법을 정리한다. 예를 들어 에이전트 실행 이력을 tenant별로 보관할 때 단건 조회에 ID와 partition key가 함께 필요한지, 무심코 전체 partition을 조회하는 코드가 있는지 검토하는 데 적합하다.

원문은 cross-partition 조회의 비용과 point read의 사용을 구분한다. 별도 Skill인 azure-cosmos-db-py까지 함께 신규 개수로 세지 않았다. 같은 서비스의 중첩 후보를 늘리는 대신 오늘은 한 항목만 선정했다.

### 실전 프롬프트

> azure-cosmos-py를 참고해 저장소의 에이전트 실행 상태 모델을 검토해 줘. tenant_id와 run_id의 역할, point read에 필요한 키, cross-partition 쿼리 발생 경로를 정리해. 가짜 데이터와 mock client만 사용하고 컨테이너 생성, 문서 쓰기·삭제, throughput 변경, 실제 계정 접속은 하지 마.

### 설치·주의

검토용 패키지는 `pip install azure-cosmos azure-identity`다. 원문에는 리소스 생성·upsert·삭제·throughput 변경도 포함되므로 읽기 검토와 분리해야 한다. upsert는 기존 문서를 바꿀 수 있으며 업무 전체의 중복 실행 방지까지 자동 보장하지 않는다. 원문의 preview 표기나 개별 메서드가 설치 버전에서도 유효한지는 별도 확인한다. 이 보고서는 Cosmos NoSQL용 SDK 범위만 다루며 다른 Cosmos API에 같은 코드를 적용하지 않는다. [공식 Cosmos SDK 개요](https://learn.microsoft.com/en-us/python/api/overview/azure/cosmos-readme?view=azure-python)

## 2. azure-data-tables-py

**간단한 작업 상태·처리 결과를 복합 키로 관리하는 코드의 저장 규칙을 점검하는 Skill.**

- 조직 / 라이선스: Microsoft / MIT
- 대상 패키지: `azure-data-tables`
- 태그: `key-value` `job-status` `partitioning` `batch-operations`
- 난이도: 중급
- 원문: [SKILL.md](https://github.com/microsoft/skills/blob/2130750147dee0311215099ddf36647ba1e0f006/.github/plugins/azure-sdk-python/skills/azure-data-tables-py/SKILL.md)

### 무엇을 해주나

TableServiceClient와 TableClient의 역할, PartitionKey·RowKey, entity 조회·갱신, 필터 매개변수화, 같은 partition의 batch 작업을 안내한다. 복잡한 문서 검색보다 “어떤 실행이 어떤 상태인가”를 키로 찾는 작은 상태표 설계에 활용하기 좋다. 오늘의 Cosmos 항목과 목적이 겹쳐 보일 수 있지만 대상 API와 엔터티 구조가 달라 구현 전에 선택해야 한다.

### 실전 프롬프트

> azure-data-tables-py를 참고해 실행 상태표의 PartitionKey·RowKey 규칙을 제안해 줘. tenant가 다른 행을 혼동하지 않는 테스트와 merge·replace 의도를 명시하는 테스트를 작성해. 모든 예제는 메모리 내 fixture로 한정하고 테이블 생성·변경·삭제나 운영 데이터 읽기는 하지 마.

### 설치·주의

검토용 패키지는 `pip install azure-data-tables azure-identity`다. 원문이 Azure Storage와 Cosmos DB Table API를 함께 언급하더라도 인증 지원을 동일하게 가정하면 안 된다. 확인한 공식 SDK 개요는 TokenCredential / Microsoft Entra ID 지원을 **Storage**로 한정해 표기한다. 대상 backend를 먼저 확인하고 계정 키를 대안으로 자동 수집·출력하지 않는다. 원문의 upsert 주석만 보고 merge·replace 동작을 결정하지 말고 설치 버전에서 모드를 명시·검증한다. [공식 Tables SDK 개요](https://learn.microsoft.com/en-us/python/api/overview/azure/data-tables-readme?view=azure-python)

## 3. azure-eventgrid-py

**작업 완료 같은 이벤트를 CloudEvents 형식으로 표현하고 발행 경계를 검토하는 Skill.**

- 조직 / 라이선스: Microsoft / MIT
- 대상 패키지: `azure-eventgrid`
- 태그: `cloudevents` `event-routing` `pub-sub` `schema-validation`
- 난이도: 중급
- 원문: [SKILL.md](https://github.com/microsoft/skills/blob/2130750147dee0311215099ddf36647ba1e0f006/.github/plugins/azure-sdk-python/skills/azure-eventgrid-py/SKILL.md)

### 무엇을 해주나

EventGridPublisherClient, CloudEvent·EventGridEvent, 이벤트 속성과 batch 발행을 소개한다. 에이전트가 작업 결과를 다른 시스템으로 알릴 때 type·source·subject·data의 역할을 구분하고, 결과 본문 전체를 이벤트에 넣지 않도록 스키마를 검토하는 데 유용하다. 실제 발행은 후속 구독자를 작동시킬 수 있으므로 단순 로그 출력과 다르게 취급한다.

### 실전 프롬프트

> azure-eventgrid-py를 참고해 agent.run.completed 이벤트의 로컬 fixture와 검증 테스트를 만들어 줘. run_id와 결과 참조만 담고 프롬프트 원문·개인정보·토큰은 제외해. Basic과 Namespace의 클라이언트 설정 차이를 표시하고 send 호출은 mock으로 막아. 구독 생성이나 실제 발행은 하지 마.

### 설치·주의

검토용 패키지는 `pip install azure-eventgrid azure-identity`다. **원문의 Namespace 예제를 그대로 복사하지 않는다.** 확인한 공식 SDK 문서는 `namespace_topic`을 `send()`가 아니라 **EventGridPublisherClient 생성 시** 지정한다. CloudEvent 예제의 공식 import 경로는 `azure.core.messaging`이다. Namespace는 CloudEvents v1.0 스키마만 지원하며 Basic과 전달 방식도 구분해야 한다. 이 차이를 수정하고 설치 버전에 맞춘 뒤 검토한다. [공식 Event Grid SDK 개요·예제](https://learn.microsoft.com/en-us/python/api/overview/azure/eventgrid-readme?view=azure-python)

## 4. azure-eventhub-py

**많은 이벤트를 연속 처리하는 소비자의 재시작 지점과 체크포인트를 설계하는 Skill.**

- 조직 / 라이선스: Microsoft / MIT
- 대상 패키지: `azure-eventhub`
- 태그: `streaming` `checkpoint` `consumer-groups` `reprocessing`
- 난이도: 중상급
- 원문: [SKILL.md](https://github.com/microsoft/skills/blob/2130750147dee0311215099ddf36647ba1e0f006/.github/plugins/azure-sdk-python/skills/azure-eventhub-py/SKILL.md)

### 무엇을 해주나

producer·consumer, batch 크기 제한, partition, consumer group, BlobCheckpointStore를 이용한 처리 진도를 설명한다. 에이전트 평가 이벤트나 실행 관측 데이터를 스트림으로 처리하는 코드를 검토할 때 “읽었다”와 “업무 처리가 끝났다”를 구분하는 데 실익이 있다. Event Grid의 개별 알림 라우팅과 달리 여기서는 스트림 소비 위치와 재처리가 핵심이다.

### 실전 프롬프트

> azure-eventhub-py를 참고해 소비자의 처리 성공 전 체크포인트 갱신 경로를 찾아 줘. 처리 실패, 재시작, 같은 이벤트 재수신을 가짜 partition context로 테스트해. 외부 부작용은 mock으로 대체하고 consumer group 접속, 이벤트 발행, Blob checkpoint 쓰기는 하지 마.

### 설치·주의

검토용 패키지는 `pip install azure-eventhub azure-identity`다. 영속 Blob 체크포인트는 별도 checkpoint-store 패키지·저장소와 sync/async 조합을 확인해야 한다. 공식 문서에서 체크포인트는 partition·consumer group별 마지막 성공 처리 위치를 나타내며 부하 분산에도 쓰인다. 체크포인트를 남겼다는 사실만으로 외부 업무의 exactly-once 처리를 보장하지 않는다. 원문의 `starting_position="-1"`은 처음부터 읽는 설정이므로 대량 재처리를 의도한 것인지 확인한다. 이벤트 본문을 그대로 print하는 예제는 운영 로그에 옮기지 않는다. [공식 Event Hubs SDK 개요·체크포인트](https://learn.microsoft.com/en-us/python/api/overview/azure/eventhub-readme?view=azure-python)

## 5. azure-storage-queue-py

**작업 큐를 관찰하는 코드와 작업을 가져가 상태를 바꾸는 코드를 분리하는 Skill.**

- 조직 / 라이선스: Microsoft / MIT
- 대상 패키지: `azure-storage-queue`
- 태그: `task-queue` `visibility-timeout` `peek` `retry-safety`
- 난이도: 중급
- 원문: [SKILL.md](https://github.com/microsoft/skills/blob/2130750147dee0311215099ddf36647ba1e0f006/.github/plugins/azure-sdk-python/skills/azure-storage-queue-py/SKILL.md)

### 무엇을 해주나

QueueServiceClient·QueueClient, 메시지 전송·수신·peek·삭제, visibility timeout, TTL, dequeue_count를 다룬다. 오래 걸리는 에이전트 작업을 큐로 넘길 때 관측 도구가 실수로 메시지를 가져가거나 지우지 않는지 검토할 수 있다. 기존 Service Bus 항목의 session·topic 중심 작업과 구분되는 간단한 Queue Storage 모델이다.

### 실전 프롬프트

> azure-storage-queue-py를 참고해 운영 큐 상태 점검 스크립트를 정적 검토해 줘. receive_messages·delete_message·clear_messages가 관측 경로에 있으면 표시하고, queue properties와 제한된 peek만 사용하는 설계를 제안해. 메시지 내용은 기록하지 말고 mock 응답으로 테스트해. 실제 큐 조회나 변경은 하지 마.

### 설치·주의

검토용 패키지는 `pip install azure-storage-queue azure-identity`다. 공식 SDK 문서상 **receive는 메시지를 다른 소비자에게 일시적으로 보이지 않게 하며, peek는 visibility를 바꾸지 않는다.** 따라서 receive를 “읽기 전용 점검”으로 취급하지 않는다. clear는 전체 메시지 삭제다. 처리 성공 후 삭제, 작업 시간에 맞춘 visibility timeout, 반복 실패 처리를 별도로 설계하고 민감한 본문 출력은 제거한다. [공식 Queue Storage SDK 개요·연산 의미](https://learn.microsoft.com/en-us/python/api/overview/azure/storage-queue-readme?view=azure-python)
