[SKILL.md](https://github.com/microsoft/skills/blob/a779d00cf3749577a7777422ab6dee9e66dcb2e2/.github/plugins/azure-sdk-python/skills/fastapi-router-py/SKILL.md)

“azure-identity-py를 참고해 이 Python 프로젝트의 인증 경로를 정적으로 검토해줘. 로컬과 배포 환경을 나누고 선택될 자격 증명, 패키지 버전, 필요한 환경 변수 이름, 클라이언트·credential 종료 위치를 적어줘. 비밀값은 읽거나 출력하지 마. 운영에서 사용할 명시적 credential 후보와 RBAC 확인 항목만 제안하고 로그인·토큰 발급·역할 부여·설정 변경은 하지 마.”

[공식 credential chain 문서](https://learn.microsoft.com/en-us/azure/developer/python/sdk/authentication/credential-chains)

`prod`는 개발 도구 자격 증명을 제외하는 선택 조건이지, 최소 권한을 부여하거나 서비스 접근을 보장하는 설정이 아니다. 인증 성공과 데이터 작업 권한은 별도로 확인한다. Skill의 디스크 캐시·다중 테넌트 예제도 기본 보안 정책으로 취급하지 않는다. 암호화 없는 캐시나 광범위 테넌트 허용을 무심코 채택하지 말고, 디버그 로그에 식별 정보가 남을 수 있어 원문 로그를 공개하지 않는다.

## 4. azure-storage-blob-py

**파일이 올라갔는지뿐 아니라, 무엇을 덮어썼고 누구에게 열렸는지 확인하기**

- 조직·출처: Microsoft / microsoft/skills
- 라이선스: MIT. 저장·요청·전송 비용은 별도다.
- 대상 패키지: `azure-storage-blob`
- 태그: 객체 저장 · 업로드 · 다운로드 · 동시성 · SAS · 자원 정리
- 난이도: 중급. 컨테이너·객체명·덮어쓰기·보존 정책을 정해야 한다.

### 무엇을 해주나

계정·컨테이너·단일 Blob 클라이언트를 구분하고 업로드, 다운로드, 접두사 목록 조회, 속성·메타데이터, 동기·비동기 사용 패턴을 안내한다. user delegation SAS 예제로 제한된 공유를 다루며, 전송 동시성과 클라이언트 수명주기도 정리한다. [SKILL.md](https://github.com/microsoft/skills/blob/a779d00cf3749577a7777422ab6dee9e66dcb2e2/.github/plugins/azure-sdk-python/skills/azure-storage-blob-py/SKILL.md)

기존 Azure 자산 검색·구성 시각화 스킬과 달리 애플리케이션의 실제 파일 데이터 경로를 대상으로 한다. 저장소를 생성·구성하는 인프라 작업과도 구분한다.

### 실전 프롬프트

“azure-storage-blob-py를 참고해 승인된 공개 테스트 파일의 저장 설계를 검토해줘. tenant별 객체명 충돌 방지, 기본 덮어쓰기 거부, 대용량 다운로드의 메모리 사용, 업로드 후 크기·내용 검증, 실패 재시도를 설명해. 기존 객체 변경이나 컨테이너 생성은 하지 마. 공유가 필요해도 SAS를 발급하지 말고 최소 권한·기간과 노출 방지 요구만 정리해줘.”

### 설치·주의

원문의 업로드 예제에는 `overwrite=True`가 반복된다. 재업로드 편의를 기존 데이터 덮어쓰기 허가로 해석하지 않는다. 같은 Blob에 대한 여러 작성자의 동시 업로드도 자동 안전하지 않으며, 공식 문서는 애플리케이션의 동시성 제어를 요구한다. 고유 객체명·조건부 갱신 등은 프로젝트 요구에 맞게 별도 설계한다. [공식 업로드 문서](https://learn.microsoft.com/en-us/azure/storage/blobs/storage-blob-upload-python)

원문의 `readall()`은 내용을 메모리에 모으며, `readinto(BytesIO())` 역시 메모리 버퍼를 쓴다. 단순히 메서드 이름만 바꾸었다고 대용량 메모리 문제가 해결됐다고 주장할 수 없다. 실제 출력 대상과 청크 처리 방식을 확인한다.

SAS가 붙은 URL은 일반 공개 문서 링크처럼 로그·이슈에 남길 대상이 아니다. 원문이 제시하는 Entra 기반 위임 방식도 발급자 권한, 대상, 만료, 실제 데이터 접근 범위를 확인해야 한다. 이번 조사에서는 키·토큰·SAS 생성이나 Blob 전송을 수행하지 않았다.

## 5. azure-servicebus-py

**메시지를 받은 것, 업무가 끝난 것, 큐에서 지운 것을 분리하기**

- 조직·출처: Microsoft / microsoft/skills
- 라이선스: MIT
- 대상 패키지: `azure-servicebus`
- 태그: 작업 큐 · 토픽 · PeekLock · 멱등성 · DLQ · 세션
- 난이도: 중상급. 재전달과 부분 실패에 대응하는 업무 상태 설계가 필요하다.

### 무엇을 해주나

큐와 토픽·구독, 배치 전송, 수신 잠금, complete·abandon·dead-letter·defer 처리, 세션과 예약 메시지의 Python 사용 패턴을 제공한다. 동기·비동기 사용을 섞지 않고 클라이언트와 비동기 credential을 정리하도록 한다. [SKILL.md](https://github.com/microsoft/skills/blob/a779d00cf3749577a7777422ab6dee9e66dcb2e2/.github/plugins/azure-sdk-python/skills/azure-servicebus-py/SKILL.md)

문서 분석처럼 오래 걸리는 작업을 요청 처리에서 분리할 때 유용하지만, 이 Skill만 추가했다고 전체 파이프라인이 정확히 한 번 실행되는 것은 아니다. 세션의 순서 보장도 모든 세션을 합친 전역 순서로 확대 해석하지 않는다.

### 실전 프롬프트

“azure-servicebus-py를 참고해 문서 분석 작업 consumer의 실패 경로를 검토해줘. 업무 결과 저장 뒤 complete가 실패하는 경우, 잠금 만료, 중복 수신, 처리 불가능한 메시지를 나눠줘. 작업 ID 기반 멱등성, 완료 확인 시점, DLQ 조사와 재처리 승인을 설계해. 운영 큐 수신·complete·재전송이나 큐 생성·설정 변경 없이 코드와 테스트 계획만 제안해줘.”

### 설치·주의

PeekLock은 수신 후 명시적 완료를 기다린다. 업무 처리가 성공해도 complete 통신이 실패하면 메시지가 다시 올 수 있어, 지속 저장한 처리 결과와 멱등성을 함께 설계해야 한다. ReceiveAndDelete는 전송 단계에서 소비된 것으로 처리하므로 전송 실패 시 메시지를 잃을 수 있다. [공식 잠금·완료 문서](https://learn.microsoft.com/en-us/azure/service-bus-messaging/message-transfers-locks-settlement)

**원문의 DLQ 예제는 읽기 전용 모니터링이 아니다.** 메시지를 받아 이유를 출력한 뒤 `complete_message()`를 호출하므로 메시지를 제거한다. 장애 조사 목적으로 그대로 실행하면 재처리할 자료를 소비할 수 있다. 조회·처리·삭제를 분리하고, 운영 큐에는 승인된 작업만 수행한다. 또한 간략한 예제에서 생략된 credential 종료와 잠금 갱신·업무 중복 방지까지 자동 구현됐다고 가정하지 않는다.
