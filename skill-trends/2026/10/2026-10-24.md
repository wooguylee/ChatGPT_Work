## 1. azure-appconfiguration-py

**환경별 설정을 코드에서 분리하고, 배포 시 어떤 설정을 사용했는지 추적하는 Skill.**

- 조직 / 라이선스: Microsoft / MIT
- 대상 패키지: `azure-appconfiguration`
- 태그: `configuration` `feature-flags` `snapshots` `python`
- 난이도: 중급
- 원문: [SKILL.md](https://github.com/microsoft/skills/blob/2130750147dee0311215099ddf36647ba1e0f006/.github/plugins/azure-sdk-python/skills/azure-appconfiguration-py/SKILL.md)

### 무엇을 해주나

키 prefix와 label로 설정을 조회하고, feature flag JSON, 읽기 전용 설정, snapshot을 다룬다. 에이전트 서비스의 모델 라우팅이나 기능 활성화 설정을 개발·운영 환경별로 구분하는 설계에 유용하다. 이전 인증 Skill은 “누가 접근하는가”에 집중했다면, 이 Skill은 “어떤 환경의 어떤 설정을 사용하는가”를 다룬다.

### 실전 프롬프트

> azure-appconfiguration-py를 참고해 현재 설정 로딩 코드를 검토해 줘. 개발·운영 label이 섞이는 경로와 누락된 키의 fallback을 찾아 줘. 값 자체는 출력하지 말고 키 이름·label·코드 위치만 정리해. feature flag를 변경하거나 snapshot을 새로 만들지 말고, 기존 snapshot을 사용하는 재현 가능한 배포 설계와 단위 테스트 초안만 제시해.

### 설치·주의

SDK 설치 예시는 `pip install azure-appconfiguration`이며 인증용 패키지는 별도로 확인한다. 공식 SDK 문서에서 `set_configuration_setting`은 기존 값을 덮어쓸 수 있다. snapshot은 일관된 시점의 불변 설정 묶음이지만, 생성 자체는 쓰기 작업이다.

**원문 수정 필요:** Skill의 snapshot 예시는 `ConfigurationSettingFilter`와 객체 전달 방식을 사용하지만, 확인한 SDK 1.10.0 문서는 `ConfigurationSettingsFilter`와 `begin_create_snapshot(name=..., filters=...)`를 제시한다. 해당 부분을 복사하지 말고 설치 버전 API를 확인해야 한다. [공식 SDK 설명 및 snapshot 예제](https://learn.microsoft.com/en-us/python/api/overview/azure/appconfiguration-readme?view=azure-python)

## 2. azure-keyvault-py

**비밀·암호화 키·인증서를 구분하고, 필요한 메타데이터만 읽는 작업을 설계하는 Skill.**

- 조직 / 라이선스: Microsoft / MIT
- 대상 패키지: `azure-keyvault-secrets`, `azure-keyvault-keys`, `azure-keyvault-certificates`
- 태그: `secrets` `key-management` `certificates` `least-privilege`
- 난이도: 중급
- 원문: [SKILL.md](https://github.com/microsoft/skills/blob/2130750147dee0311215099ddf36647ba1e0f006/.github/plugins/azure-sdk-python/skills/azure-keyvault-py/SKILL.md)

### 무엇을 해주나

SecretClient, KeyClient, CertificateClient의 역할과 비밀 버전, 키 연산, 인증서 관리 흐름을 안내한다. 에이전트가 “비밀이 만료됐는지 점검”하는 일을 “비밀 원문을 읽고 출력”하는 일과 혼동하지 않도록 작업을 쪼개는 데 유용하다. 어제 소개한 인증 체인과는 달리, 인증 뒤 접근하는 보안 객체의 종류·버전·수명주기가 핵심이다.

### 실전 프롬프트

> azure-keyvault-py를 참고해 비밀정보 접근 코드의 점검 계획을 작성해 줘. 우선 저장소 코드만 읽고 get_secret 결과를 로그·예외·테스트 fixture로 흘리는 경로를 찾아 줘. 원격 점검이 필요하면 비밀 값을 가져오지 않는 속성 목록 조회와 권한을 별도로 제안해. 비밀 생성·교체·삭제·복구·purge 및 private key 추출은 하지 마.

### 설치·주의

비밀 관리만 필요하면 `azure-keyvault-secrets azure-identity`부터 검토하고 키·인증서 패키지를 불필요하게 함께 쓰지 않는다. 원문에 있는 `print(secret.value)`와 인증서 private key를 secret으로 읽는 예시는 보안 점검 프롬프트에서 제외해야 한다.

공식 문서상 `list_properties_of_secrets`는 비밀 값을 반환하지 않는다. 다만 이름·태그도 업무정보일 수 있어 출력 범위를 제한한다. 상세 HTTP DEBUG logging은 본문이나 마스킹되지 않은 헤더를 노출할 수 있다. 삭제와 영구 삭제는 단순 조회가 아니며, 복구 가능성을 가정하지 말아야 한다. [공식 Secrets SDK 문서](https://learn.microsoft.com/en-us/python/api/overview/azure/keyvault-secrets-readme?view=azure-python)

## 3. azure-monitor-opentelemetry-py

**에이전트 API의 trace·metric·log를 계측하되, 전송 전 데이터 경계를 검토하는 Skill.**

- 조직 / 라이선스: Microsoft / MIT
- 대상 패키지: `azure-monitor-opentelemetry`
- 태그: `opentelemetry` `tracing` `application-insights` `data-minimization`
- 난이도: 중상급
- 원문: [SKILL.md](https://github.com/microsoft/skills/blob/2130750147dee0311215099ddf36647ba1e0f006/.github/plugins/azure-sdk-python/skills/azure-monitor-opentelemetry-py/SKILL.md)

### 무엇을 해주나

`configure_azure_monitor`, 사용자 정의 span·counter·logging, sampling, service name, 종료 시 flush/shutdown을 안내한다. 도구 호출 실패나 요청 지연을 관측할 때 어디에 계측 지점을 둘지 설계하는 참고 자료다. 단순 로그 출력이 아니라 Azure Monitor로 데이터가 전송되는 흐름이라는 점이 중요하다.

### 실전 프롬프트

> azure-monitor-opentelemetry-py를 참고해 FastAPI 에이전트 서비스의 계측 변경안을 작성해 줘. 프롬프트 원문·사용자 입력·Authorization 헤더·도구 결과는 수집하지 않는 설계로 해. 필요한 span 이름과 집계 지표만 정의하고, SDK 버전별 옵션·sampling·종료 처리를 비교해. 실제 exporter를 시작하거나 Application Insights로 데이터를 전송하지 말고 로컬 mock 테스트 초안만 만들어.

### 설치·주의

`pip install azure-monitor-opentelemetry`는 SDK 설치 예시이며 이번 조사에서는 실행하지 않았다. 계측 초기화는 외부 전송을 시작할 수 있으므로 단순 읽기 전용 검토로 취급하지 않는다.

**원문 수정 필요:** 확인한 공식 문서 1.8.11은 선택적 계측에 `instrumentation_options` 사전을 사용한다. Skill의 `instrumentations=[...]` 예제를 그대로 채택하지 않는다. 문서는 Live Metrics 기본값을 **True**로 표기하지만 Skill 표는 False다. 원치 않는 전송을 피하려면 설치 버전에서 옵션을 명시적으로 확인해야 한다. 지원 계측 목록도 Skill의 긴 목록 전체와 동일하다고 가정하지 않는다. [공식 Distro 설정·지원 목록](https://learn.microsoft.com/en-us/python/api/overview/azure/monitor-opentelemetry-readme?view=azure-python)

## 4. azure-monitor-query-py

**운영 로그를 제한된 시간 범위로 조회하고, 불완전한 결과를 성공으로 오인하지 않게 하는 Skill.**

- 조직 / 라이선스: Microsoft / MIT
- 대상 패키지: `azure-monitor-query` (로그 조회 중심으로 활용)
- 태그: `log-analytics` `kql` `partial-results` `incident-analysis`
- 난이도: 중급
- 원문: [SKILL.md](https://github.com/microsoft/skills/blob/2130750147dee0311215099ddf36647ba1e0f006/.github/plugins/azure-sdk-python/skills/azure-monitor-query-py/SKILL.md)

### 무엇을 해주나

LogsQueryClient, workspace 조회, 시간 범위, batch 처리와 표 형태 결과를 다룬다. 과거의 `azure-kusto`가 KQL 분석 관점이라면 오늘의 활용은 Python 호출 코드에서 응답 종류·오류·부분 결과를 분기하는 작업이다. 에이전트가 일부 로그만 받은 상태로 “장애 없음”이라고 요약하는 실수를 방지하는 데 초점을 둔다.

### 실전 프롬프트

> azure-monitor-query-py를 참고하되 현재 설치된 SDK 문서를 우선해 로그 조회 모듈을 검토해 줘. 최근 1시간의 집계 쿼리만 대상으로 하고 원시 사용자 입력은 반환하지 않게 해. 성공·부분 결과·batch 오류·HTTP 실패를 구분하고, 누락 가능성이 있으면 분석 결론에 표시하도록 mock 테스트를 작성해. 실제 원격 쿼리와 권한 변경은 하지 마.

### 설치·주의

**중요한 버전 차이:** 공식 SDK 2.0.0에서는 `MetricsQueryClient`와 `MetricsClient`가 `azure-monitor-query`에서 제거되었다. 원문의 metrics import는 최신 버전에 그대로 적용되지 않는다. metrics가 필요하면 별도 `azure-monitor-querymetrics` 또는 `azure-mgmt-monitor` 문서를 검토한다.

또한 공식 응답 구조는 정상 결과의 `tables`와 부분 결과의 `partial_data`를 구분하며 batch에는 오류 객체도 올 수 있다. 원문의 모든 응답에 `response.tables`가 있다고 가정하는 예시는 보완한다. DataFrame 열도 공식 예제는 `columns=table.columns`를 사용한다. 로그 조회는 데이터를 변경하지 않더라도 민감정보 접근·쿼리 비용·throttling을 고려해야 한다. [공식 SDK 2.0.0 및 응답 처리](https://learn.microsoft.com/en-us/python/api/overview/azure/monitor-query-readme?view=azure-python)

## 5. azure-containerregistry-py

**컨테이너 태그보다 실제 digest를 기준으로 배포 대상을 점검하는 Skill.**

- 조직 / 라이선스: Microsoft / MIT
- 대상 패키지: `azure-containerregistry`
- 태그: `acr` `oci` `container-images` `deployment-audit`
- 난이도: 중급
- 원문: [SKILL.md](https://github.com/microsoft/skills/blob/2130750147dee0311215099ddf36647ba1e0f006/.github/plugins/azure-sdk-python/skills/azure-containerregistry-py/SKILL.md)

### 무엇을 해주나

repository·tag·manifest 메타데이터를 조회하고 digest, OS·architecture, 삭제·쓰기 허용 속성을 확인하는 작업을 안내한다. 에이전트 서비스 이미지가 “latest”라는 이름만 같은지, 실제 내용 식별자인 digest까지 일치하는지 점검하는 데 유용하다. 이전의 Dockerfile 작성이나 Blob 저장소 작업과는 대상·검증 단위가 다르다.

### 실전 프롬프트

> azure-containerregistry-py를 참고해 배포 명세와 승인된 이미지 목록을 비교하는 읽기 전용 감사 도구를 설계해 줘. repository·tag·digest·architecture만 결과로 남기고, 같은 digest를 가리키는 여러 tag를 함께 표시해. 오래됐거나 tag가 없다는 이유만으로 삭제하지 마. upload·delete·잠금 변경·이미지 실행 없이 mock 응답으로 검증해.

### 설치·주의

`pip install azure-containerregistry`를 검토하되 설치 버전 API에 맞춘다. 원문의 `download_manifest` 예시와 달리 확인한 공식 SDK 문서의 manifest 조회 예시는 `get_manifest`를 사용한다. write/delete 속성 설정도 문서의 실제 호출 인자를 확인해야 한다.

manifest는 digest로 식별되고 하나에 여러 tag가 연결될 수 있다. tag 제거와 manifest 삭제를 같은 작업으로 보지 않는다. 원문의 오래된 untagged 이미지 정리 예시는 실제 삭제 코드이므로, 배포에서 digest로 참조하는지 별도 확인 없이 실행하지 않는다. digest 일치는 내용 식별일 뿐 이미지의 안전성·서명 신뢰를 보증하지 않는다. [공식 Container Registry SDK 개념·예제](https://learn.microsoft.com/en-us/python/api/overview/azure/containerregistry-readme?view=azure-python)

- **Top Pick: azure-keyvault-py의 비밀 원문 출력 경로 점검.** 원문 자체에 값 출력 예시가 있어, 개발 편의 코드가 운영 로그로 넘어가지 않도록 검토할 실익이 분명하다. 첫 작업은 클라우드 접속 없이 코드 검색·테스트 검토로 제한한다.
- **Codex 활용 후보: azure-containerregistry-py의 배포 명세 검토.** 저장소 안의 이미지 참조가 tag인지 digest인지 목록화하는 작업부터 시작할 수 있다. 실제 레지스트리 접근은 승인된 범위와 기존 권한이 확인된 뒤 별도 단계로 둔다.
- Monitor 두 Skill은 활용 가능하지만 **SDK 불일치 수정이 선행 조건**이다. 복사해서 즉시 실행할 준비가 된 템플릿으로 추천하지 않는다.
