## 1. redis-core

**객체 모양보다 읽기·쓰기 패턴을 먼저 정하는 데이터 모델링 지침.**

- 출처: [SKILL.md](https://github.com/redis/agent-skills/blob/a84871d065f398fed55e1633f66b66f731eb4e2b/skills/redis-core/SKILL.md)
- 태그: `data-modeling` `key-design` `cache` `redis`
- 난이도: 초중급

### 무엇을 해주나

카운터, 일부 필드만 수정하는 객체, 순위, 중복 없는 집합, 중첩 문서, 이벤트 기록처럼 서로 다른 요구를 String·Hash·Sorted Set·Set·JSON·Stream에 연결한다. 모든 객체를 직렬화한 문자열 하나에 넣기보다 갱신 단위를 고려하게 한다. 키는 일관된 계층과 짧은 식별자로 설계하도록 안내한다.

실무 적용은 캐시 키 사전과 데이터 수명 표를 만드는 데서 시작하기 좋다. 세션·작업 상태·조회 캐시가 같은 만료 정책을 갖는다고 가정하지 말고, 원본 데이터 위치와 캐시 미스 때의 행동을 별도로 적는다. **키 접두사는 이름 규칙일 뿐 접근 제어의 대체물이 아니다.** 테넌트 격리는 실제 권한·조회 경로·테스트로 검증해야 한다.

### 실전 프롬프트

> redis-core를 참고해 가상의 문서 처리 서비스에 사용할 조회 캐시, 진행 상태, 작업 이벤트를 설계해 줘. 읽기·쓰기 패턴별 자료형과 키 예시, 만료 여부, 원본 저장소, 캐시 미스 처리를 표로 만들어. 모든 값을 JSON 문자열로 통일하지 말고 장단점을 적어. 실제 서버 접속·키 생성·기존 키 이름 변경은 하지 마.

### 설치·주의

README는 TTL 등 넓은 주제를 소개하지만 현재 이 SKILL.md의 중심은 자료형 선택과 키 이름이다. 이 문서 하나가 영속성·만료·복구 설계 전체를 검증해 준다고 과장하지 않는다. JSON·Vector Set·검색 기능은 대상 배포의 버전과 제공 기능을 확인해야 한다. 예제의 자료형 이름만 보고 기존 Redis 인스턴스에 모두 있다고 가정하지 않는다.

## 2. redis-connections

**요청마다 연결하는 코드와 잘못된 배치·재시도를 찾아내는 클라이언트 검토 지침.**

- 출처: [SKILL.md](https://github.com/redis/agent-skills/blob/a84871d065f398fed55e1633f66b66f731eb4e2b/skills/redis-connections/SKILL.md)
- 태그: `connection-pool` `pipelining` `timeouts` `latency`
- 난이도: 중급

### 무엇을 해주나

연결 풀 또는 멀티플렉싱 재사용, 독립 명령의 배치, 큰 자료구조 조회, 클라이언트 캐시, 시간 초과를 검토한다. 처리량 저하가 곧 서버 CPU 부족이라는 결론으로 이어지지 않도록 클라이언트 수명과 왕복 횟수부터 살펴보게 한다.

원문 예제의 `redis`가 모듈인지 클라이언트 인스턴스인지 일관되지 않은 부분은 그대로 복사하지 않는다. 특히 redis-py의 `r.pipeline()`은 **기본적으로 트랜잭션**이며, 비트랜잭션 배치를 원하면 `r.pipeline(transaction=False)`를 명시해야 한다. 원문의 “성능용 비트랜잭션” 설명과 코드 기본값을 구분한다. [공식 redis-py 문서](https://redis.io/docs/latest/develop/clients/redis-py/transpipe/)

### 실전 프롬프트

> redis-connections로 제공한 테스트 클라이언트 코드를 검토해 줘. 연결 생성 위치, 요청마다 재연결 여부, 독립 GET 배치 가능성, 블로킹 소비자의 연결 분리, 시간 초과와 재시도 정책을 정리해. 재시도가 쓰기를 중복 실행할 수 있는 경우는 별도 표시하고 실제 서버·환경 변수·배포 설정은 변경하지 마.

### 설치·주의

원문의 연결 풀 설명을 모든 클라이언트에 동일하게 적용하면 안 된다. 풀 소진 때 대기하는지 예외를 내는지는 클라이언트·풀 클래스·옵션에 따라 확인한다. 시간 초과가 “서버에서 실행되지 않았다”는 증거도 아니므로 비멱등 쓰기의 재시도에는 별도 설계가 필요하다.

큰 키 공간에는 SCAN 계열을 검토하되 COUNT를 정확한 페이지 크기나 최대 반환 개수로 가정하지 않는다. 빈 결과에도 커서가 남을 수 있으며, 조회 중 데이터 변경을 하나의 원자적 스냅샷으로 표현하지 않는다. 전체 순회 비용이 사라지는 것도 아니다. [공식 SCAN](https://redis.io/docs/latest/commands/scan/)

## 3. redis-search

**정확 일치·전문 검색·벡터 검색을 구분하고 RAG 검색 조건을 설계하는 스킬.**

- 출처: [SKILL.md](https://github.com/redis/agent-skills/blob/a84871d065f398fed55e1633f66b66f731eb4e2b/skills/redis-search/SKILL.md)
- 태그: `rag` `vector-search` `hybrid-search` `schema`
- 난이도: 중상급

### 무엇을 해주나

TEXT·TAG·NUMERIC·VECTOR 등 필드의 의미를 먼저 정하고, 문서 검색·집계·어휘와 벡터 순위 결합을 다른 명령으로 구분한다. 임베딩 차원·저장 타입·거리 기준과 조회 필터를 일치시키는 검토에 유용하다. 검색 인덱스 별칭을 활용한 변경 절차도 설명하지만, 실제 무중단 전환을 보장하는 검증 결과는 아니다.

특히 **속성 필터를 포함한 벡터 검색**과 **텍스트·벡터 순위 융합**을 같은 “하이브리드”라는 말로 뭉뚱그리지 않는다. 공식 Redis 8.4 문서는 FT.HYBRID의 RRF·선형 결합을 설명한다. 오래된 서버에 해당 명령이 있다고 가정하지 말고 배포 종류와 기능 버전을 확인한다. [Redis 8.4 공식 변경 사항](https://redis.io/docs/latest/develop/whats-new/8-4/)

### 실전 프롬프트

> redis-search로 가짜 문서 20개를 검색하는 RAG 설계안을 만들어 줘. tenant_id와 문서 상태는 정확 일치 필터, 본문은 전문 검색으로 나눠. 사용할 임베딩의 차원·타입·거리 기준은 확인 전까지 TBD로 두고, 어휘 검색·벡터 검색·융합 검색의 평가 쿼리를 각각 제안해. 실제 인덱스 생성·별칭 교체·문서 업로드는 하지 마.

### 설치·주의

원문의 TAG “10배”, HNSW “95%+ recall”, 문서 1만 개 기준 같은 수치는 이번 워크로드에서 검증되지 않았다. 보편적 성능 보장이나 알고리즘 선택의 절대 경계로 인용하지 않는다. 차원 불일치 처리도 실제 서버·클라이언트의 오류를 확인해야 하며 “항상 조용히 잘못된 값이 나온다”고 단정하지 않는다.

필터 조건이 있다고 자동으로 권한이 안전해지는 것은 아니다. 서버 측에서 허용된 테넌트 범위를 강제하는 경로와 누락 필터 테스트가 필요하다. 스키마 변경은 새 인덱스의 건수·결과·오류를 검증하고 롤백 계획을 세운 뒤 별도 승인 범위에서 수행한다.

## 4. redis-observability

**지표를 원인 가설로 연결하되 진단 명령과 상태 변경을 섞지 않는 관측 지침.**

- 출처: [SKILL.md](https://github.com/redis/agent-skills/blob/a84871d065f398fed55e1633f66b66f731eb4e2b/skills/redis-observability/SKILL.md)
- 태그: `observability` `incident-triage` `memory` `slowlog`
- 난이도: 중급

### 무엇을 해주나

메모리·연결 수·적중과 미스·처리량·연결 거절·영속화 상태를 살피고 INFO·SLOWLOG·MEMORY·검색 프로파일 명령으로 조사 범위를 좁힌다. 한 숫자만 보고 증설하는 대신, 같은 시간 구간의 지표와 애플리케이션 증상을 연결하는 체크리스트로 쓸 수 있다.

다만 원문의 “blocked_clients가 계속 0보다 크면 경고”, “적중률 80% 미만”, “메모리 80% 초과”는 모든 서비스에 맞는 기준이 아니다. 정상적인 블로킹 큐 소비자, maxmemory 설정 여부, 업무별 캐시 특성과 SLO를 고려해야 한다. 누적 카운터의 전체 비율과 최근 구간의 변화율도 구분한다.

### 실전 프롬프트

> redis-observability로 제공한 익명화 INFO·SLOWLOG fixture를 분석해 줘. 사실, 가설, 추가로 필요한 관측을 구분하고 연결 급증과 메모리 증가의 시간 순서를 비교해. 정상 큐 소비자의 blocked_clients를 장애로 단정하지 마. 설정 변경, 연결 종료, 로그 초기화, 서비스 재시작은 하지 마.

### 설치·주의

원문 명령 표에는 **SLOWLOG RESET**도 포함돼 있다. 이는 읽기 진단이 아니라 기록을 지우는 작업이므로 단순 조사에서 실행하지 않는다. 상세 명령 로그·CLIENT LIST에는 값·키·접속 정보가 섞일 수 있어 외부 공유 전에 범위를 줄이고 민감 값을 제거한다. [공식 SLOWLOG 명령군](https://redis.io/docs/latest/commands/slowlog/)

FT.PROFILE 같은 진단도 무부하 조회라고 보장할 수 없다. 필요한 쿼리·범위만 제한하고 운영 환경의 부하·접근 권한을 먼저 확인한다. Redis Insight 설치나 서버 연결까지 이 스킬을 읽었다는 이유만으로 승인된 것은 아니다.

## 5. redis-semantic-cache

**비슷한 질문에 과거 답을 재사용해도 되는지를 평가하는 LLM 캐시 설계 지침.**

- 출처: [SKILL.md](https://github.com/redis/agent-skills/blob/a84871d065f398fed55e1633f66b66f731eb4e2b/skills/redis-semantic-cache/SKILL.md) · [상세 사용 원문](https://github.com/redis/agent-skills/blob/a84871d065f398fed55e1633f66b66f731eb4e2b/skills/redis-semantic-cache/references/langcache-usage.md)
- 태그: `llm-cache` `semantic-similarity` `cost-control` `evaluation`
- 난이도: 중상급

### 무엇을 해주나

LLM 호출 전에 LangCache를 검색하고, 미스일 때 모델을 호출한 뒤 결과를 저장하는 cache-aside 흐름을 설명한다. 작업 종류별 캐시 분리와 속성 필터, 유사도 임계값을 조정해 적중률과 잘못된 재사용을 함께 평가한다.

현행 공식 문서는 Redis Cloud의 public preview와 self-managed private preview 등을 구분한다. 일반 Redis 설치만으로 같은 관리형 기능을 즉시 쓸 수 있다고 가정하지 않는다. 최신 문서의 경로는 원문의 옛 링크에서 **context-engine/langcache**로 옮겨졌다. [현재 LangCache 문서](https://redis.io/docs/latest/develop/ai/context-engine/langcache/)

### 실전 프롬프트

> redis-semantic-cache로 가짜 FAQ 응답 캐시의 평가 계획을 만들어 줘. 같은 뜻의 질문과 비슷하지만 답이 다른 질문을 나누고, 테넌트·문서 버전·언어가 다르면 재사용하지 않는 테스트를 포함해. 시간 민감한 답과 사용자별 답은 우선 캐시 대상에서 제외해. 실제 프롬프트 전송, API 키 발급, 유료 서비스 생성이나 저장·삭제는 하지 마.

### 설치·주의

원문의 0.9·0.95 임계값은 검증된 정답 기준이 아니다. 유사도가 높아도 문서 버전·사용자 권한·시점이 다르면 틀린 답일 수 있다. 평가 데이터에서 잘못된 적중을 측정하고, TTL·무효화·격리 정책을 정한다. 실제 절감액은 캐시·임베딩·저장 비용과 오답 비용을 함께 고려해야 한다.

공식 API 예제는 Python의 search/set과 JavaScript SDK를 제공한다. 그러나 이번에는 SDK를 설치하지 않았고 응답 객체 형태나 원문의 result[0] 접근을 런타임 검증하지 않았다. 버전을 고정하고 응답 스키마를 확인한 뒤 오류·미스·부분 결과를 구분한다. **속성 없는 delete_query는 전체 응답 삭제가 될 수 있고 되돌릴 수 없다는 경고**가 있으므로 조회·저장 예제와 삭제를 묶어 실행하지 않는다. [공식 API·SDK 예제](https://redis.io/docs/latest/develop/ai/context-engine/langcache/api-examples/)

## 공통 도입 방법

```bash
npx skills add redis/agent-skills
```

원본은 top-level skills/이고 plugins/redis-development/skills/는 배포용 복사본이다. 필요 항목의 SKILL.md와 references를 함께 검토한다. 설치 명령은 현재 배포를 가져오므로 이 보고서의 고정 커밋과 자동으로 같은 버전이 되는 것은 아니다. 설치 대상 에이전트·프로젝트 범위·원하는 버전을 먼저 확인한다. [공식 설치·구조 설명](https://github.com/redis/agent-skills/blob/a84871d065f398fed55e1633f66b66f731eb4e2b/README.md)

호스트가 스킬을 인식하는 것과 Redis 클라이언트·서버·검색 기능·LangCache 접근을 확보하는 것은 별도다. 자격증명을 코드·보고서·로그에 넣지 않고, 인증 설정이나 접근 범위 확대는 필요한 승인을 거친다. 이번 조사는 원본 Skill을 실행하거나 원문에 있는 운영 명령을 수행할 권한을 의미하지 않는다.
