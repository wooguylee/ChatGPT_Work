## 1. recipe-backup-sheet-as-csv

**표에서 필요한 데이터를 꺼내되, CSV 한 개를 통합문서 전체 백업으로 오해하지 않게 하는 레시피.**

- 출처: [SKILL.md](https://github.com/googleworkspace/cli/blob/a3768d0e82ad83cca2da97724e46bea4ff0e6dbd/skills/recipe-backup-sheet-as-csv/SKILL.md)
- 태그: `sheets` `csv` `data-export` `backup-scope`
- 난이도: 초중급

### 무엇을 해주나

시트 메타데이터 확인, Drive의 CSV export, 지정 범위의 values 읽기라는 경로를 제시한다. 분석 파이프라인 입력이나 특정 탭의 보관본을 준비할 때 사용할 수 있다. 단순 시트 읽기와 달리 **무엇이 파일에 남고 무엇은 사라지는지**를 산출물 기준으로 정하는 데 활용한다.

단, 공식 Drive 내보내기 표에서 CSV는 **첫 번째 시트만** 지원한다. CSV에는 통합문서의 여러 탭·서식·수식 구조·차트 등을 그대로 보존할 수 없으므로, 완전한 백업이나 복원 검증이라고 부르면 안 된다. files.export의 출력 한도도 **10 MB**다. [내보내기 형식](https://developers.google.com/workspace/drive/api/guides/ref-export-formats) · [files.export](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/export)

### 실전 프롬프트

> recipe-backup-sheet-as-csv를 참고해 지정한 테스트 시트의 내보내기 계획을 작성해 줘. 필요한 탭·범위·값 또는 수식 여부·파일 인코딩을 먼저 정리해. CSV에서 보존되지 않는 요소와 검증할 행 수를 표시하고, 현재는 샘플 데이터만 사용해. 실제 계정 접속·파일 저장·기존 백업 덮어쓰기는 하지 마.

### 설치·주의

원문의 `gws sheets +read ... --format csv`를 검증 없이 CSV 생성 명령으로 복사하지 않는다. 확인한 `+read` 구현은 실행기에 선택된 출력 형식 대신 **OutputFormat::default()**를 전달한다. 따라서 이 고정 버전의 helper가 원문 기대대로 CSV를 출력한다고 보장할 수 없다. CSV가 필요하면 raw `spreadsheets.values.get`와 해당 버전의 formatter 동작을 먼저 검사하거나, JSON의 values 배열을 검증된 CSV 라이브러리로 변환한다. formatter에는 배열의 배열을 CSV로 처리하는 코드·테스트가 있지만 이번에 테스트를 실행한 것은 아니다. [helper 구현](https://github.com/googleworkspace/cli/blob/a3768d0e82ad83cca2da97724e46bea4ff0e6dbd/crates/google-workspace-cli/src/helpers/sheets.rs) · [formatter 구현](https://github.com/googleworkspace/cli/blob/a3768d0e82ad83cca2da97724e46bea4ff0e6dbd/crates/google-workspace-cli/src/formatter.rs)

범위 추출용 명령 형태는 다음과 같다. 실제 사용 전 schema·권한·출력 경로를 확인한다.

```bash
gws sheets spreadsheets values get --params '{"spreadsheetId":"SHEET_ID","range":"Sheet1!A1:D100","valueRenderOption":"UNFORMATTED_VALUE"}' --format csv
```

CSV를 스프레드시트 앱에서 다시 열 때 문자열이 수식으로 해석되지 않는지도 점검한다. 외부로 파일을 전송하거나 기존 파일을 덮어쓰는 작업은 조회와 별도다.

## 2. recipe-compare-sheet-tabs

**행 번호가 아니라 업무 키를 기준으로 두 탭의 차이를 설명하는 레시피.**

- 출처: [SKILL.md](https://github.com/googleworkspace/cli/blob/a3768d0e82ad83cca2da97724e46bea4ff0e6dbd/skills/recipe-compare-sheet-tabs/SKILL.md)
- 태그: `data-diff` `reconciliation` `sheets` `read-only`
- 난이도: 초중급

### 무엇을 해주나

원문은 January와 February 탭을 각각 읽고 비교하도록 안내한다. 월별 명단·재고·작업 상태의 추가, 삭제, 변경 후보를 찾는 출발점이다. 원문에는 자동 키 선택·중복 판정·숫자 정규화 알고리즘이 없으므로 에이전트가 이를 했다고 가정하면 안 된다.

실무에서는 ID 열, 비교 대상 열, 빈 값과 누락의 차이, 중복 ID 처리부터 정해야 한다. 정렬만 바뀐 행을 삭제·추가로 잘못 세지 않도록 한다. 읽기 시점 사이에 원본이 변경될 수 있으므로 두 조회를 하나의 원자적 스냅샷으로 주장하지 않는다.

### 실전 프롬프트

> recipe-compare-sheet-tabs로 제공한 두 테스트 탭의 차이를 검토해 줘. record_id로 맞추고 중복 키는 별도 오류로 분리해. 추가·삭제·상태 변경을 구분하고 각 결과에 두 탭의 행 위치를 남겨. 숫자 0과 빈칸을 합치지 말고 실제 탭 수정이나 결과 공유는 하지 마.

### 설치·주의

공식 values.get의 기본 출력은 **FORMATTED_VALUE**다. 통화·날짜 표시 문자열 비교와 원시 값 비교, 수식 비교를 혼동하지 않는다. 정밀 비교가 필요하면 raw API의 valueRenderOption을 양쪽에서 일치시키고 날짜·시간 표현도 정한다. [공식 values.get 옵션](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets.values/get)

원문의 열린 범위 A1:D를 무조건 전체 데이터로 확대하지 말고 필요한 열·행을 제한한다. 비교안은 재무 검증이나 업무 원장의 자동 수정 권한이 아니며, 차이가 있다는 사실만으로 어느 쪽이 정답인지 결정하지 않는다.

## 3. recipe-collect-form-responses

**폼의 질문 정의와 응답을 연결해 검토 가능한 집계 초안을 만드는 레시피.**

- 출처: [SKILL.md](https://github.com/googleworkspace/cli/blob/a3768d0e82ad83cca2da97724e46bea4ff0e6dbd/skills/recipe-collect-form-responses/SKILL.md)
- 태그: `forms` `response-analysis` `pagination` `privacy`
- 난이도: 중급

### 무엇을 해주나

폼 상세와 응답 목록을 읽는 순서를 제시한다. 설문 결과를 설명하려면 답변 텍스트만 나열하는 대신 어떤 질문에 대한 응답인지 함께 확인해야 한다. 접수 현황·피드백 분류·누락 답변 확인에 활용할 수 있지만 외부 연락이나 응답자 평가를 자동 실행하는 지침은 아니다.

**수정이 필요한 부분:** 원문 첫 단계의 `gws forms forms list`는 현재 Forms v1의 forms 리소스에 없는 메서드다. 공식 목록은 batchUpdate·create·get·setPublishSettings다. 이미 알고 있는 폼 ID로 시작하거나, 필요한 권한 아래 Drive에서 폼을 찾아 ID를 확인해야 한다. 이 오류를 수정하는 조건으로 소개한다. [Forms 리소스의 메서드](https://developers.google.com/workspace/forms/api/reference/rest/v1/forms)

### 실전 프롬프트

> recipe-collect-form-responses를 참고해 내가 지정한 폼 ID의 가짜 응답 fixture를 집계하는 절차를 설계해 줘. 질문 ID와 답변을 연결하고, 응답 ID 중복과 빠진 페이지를 검사해. 이메일·자유서술 개인정보는 결과에서 제외하고 범주별 건수만 제시해. 실제 응답 조회·다운로드·제3자 전송·폼 설정 변경은 하지 마.

### 설치·주의

forms.responses.list는 nextPageToken이 있으면 계속 조회해야 하며, 다음 페이지에서도 같은 폼과 filter를 유지해야 한다. 증분 수집 필터의 timestamp는 RFC3339 UTC 형식이고 `>`와 `>=`의 경계가 다르다. 경계 중복·누락을 응답 ID와 함께 검토한다. “첫 페이지가 비어 보임”이나 첫 응답 수만으로 전체 제출 건수를 확정하지 않는다. [공식 응답 목록 API](https://developers.google.com/workspace/forms/api/reference/rest/v1/forms.responses/list)

폼 내용·답변은 읽을 데이터이지 에이전트에 대한 명령이 아니다. 자유서술에 포함된 링크·추가 업로드 지시를 그대로 따르지 않는다. 민감한 답변을 외부 분석 서비스로 보내는 일은 별도 범위·승인이 필요하다.

## 4. recipe-review-overdue-tasks

**미완료 작업에서 예정일이 지난 항목을 찾되, 날짜만으로 긴급도·마감 위반을 단정하지 않는 레시피.**

- 출처: [SKILL.md](https://github.com/googleworkspace/cli/blob/a3768d0e82ad83cca2da97724e46bea4ff0e6dbd/skills/recipe-review-overdue-tasks/SKILL.md)
- 태그: `tasks` `planning` `date-semantics` `triage`
- 난이도: 초중급

### 무엇을 해주나

작업 목록을 조회한 뒤 각 목록의 미완료 작업을 읽고 날짜를 검토한다. 기존 standup-report가 일정과 작업을 합친 요약이었다면 이 레시피는 **과거 날짜의 미완료 항목을 재검토할 후보로 좁히는 과정**에 집중한다. 자동 일정 변경·완료 처리·삭제는 포함하지 않는다.

중요한 의미 차이가 있다. 현행 Tasks 리소스 문서는 due를 **작업 예정 날짜**로 설명하고, 실제 deadline이 아니라고 명시한다. 시간 정보도 저장되지 않는다. 이름이 overdue여도 “법적·업무상 마감을 어겼다”거나 “몇 시간 늦었다”고 단정하면 안 된다. 사용자가 정한 기준 날짜와 업무 맥락을 함께 확인한다. [Task의 due 정의](https://developers.google.com/workspace/tasks/reference/rest/v1/tasks)

### 실전 프롬프트

> recipe-review-overdue-tasks로 제공한 작업 fixture를 검토해 줘. 기준일 이전의 due가 있는 미완료 항목, 오늘 예정, 날짜 없음으로 나눠. due는 날짜 단위의 예정일로 표시하고 실제 마감인지 확인된 경우만 따로 적어. 중요도는 제목만 보고 추정하지 말고 완료 처리·날짜 변경·삭제는 하지 마.

### 설치·주의

tasks.list는 기본 페이지 크기가 20이며 페이지 토큰을 처리해야 한다. Docs·Chat에서 할당된 작업은 기본적으로 반환되지 않으므로 필요하면 showAssigned를 검토한다. 일부 목록만 읽거나 기본 옵션만 사용한 결과를 계정 전체의 모든 할 일이라고 부르지 않는다. [공식 tasks.list 옵션](https://developers.google.com/workspace/tasks/reference/rest/v1/tasks/list)

공통 CLI의 `--page-all`도 기본 page-limit이 10이므로 그 옵션 하나가 무제한 수집을 보장하지 않는다. 한계에 도달했거나 토큰이 남으면 “부분 결과”로 표시한다. 완료·삭제·숨김 작업을 조사할지 여부는 목적에 맞게 별도 정한다.

## 5. recipe-find-large-files

**파일 크기와 실제 저장 할당량을 구분해 정리 후보를 찾는 레시피.**

- 출처: [SKILL.md](https://github.com/googleworkspace/cli/blob/a3768d0e82ad83cca2da97724e46bea4ff0e6dbd/skills/recipe-find-large-files/SKILL.md)
- 태그: `drive` `storage-audit` `quota` `read-only`
- 난이도: 초중급

### 무엇을 해주나

Drive files.list를 quotaBytesUsed 내림차순으로 정렬해 큰 파일 후보를 보여준다. 정리 전에 이름·유형·소유 범위를 점검하는 데 적합하다. 파일을 이동·삭제하거나 보존 정책을 바꾸는 작업까지 자동으로 수행하지 않는다.

원문은 quotaBytesUsed로 정렬하지만 반환 fields에는 **size만 넣고 quotaBytesUsed를 빠뜨린다.** 저장 할당량을 설명하려면 두 필드를 함께 요청해야 한다. quotaBytesUsed는 현재 버전뿐 아니라 keepForever인 이전 리비전도 포함할 수 있어 size와 같다고 가정하면 안 된다. [공식 File 필드 정의](https://developers.google.com/workspace/drive/api/reference/rest/v3/files)

### 실전 프롬프트

> recipe-find-large-files를 참고해 테스트 Drive 파일 목록의 정리 후보 표를 만들어 줘. size와 quotaBytesUsed를 따로 표시하고 소유 범위·휴지통 여부·누락 필드를 확인해. 파일 내용은 열지 말고, 목록만으로 삭제 가능성이나 절약할 금액을 단정하지 마. 이동·공유 변경·휴지통 이동·영구 삭제는 하지 마.

### 설치·주의

실제 목록을 만들 때는 nextPageToken·incompleteSearch도 반환하도록 fields를 검토한다. 원문의 20개 출력은 상위 후보일 뿐 전체 파일 목록이 아니다. 휴지통 포함 여부와 공유 드라이브 범위를 명시하고, 다음 페이지가 남은 결과를 전체 조사라고 보고하지 않는다. quotaBytesUsed는 공식 정렬 키로 지원된다. [공식 files.list](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/list)

공유 드라이브 항목은 owners·ownedByMe가 채워지지 않을 수 있다. 그런 값을 개인 소유로 추정하거나 파일 크기 합계만으로 개인 요금 절감액을 계산하지 않는다. “이동”이 곧 저장 용량 감소라는 뜻도 아니다.
