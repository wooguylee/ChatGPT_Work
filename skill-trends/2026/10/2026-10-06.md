## 1. huggingface-community-evals

- **출처/제작자:** [Hugging Face 공식 Skills](https://github.com/huggingface/skills), [skills.sh 항목](https://www.skills.sh/huggingface/skills/huggingface-community-evals)
- **원 Skill:** [huggingface-community-evals/SKILL.md](https://github.com/huggingface/skills/blob/main/skills/huggingface-community-evals/SKILL.md)
- **지원 Agent:** 공식 모음은 Claude Code·Codex·Gemini CLI·Cursor를 명시한다. 실제 평가는 Python/CLI 실행 환경이 필요하다.
- **태그:** `#모델평가` `#InspectAI` `#LightEval` `#스모크테스트`
- **도입 난이도:** 중간~높음. GPU·모델 접근 권한·평가 설정을 함께 확인한다.

### 인기 및 트렌드 지표

- skills.sh: **installs 1.7K**, First Seen **2026-03-23**
- 감사 표시: **Gen Agent Trust Hub Pass / Socket Pass / Snyk Warn**
- Hugging Face Skills 모음 전체: **11,138 stars / 759 forks**
- First Seen은 디렉터리 관측일이며 출시일은 아니다.

### 내용

Hub 모델을 평가할 때 `inspect-ai`와 `lighteval` 중 작업에 맞는 framework를 고르고, 추론 backend를 선택하는 Skill이다. 지원 모델에서는 vLLM을 활용하고, 호환성이 맞지 않으면 Transformers 또는 accelerate 경로를 검토한다. 처음부터 전체 benchmark를 돌리기보다 `--limit`·`--max-samples`로 작은 실행을 확인한 뒤 규모를 늘린다. [공식 원문](https://github.com/huggingface/skills/blob/main/skills/huggingface-community-evals/SKILL.md)

**이름만 보고 평가 결과 게시 도구로 오해하면 안 된다.** 현재 원문은 HF Jobs 관리, 모델 카드·model-index 수정, README 표 추출, 평가 결과 게시와 PR 생성을 범위 밖으로 둔다. Inference Providers용 스크립트도 있지만, 이때 로컬에서 실행되는 것은 평가 절차이고 **추론은 외부 API에 요청**한다. 완전한 로컬 평가와 전송·비용 조건이 다르다. [Provider 스크립트](https://github.com/huggingface/skills/blob/main/skills/huggingface-community-evals/scripts/inspect_eval_uv.py)

원문에 남은 원격 작업 참조명 `hugging-face-jobs`와 특정 개발자 로컬 경로는 현재 설치 가능한 대상으로 검증하지 못했다. 원격 실행·게시가 필요하면 현행 Hub CLI와 별도 workflow를 확인해야 한다. `--trust-remote-code`도 단순 호환성 옵션으로 자동 추가하지 말고 모델 저장소 코드 실행을 허용하는 결정으로 다룬다.

### 설치 및 사용

현재 공식 README가 안내하는 개별 workflow 설치:

```bash
hf skills add huggingface-community-evals
```

**전제조건:** `hf` CLI와 Skill을 읽는 host가 필요하다. 번들 스크립트는 Python 3.10 이상을 선언하며 `uv run` 사용을 권장한다. 로컬 GPU 경로는 backend·모델을 지원하는 GPU와 메모리, gated/private 모델은 별도 접근 권한이 필요하다. 설치한 Skill 디렉터리에서 먼저 도움말과 의존성을 확인한다. [로컬 GPU 스크립트](https://github.com/huggingface/skills/blob/main/skills/huggingface-community-evals/scripts/inspect_vllm_uv.py)

```bash
uv run scripts/inspect_vllm_uv.py --help
```

**Agent 활용 예시**

> 이 Hub 모델을 GSM8K로 평가할 계획을 세워줘. 모델 revision과 backend, task 설정을 기록하고 먼저 10개 샘플로 로컬 smoke test를 하자. 외부 provider로 전환하기 전에는 보낼 데이터와 비용을 알려줘. 결과 게시는 하지 마.

**평가:** 모델 선정·학습 후 검증에 실용적이다. 작은 표본의 성공은 전체 품질이나 한국어 성능의 증거가 아니므로, 정식 비교에서는 동일한 데이터·prompt·revision·채점 조건을 유지해야 한다.

## 2. huggingface-gradio

- **출처/제작자:** [Hugging Face 공식 Skills](https://github.com/huggingface/skills)
- **원 Skill:** [huggingface-gradio/SKILL.md](https://github.com/huggingface/skills/blob/main/skills/huggingface-gradio/SKILL.md)
- **지원 Agent:** 공식 모음의 Codex 등 Agent Skills 호스트. 앱 실행용 Python과 결과 확인용 브라우저가 별도로 필요하다.
- **태그:** `#Gradio` `#ML데모` `#PythonUI` `#프로토타입`
- **도입 난이도:** 낮음~중간. 기존 Python 함수에 UI를 붙이는 작업부터 시작하기 좋다.

### 인기 및 트렌드 지표

- Hugging Face Skills 모음 전체: **11,138 stars / 759 forks**
- 정확한 현재 이름의 개별 installs·First Seen·감사 상태: **미확인**
- Gradio 라이브러리의 인기와 이 Skill의 채택을 같은 수치로 취급하지 않았다.

### 내용

Python 함수의 입력·출력을 `Interface`로 감싸거나, `Blocks`에서 버튼·파일·이미지·챗봇을 배치하고 이벤트를 연결한다. 단순한 함수 데모에서 출발해 `ChatInterface`, 스트리밍, 사용자 정의 HTML 구성 요소까지 확장할 수 있다. 모델의 결과를 코드 출력만으로 설명하기 어려울 때 직접 조작 가능한 화면을 빠르게 준비하는 데 적합하다. [공식 Skill](https://github.com/huggingface/skills/blob/main/skills/huggingface-gradio/SKILL.md)

앱을 만드는 지침 외에 `gradio info`로 API endpoint와 parameter를 조사하고 `gradio predict`로 호출하는 방법도 포함한다. 이때 **파일 입력은 원격 서버로 업로드될 수 있다**. 로컬 파일 경로가 명령에 등장한다고 해서 데이터 처리가 로컬에서 끝나는 것은 아니다.

`share=True`는 공개 접속 URL을 만든다. 계산이 로컬 컴퓨터에서 수행되더라도 접근 범위는 넓어진다. 첫 시도는 로컬 전용으로 두고, 모델 다운로드·외부 API 호출·Space 배포는 별도 단계로 다루는 것이 좋다. [Gradio 공식 설치·공유 안내](https://github.com/gradio-app/gradio/blob/main/README.md)

### 설치 및 사용

```bash
hf skills add huggingface-gradio
```

**전제조건:** 현재 Gradio는 Python 3.10 이상이 필요하다. Skill 설치와 Gradio 패키지 설치는 별개다. 기존 프로젝트에서는 사용 중인 버전과 lockfile을 존중하고, 최신 API 예제를 맞추기 위해 dependency를 무단 갱신하지 않는다. 모델·GPU·추론 API는 실제 데모 기능에 따라 따로 준비한다.

설치 후 로컬 앱의 endpoint를 살피는 예:

```bash
gradio info http://127.0.0.1:7860
```

실제 port는 실행 결과로 확인한다. 이 조회는 앱 실행 자체를 대신하지 않는다.

**Agent 활용 예시**

> 내 Python 이미지 분류 함수에 업로드·실행 버튼·예측 결과가 있는 로컬 Gradio 데모를 붙여줘. 빈 입력과 잘못된 파일, 연속 클릭도 확인해. 공개 공유 URL이나 외부 배포는 만들지 마.

**평가:** 오늘의 Codex 즉시 활용 후보다. UI를 만들었다는 것과 모델 품질·동시 사용자 처리·운영 보안이 검증됐다는 것은 별개이므로, 작은 데모부터 실제 동작을 확인하며 확장한다.

## 3. huggingface-trackio

- **출처/제작자:** [Hugging Face 공식 Skills](https://github.com/huggingface/skills)
- **원 Skill:** [huggingface-trackio/SKILL.md](https://github.com/huggingface/skills/blob/main/skills/huggingface-trackio/SKILL.md)
- **지원 Agent:** 공식 모음의 Codex 등. Python API로 기록하고 CLI로 결과를 읽는다.
- **태그:** `#실험추적` `#학습관측` `#JSON` `#데이터보존`
- **도입 난이도:** 낮음~중간. 로컬 기록은 가볍고 원격 dashboard·webhook에는 별도 권한 설계가 필요하다.

### 인기 및 트렌드 지표

- Hugging Face Skills 모음 전체: **11,138 stars / 759 forks**
- 개별 installs·First Seen·감사 상태·독립 품질점수: **미확인**

### 내용

`trackio.init()`·`log()`·`finish()`로 loss·정확도·learning rate 등을 기록하고, dashboard와 CLI로 비교한다. TRL의 `report_to="trackio"` 연동도 제공한다. 학습 코드에 INFO/WARN/ERROR 알림을 넣고 Agent가 `--json`으로 다시 조회할 수 있어, 긴 로그에서 중요한 사건과 해당 지표를 찾는 작업에 유용하다. [공식 Skill](https://github.com/huggingface/skills/blob/main/skills/huggingface-trackio/SKILL.md)

기본 저장은 로컬 SQLite다. `space_id`로 HF Space에 동기화할 수 있지만 **자동 생성 Space는 기본 공개**이고 조직 설정에 따라 달라질 수 있다. 생성 시 `private=True`를 주더라도 **이미 존재하는 Space의 공개 범위를 바꾸지는 않는다**. 실제 대상의 권한을 확인해야 한다. 단기 클라우드 머신에서는 로컬 디스크가 없어질 수 있으므로 승인된 영속 저장 위치를 따로 준비한다. [기록·저장·공개 범위](https://github.com/huggingface/skills/blob/main/skills/huggingface-trackio/references/logging_metrics.md)

원문은 알림을 보고 실행을 중단하고 hyperparameter를 조정해 재시작하는 반복도 제안한다. 지표 관찰을 허용했다고 해서 추가 유료 학습이나 외부 webhook 발송까지 허용된 것은 아니다. 또한 알림은 코드에 넣은 조건을 기록하는 장치이지 모든 이상을 자동 발견하는 품질 보증기가 아니다.

### 설치 및 사용

```bash
hf skills add huggingface-trackio
```

**전제조건:** Trackio 패키지와 Python 3.10 이상이 필요하다. 원격 Space 생성·동기화에는 대상에 대한 쓰기 권한이 필요하며 GPU 시스템 지표는 선택적 의존성이다. 처음에는 로컬 저장·조회만 사용해도 된다. [설치 문서](https://huggingface.co/docs/trackio/installation), [Python 요구사항](https://github.com/gradio-app/trackio/blob/main/pyproject.toml)

이미 기록한 프로젝트를 읽는 예:

```bash
trackio list alerts --project my-project --json
trackio get metric --project my-project --run my-run --metric loss --json
```

**Agent 활용 예시**

> 이번 학습의 loss와 learning rate를 로컬 Trackio에 기록해줘. NaN과 갑작스러운 loss 상승을 알림으로 남기고, 종료 후 어느 step에서 발생했는지 JSON으로 조회하자. Space 동기화나 webhook 전송, 자동 재학습은 별도 검토하자.

**평가:** 학습을 제출하는 데서 끝나지 않고 무엇이 일어났는지 남기는 데 유용하다. 평가 점수와 학습 지표를 구분하고, dashboard에서 수치가 보인다는 이유만으로 최종 모델의 일반화 성능이 개선됐다고 판단하지 않는다.

- **태그:** `#Nextjs` `#CloudflareWorkers` `#vinext` `#마이그레이션`
- **도입 난이도:** 중간~높음. routing·인증·캐시·빌드 설정의 호환성 검증이 필요하다.

### 인기 및 트렌드 지표

- skills.sh: **installs 22.7K**, First Seen **2026-09-05**
- 검색 도구에 **3일 전 크롤링**으로 표시됐다. 수치 자체의 갱신 시각은 미확인이며 당일 실시간 설치량으로 보지 않았다.
- 감사 표시: **Gen Agent Trust Hub Pass / Socket Warn / Snyk Pass**
- Cloudflare Skills 모음 전체: **2,990 stars / 300 forks**

### 내용

Next.js 앱을 Cloudflare Workers에서 시작하거나 이전할 때 현재 경로를 찾아주는 라우팅 Skill이다. Vite 위에서 Next.js API를 구현하는 **vinext**를 기본으로 안내하고, 실제 이전에는 vinext 저장소의 upstream Skill과 최신 문서를 읽도록 한다. 기존 `cloudflare`의 전체 제품 탐색이나 `wrangler`의 CLI 운영과 달리 Next.js 앱의 실행 환경 선택과 호환성이 초점이다. [공식 Skill](https://github.com/cloudflare/skills/blob/main/skills/nextjs-on-cloudflare/SKILL.md)

현재 Cloudflare Next.js 가이드도 vinext 기반 절차를 안내하며 **vinext는 beta**라고 명시한다. 운영 앱 도입 전 필수 기능의 호환성을 확인해야 한다. 기존 OpenNext 프로젝트를 관련 없는 유지보수 중에 바꾸라는 뜻은 아니다. 원문은 기존 설정과 사용자의 명시적인 선택을 보존하게 한다. 신규 프로젝트와 기존 앱 이전을 구분하며, 빈 디렉터리에 기존 앱용 migration Skill을 적용하지 않는다. [현재 플랫폼 가이드](https://developers.cloudflare.com/workers/framework-guides/web-apps/nextjs/)

upstream workflow는 `vinext check`로 호환성을 살핀 뒤 기존 Next.js 설정과 병행해 시험할 수 있게 한다. 완전한 기능 동등성을 가정하면 안 된다. 예를 들어 현재 upstream 원문은 domain 기반 i18n, `next/jest`, webpack/Turbopack 설정 등에 제약을 적고 있다. 실제 앱의 필수 기능·인증·데이터 갱신·이미지 경로를 확인해야 한다. [upstream 이전 원문](https://github.com/cloudflare/vinext/blob/main/.agents/skills/migrate-to-vinext/SKILL.md)

### 설치 및 사용

```bash
npx skills add cloudflare/skills --skill nextjs-on-cloudflare --agent codex
```

실제 이전을 진행한다면 원문이 연결하는 `cloudflare/vinext`의 관련 Skill·reference도 함께 확인한다. 이는 오늘의 별도 신규 소개 항목으로 세지 않은 **upstream 의존 workflow**다.

**전제조건:** 기존 앱의 package manager·lockfile·Next.js dependency와 배포 대상을 먼저 확인한다. 호환성 점검과 로컬 build는 실제 운영 배포와 다른 단계다. 설치 자체가 runtime 전환·계정 변경·배포 승인은 아니다. Socket Warn의 상세 사유도 설치 전에 확인할 항목이다.

**Agent 활용 예시**

> 이 Next.js 앱을 Workers로 옮길 수 있는지 먼저 평가해줘. 현재 OpenNext 설정은 유지하고 vinext 호환성, 인증, 이미지, i18n, 캐시와 주요 경로를 확인하자. 변경안과 로컬 검증 계획을 만든 뒤 실제 이전·배포 여부를 결정하자.

**평가:** 오래된 배포 예제를 그대로 따르지 않게 하는 안내판으로 가치가 있다. 어제 소개한 Cache Components optimizer가 앱 내부의 렌더링·캐시 검증이었다면, 이번 항목은 **다른 runtime에서 앱을 실행할 수 있는지**를 다룬다.

### 내용

`.tftest.hcl`의 run·assert·expect_failures를 사용해 모듈 입력, 자원 구성과 출력의 회귀를 검사한다. plan 기반 검사, mock provider, 실제 apply 통합 테스트를 나눠 작성하는 예시와 CI reference가 있다. Agent가 인프라 코드를 변경할 때 “문법이 맞는다”에서 “원하는 조건을 만족한다”로 검증 범위를 넓히는 데 유용하다. [공식 Skill](https://github.com/hashicorp/agent-skills/blob/main/plugins/terraform/skills/terraform-test/SKILL.md)

**현재 Skill의 CLI 예제는 그대로 복사하면 안 된다.** 원문은 `-filter`를 run 이름 선택으로 설명하지만 현행 공식 CLI 문서는 **test 파일 선택**으로 정의한다. 특정 파일은 아래처럼 `-filter=tests/...`로 실행한다. 원문의 `-no-cleanup`도 조회한 공식 CLI 옵션 목록에서 확인되지 않아 사용 예시에서 제외했다. 설치된 버전의 `terraform test -help`와 현재 문서를 먼저 확인해야 한다. [CLI 문서](https://developer.hashicorp.com/terraform/cli/commands/test)

테스트의 기본 command는 **apply**여서 실제 자원과 비용이 생길 수 있다. Terraform 1.6+의 테스트 framework와 1.7+의 provider mocking을 구분하며, plan만 사용해도 실제 provider의 데이터 조회까지 모두 사라지는 것은 아니다. 테스트 전용 계정·권한을 쓰고, 실제 자원을 만든 실행은 종료 후 cleanup 실패와 잔여 자원을 확인한다. [테스트 언어 문서](https://developer.hashicorp.com/terraform/language/tests)

### 설치 및 사용

공식 README의 현행 plugin 디렉터리 구조를 사용한다.

```bash
npx skills add hashicorp/agent-skills/plugins/terraform/skills/terraform-test --agent codex
terraform test -help
```

검토한 테스트 파일만 실행하는 현재 CLI 문법:

```bash
terraform test -filter=tests/validations.tftest.hcl
```

**전제조건:** 마지막 명령은 테스트를 실제 실행한다. 파일에 `command = plan`과 필요한 mock이 있는지, 관련 setup run이 apply를 수행하지 않는지 먼저 확인한다. 단순 명령 옵션만으로 비용 없는 실행이 보장되지 않는다. 기존 module/provider 버전과 lockfile을 유지하며 CI 예제는 해당 프로젝트에 맞게 검토한다.

**Agent 활용 예시**

> 이 Terraform 모듈의 옵션 변경에 회귀 테스트를 추가해줘. 우선 plan과 mock으로 입력 검증·태그·자원 수를 확인하고, 실제 cloud API가 필요한 부분은 분리해. 비용이 드는 apply 테스트는 계정·자원·정리 계획을 검토한 뒤 실행하자.

**평가:** 인프라 변경을 Agent에게 맡기는 팀에 유용한 **검토형 후보**다. 공식 제작자의 Skill이어도 CLI 세부 지침은 실제 제품 문서와 대조해야 한다는 사례이며, 감사 Pass를 정확성 검증으로 대체하면 안 된다.

### 내용

문서를 배경 수집, 구조·내용 다듬기, 독자 테스트의 세 단계로 작성하는 지침이다. 문서 유형·독자·원하는 결정·기존 양식을 먼저 확인하고, 불확실한 핵심 제안부터 쓰며 요약은 뒤에 정리한다. 각 절은 선택·수정 과정을 거쳐 다듬어 작성자가 의도하지 않은 주장이나 필요 없는 내용을 줄인다. [공식 Skill](https://github.com/anthropics/skills/blob/main/skills/doc-coauthoring/SKILL.md)

가장 특징적인 단계는 **작성 대화를 모르는 새 검토자에게 문서와 질문만 제공하는 독자 테스트**다. 작성자에게 당연한 전제, 모호한 용어, 상충하는 설명을 찾고 해당 절을 고친다. 이전에 소개한 `to-spec`이 합의된 요구사항을 개발 명세로 정리하는 데 가깝다면, 이 Skill은 제안서·의사결정 문서 등에서 독자의 이해를 확인하는 협업 과정이다.

원문에는 많은 질문과 반복 선택 절차가 있으므로 짧은 메모에는 과할 수 있다. 사용자에게 이 과정을 제안하고 자유로운 작성 방식도 허용한다. 독자 테스트의 답이 맞아도 원래 사실·수치·출처까지 자동 검증된 것은 아니므로, 최종 사실 확인은 별도로 한다.


**전제조건:** 대화에 제공한 자료만으로도 시작할 수 있다. 공유 문서를 읽거나 수정하려면 해당 도구와 권한이 필요하다. 원문의 Claude 전용 설정·artifact 명령을 다른 host에서 그대로 실행된다고 가정하지 않는다. 민감한 문서를 외부 서비스나 다른 계정의 모델에 붙여 넣는 독자 테스트는 전송 대상과 자료 범위를 먼저 검토해야 한다.

**평가:** 사전 맥락을 공유하지 않은 사람에게 넘길 RFC·설계 제안에 특히 적합하다. 형식적인 문장 윤문보다 설명의 빠진 고리를 찾는 것이 목적이며, 확인하지 않은 합의나 결정을 채워 넣지 않는 것이 중요하다.

> 이번 조사는 문서·원문·공개 지표를 확인한 보고서다. Skill 설치, GPU 평가, Gradio 앱 실행, 학습·동기화, cloud 배포, Terraform 테스트, 독자 검증을 실제 수행한 실험은 아니다. 설치 안내는 실행 승인을 대신하지 않으며 credential·데이터 전송·유료 자원·공개 범위는 적용 시 따로 확인해야 한다.
