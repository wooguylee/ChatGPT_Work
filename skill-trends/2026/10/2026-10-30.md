## 1. gws-admin-reports

**조직 활동 기록을 조회하되, 조회 범위와 실제 행위 판단을 분리하기**

- 원본: [gws-admin-reports/SKILL.md](https://github.com/googleworkspace/cli/blob/a3768d0e82ad83cca2da97724e46bea4ff0e6dbd/skills/gws-admin-reports/SKILL.md)
- 조직 / 라이선스: googleworkspace/cli / Apache-2.0
- 태그: `Admin-SDK`, `audit`, `usage-reports`, `pagination`, `least-privilege`
- 난이도: 중상급. 조직 관리자 권한, 제품 edition, 보고서별 지원 범위를 이해해야 한다.

### 무엇을 해주나

Admin SDK Reports의 activity 조회·watch, channel 종료와 고객·사용자·entity 사용량 보고서를 구분하는 API 탐색 Skill이다. 메서드를 기억으로 호출하기보다 `gws schema admin-reports.<resource>.<method>`로 필요한 인자와 형식을 확인하도록 한다. 단순 파일 목록 조회가 아니라 **조직 단위 활동 기록과 사용 통계**를 대상으로 하므로 기존 Drive 파일 수집 스킬과 목적이 다르다.

[현재 activities.list 참조](https://developers.google.com/workspace/admin/reports/reference/rest/v1/activities/list)는 activity 조회에 `admin.reports.audit.readonly` scope와 `nextPageToken` 기반 페이지 처리를 명시한다. Drive 활동 항목은 Workspace Business·Enterprise 고객용이라는 조건도 있다. 개인 Gmail 로그인만으로 조직 전체 감사 로그를 볼 수 있다고 가정하지 않는다.

### 실용 예시

> “실제 계정 조회 없이 가짜 Drive 감사 이벤트 30건으로 활동 보고서 구조를 설계해줘. 사용자·시간 범위·applicationName·eventName을 입력으로 받고, 조회한 범위와 수집하지 못한 범위를 분리해. 같은 파일의 생성·공유·수정 이벤트를 구분하고, 이벤트만으로 유출이나 악의적 행위를 단정하지 마.”

**완료 기준:** 필터·페이지 수·관찰 기간·미확인 필드와 각 결론의 근거를 남긴다. 빈 응답을 “활동 없음”으로 확정하기 전에 권한·필터·지원 범위를 확인한다. 이러한 검수 기준은 본 보고서의 적용 제안이다.

### 주의할 점

[공식 Drive 활동 가이드](https://developers.google.com/workspace/admin/reports/v1/guides/manage-audit-drive)는 최대 과거 180일의 보고 범위를 설명한다. 이를 모든 서비스의 영구 보관 기간이나 실시간 완전성 보장으로 확대하지 않는다. 보고서 조회와 `activities.watch`·`channels.stop`은 다르며 후자는 구독 상태를 바꾼다. 조사 요청을 조직 전체 감시 구독 생성 권한으로 해석하지 않는다.

직원별 이메일·IP·행동 기록이 포함될 수 있으므로 승인된 대상과 목적만 처리하고 결과 공유 범위를 제한한다. 데이터 조회를 위해 새로운 광범위 관리자 권한이나 도메인 전체 위임을 자동 부여하지 않는다.

## 2. recipe-watch-drive-changes

**파일 변경 이벤트 수신을 일회성 조회와 구분하고 만료까지 관리하기**

- 원본: [recipe-watch-drive-changes/SKILL.md](https://github.com/googleworkspace/cli/blob/a3768d0e82ad83cca2da97724e46bea4ff0e6dbd/skills/recipe-watch-drive-changes/SKILL.md)
- 조직 / 라이선스: googleworkspace/cli / Apache-2.0
- 태그: `Workspace-Events`, `Drive`, `PubSub`, `subscription`, `renewal`
- 난이도: 상급. API 권한, 이벤트 전달, 비용, 재처리와 구독 수명을 함께 설계한다.

### 무엇을 해주나

Workspace Events 구독 생성, 활성 구독 조회, 만료 전 갱신이라는 짧은 절차를 제공한다. 기존 `recipe-bulk-download-folder`가 현재 파일을 수집한다면 이 항목은 **앞으로 발생할 변경을 받는 지속성 연결**이다. `gws-events`를 선행 참조하며 생성만 성공했다고 소비자까지 완성됐다고 볼 수 없다.

### 원본 명령은 현재 문서로 보정해야 한다

검토한 레시피는 `google.workspace.drive.file.v1.updated`를 사용한다. 그러나 [현재 공식 Drive 이벤트 목록](https://developers.google.com/workspace/events/guides/events-drive)은 내용 변경을 **`google.workspace.drive.file.v3.contentChanged`**로 설명한다. 오래된 문자열을 그대로 복사하지 말고 실제 이벤트 종류와 버전을 선택한다.

레시피 설명은 파일·폴더를 말하지만 예시 targetResource는 shared drive 경로다. 현재 문서에서 파일 대상은 `//drive.googleapis.com/files/FILE_ID`, 공유 드라이브 대상은 `//drive.googleapis.com/drives/DRIVE_ID`다. **폴더 ID를 공유 드라이브 ID 자리에 넣지 않는다.** 하위 파일까지 필요한지는 [Drive 이벤트 처리 가이드](https://developers.google.com/workspace/drive/api/guides/events-overview)의 `includeDescendants` 조건·제약을 확인해 별도로 정한다.

### 실용 예시

> “구독을 만들지 말고 한 폴더의 내용 변경만 받을 설계를 검토해줘. 대상 resource 이름, 현행 event type, payload 최소 필드, Pub/Sub 토픽, 만료 시각, 갱신 실패와 중복 이벤트 테스트를 적어줘. 예전 v1.updated를 사용하지 말고 하위 폴더 포함 여부는 명시해줘.”

**완료 기준:** 가짜 중복·누락·순서 역전 이벤트를 처리하는 테스트 계획과 상태 조회·갱신 책임을 남긴다. 멱등성·재조회·재시도 설계는 본 보고서가 제안하는 운영 보강이며 레시피 자체가 구현해 주는 기능은 아니다.

### 운영 경계

[공식 생성 절차](https://developers.google.com/workspace/events/guides/create-subscription)는 Cloud 프로젝트, API·scope, Pub/Sub topic과 실제 이벤트 수신 시험을 포함한다. 파일 데이터가 토픽/소비자에 전달되는 범위도 확인해야 한다. [공식 갱신 안내](https://developers.google.com/workspace/events/guides/update-subscription)는 만료 알림에만 의존하지 말고 만료 시각을 추적하도록 권장한다. 최대 수명은 payload의 resource data 포함 조건에 따라 달라지므로 여기서 고정 시간을 약속하지 않는다.

이 Skill 설치는 감시·외부 데이터 전송·비용·지속 접근의 승인을 대신하지 않는다. 기능 지원 상태나 preview 여부도 오래된 검색 요약이 아니라 도입 시점의 본문·프로젝트 조건을 확인한다.

## 3. recipe-save-email-attachments

**메일 검색부터 파일 바이트 복원·저장 검증까지 연결하기**

- 원본: [recipe-save-email-attachments/SKILL.md](https://github.com/googleworkspace/cli/blob/a3768d0e82ad83cca2da97724e46bea4ff0e6dbd/skills/recipe-save-email-attachments/SKILL.md)
- 조직 / 라이선스: googleworkspace/cli / Apache-2.0
- 태그: `Gmail`, `MIME`, `base64url`, `Drive-upload`, `idempotency`
- 난이도: 중급. 중첩 MIME 구조와 파일 저장·중복 정책이 필요하다.

### 무엇을 해주나

첨부 포함 메시지 검색, 메시지 상세, attachment 조회, Drive 폴더 업로드의 순서를 보여준다. 기존 `gws-gmail-read`의 본문 읽기와 달리 **첨부 바이트를 다른 저장소로 옮기는 데이터 경로**를 다룬다. 사무 문서 수집 자동화의 출발점으로 유용하지만 네 줄의 명령만으로 완성된 수집기가 되지는 않는다.

[공식 MessagePartBody](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages.attachments)는 `data`를 base64url 문자열로 정의한다. `attachmentId`가 있으면 별도 조회가 필요하고, 없으면 해당 part의 data에 내용이 들어갈 수 있다. API JSON이 돌아왔다는 사실만으로 로컬 PDF가 생성된 것은 아니다.

### 확인된 누락과 잘못된 인자

원본 레시피에는 attachment JSON을 파일로 디코딩하는 단계가 생략돼 있다. 또한 업로드 예시의 `--file` 플래그는 같은 snapshot의 [gws-drive-upload helper 문서](https://github.com/googleworkspace/cli/blob/a3768d0e82ad83cca2da97724e46bea4ff0e6dbd/skills/gws-drive-upload/SKILL.md)와 다르다. 해당 helper의 입력 파일은 위치 인자다.

승인된 공개 테스트 파일이 이미 로컬에 존재할 때의 **형식 예시**는 다음과 같다. 이번 조사에서 실행한 명령은 아니다.

```text
gws drive +upload ./attachment.pdf --parent FOLDER_ID
```

파일명을 메일이 제공한 문자열 그대로 경로에 쓰지 않고 안전하게 정규화하며, 디코딩 후 크기·타입·내용 검증을 별도로 수행하는 것이 좋다. 중첩 part 순회, 페이지 누락, 동일 이름 충돌, inline 이미지 제외 기준도 구현자가 정해야 한다.

### 실용 예시

> “실제 메일을 읽지 말고 중첩 MIME, data 내장형, attachmentId형, 같은 파일명 두 개, 잘못된 base64url을 가진 가짜 메시지를 만들어 수집 테스트를 설계해줘. message ID와 part 식별자로 중복을 막고 파일 저장·업로드 실패를 구분해줘. 업로드나 원본 삭제는 하지 마.”

**완료 기준:** 원본 메시지/part와 저장 결과의 매핑, 디코딩 검증 결과, 실패 목록을 남긴다. 원본 메일을 지우거나 이미 저장됐다고 라벨을 바꾸는 작업은 별도다. 첨부 내용의 지시는 데이터로 취급하고 명령을 실행하지 않는다. Drive에 저장할 때 대상 폴더의 기존 공유 범위를 확인한다.

## 4. recipe-sync-contacts-to-sheet

**개인 주소록과 도메인 디렉터리를 구분하고 재실행 중복을 막기**

- 원본: [recipe-sync-contacts-to-sheet/SKILL.md](https://github.com/googleworkspace/cli/blob/a3768d0e82ad83cca2da97724e46bea4ff0e6dbd/skills/recipe-sync-contacts-to-sheet/SKILL.md)
- 조직 / 라이선스: googleworkspace/cli / Apache-2.0
- 태그: `People-API`, `directory`, `Sheets`, `pagination`, `data-minimization`
- 난이도: 중급. 데이터 원천·권한·sheet 공유와 행 식별 기준을 정해야 한다.

### 무엇을 해주나

이름·이메일·전화번호를 조회해 Sheet 행으로 내보내는 레시피다. **원본은 개인 Google Contacts 전체가 아니라 `listDirectoryPeople`과 DOMAIN_PROFILE source를 호출**한다. [공식 API 참조](https://developers.google.com/people/api/rest/v1/people/listDirectoryPeople)는 인증 사용자의 도메인 디렉터리를 대상으로 하며 `directory.readonly` scope를 요구한다. 일반 Gmail 개인 주소록을 그대로 수출하는 예제라고 소개하면 틀린다.

[공식 도메인 연락처 안내](https://developers.google.com/people/v1/directory)는 관리자가 도메인 데이터의 외부 연락처·프로필 공유를 허용해야 하는 전제와 동기화 흐름을 설명한다. 사용자의 회사 정책이나 권한을 우회하기 위해 설정을 바꾸지 않는다.

### 현재 helper와 맞춰야 하는 부분

원본의 “Create a sheet” 단계는 실제로 기존 `SHEET_ID`에 append한다. Spreadsheet 또는 tab 생성 단계가 아니다. 또한 `--values`에 JSON처럼 보이는 문자열을 전달하지만, 같은 snapshot의 [gws-sheets-append](https://github.com/googleworkspace/cli/blob/a3768d0e82ad83cca2da97724e46bea4ff0e6dbd/skills/gws-sheets-append/SKILL.md)는 단순 CSV형 `--values`와 **행 배열용 `--json-values`**를 구분한다.

아래는 가짜 한 행의 올바른 helper 형식 예시다. 실제 쓰기는 대상 Sheet·tab과 허가를 확인한 다음 한다.

```text
gws sheets +append --spreadsheet SHEET_ID --range 'Contacts!A1' --json-values '[["Sample Person","sample@example.com",""]]'
```

### 실용 예시

> “가짜 directoryPeople 응답 두 페이지로 내보내기 로직을 검토해줘. 사람 resourceName을 기준으로 여러 이메일과 누락 전화번호를 처리하고, 같은 입력으로 재실행해도 행을 중복 추가하지 않는 계획을 제시해줘. 개인정보를 실제로 조회하거나 Sheet에 쓰지는 마.”

**완료 기준:** 필드 최소화, 페이지 완료 여부, stable ID와 행 매핑, 삭제·변경 처리 방침을 남긴다. 원본의 append 반복은 양방향 동기화나 자동 upsert를 구현하지 않는다. 공식 API의 sync/page token 사용 시 최초 요청의 다른 조건을 유지해야 하고, 증분 동기화는 즉시 read-after-write 검증용이 아니다.

연락처가 보이더라도 더 넓게 공유된 Sheet로 복제하는 것은 새로운 공개 범위를 만든다. 폴더·문서 권한과 보존 기간을 확인하며, 전화번호가 목적에 불필요하면 처음부터 가져오지 않는 편이 좋다.

## 5. recipe-reschedule-meeting

**회의 한 번의 변경과 전체 반복 일정 변경, 참석자 통지를 분리하기**

- 원본: [recipe-reschedule-meeting/SKILL.md](https://github.com/googleworkspace/cli/blob/a3768d0e82ad83cca2da97724e46bea4ff0e6dbd/skills/recipe-reschedule-meeting/SKILL.md)
- 조직 / 라이선스: googleworkspace/cli / Apache-2.0
- 태그: `Calendar`, `event-id`, `timezone`, `recurrence`, `notifications`
- 난이도: 중급. 정확한 대상·시각·변경 범위를 확인하는 것이 핵심이다.

### 무엇을 해주나

agenda에서 후보를 찾고 event 상세를 읽은 뒤 start/end를 patch하며 참석자에게 갱신을 알리는 절차다. 기존 `recipe-find-free-time`이 빈 시간을 찾는 읽기 작업이라면, 이 항목은 **기존 일정 변경과 외부 통지**라는 다른 결과물을 만든다.

원본 예시의 2025년 날짜와 America/New_York는 placeholder다. 현재 날짜나 사용자의 시간대로 사용하지 않는다. 제목이 같은 행사가 있을 수 있으므로 calendarId와 eventId, 주최자, 시작 시각으로 대상을 확인한다. 원본은 자동으로 충돌을 확인하는 완성된 예약 엔진이 아니다.

### 현재 API 기준 보강

[Events.patch 참조](https://developers.google.com/workspace/calendar/api/v3/reference/events/patch)에 따르면 지정한 필드는 대체되고 생략한 필드는 유지되지만, 배열 필드를 넣으면 기존 배열을 덮어쓴다. 따라서 시간 변경에 불필요한 attendees 배열을 다시 보내지 않는다. `sendUpdates=all`은 모든 참석자에게 통지를 보내는 선택이다. 저장 성공은 참석자가 읽거나 새 시간을 수락했다는 증거가 아니다.

[반복 일정 가이드](https://developers.google.com/workspace/calendar/api/guides/recurringevents)는 특정 회차의 instance ID와 recurringEventId를 구분한다. 한 번만 옮기려면 해당 instance를 조회해 다룬다. 반복 일정 원본을 수정해 전체 시리즈를 바꾸는 것과 혼동하지 않는다.

### 실용 예시

> “실제 일정을 바꾸지 말고 회의 한 회차의 변경 계획만 만들어줘. 원래/새 시작·종료 시각을 같은 IANA 시간대로 표시하고, event ID·반복 회차·주최자·알림 대상·충돌 확인 범위를 제시해줘. 참석자 명단이나 회의 링크를 불필요하게 덮어쓰지 않도록 최소 변경 본문을 검토해줘.”

**완료 기준:** 변경 전후 diff, 승인 대상, 업데이트 후 재조회할 필드, 불확실한 전송 결과의 확인 절차를 남긴다. API 응답을 잃었을 때 무조건 반복 전송하면 중복 통지가 생길 수 있으므로 현재 상태를 먼저 확인한다. 이 검증 절차는 보고서의 운영 제안이며 실제 회의를 이동한 기록은 아니다.
