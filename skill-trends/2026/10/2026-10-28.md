## 1. redis-clustering

**여러 키를 함께 처리할 때 슬롯 제약과 일관성 요구를 먼저 확인하는 설계 지침.**

- 출처: [SKILL.md](https://github.com/redis/agent-skills/blob/a84871d065f398fed55e1633f66b66f731eb4e2b/skills/redis-clustering/SKILL.md)
- 태그: `redis-cluster` `hash-tag` `consistency` `replication`
- 난이도: 중상급

### 무엇을 해주나

Redis Cluster의 키 분산과 다중 키 연산을 연결해 설명한다. 같은 엔터티의 키를 의도적으로 같은 hash tag로 묶는 방법, 지나친 묶음으로 특정 슬롯에 부하가 쏠리는 문제, 복제본 읽기로 부하를 분산할 때 오래된 값을 볼 수 있는 문제를 검토한다.

어제의 redis-core가 자료형·키 이름을 다뤘다면 이 스킬은 **샤딩된 배치 위치와 읽기 일관성**을 다룬다. 같은 이름 규칙을 쓰는 것만으로 트랜잭션이 여러 노드에서 원자적으로 수행되는 것은 아니다. 해시 태그를 바꾸는 운영 키 이전도 단순 문자열 수정이 아닌 데이터 이행 작업이다.

### 원문에서 교정할 점

원문은 pipeline까지 모든 키가 같은 슬롯이어야 한다고 일반화한다. 그러나 현행 redis-py 문서의 **비트랜잭션 ClusterPipeline은 노드별로 명령을 나누어 실행**한다. 반면 클러스터 트랜잭션의 키들은 같은 슬롯이어야 한다. 따라서 단일 다중 키 명령, 비원자적 배치, 트랜잭션을 구분해야 한다. “pipeline이면 무조건 CROSSSLOT”이라는 원문 예제를 그대로 장애 판정 기준으로 쓰지 않는다. [공식 redis-py 상세 설명](https://redis.readthedocs.io/en/stable/advanced_features.html#pipelines-in-clusters)

복제본 읽기의 선택 API와 지원 범위는 사용하는 클라이언트 버전에서 확인한다. 쓰기 직후 확인, 중복 실행 방지 상태처럼 신선도가 중요한 읽기는 복제 지연을 허용하는 대시보드 조회와 분리한다. 실제 성능 개선은 측정하지 않았다.

### 실전 프롬프트

> redis-clustering을 참고해 가상 작업 큐의 키 설계를 검토해 줘. 다중 키 원자 연산이 꼭 필요한 그룹만 hash tag로 묶고, 비트랜잭션 배치와 트랜잭션을 구분해. 쓰기 직후 읽기·중복 실행 방지·집계 화면의 일관성 요구를 따로 적어. 실제 클러스터 생성, 키 이전, replica read 설정 변경은 하지 마.

## 2. redis-security

**인증이 있다는 사실과 충분히 제한된 접근 권한을 구분하는 보안 검토 지침.**

- 출처: [SKILL.md](https://github.com/redis/agent-skills/blob/a84871d065f398fed55e1633f66b66f731eb4e2b/skills/redis-security/SKILL.md)
- 태그: `acl` `tls` `least-privilege` `network-boundary`
- 난이도: 중상급

### 무엇을 해주나

비밀번호·TLS, 앱별 ACL 사용자, 명령과 키 범위 제한, 외부 네트워크 노출을 함께 점검한다. “비밀번호를 붙였으니 인터넷에 열어도 된다”거나 “방화벽이 있으니 앱은 관리자 계정을 써도 된다”는 식의 단일 방어선 판단을 피하는 데 유용하다.

처음에는 익명화된 설정과 필요한 명령 목록만으로 현재 권한·목표 권한·검증 방법을 표로 정리한다. 실제 비밀번호·토큰·인증서 개인키를 프롬프트나 저장소에 넣을 필요는 없다. ACL·TLS·방화벽 변경은 서비스 접속 중단이나 접근 범위 변경을 일으킬 수 있으므로 검토 작업과 분리한다.

### 원문에서 교정할 점

원문의 `+@all -@dangerous` 예제는 일부 위험 명령을 빼는 넓은 권한이며, **업무에 필요한 최소 허용 목록과 동등하지 않다**. 실제 명령·키·Pub/Sub 채널 요구를 확인해 좁혀야 한다. 키 패턴은 네트워크 격리나 사용자별 애플리케이션 권한 검증을 대신하지 않는다. [공식 ACL 문서](https://redis.io/docs/latest/operate/oss_and_stack/management/security/acl/)

원문이 선택적으로 권하는 `rename-command` 방식은 현행 Redis 보안 문서에서 **deprecated이며 ACL을 대신 권장**한다. 새 보안 계획에 이름 숨기기를 핵심 대책으로 넣지 않는다. TLS 포트 설정만으로 기존 평문 리스너가 사라진다고 가정하지 말고 실제 리스너와 연결 정책을 검증한다. [공식 보안 문서](https://redis.io/docs/latest/operate/oss_and_stack/management/security/)

### 실전 프롬프트

> redis-security로 비밀값을 제거한 설정과 앱의 명령 목록을 검토해 줘. 현재 권한, 실제 필요한 권한, 과도한 권한, 롤백·접속 검증 절차를 구분해. 원문의 넓은 ACL 예제나 명령 이름 변경을 그대로 적용하지 마. 계정 생성, 비밀번호 교체, ACL·TLS·방화벽 수정은 하지 말고 제안만 작성해.

## 3. iris-development

**대화 기록 저장과 장기 기억 생성 완료를 분리하는 Redis Agent Memory 개발 지침.**

- 출처: [SKILL.md](https://github.com/redis/agent-skills/blob/a84871d065f398fed55e1633f66b66f731eb4e2b/skills/iris-development/SKILL.md)
- 태그: `agent-memory` `session-events` `async-processing` `tenant-isolation`
- 난이도: 중상급

### 무엇을 해주나

Redis Cloud의 관리형 Redis Agent Memory에 세션 이벤트를 기록하고 장기 메모리를 검색·구성하는 Python·TypeScript SDK 사용을 안내한다. 일반 Redis 서버를 설치하면 자동으로 같은 관리형 서비스가 생긴다는 뜻은 아니다. 스킬은 Iris 전체 제품군이 아니라 현재 **RAM 데이터 처리 API**를 중심으로 다룬다.

이벤트에는 세션 식별자·발화 주체·역할·시각을 일관되게 전달한다. 장기 메모리는 owner·namespace·topics 등 구조 필드로 분리하고, 재시도에는 논리적 사실에 대응하는 안정적인 ID를 사용한다. 일괄 생성은 성공 목록과 개별 오류를 따로 처리해야 한다. [이벤트 기록](https://github.com/redis/agent-skills/blob/a84871d065f398fed55e1633f66b66f731eb4e2b/skills/iris-development/references/session-add-event.md) · [일괄 생성](https://github.com/redis/agent-skills/blob/a84871d065f398fed55e1633f66b66f731eb4e2b/skills/iris-development/references/ltm-bulk-create.md)

### 원문에서 교정할 점

원문은 이벤트 저장 후 배경 승격 작업이 실행되며 **5분 묶음 창과 LLM 처리 지연**이 있다고 설명한다. 같은 참고 문서의 예제 대기 기본값은 30초이므로 설명된 정상 지연을 다 수용하지 못한다. 이 숫자를 운영 SLA로 단정하지 말고 실제 서비스 상태·실패·재시도 정책에 맞춰 대기와 관측을 설계한다. HTTP 성공은 장기 메모리 생성 완료 증명이 아니다. [승격 처리 원문](https://github.com/redis/agent-skills/blob/a84871d065f398fed55e1633f66b66f731eb4e2b/skills/iris-development/references/promotion-overview.md)

`owner_id`는 검색 분류 필드이며 누락되면 다른 사용자 기록까지 조회될 수 있다고 원문이 경고한다. 따라서 요청자가 임의 owner를 선택하게 두지 않고 서버 측 권한에 따라 검색 범위를 강제해야 한다. 이름 필드를 채웠다는 이유만으로 테넌트 격리가 완성됐다고 보지 않는다. [분류와 격리 주의](https://github.com/redis/agent-skills/blob/a84871d065f398fed55e1633f66b66f731eb4e2b/skills/iris-development/references/ltm-organize.md)

대화를 외부 관리형 서비스와 추출 모델에 전달하는 데이터 흐름이므로 저장 대상·보존 기간·삭제 범위·리전·비용을 별도 검토한다. 생성된 “기억”은 모델의 추출 결과이므로 사실 확정이나 사용자 동의로 취급하지 않는다. 원문의 API·지연·보존 설명을 실제 SDK 또는 서비스에서 재현하지 않았으며 현행 제품 계약의 보장은 아니다.

### 실전 프롬프트

> iris-development를 참고해 가짜 사용자 두 명의 메모리 처리 테스트를 설계해 줘. 이벤트 저장 성공 후 검색 결과가 아직 없는 경우, 부분 성공, 중복 재시도, owner 필터 누락, 사실 정정·삭제를 포함해. 30초 이내 결과가 없다고 바로 실패를 단정하지 말고 근거를 남겨. 실제 대화 전송, 서비스 생성, API 키 발급·설정은 하지 마.

## 4. recipe-review-meet-participants

**참석자 목록과 개별 접속 세션을 나누어 회의 참석 기록을 검토하는 레시피.**

- 출처: [SKILL.md](https://github.com/googleworkspace/cli/blob/a3768d0e82ad83cca2da97724e46bea4ff0e6dbd/skills/recipe-review-meet-participants/SKILL.md)
- 선행 스킬: [gws-meet](https://github.com/googleworkspace/cli/blob/a3768d0e82ad83cca2da97724e46bea4ff0e6dbd/skills/gws-meet/SKILL.md), gws-shared
- 태그: `google-meet` `attendance` `session-analysis` `read-only`
- 난이도: 중급

### 무엇을 해주나

회의 기록 목록 → 회의별 참석자 → 참석자별 접속 세션의 세 단계로 조사한다. 달력의 초대 명단과 실제 연결 기록을 혼동하지 않게 하고, 재접속이 있는 참석자의 시간 계산 자료를 확보하는 데 유용하다. 이전 meeting-prep가 예정 회의 준비를 다뤘다면 이 레시피는 **실제 회의 기록을 사후 분석**한다.

Google 문서는 참석자와 기기별 접속 세션을 구분하며 같은 사람이 같은 회의에 재접속하면 별도 session ID가 생긴다고 설명한다. 이름만 같은 기록을 같은 사람으로 합치지 않고, 익명·전화 참가자는 신원 확인의 한계를 남긴다. 접속 기록은 집중도·실제 발언·근무 성과의 증명이 아니다. [공식 참석자 안내](https://developers.google.com/workspace/meet/api/guides/participants)

### 실전 프롬프트

> recipe-review-meet-participants를 참고해 익명화한 회의 JSON fixture를 정리해 줘. participant ID별 재접속 세션을 분리하고, 시간 구간이 겹치면 중복 집계하지 않는 규칙을 제안해. 종료 시각이 없는 세션과 신원 미확인은 따로 표시해. 참석 기록으로 업무 성과를 평가하지 말고 실제 계정 조회나 타인 공유는 하지 마.

### 주의

레시피의 세 명령은 계산·페이지 완결성·신원 검증을 자동 보장하지 않는다. 세 단계 모두 다음 페이지를 확인하고, 실패·권한 부족·결과 없음의 차이를 기록한다. 원문의 table 출력보다 계산에는 원본 구조를 보존하는 JSON이 적합하다.

회의 기록에는 만료 시각이 있고 공식 문서는 회의 종료 **30일 후 삭제**를 명시한다. 따라서 조회 결과가 없다는 사실만으로 참석하지 않았다고 결론 내리지 않는다. [ConferenceRecord 문서](https://developers.google.com/workspace/meet/api/reference/rest/v2/conferenceRecords)

회의 데이터는 개인정보일 수 있으므로 필요한 회의·항목만 조회하고 보고 범위와 보관 기한을 정한다. API의 실제 접근 가능 범위는 현재 사용자 권한과 OAuth scope에 달려 있다. 이 조사는 회의 참가자 정보를 실제로 가져오거나 공유하는 작업이 아니다.

## 5. recipe-bulk-download-folder

**Drive의 파일 바이트 다운로드와 네이티브 문서 내보내기를 구분하는 수집 레시피.**

- 출처: [SKILL.md](https://github.com/googleworkspace/cli/blob/a3768d0e82ad83cca2da97724e46bea4ff0e6dbd/skills/recipe-bulk-download-folder/SKILL.md)
- 선행 스킬: [gws-drive](https://github.com/googleworkspace/cli/blob/a3768d0e82ad83cca2da97724e46bea4ff0e6dbd/skills/gws-drive/SKILL.md), gws-shared
- 태그: `google-drive` `download` `export` `completeness-check`
- 난이도: 중급

### 무엇을 해주나

폴더의 파일을 목록으로 확인한 다음, 일반 파일은 media 응답으로 내려받고 Google Docs 같은 네이티브 문서는 지원 형식으로 내보내는 흐름이다. 이전 CSV 레시피가 Sheets의 표 표현을 다뤘다면 이번 항목은 **여러 MIME 유형의 파일 수집**을 다룬다.

다만 “모든 파일”이라는 제목과 달리 원문의 간단한 목록 명령은 하위 폴더 재귀 탐색·모든 페이지 처리·바로가기 대상 검토·중복 파일명 충돌 방지를 구현하지 않는다. 먼저 다운로드 manifest를 만들고 파일 ID, 이름, MIME, 저장 경로, 처리 상태를 분리하는 보강이 필요하다.

### 실전 프롬프트

> recipe-bulk-download-folder로 가상의 Drive 폴더 목록 fixture를 검사해 줘. 일반 파일, Google 문서, 하위 폴더, 바로가기를 분리하고 파일 ID 기반 충돌 없는 저장 이름과 완료 manifest를 설계해. 재귀 범위·휴지통 제외·페이지 누락·실패 재시도를 명시해. 실제 파일 다운로드, 기존 로컬 파일 덮어쓰기, 클라우드 삭제나 공유 설정 변경은 하지 마.

### 주의

Drive의 blob 다운로드는 `files.get`의 `alt=media`, 네이티브 문서 내보내기는 `files.export`를 구분한다. 일반 export에는 **10MB 제한**이 있고 모든 MIME 유형에 같은 출력 형식을 적용할 수 없다. 권한·다운로드 제한도 확인해야 한다. [공식 다운로드·내보내기 문서](https://developers.google.com/workspace/drive/api/guides/manage-downloads)

gws-shared는 `-o/--output`을 바이너리 응답 저장 옵션으로 안내한다. 저장 파일 존재뿐 아니라 성공 상태·파일 유형·예상 크기·manifest 건수를 확인하고 실패 응답을 정상 파일로 간주하지 않는다. 경로 구분자·예약 이름·같은 이름의 다른 파일 등은 로컬 플랫폼에 맞춰 처리한다. [공통 옵션](https://github.com/googleworkspace/cli/blob/a3768d0e82ad83cca2da97724e46bea4ff0e6dbd/skills/gws-shared/SKILL.md)

목록의 부모 조건은 직접 자식 범위다. 휴지통 제외 조건과 shared drive 지원 여부도 따로 정한다. gws의 `--page-all`에도 기본 최대 페이지 수가 있으므로 모든 결과를 가져왔는지는 남은 토큰으로 확인해야 한다. 다운로드는 원본 공유권한 변경과 별개이며, 로컬 사본의 접근·보관·삭제 정책을 새로 고려해야 한다.
