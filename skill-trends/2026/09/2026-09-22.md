### 무엇을 해결하나

`momentic-spec`은 코드를 먼저 고친 뒤 테스트를 맞추는 흐름을 거꾸로 뒤집는다. Agent가 `momentic.config.yaml`과 주변 테스트를 읽고, 영향을 받을 E2E 테스트를 먼저 특정한 다음 **테스트 변경분 자체를 제품 요구사항의 실행 가능한 명세**로 취급한다. 구현 코드는 테스트 diff를 검토한 뒤에만 수정하도록 순서를 강제해, Agent가 구현에 맞춰 테스트를 느슨하게 바꾸는 문제를 줄인다.

내부적으로는 Momentic의 테스트/모듈 자산과 프로젝트 설정을 읽고, 작은 코드 수준 검증을 반복하다가 내구성 있는 체크포인트에서 최소 영향 테스트 집합을 실행하는 방식이다. 즉 단순한 “TDD 하라” 프롬프트보다 E2E 명세와 구현 사이의 순서를 더 강하게 고정한다.

### 설치 및 사용

```bash
npx skills add https://github.com/momentic-ai/skills --skill momentic-spec
```

- Node.js/npx 필요.
- 실제 E2E 실행까지 하려면 Momentic을 사용하는 프로젝트와 `momentic.config.yaml` 등 해당 프로젝트의 Momentic 설정이 필요하다.
- Skill 페이지에서 별도 API Key 요구는 명시하지 않았다. 실제 Momentic 실행 환경의 인증/계정 요구는 프로젝트 설정에 따른다.

**Agent 예시 명령**

> 로그인 세션 만료 동작을 변경하려고 해. momentic-spec 절차대로 영향을 받는 E2E 테스트를 먼저 찾고 테스트를 제품 명세로 수정한 뒤, 테스트 diff를 검토하고 나서 구현 코드를 변경해줘.

**평가:** Hot 상위권이면서 “구현 → 테스트”가 아니라 “실행 가능한 제품 명세 → 구현”을 강제한다는 점이 실무적이다. 다만 Momentic을 사용하지 않는 프로젝트라면 적용 범위가 제한된다.

Fastify는 단순 라우트 작성보다 plugin encapsulation, schema 기반 validation/serialization, error handling, TypeScript, `inject()` 기반 테스트 같은 구조 규칙을 지키는 것이 중요하다. 이 Skill은 Agent가 “동작만 하는 코드”를 만드는 대신 Fastify의 플러그인 경계와 테스트 가능한 구조를 기본값으로 선택하도록 유도한다.

특히 route handler와 plugin 설계, validation/serialization, Fastify `inject` 테스트까지 한 흐름으로 다루기 때문에 Node.js 백엔드에서 프레임워크 관용구를 놓치는 문제를 줄이는 데 유용하다.

### 설치 및 사용

```bash

```

- Node.js/npx 필요.
- 별도 MCP/API Key/Docker 요구는 Skill 페이지에서 확인되지 않았다.
- 대상 프로젝트에 Fastify가 있어야 실제 코드 변경에 직접 활용하기 좋다.

**Agent 예시 명령**

> 이 Node.js API를 Fastify 플러그인 구조로 정리하고, 요청/응답 schema validation과 공통 error handling을 추가한 다음 `fastify.inject()` 기반 테스트까지 작성해줘.

**평가:** 설치 즉시 적용 가능하고, 성숙한 Node.js 프로젝트의 실제 설계 규칙을 Agent에 주입한다는 점이 강점이다. 다만 Fastify 전용이라 다른 백엔드 프레임워크에는 직접 적용되지 않는다.

### 무엇을 해결하나

기존의 일반 PyTorch 학습 루프를 여러 기관/사이트가 데이터를 공유하지 않고 함께 학습하는 **NVFLARE federated job**으로 변환한다. Agent는 먼저 `nvflare agent inspect source <path> --format json`으로 코드를 정적으로 조사해 모델 생성자, 체크포인트, 데이터 로더, metric, local step 수 등을 추출하고, 선택한 federation 방식에 맞는 recipe를 확인한 뒤 Client API의 `FLModel` 교환 구조로 훈련/평가 코드를 바꾼다.

중요한 점은 “PyTorch 코드를 대충 감싸는” Skill이 아니라는 것이다. recipe 선택 → 모델 교환 → `NUM_STEPS_CURRENT_ROUND` 같은 집계 메타데이터 → 검증 ladder → export/artifact 보고까지 단계가 정해져 있고, Lightning/Hugging Face/TensorFlow 같은 다른 소유 패턴은 별도 Skill로 라우팅한다. 이런 좁고 명시적인 경계가 Agent의 잘못된 자동 변환을 줄인다.

### 설치 및 사용

```bash
npx skills add https://github.com/NVIDIA/skills --skill nvflare-convert-pytorch
```

주요 요구사항:

- **NVFLARE >= 2.9.0**
- Python + PyTorch 프로젝트
- 표준 FedAvg의 경우 Skill이 `nvflare recipe show fedavg-pt --format json` 등 NVFLARE CLI를 사용해 recipe 계약을 확인
- PyTorch Lightning/Hugging Face Trainer 등은 이 Skill의 대상이 아니며 각각 전용 converter Skill로 라우팅

**Agent 예시 명령**

> `train.py`의 plain PyTorch training loop를 5개 site가 참여하는 NVFLARE FedAvg job으로 변환해줘. 먼저 source inspect로 모델/데이터/metric 의미를 추출하고, recipe 계약을 확인한 뒤 최소 validation ladder까지 실행해줘.

**평가:** 오늘 후보 중 가장 “Agent가 복잡한 전문 도메인의 변환 절차를 안전하게 수행하는 방식”을 잘 보여준다. 다만 NVFLARE/PyTorch라는 명확한 전문 영역에 한정된다.

기존 인덱스의 `systematic-debugging`과 주제는 가깝지만, 오늘 후보는 복수 가설을 병렬로 유지하고 증거 경쟁으로 탈락시키는 구조가 중심이라 동일 Skill/fork로 판단하지 않았다. 복수 Agent나 병렬 작업 기능과 결합하면 서로 다른 가설을 독립적으로 조사시키는 방식으로 확장하기 좋다.

### 설치 및 사용

AgentSkill.sh CLI를 처음 쓰는 경우:

```bash
npx @agentskill.sh/cli@latest setup
```

그 다음 Agent에서:

```text
/learn @wshobson/parallel-debugging
```

AgentSkill.sh의 programmatic install 응답은 플랫폼별 경로를 제공하며 Codex 경로는 다음과 같이 안내된다.

```text
~/.codex/skills/wshobson/parallel-debugging/SKILL.md
```

**Agent 예시 명령**

> 배포 후 간헐적으로 API가 504를 내는데 원인을 하나로 가정하지 말고 최소 4개의 경쟁 가설을 세워줘. 각 가설을 반증할 가장 값싼 로그/메트릭/재현 실험부터 병렬로 수집하고 증거표를 만들어 root cause를 좁혀줘.

**평가:** 범용성이 높고 최근 업데이트·대형 repository·100/100 보안 점수까지 갖춘 강한 후보다. 다만 단순 버그에는 절차가 과할 수 있어 복잡하고 재현이 어려운 문제에 쓰는 편이 낫다.

### 무엇을 해결하나

문서 전체를 막연히 “검토”하는 대신, 먼저 **검증 가능한 사실 주장**만 뽑아내고 기술 사양·버전·통계·API 제약 등으로 분류한 다음 공식 문서, 공식 발표, GitHub release, package registry 같은 권위 있는 1차 출처를 우선해 검증한다. 결과는 Accurate / Incorrect / Outdated / Unverifiable로 분리하고, 수정안을 만든 뒤 사용자의 승인 후 실제 문서를 변경하도록 되어 있다.

이 구조는 Agent가 최신 정보를 검색한 뒤 곧바로 문서를 덮어쓰는 위험을 줄이고, “어떤 주장에 어떤 근거를 적용했는지”를 남기는 데 유리하다. 다만 Skill 본문 안의 일부 예시 모델명/사양은 시간이 지나면 낡을 수 있으므로, Skill 자체 예시를 사실 근거로 쓰지 말고 항상 최신 공식 출처를 다시 확인해야 한다.

### 설치 및 사용

ClaudeSkills 페이지에 노출된 Claude Code용 정확한 명령:

```bash
npx skills add daymade/claude-code-skills --skill fact-checker --agent claude-code
```

페이지는 Codex 설치 탭도 제공하지만 정적 snapshot에 Codex용 명령 문자열이 노출되지 않아 임의로 추정하지 않았다.

**Agent 예시 명령**

> `docs/architecture.md`에서 버전 번호, API 제한, 성능 수치처럼 검증 가능한 주장만 추출해줘. 공식 문서와 공식 GitHub를 우선해 확인하고 Accurate/Incorrect/Outdated/Unverifiable 표를 만든 뒤, 수정은 내가 승인한 항목만 적용해줘.

**평가:** 문서 유지보수와 최신성 검증에 바로 쓸 수 있는 명확한 workflow다. 다만 웹 검색 품질과 출처 선택에 결과가 크게 좌우되며, 주관적 주장이나 논쟁적 사실에는 적합하지 않다.
