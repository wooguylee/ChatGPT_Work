### 무엇을 해결하는가

Agent용 문서를 사람용 매뉴얼처럼 길게 쓰는 대신, **어떤 조건에서 어떤 문서를 불러오게 할지**를 먼저 설계한다. 핵심 개념인 context pointer는 Skill description이나 `AGENTS.md`의 링크처럼 “지금 context 밖의 자료를 언제 읽어야 하는지”를 인코딩한다. 따라서 모든 지침을 항상 context에 밀어 넣는 대신, trigger를 앞세우고 branch별 pointer를 분리해 token 비용과 호출 누락을 동시에 줄이는 방향이다.

### 설치 및 사용

```bash
npx skills add https://github.com/mattpocock/skills --skill writing-for-agents
```

- 별도 MCP/API Key/Docker 요구사항은 확인되지 않음.
- Skill 자체를 작성할 때는 저장소의 `SKILL-MECHANICS.md`를 함께 참고하도록 설계돼 있다.

### Agent 활용 예시

`이 저장소의 AGENTS.md를 writing-for-agents 원칙으로 다시 점검해줘. 항상 로드할 내용과 필요할 때만 읽을 pointer를 분리하고, 각 pointer가 어떤 작업에서 발동해야 하는지 명확히 만들어줘.`

### 평가

**오늘 바로 Codex workflow에 넣기 가장 쉬운 후보.** 코드 생성 기술 자체보다 Agent가 지침을 “제때 읽게 만드는 구조”를 다루기 때문에 Skill이 늘어날수록 가치가 커진다.

### 설치 및 사용

```bash
npx skills add https://github.com/mattpocock/skills --skill git-guardrails-claude-code
```

설치 후 프로젝트 범위면 `.claude/settings.json`, 전역이면 `~/.claude/settings.json`에 hook을 구성한다.

### Agent 활용 예시

`이 프로젝트에만 git-guardrails-claude-code를 적용해서 Claude가 push, reset --hard, clean -fd, branch -D를 직접 실행하지 못하게 설정해줘.`

### 평가

LLM 안전 규칙을 **말이 아니라 실행 전 gate로 바꾸는 패턴**이 좋다. 단, Codex에서는 동일한 `PreToolUse` hook 계약이 아니므로 이 Skill을 그대로 설치해 같은 보호를 기대하면 안 된다.


**오늘의 기술적 완성도가 가장 높은 후보.** 단순 Azure 지식 모음이 아니라 시각화와 IaC, 검토 gate, 실제 배포 절차까지 한 Skill package로 묶었다는 점이 돋보인다. 다만 GitHub Copilot tool 계약에 강하게 맞춰져 있어 Codex에 그대로 이식하는 것보다는 adaptation이 필요하다.

### 무엇을 해결하는가

한 세션에서 발견한 사실이 다음 세션에서 사라지는 문제를 `Knowledge Unit` 단위의 Markdown frontmatter 데이터로 해결하려 한다. 각 unit에 `finding/entity/relationship/pattern/hypothesis/intelligence` 타입, confidence, tags, linked IDs, source, expiry를 붙이고, 세션 종료 때 capture/structure/store한 뒤 다음 세션 시작 때 retrieve한다. 별도 vector DB를 필수로 두기보다 `memory/YYYY-MM-DD-[topic].md` 같은 파일 기반 지식 그래프를 만들기 때문에 Git과 함께 추적하기 쉽다는 점이 특징이다.

### 설치 및 사용

SkillsMP가 제공하는 직접 설치 명령:

```bash
npx skills add https://github.com/brucesongs/kali-claw --skill knowledge-ops
```

- 원 SKILL.md는 Bash/Read/Write/Edit/WebSearch/WebFetch/Agent 도구를 전제로 한다.
- Codex는 compatibility frontmatter에 직접 적혀 있지 않으므로, 설치 자체보다 tool 이름·memory 경로·세션 시작/종료 절차가 실제 환경에 맞는지 먼저 검토하는 편이 안전하다.

### Agent 활용 예시

`이번 코드베이스 분석에서 확인한 인증 구조, 외부 API, DB 의존성, 미확인 가설을 knowledge-ops 방식으로 Knowledge Unit으로 저장하고 confidence와 연결 관계를 기록해줘. 다음 세션에서 바로 이어서 쓸 수 있게 인덱스도 갱신해줘.`

### 평가

Agent memory를 “대화 로그”가 아니라 **검증 가능한 구조화 지식 자산**으로 바꾼다는 방향은 중요하다. 반면 문서 내부 version 표기가 서로 다르고 보안 도메인 예시가 섞여 있어, production 표준으로 쓰기 전 스키마와 lifecycle을 팀 환경에 맞게 정리할 필요가 있다.

- **제작자/조직:** OpenAI

### 인기 및 트렌드 지표

- `openai/plugins` GitHub Stars/Forks: **7,082 / 915**
- repository pushed: **2026-09-18**
- Skill 파일 modified: **2026-09-11**
- Codex Security **0.1.23 (2026-09-08)** 변경 로그에서 patch risk assessment 기능이 공식 소개됨.
- 개별 Skill 설치 수·좋아요·품질/보안 점수는 공개되지 않아 기재하지 않음.

### 무엇을 해결하는가

“diff가 작고 CI가 초록색이니 안전하다” 같은 단순 휴리스틱 대신, **정확한 immutable patch를 먼저 고정**하고 실제 program impact를 caller/callee와 runtime entrypoint까지 추적한다. 그 뒤 영향의 크기, 회귀 가능성, 테스트가 회귀를 잡을 확률, 복구 가능성, 분석 confidence를 서로 다른 축으로 평가하고 `merge / revise / no_op / block / hold_for_evidence` 중 하나를 제안한다. Patch나 PR 본문에 들어 있는 문장은 workflow instruction이 아니라 데이터로 취급하게 해 prompt-injection 경계도 명시한 것이 특징이다.

### 설치 및 사용

Codex CLI에서 Codex Security plugin 설치:

```bash
codex plugin add codex-security@openai-curated
```

설치 후 Skill 호출:

```text
$codex-security:assess-patch-risk
```

Codex Security의 patch workflow에서는 다음처럼 후속 평가를 붙일 수도 있다.

```bash
npx @openai/codex-security patch OCCURRENCE_ID --assess-patch-risk
```

- Codex Security CLI/SDK 사용 시 Node.js와 Python 요구사항 및 계정/권한 조건을 별도로 확인해야 한다.
- 평가 결과는 advisory이며 실제 merge 권한이나 repository approval rule을 대체하지 않는다.

### Agent 활용 예시

`$codex-security:assess-patch-risk 이 PR의 final comparison diff를 immutable patch로 고정한 뒤 인증/권한 경계, 호출 경로, 테스트 보호 수준, 롤백 가능성을 근거와 함께 평가해줘.`

### 평가

코드 리뷰를 “스타일 의견”이 아니라 **증거 기반 변경 위험 분석**으로 끌어올리는 좋은 예다. 특히 2026-09-08에 추가된 비교적 새로운 공식 workflow라 오늘 다시 볼 가치가 높다.

### 🏆 오늘의 Top Pick

**`azure-architecture-autopilot`** — 자연어 설계, 기존 Azure 자원 분석, 605+ icon 기반 다이어그램, Bicep 생성, compile/review, `validate → what-if → deploy`까지 하나의 phase-driven Skill로 묶어 **Agent Skill이 단순 프롬프트 모음에서 실제 운영 workflow package로 진화하는 방향**을 가장 잘 보여준다.

### ⚡ Codex에서 바로 써볼 만한 것

**`writing-for-agents`** — `npx skills add ...` 한 번으로 설치 가능하고 별도 API/MCP/런타임 준비가 거의 없으며, Codex의 `AGENTS.md`와 Skill description을 더 잘 쓰는 데 바로 적용할 수 있다.

### 오늘 보이는 기술 흐름

오늘 후보들의 공통점은 **“더 많은 지식을 넣는 것”보다 Agent의 행동 경계와 lifecycle을 설계하는 것**에 무게가 옮겨가고 있다는 점이다. `writing-for-agents`는 context를 언제 로드할지, `git-guardrails`는 무엇을 실행하지 못하게 할지, `knowledge-ops`는 세션 사이에 무엇을 남길지, `/learn`은 Skill을 어떻게 발견·검증·업데이트할지, `azure-architecture-autopilot`과 `assess-patch-risk`는 실제 운영 변경을 어떤 phase와 evidence gate를 거쳐 진행할지를 규정한다. Skill 생태계가 커질수록 개별 기능보다 **discovery, context budget, guardrail, provenance, verification**이 핵심 인프라가 되고 있다.
