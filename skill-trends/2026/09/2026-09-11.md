특히 PRD·ADR·issue·commit·diff처럼 이미 파일에 있는 정보는 다시 붙여 넣지 않고 참조만 남기며, API key·password·개인정보는 제거하도록 명시한다. 즉 더 큰 context window에 의존하는 대신 **작고 검증 가능한 인계 artifact**를 만드는 방식이다.

### 설치 및 사용

```bash

```

별도 MCP/API Key는 필요하지 않는다. 결과 파일은 현재 프로젝트가 아니라 OS temp 디렉터리에 저장하는 것이 Skill의 기본 규칙이다.

### 활용 예시

```text
$handoff 다음 세션에서는 Windows 파일 관리자 프로젝트의 문서 분류 파이프라인 구현부터 이어갈 거야. 이미 만든 계획과 코드 경로는 중복해서 복사하지 말고 링크/경로로 참조하고, 다음 Agent가 바로 시작할 수 있게 인수인계 문서를 만들어줘.
```

### 평가

### 무엇을 해결하나

Agent에게 큰 계획을 그대로 주면 한 컨텍스트 안에서 너무 많은 계층을 동시에 바꾸거나, 작업 순서를 잘못 잡아 중간 상태가 깨지기 쉽다. `to-tickets`는 계획·스펙·현재 대화를 **tracer-bullet vertical slice**로 나누고, 각 티켓이 schema/API/UI/test를 가로지르는 완결된 작은 동작을 만들도록 한다.

각 티켓은 한 번의 fresh context window에 들어갈 크기로 제한하고 `Blocked by` edge를 명시해 사실상 실행 가능한 DAG를 만든다. 넓은 기계적 refactor는 억지로 vertical slice로 쪼개지 않고 expand→migrate batches→contract 순서로 처리하며, 실제 issue tracker에 publish하기 전에 사용자에게 granularity와 dependency를 확인받는다.

### 설치 및 사용

```bash
npx skills add https://github.com/mattpocock/skills --skill to-tickets
```

이 Skill은 `disable-model-invocation: true`로 설정되어 있어 Agent가 임의로 부르는 용도보다 사용자가 `/to-tickets`처럼 명시적으로 시작하는 workflow다. GitHub Issues·Linear·로컬 `.scratch/` 등 사용할 tracker와 triage label vocabulary를 먼저 설정하는 것이 권장된다.

### 활용 예시

```text
/to-tickets 이 파일 관리자 프로그램의 “이미지 유사도 클러스터링” 기능 계획을 한 컨텍스트에서 완료 가능한 vertical slice 티켓들로 나눠줘. 각 티켓의 Blocked by 관계를 만들고, 내가 승인하기 전에는 GitHub Issue를 생성하지 마.
```

### 평가

**오늘 볼 가치:** Agent 작업을 단순 TODO 목록이 아니라 **독립 실행 가능한 vertical slice + dependency graph**로 바꿔 병렬 Agent와 장기 프로젝트에 특히 잘 맞는다. 단, tracker 설정이 없거나 너무 작은 변경에는 오히려 관리 ceremony가 커질 수 있다.


Codex 권장 설치 위치는 AgentSkill.sh 안내 기준 `~/.codex/skills/affaan-m/orch-pipeline/SKILL.md`다. **주의:** 이 Skill은 공통 엔진이라 보통 직접 호출하지 않고 `orch-add-feature`, `orch-fix-defect`, `orch-refine-code`, `orch-build-mvp` 같은 operation Skill이 이를 참조하도록 쓰는 것이 설계 의도다.

### 활용 예시

```text
orch-fix-defect 흐름으로 이 인증 버그를 처리해줘. 먼저 작업 크기를 분류하고 재현 테스트를 만든 다음 계획을 보여줘. 내가 Gate 1을 승인하기 전에는 구현하지 말고, auth 변경이므로 security-reviewer를 포함해줘.
```

### 평가

**오늘 볼 가치:** 최근 업데이트와 활발한 upstream 활동에 더해, Agent autonomy를 “전부 자동”이 아니라 **작업 규모별 ceremony + 명시적 human gate**로 제어하는 구조가 좋다. 단, ECC 전체 agent/command 체계를 함께 쓸 때 가치가 크며 단일 SKILL.md만 떼어 쓰면 일부 delegate가 없어 기능이 축소된다.

## 6. `qodo-review`

- **출처:** **OpenAI 공식 Codex curated marketplace**에서 최근 Qodo plugin 채택 + Qodo upstream Skill
- **OpenAI marketplace 저장소:** https://github.com/openai/plugins
- **OpenAI marketplace 반영 commit:** https://github.com/openai/plugins/commit/d416fd5a43426019986b1e489506db3db66dee3d
- **원본 Skill:** https://github.com/qodo-ai/qodo-skills/blob/main/codex-packages/qodo/skills/qodo-review/SKILL.md
- **원본 저장소:** https://github.com/qodo-ai/qodo-skills
- **제작자/조직:** Qodo
- **Skill metadata:** **v1.10.2**, Qodo plugin manifest **v2.0.8**
- **지원 Agent:** 공식 Codex marketplace 배포가 명시되어 있고, Qodo CLI를 사용할 수 있는 coding-agent 환경에서 동작

### 인기 및 트렌드 지표

- OpenAI `openai/plugins`가 **2026-09-08 17:57 UTC (2026-09-09 02:57 KST)**에 Qodo core plugin을 standard/API-key curated marketplace 양쪽에 추가
- OpenAI marketplace source: `qodo-ai/qodo-skills`의 `codex-packages/qodo`
- Qodo upstream GitHub 최신 snapshot: **52★ / 7 forks**
- Qodo upstream 최근 push: **2026-09-11 06:38 KST**
- OpenAI `plugins` repo snapshot: **6,384★ / 839 forks**
- 공식 marketplace/원본 저장소에 이 개별 Skill의 설치 수·Quality/Security 점수는 노출되지 않아 추정하지 않음

### 무엇을 해결하나

일반 PR review bot은 이미 push된 diff와 repository context는 볼 수 있지만, 코딩 세션 중 “왜 이 선택을 했는지”, 어떤 ticket/spec/design을 따라갔는지는 놓치기 쉽다. `qodo-review`는 PR을 만들기 **전** 로컬 working tree의 uncommitted/unpushed diff와 session context를 Qodo review engine에 함께 보내고, structured finding을 받아 사용자가 승인한 수정만 적용하도록 한다.

또한 `--deep`/`--fast`, pathspec, base branch, ticket URL, JSON 결과, async execution과 progress channel을 정의해 긴 review를 Agent가 다룰 수 있게 한다. 특히 result와 progress를 분리하고, review가 끝나기 전 임의로 실패 이유를 추정하지 않는 규칙은 외부 장기 작업을 Agent workflow에 붙이는 좋은 사례다.

### 설치 및 사용

**Codex 권장:** OpenAI 공식 curated marketplace의 **Qodo** plugin을 설치하면 `qodo-review`, `qodo-codebase-wisdom`, `qodo-review-resolver`, `qodo-setup`이 함께 제공된다. 공식 marketplace entry는 다음 upstream path를 가리킨다.

```text
https://github.com/qodo-ai/qodo-skills.git
codex-packages/qodo
```

Plugin 설치 뒤 먼저 `$qodo-setup`으로 Qodo CLI 설치/브라우저 로그인/도구 카탈로그 검증을 수행한다. `qodo-review`는 Qodo CLI **0.1.0-next.37 이상**과 인증이 필요하며, 기본 사용은 다음과 같다.

```bash
qodo --version
qodo review --context-file .qodo/session-context.json --json --progress
```

Qodo가 제공하는 정확한 flag는 실행 환경의 `qodo review --help`로 다시 확인한다.

### 활용 예시

```text
$qodo-review 아직 push하지 않은 이 변경을 origin/main 기준으로 검토해줘. 이번 변경의 목적과 설계 결정을 session context에 포함하고, finding은 먼저 보여준 뒤 내가 승인한 것만 수정해줘. PR은 만들지 마.
```

### 평가

**오늘 볼 가치:** OpenAI가 불과 며칠 전 Codex curated marketplace에 Qodo를 추가했고 upstream도 오늘 업데이트되어, “코딩 중 Agent의 세션 문맥을 외부 review engine에 넘기는 pre-PR 검증”이 본격적인 plugin workflow로 들어온 사례다. **주의:** 로컬 diff와 session context가 Qodo 서비스로 전송되므로 회사 소스코드·고객정보·비밀정보가 포함된 저장소에서는 조직의 외부 전송 정책과 Qodo 약관/프라이버시 정책을 먼저 확인해야 한다.

### 🏆 오늘의 Top Pick

**`qodo-review`** — 최근 OpenAI Codex curated marketplace에 편입된 시점성, 로컬 diff뿐 아니라 **coding-session의 이유와 결정 문맥까지 review 입력으로 사용**한다는 독창성, structured result/async/progress까지 Agent-friendly하게 설계한 실무성을 종합해 오늘의 Top Pick으로 선정했다. 다만 외부 서비스 전송 정책을 확인할 수 있는 환경에서 쓰는 것이 전제다.

### ⚡ Codex에서 바로 써볼 만한 것

**`handoff`** — `npx skills add ... --skill handoff`만으로 설치할 수 있고 MCP/API Key가 필요 없다. 긴 Codex 세션을 끝낼 때 artifact 경로와 결정만 압축해 새 세션으로 넘기므로, 현재 개발 workflow에 가장 낮은 비용으로 바로 붙일 수 있다.

### 오늘 보이는 공통 흐름

오늘은 Skill이 “좋은 프롬프트 모음”에서 **Agent 작업의 경계와 상태를 명시적으로 관리하는 실행 프로토콜**로 이동하는 흐름이 강하다. `handoff`는 세션 경계, `to-tickets`는 작업/의존성 경계, `systematic-debugging`은 조사와 수정의 경계, `orch-pipeline`은 human approval 경계, `qodo-review`는 로컬 구현과 PR 사이의 검증 경계를 만든다. 여기에 `supabase`처럼 vendor가 최신 문서와 보안 규칙을 직접 Skill에 넣는 방식이 합쳐지면서, 앞으로 중요한 Skill은 단순 지식량보다 **언제 멈추고, 무엇을 검증하고, 어떤 상태를 다음 단계로 넘길지**를 얼마나 명확히 정의하는지가 경쟁력이 될 가능성이 높다.
