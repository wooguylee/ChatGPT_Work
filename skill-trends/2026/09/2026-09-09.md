### 무엇을 해결하나

보통 “TDD를 해라”라고 Agent에게 말하면 테스트를 한꺼번에 먼저 만들고 구현을 나중에 몰아서 하는 **수평 슬라이스**로 흘러가기 쉽다. 이 Skill은 한 동작에 대해 `RED → 최소 구현 → GREEN → 다음 동작`을 반복하는 **수직 슬라이스**를 강제하고, 내부 함수나 mock 호출 횟수 대신 공개 인터페이스에서 관찰되는 행동을 테스트하도록 한다.

특히 테스트를 쓸 위치를 “seam”으로 정의하고, 테스트 작성 전 어떤 seam을 검증할지 먼저 합의하게 한다. 그래서 Agent가 리팩터링에 쉽게 깨지는 implementation-coupled 테스트를 대량 생성하는 문제를 줄이는 데 유용하다.

### 설치 및 사용

```bash
npx skills add https://github.com/mattpocock/skills --skill tdd
```

별도 MCP/API Key는 필요하지 않는다. 프로젝트에 `CONTEXT.md`나 ADR이 있으면 Skill이 해당 도메인 용어와 설계 결정을 먼저 읽도록 지시한다.

### 활용 예시

```text
이 결제 API에 쿠폰 중복 적용 버그를 고쳐줘. tdd skill을 사용해서 공개 인터페이스 기준의 재현 테스트부터 만들고, 한 테스트씩 red-green-refactor로 진행해줘.
```

### 평가

**오늘 볼 가치:** 설치 부담이 거의 없는데도 Agent가 테스트 코드를 “많이” 만드는 대신 **리팩터링에 살아남는 테스트를 단계적으로 만드는 방식**으로 행동을 바꾼다. 단, 아주 작은 수정에도 seam 합의 절차가 들어가면 다소 느리게 느껴질 수 있다.

### 무엇을 해결하나

Agent에게 “아키텍처를 개선해줘”라고 하면 `service`, `component`, `layer` 같은 포괄적인 단어로 추상화만 늘리는 경우가 많다. `codebase-design`은 **module / interface / implementation / depth / seam / adapter**라는 제한된 설계 언어를 사용하고, 핵심 목표를 “작은 interface 뒤에 많은 behavior를 숨기는 deep module”로 고정한다.

즉 파일 수나 레이어 수를 늘리는 것이 아니라, caller가 알아야 할 지식을 줄이고 변경 지점을 한곳에 모으는 **leverage와 locality**를 설계 기준으로 삼는다. 테스트 역시 내부 구현이 아니라 seam의 interface를 통해 가능해야 한다는 점에서 `tdd`와 잘 맞는다.

### 설치 및 사용

```bash
npx skills add https://github.com/mattpocock/skills --skill codebase-design
```

추가 런타임이나 API Key는 필요 없다.

### 활용 예시

```text
이 Node.js 백엔드의 auth/payment 모듈 경계를 codebase-design 관점에서 검토해줘. shallow module과 불필요하게 넓은 interface를 찾아서 deep module로 만드는 2~3개 대안을 비교해줘.
```

### 평가

**오늘 볼 가치:** Agent 아키텍처 대화를 추상적인 “클린 코드” 조언에서 **측정 가능한 interface 깊이와 seam 설계**로 옮겨준다. 다만 이 용어 체계를 강하게 따르므로 기존 팀의 DDD/Hexagonal 용어와 충돌할 수 있어, 팀 표준이 이미 있다면 번역 규칙을 정하는 편이 좋다.

### 무엇을 해결하나

`hyperframes`는 단순 “영상 생성 프롬프트 모음”이 아니라 영상 요청을 받아 **어떤 하위 workflow가 소유할지 결정하는 front-door/orchestrator Skill**이다. 웹사이트, GitHub PR, Figma, 텍스트 brief, 기존 영상, 음악 같은 입력을 받아 slideshow, embedded captions, talking-head recut, music-to-video, PR-to-video, product launch, faceless explainer 등 전문 workflow로 라우팅한다.

핵심 구조는 HTML/DOM의 `data-*` timing 속성과 seekable animation runtime을 사용해 영상을 **코드처럼 재현 가능하게 렌더링**하는 것이다. Agent가 한 번의 거대한 영상 프롬프트를 만드는 대신 프로젝트 상태를 유지하면서 lint/check/preview/render 단계로 반복 검증할 수 있다는 점이 기존 생성형 영상 workflow와 다르다.

### 설치 및 사용

```bash
npx skills add https://github.com/heygen-com/hyperframes --skill hyperframes
```

하위 workflow는 필요에 따라 HyperFrames CLI가 갱신한다.

```bash
npx hyperframes skills update <workflow-name>
npx hyperframes@latest upgrade --project . --check
npx hyperframes check
```

영상 렌더링 경로에 따라 Node.js, 브라우저/Puppeteer 계열 런타임, FFmpeg 및 클라우드 렌더링 설정 등이 추가로 필요할 수 있다. 정확한 요구사항은 선택된 하위 workflow의 문서를 따라야 한다.

### 활용 예시

```text
이 GitHub PR의 변경 내용을 개발자용 45초 설명 영상으로 만들어줘. hyperframes를 front door로 사용하고, PR-to-video workflow를 선택해서 storyboard → preview → 최종 render까지 검증해줘.
```

### 평가

**오늘 볼 가치:** Agent Skill이 단순 지식 파일을 넘어 **미디어 제작의 상태·라우팅·검증을 관리하는 오케스트레이터**로 진화한 사례다. 단점은 영상 툴체인이 무겁고, 간단한 단일 클립에는 일반 영상 생성 API보다 준비 비용이 크다.

- SkillsMP에 별도 품질/보안 점수는 노출되지 않아 추정하지 않음

> 위 수치는 조사 당시 snapshot이다.

### 무엇을 해결하나

대부분의 Agent 메모리는 “지난 대화 몇 개를 검색해 프롬프트에 다시 넣기” 수준이다. OpenViking은 장기 memory, 세션 archive, 문서/RAG resource, Agent Skill, 대형 tool result를 `viking://...` 가상 URI 체계 아래 묶고, 검색 과정 자체를 추적할 수 있는 **Context Database**로 취급한다.

OpenClaw는 실행과 tool invocation을 담당하고, OpenViking은 `assemble`에서 압축 세션+recall을 주입하고 `afterTurn`에서 새 turn을 누적하며 `compact` 때 비동기 추출/commit을 수행한다. `ov_recall_trace`로 “왜 이 기억이 검색됐는지” 추적할 수 있고, 큰 tool output을 별도 저장한 뒤 search/read로 부분 회수할 수 있어 장기 실행 Agent의 context 비용과 디버깅 문제를 함께 다룬다.

### 설치 및 사용

Skill 자체는 SkillsMP에서 다음처럼 설치할 수 있다.

```bash
npx skills add https://github.com/volcengine/OpenViking --skill openviking-context-database
```

하지만 이 Skill은 **이미 설치된 OpenViking 서버와 OpenClaw plugin을 운영하는 Skill**이다. 첫 설치에는 `install-openviking-memory` workflow가 권장된다. 정상 설정 예시는 다음과 같다.

```bash
openclaw openviking setup --base-url <OPENVIKING_URL> --api-key <API_KEY> --json
openclaw openviking status --json
openclaw config get plugins.entries.openviking.config
openclaw config get plugins.slots.contextEngine
```

필수/주의 사항:
- `@openviking/openclaw-plugin`
- 별도 실행 중인 OpenViking 서버(이 plugin은 remote-only)
- 필요 시 API Key
- 로컬 파일 import 시 plugin의 업로드 경로를 사용하고 raw 로컬 경로를 원격 서버로 직접 보내지 않음
- AGPL-3.0이므로 배포 형태에서 라이선스 의무 검토 필요

### 활용 예시

```text
지난 세션에서 결정한 PostgreSQL 복제 방식과 관련 문서를 OpenViking에서 찾아줘. 먼저 memory_recall로 찾고, 정확한 명령이 부족하면 archive search를 사용한 뒤 어떤 recall trace로 선택됐는지도 보여줘.
```

### 평가

**오늘 볼 가치:** Agent의 memory/RAG/skill/tool-output을 따로 관리하지 않고 **하나의 장기 context 계층으로 통합**한다는 점에서 향후 장기 실행 Agent 인프라의 방향성을 잘 보여준다. 단, 즉시 설치해 쓰는 가벼운 Skill이 아니라 서버+OpenClaw plugin이 필요한 인프라형 구성이고 AGPL 라이선스도 확인해야 한다.

### 무엇을 해결하나

복잡한 Agent 시스템 장애에서 로그를 처음부터 끝까지 읽는 방식은 신호보다 잡음이 많다. 이 Skill은 증상에 맞는 로그를 먼저 고르고, **“요청이 어디까지 정상 통과했고 어디서 증거가 끊기는가”라는 proof path**를 만들어 model/provider/tool/plugin 중 실패 계층을 좁히도록 한다.

즉 단순 오류 메시지 해석보다 재현→관련 로그 선택→증거 경로 확인→가설 검증 순으로 문제를 압축하는 디버깅 discipline에 가깝다. OpenClaw처럼 모델, provider, tool, gateway가 함께 움직이는 시스템에서 특히 유용하다.

### 설치 및 사용

AgentSkill.sh CLI를 처음 사용하는 경우:

```bash
npx @agentskill.sh/cli@latest setup
```

그 뒤 AgentSkill.sh에서:

```text
/learn @openclaw/openclaw-debugging
```

Agent가 직접 설치할 경우 AgentSkill.sh API가 `skillMd`, companion files, `installPath`를 반환한다. Codex의 제안 설치 경로는:

```text
~/.codex/skills/openclaw/openclaw-debugging/SKILL.md
```

### 활용 예시

```text
OpenClaw에서 tool 호출은 시작되는데 응답이 중간에 사라진다. openclaw-debugging 방식으로 재현 가능한 proof path를 만들고, model/provider/tool/gateway 중 어느 단계에서 증거가 끊기는지 찾아줘.
```

### 평가

**오늘 볼 가치:** 전날 업데이트됐고 원본 저장소도 오늘까지 활발히 움직이며, 92/100 품질·100/100 보안 평가까지 확인된다. 다만 내용이 OpenClaw 내부 운영에 강하게 특화되어 일반 Node.js 앱 디버깅에는 과도하다.

### 무엇을 해결하나

정적 분석이나 Agent 보안 리뷰는 “위험해 보이는 코드 패턴”을 finding으로 내는 데는 강하지만, 그 코드가 실제 공격 표면에서 **공격자가 도달 가능한지** 판단하지 못하면 false positive가 많아진다. `attack-path-analysis`는 검증된 finding을 source→sink 경로, 서비스 노출, identity/privilege/trust boundary, secret/data flow, reachability, 기존 mitigation으로 다시 구성해 “실제 attacker story”로 만든다.

특히 중요한 점은 자신이 세운 공격 가설만 강화하지 않고, **가장 강한 repository counterevidence를 일부러 찾도록 강제**한다는 것이다. 공격 경로 분석, severity calibration, 최종 policy suppression을 서로 다른 단계로 분리해 Agent가 “심각해 보인다”는 인상만으로 severity를 올리는 문제를 줄인다.

### 설치 및 사용

이 Skill은 독립 `npx skills add` 패키지가 아니라 공식 `codex-security` plugin에 포함된다. 공식 plugin manifest는 `skills`, MCP server, app surface를 함께 묶는다.

현재 Codex에서 plugin manager를 사용할 수 있는 빌드라면 `codex-security` plugin을 설치한 뒤 사용한다. CLI 구문은 Codex 빌드에 따라 달라질 수 있으므로 먼저 확인한다.

```bash
codex plugin --help
codex plugin install codex-security
```

공식 저장소의 기본 marketplace는 `.agents/plugins/marketplace.json`이며 `plugins/` 디렉터리를 가리킨다. 설치 UI가 제공되는 환경에서는 **Codex Plugins → codex-security** 경로를 사용하는 것이 더 안전하다.

주의: 이 Skill은 전체 보안 스캔의 1차 trigger가 아니라, 이미 finding이 있거나 사용자가 명시적으로 source-to-sink 공격 경로 분석을 요청했을 때 쓰는 phase skill이다.

### 활용 예시

```text
이 SSRF finding을 attack-path-analysis로 검토해줘. 외부 entry point부터 sink까지 실제 도달 경로를 repository evidence로 증명하고, 반대 증거도 찾아서 severity와 reportability를 따로 결정해줘.
```

### 평가

**오늘 볼 가치:** OpenAI 공식 Codex Skill이 단순 취약점 탐지에서 한 단계 더 나아가 **공격 가능성, 반증, severity, 정책 판단을 구조화된 단계로 분리**하고 있다는 점이 중요하다. 단독으로 쓰는 범용 Skill이 아니라 Codex Security workflow 안에서 가장 가치가 크다.
