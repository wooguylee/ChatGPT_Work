### 무엇을 해결하나

이 Skill은 결제 자체를 수행하는 Skill이 아니라, Agent가 Stripe Link 기능을 쓰기 전에 **Link CLI를 설치하고 인증·권한 범위를 올바르게 잡는 진입점**이다. 먼저 `auth status`로 기존 세션을 확인하고, 결제와 금융 인사이트 중 필요한 범위만 선택해 `login` 또는 `upgrade`를 사용한다. 인증 흐름에서 verification/approval URL을 사용자에게 명확히 넘기고 access token이나 credential 파일 내용을 노출하지 않도록 규칙이 박혀 있어, “Agent가 돈을 쓸 수 있게 한다”보다 **사용자 승인과 최소 권한을 결제 Agent의 계약으로 만든다**는 점이 핵심이다.

### 설치 및 사용

Skill 설치:

```bash
npx skills add https://github.com/stripe/link-cli --skill link-cli
```

Link CLI가 없다면:

```bash
npm install -g @stripe/link-cli
```

글로벌 설치 없이 실행하려면 모든 `link-cli` 명령을 `npx @stripe/link-cli@latest`로 대체할 수 있다.

첫 확인 명령:

```bash
link-cli auth status --format json
```

**추가 요구사항:** Link 계정/인증, 사용자 approval. 결제 단계는 이 Skill이 아니라 저장소의 `create-payment-credential` 같은 후속 Skill로 넘긴다. 인증 자체가 개별 구매 승인을 뜻하지는 않는다.

### 활용 예시

> Codex에서 Stripe Link를 이용한 구매 Agent를 준비하고 싶어. 먼저 link-cli Skill 기준으로 현재 인증 상태를 확인하고, 결제에 꼭 필요한 scope만 요청해. 승인 URL이 나오면 나에게 보여주고 토큰이나 credential 파일 내용은 절대 출력하지 마.

### 평가

**오늘 볼 가치:** 결제 Agent가 실제 경제 행동으로 확장될 때 필요한 **권한 최소화 + 명시적 사용자 승인 + credential 비노출** 패턴을 Stripe가 Skill 형태로 제공한다는 점이 매우 중요하다.  
**주의:** 금전이 오가는 기능이므로 자동화 범위를 넓히기 전에 거래 한도·승인 지점·감사 로그를 별도로 설계하는 편이 안전하다.

### 평가

**오늘 볼 가치:** Agent용 업무 자동화가 “API 사용법을 기억하는 Skill”에서 **플랫폼 자체가 제공하는 최신 실행 레시피를 동적으로 해석하는 Skill**로 진화하는 좋은 사례다.  
**주의:** Salesforce Unified Catalog와 headless-360 MCP에 강하게 종속되며, org 라이선스나 권한이 없으면 Skill만 설치해도 사용할 수 없다.

### 인기 및 트렌드 지표

- 현재 원 GitHub snapshot: **87 Stars / 19 Forks**.

### 무엇을 해결하나

이 Skill은 “작업 목록을 어떻게 보여줄까”가 아니라 **Agent runtime이 일을 어떤 상태 머신으로 보유해야 하는가**를 다룬다. local shell, local/remote agent, teammate, background task를 typed family로 나누고 `owner + status + inputs + blockers + cancellation semantics`를 host-owned store에 보관하며, claim/release·blocker·retry·foreground/background·abort vs kill을 명시적으로 구분한다. 특히 여러 worker가 같은 task를 집어가는 double-claim, 중단된 background task가 UI에서는 계속 도는 것처럼 보이는 문제 등 실제 동시성 실패를 설계 단계에서 잡게 한다.

### 설치 및 사용

```bash
npx skills add https://github.com/vasilyu1983/AI-Agents-public --skill ai-coding-agents-tasks
```

**추가 요구사항:** 핵심 설계 리뷰는 별도 MCP/API Key 없이 사용 가능하다. 실제 구현에서는 선택한 scheduler, durable store, queue/worker 시스템이 후속 의존성이 될 수 있다.

### 활용 예시

> Codex 기반 background worker 기능을 설계하려고 해. ai-coding-agents-tasks 기준으로 local agent, remote agent, teammate task를 타입으로 분리하고 claim/release, blocker, retry, pending permission, abort와 kill의 차이를 포함한 task state machine과 저장 스키마를 제안해줘.

### 평가

**오늘 볼 가치:** coding agent가 단일 채팅 세션에서 벗어나 background·remote·multi-worker 실행으로 가면서 **task lifecycle 자체가 핵심 인프라**가 되고 있다는 흐름을 잘 정리한다.  
**주의:** 구현 라이브러리를 제공하는 Skill이 아니라 architecture/reference 성격이 강하므로 바로 실행 가능한 도구를 기대하면 맞지 않는다.

- 현재 원 GitHub snapshot: **87 Stars / 19 Forks**.
- repo updated: **2026-09-07**, 최근 push: **2026-09-02**.
- Skill version: **1.5**, `last_validated: 2026-08-15`.
- SkillsMP 개별 설치 수·좋아요·품질/보안 점수는 확인할 수 없어 미기재.

### 무엇을 해결하나

Agent에게 “위험한 명령은 하지 마”라고 프롬프트로만 말하면 모델 판단에 의존하지만, 이 Skill은 정책을 **모델 바깥의 lifecycle hook**으로 옮긴다. Claude Code에서는 pre/post tool·session·subagent·worktree 등의 hook을 사용하고, Codex에서는 안정성이 필요한 알림/콜백은 `notify`를 우선하며 새로운 lifecycle hooks는 실제 runtime에서 firing 여부를 검증하도록 안내한다. 결과적으로 preflight, destructive-command guardrail, audit trail, 자동 검사, budget/iteration cap 같은 통제를 prompt가 아니라 실행 경로에 걸 수 있다.

### 설치 및 사용

```bash
npx skills add https://github.com/vasilyu1983/AI-Agents-public --skill agents-hooks
```

**추가 요구사항:** 대상 runtime의 hook/notification 설정과 로컬 script 실행 환경. Claude Code 예시는 shell hook을 많이 사용하므로 `bash`/`shellcheck` 등이 필요할 수 있다. Codex에서는 현재 설치 버전에서 해당 hook/notify surface가 실제 firing되는지 먼저 테스트해야 한다.

### 활용 예시

> Codex에서 `git push --force`, 대규모 삭제, 운영 배포 전에 preflight 검사를 걸고 싶어. agents-hooks 기준으로 지금 Codex에서 신뢰할 수 있는 notify/hook surface를 구분하고, 실패 시 fail-closed가 필요한 항목과 단순 audit 알림 항목을 나눠 설정안을 만들어줘.

### 평가

**오늘 볼 가치:** Agent 안전성을 “잘 써놓은 지침”에서 **실행 전후에 강제되는 runtime control**로 바꾸는 방향은 앞으로 autonomy가 커질수록 더 중요해진다.  
**주의:** Claude와 Codex의 hook 기능을 동일하다고 보면 안 되며, 특히 Codex lifecycle hook은 버전별 동작 차이를 실제 환경에서 검증해야 한다.

### 설치 및 사용

AgentSkill.sh CLI 구성:

```bash
npx @agentskill.sh/cli@latest setup
```

그 뒤 Agent 안에서:

```text

```

**추가 요구사항:** [standardagents/dmux](https://github.com/standardagents/dmux) 설치와 `tmux`가 필요하다. Skill 원본은 외부 dmux 패키지를 설치하기 전에 해당 저장소를 검토하라고 안내한다.

### 활용 예시

> dmux-workflows를 사용해서 이 저장소의 인증 리팩터링을 3개 pane으로 나눠줘. 1번은 보안·호환성 조사, 2번은 구현, 3번은 회귀 테스트를 맡기고 서로 같은 파일을 수정하지 않게 worktree 경계를 정한 뒤 마지막에 결과를 합쳐 검증해줘.

### 평가

**오늘 볼 가치:** 특정 vendor의 subagent API에 묶이지 않고 **서로 다른 coding-agent harness를 OS process/pane 수준에서 조율**하는 방식이라 이식성과 디버깅 가능성이 높다.  
**주의:** 각 pane이 별도 Agent 세션이므로 토큰/API 비용과 merge conflict가 빠르게 늘 수 있고, 상호 의존성이 강한 작업은 병렬화가 오히려 느려질 수 있다.

## 6. migrate-to-codex

- **출처:** [OpenAI 공식 Skills Catalog](https://github.com/openai/skills) / [`migrate-to-codex/SKILL.md`](https://github.com/openai/skills/blob/main/skills/.curated/migrate-to-codex/SKILL.md)

### 무엇을 해결하나

Claude Code를 오래 쓴 프로젝트를 Codex로 옮길 때 `CLAUDE.md`, `.claude/commands`, `.claude/agents`, `.mcp.json`, hooks를 하나씩 손으로 번역하면 누락과 의미 변화가 생기기 쉽다. 이 Skill은 먼저 `--scan-only`, `--plan`, `--doctor`로 source surface를 조사하고, instructions → hooks → skills/commands → config/MCP → subagents 순으로 Codex artifact를 생성한 뒤 **dry-run → 실제 migration → manual block 수정 → `--validate-target` → 재검증**을 반복한다. 원본 Claude 파일은 수정하지 않고 기존 Codex config의 unrelated setting도 보존하도록 명시되어 있어 단순 복사 도구보다 **검증 가능한 migration pipeline**에 가깝다.

### 설치 및 사용

Codex에는 `skill-installer` system Skill이 기본 제공되므로, Codex에서 다음처럼 요청하는 것이 공식 경로다.

```text
$skill-installer migrate-to-codex를 설치해줘
```

설치 후 다음 turn부터 `migrate-to-codex`를 사용할 수 있다.

Skill이 제공하는 대표 점검 흐름:

```bash
$MIGRATE_TO_CODEX --source ./.claude/ --target ./.codex/ --plan
$MIGRATE_TO_CODEX --source ./.claude/ --target ./.codex/ --dry-run
$MIGRATE_TO_CODEX --source ./.claude/ --target ./.codex/
$MIGRATE_TO_CODEX --validate-target ./.codex/
```

**추가 요구사항:** Python 3, 변환할 Claude Code artifact, Codex 프로젝트/글로벌 target. 실제 migration 전에 plan과 dry-run을 읽는 것이 중요하다.

### 활용 예시

> 이 프로젝트의 `.claude/`와 `.mcp.json`을 Codex로 이전해줘. migrate-to-codex 방식대로 scan/plan/doctor를 먼저 실행하고 dry-run 결과를 검토한 뒤 `.agents/skills`, `.codex/agents`, `.codex/config.toml`, `.codex/hooks.json`으로 변환하고 validate-target이 통과할 때까지 수정해. 원본 Claude 파일은 건드리지 마.

### 평가

**오늘 볼 가치:** Claude Code와 Codex를 병행하거나 이전하려는 개발자에게 바로 필요한 **실제 ecosystem migration 도구**이며, source 보존과 반복 검증까지 포함한 점이 단순 변환 스크립트보다 훨씬 실무적이다.  
**주의:** 선택한 Codex target 안의 generated artifact는 자동 생성·교체될 수 있으므로 기존 `.codex/`를 사용 중인 프로젝트라면 plan/dry-run diff를 반드시 확인하는 편이 좋다.

### 🏆 오늘의 Top Pick

**link-cli**

Agent가 실제 돈을 쓰거나 금융 데이터에 접근하는 순간에는 단순 tool-call 능력보다 **최소 권한, credential 비노출, 사용자 승인, 권한 upgrade의 안전한 lifecycle**이 더 중요해진다. Stripe가 이 경계를 공식 Skill과 CLI 계약으로 만들었다는 점, skills.sh에서 First Seen 1일인 신생 Skill임에도 원 저장소가 활발히 업데이트되고 있다는 점, 앞으로 구매·예약·조달 Agent가 늘수록 재사용될 보안 패턴이라는 점을 종합해 오늘의 Top Pick으로 선정했다.

### ⚡ Codex에서 바로 써볼 만한 것

**migrate-to-codex**

## 오늘의 공통 흐름

오늘 후보들의 공통점은 Skill이 더 이상 “모델에게 참고 문서를 추가하는 파일”에 머물지 않고 **Agent의 실행 제어면(control plane)** 으로 이동하고 있다는 것이다. `agents-hooks`는 정책을 runtime hook으로, `ai-coding-agents-tasks`는 작업을 typed lifecycle로, `dmux-workflows`는 여러 Agent process를 orchestration layer로 끌어올린다. 동시에 Salesforce는 live recipe로 API drift를 줄이고, Stripe는 실제 금융 행동 앞에 approval/permission boundary를 세우며, OpenAI는 서로 다른 Agent 생태계의 artifact를 검증 가능한 migration pipeline으로 옮긴다. 앞으로 Skill의 경쟁력은 프롬프트 문장 자체보다 **상태·권한·검증·복구·이식성을 얼마나 구조적으로 다루는가**에 더 크게 좌우될 가능성이 높다.
