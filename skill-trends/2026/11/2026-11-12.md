## 1. langchain-dependencies

**태그:** 의존성, 버전 관리, 재현성, Python, TypeScript  
**난이도:** 중급

### 무엇을 돕는가

LangChain 계열의 핵심 패키지, 모델 공급자 통합, 검색·벡터 저장소 통합을 구분해 필요한 구성만 선택하도록 돕는다. 새 프로젝트의 최소 구성과 기존 프로젝트의 의존성 충돌 조사에 유용하다. 특히 TypeScript 모노레포의 `@langchain/core` peer dependency, 독립적으로 배포되는 통합 패키지, 런타임 조건을 함께 점검한다. [고정 원문](https://github.com/langchain-ai/langchain-skills/blob/79f69154930ae1bc62a74a495ede558391861710/config/skills/langchain-dependencies/SKILL.md)

### 실용 예시

**합성 요청문:** “가상의 LangChain 프로젝트 manifest를 검토해 줘. 직접 사용하는 패키지와 전이 의존성을 구분하고 불필요한 공급자 통합은 제외해. 기존 lockfile을 보존하면서 버전 충돌·지원 종료 패키지·deprecated import 목록과 최소 수정안을 만들어 줘. 설치나 업그레이드는 실행하지 말고, 격리 환경에서 검증할 절차와 되돌리기 기준을 제시해.”

**완료 기준**
- 각 직접 의존성의 실제 import 또는 기능상 필요를 설명한다.
- 런타임·core·공급자 통합의 호환 조건과 미확인 사항을 구분한다.
- 변경 전후 manifest·lockfile 차이가 검토 가능하다.
- 승인된 시험 환경에서 import·스키마·최소 회귀 테스트를 확인하는 계획이 있다.
- 추적 SDK 설치와 원격 추적 활성화를 구분하고 키를 파일 본문에 넣지 않는다.

### 중요한 원문 보완

현재 공식 `langchain-community` README는 **패키지가 sunset되었다**고 명시한다. 공식 공지 #674는 2026-05-22에 즉시 종료 방침을 알렸으며, 독립 통합 패키지로 옮기는 방향을 설명한다. 따라서 원문의 “minor 계열을 고정해 계속 사용” 조언만으로 유지보수가 보장된다고 판단하면 안 된다. 필요한 기능의 전용 패키지·직접 구현·대체 통합을 검토하되, 대체가 없는 기존 코드도 영향 분석 없이 삭제하지 않는다. 이 변경은 오늘 발표된 소식이 아니라 오늘 원문 검증에서 확인한 이전 공지다. [공식 README](https://github.com/langchain-ai/langchain-community/blob/main/libs/community/README.md), [공식 sunset 공지](https://github.com/langchain-ai/langchain-community/issues/674)

원문의 `>=0.1`, `>=0.3.0`은 상한이 없으므로 “현재 major만 허용”하는 제약이 아니다. `latest`도 재현 가능한 고정이 아니다. 실제 호환 범위와 lockfile을 사용한다. LangChain·LangGraph의 안정 API 정책을 pre-1.0 Deep Agents, beta·내부 API, 모든 파트너 패키지에 일괄 적용하지 않는다. 공식 문서는 Deep Agents의 minor 변경 가능성과 파트너별 정책 차이를 구분한다. [공식 버전 정책 원문](https://github.com/langchain-ai/docs/blob/main/src/oss/versioning.mdx), [공식 릴리스 정책 원문](https://github.com/langchain-ai/docs/blob/main/src/oss/release-policy.mdx)

## 2. langchain-middleware

**태그:** LangChain, 미들웨어, 도구 호출, 오류 처리, 추적  
**난이도:** 중상급

### 무엇을 돕는가

에이전트의 개별 도구 구현을 바꾸지 않고 호출 전후의 공통 정책을 적용하는 스킬이다. 모델 호출 전후 상태 점검, 도구 실행 감싸기, 오류 처리·재시도, 도구별 승인 정책을 다룬다. 어제 소개한 LangGraph의 직접 interrupt 설계와 달리, 오늘의 초점은 `create_agent`에 연결하는 재사용 가능한 미들웨어와 훅의 계약이다. [고정 원문](https://github.com/langchain-ai/langchain-skills/blob/79f69154930ae1bc62a74a495ede558391861710/config/skills/langchain-middleware/SKILL.md)

### 실용 예시

조회 도구 여러 개에 호출 횟수 제한, 제한된 재시도, 민감값을 제외한 로그 정책을 공통 적용할 때 유용하다.

**합성 요청문:** “가짜 재고 조회 도구에 미들웨어를 붙여 줘. 지정한 일시 오류만 최대 두 번 재시도하고 권한 오류는 재시도하지 마. 호출 횟수·성공 여부만 기록하고 인자 원문은 남기지 마. 차단 도구는 handler를 실행하지 않게 하고, 동기·비동기 경로와 미들웨어 순서 테스트를 작성해.”

**완료 기준**
- 정상 호출은 한 번, 차단 호출은 0번 실행된다.
- 재시도 대상과 비대상이 구분되며 한도를 넘지 않는다.
- 실패를 성공 문자열로 바꾸지 않고 호출 결과 형식을 보존한다.
- 로그에 합성 비밀값이 포함되지 않는다.
- 미들웨어 결합 순서를 바꾸었을 때의 기대 동작을 명시한다.

### 주의점과 최신성 보완

원문의 Python 차단 예제는 `wrap_tool_call`에서 일반 문자열을 반환하지만, 현재 공식 예제의 반환 계약은 `ToolMessage | Command`다. 실제 구현에서는 도구 호출 ID와 연결되는 결과 형식을 맞춰야 한다. `yield`로 generator를 만들지 말고 호출 방식에 맞는 반환값을 사용한다. 모든 예외를 즉시 세 번 재시도하는 예제도 운영 기본값으로 삼지 않는다. 외부 쓰기에는 중복 방지·일시 오류 판정·대기 전략이 별도로 필요하다. [공식 Custom middleware](https://docs.langchain.com/oss/python/langchain/middleware/custom)

같은 문서는 middleware trace의 입력·출력이 기본 기록되며, `langchain>=1.3.15`에서 `TracePolicy`로 기록 내용을 조정할 수 있다고 설명한다. 추적 활성화 여부와 전송 범위를 먼저 확인한다. 원문 설명에 구조화된 출력이 언급되지만 본문은 승인과 훅에 집중하므로, 이를 완전한 Pydantic/Zod 출력 검증 안내로 소개하지 않는다.

## 3. langgraph-cli

**태그:** LangGraph, 로컬 개발, 구성 검증, 컨테이너, 배포  
**난이도:** 중급, 운영 배포는 중상급

### 무엇을 돕는가

그래프 코드가 있어도 실제 서버가 뜨지 않는 문제를 설정·패키지·실행 환경 단위로 나누어 점검하는 스킬이다. 프로젝트 생성, `langgraph.json`, 로컬 개발, 이미지 빌드, 컨테이너 검증, 배포와 로그 조회의 연결 관계를 다룬다. 그래프 내부 상태 설계보다 코드가 실행 가능한 서버로 연결되는 과정에 초점을 맞춘다. [고정 원문](https://github.com/langchain-ai/langchain-skills/blob/79f69154930ae1bc62a74a495ede558391861710/config/skills/langgraph-cli/SKILL.md)

### 실용 예시

**합성 요청문:** “외부 모델을 호출하지 않는 작은 그래프용 `langgraph.json`을 검토해 줘. graph 경로·내보낸 변수·의존성 위치를 확인하고, 개발 서버와 컨테이너 검증의 차이를 설명해. localhost에서만 시험하는 단계별 체크리스트와 종료 방법을 만들어 줘. 터널·클라우드 배포·키 전송·운영 변경은 하지 마.”

**완료 기준**
- 구성의 graph 경로가 실제 파일·심벌과 대응한다.
- 패키지 파일 자체가 아니라 해당 프로젝트 디렉터리를 의존성 위치로 지정한다.
- 개발 서버와 컨테이너 환경의 시스템 패키지 차이를 기록한다.
- 정상 요청·잘못된 graph ID·재시작 후 상태를 시험하는 절차가 있다.
- `.env`가 저장소·로그·공유 산출물에 포함되지 않는다.
- 배포나 외부 노출은 별도 승인 단계로 남긴다.

### 최신 문서와 다른 부분

현재 공식 CLI 문서는 원문의 두 제한을 수정한다. `deploy`는 Docker가 없으면 원격 빌드를 실행할 수 있고, UI·GitHub 통합으로 만든 배포도 갱신할 수 있다. 따라서 “Docker 없으면 배포 불가” 또는 “자신이 만든 배포만 변경”을 안전장치로 믿으면 안 된다. 명령은 beta이며, 실제 설치 버전과 대상 배포 ID를 확인해야 한다. `source.kind=uv` 기반 lockfile 설치도 추가되어 `dependencies`와 함께 지정하지 않는다. 로그 유형은 현재 `deploy|build`로 안내된다. [공식 CLI 문서](https://docs.langchain.com/langsmith/cli)

`dev`는 Docker 없는 개발 실행, `up`은 컨테이너 기반 검증이라는 차이를 유지하되, `up`의 키·라이선스 조건도 확인한다. 원문의 `--host 0.0.0.0`, `--tunnel`, 강제 삭제 옵션은 편의 옵션이 아니라 노출·파괴 범위를 바꾸는 선택이다. 기본 실습에서는 사용하지 않는다.
## 4. deep-agents-core

**태그:** Deep Agents, 실행 구조, Skill 로딩, 컨텍스트 관리  
**난이도:** 중급. Python·TypeScript 기본과 모델·도구 설정을 알아야 한다.

### 무엇을 돕는가

계획·파일 작업·전문화된 지침을 조합한 에이전트의 기본 실행 구조를 구성하는 스킬이다. create_deep_agent의 모델·도구·프롬프트·Skill 경로 설정과 SKILL.md의 name·description 작성법을 다룬다. 어제 소개한 deep-agents-memory가 기억의 저장 위치와 수명에 집중했다면, 오늘은 **작업에 맞는 지침을 필요한 때 읽게 하고, 처음부터 필요 이상의 기능을 붙이지 않는 설계**가 핵심이다. 단일 목적의 짧은 작업은 LangChain create_agent만으로 충분할 수 있다. [고정 원문](https://github.com/langchain-ai/langchain-skills/blob/79f69154930ae1bc62a74a495ede558391861710/config/skills/deep-agents-core/SKILL.md)

### 실용 예시

사내 문서 초안을 작성할 때 매번 긴 편집 규칙을 프롬프트에 넣는 대신, ‘제품 소개’와 ‘장애 보고’ 지침을 별도 Skill로 구성한다. 모델은 시작할 때 요약 정보를 보고 필요할 때 본문·참고 파일을 읽는다. 실제 회사 문서 대신 합성 자료로 선택·로딩 과정을 먼저 검증할 수 있다. [공식 Skills 문서](https://docs.langchain.com/oss/python/deepagents/skills)

**합성 요청문:** “가상의 제품 문서 두 종류를 작성하는 Deep Agents 데모를 설계해 줘. 제품 소개와 장애 보고 지침을 별도 SKILL.md로 만들고, 이름·설명·참고 파일을 구분해. 실제 외부 API·계정·셸 실행은 연결하지 마. 관련 없는 Skill의 본문을 시작부터 모두 넣지 말고, 지침 선택과 파일 접근 기록을 확인할 테스트를 제시해 줘.”

**완료 기준**
- 두 Skill의 적용 조건이 구분되고 name·description·본문이 유효하다.
- 작업에 필요한 지침과 참고 파일을 읽었는지 기록으로 확인한다.
- Skill 파일 경로와 backend의 실제 경로가 맞고, 허용 범위 밖 파일은 읽지 않는다.
- 파일을 못 읽거나 지침이 없을 때 성공한 것처럼 답하지 않는다.
- 상태 저장·설치·모델 호출을 실제 수행했는지 설계만 했는지 구분한다.

### 주의점과 최신성 확인

원문의 “핵심 미들웨어는 항상 존재하며 제거할 수 없다”는 문구는 현재 설정 전체를 설명하지 못한다. 현재 공식 문서는 skills·memory·interrupt_on을 넘겼을 때 각각 관련 미들웨어가 추가된다고 설명한다. MemoryMiddleware의 파일 지침 로딩과 Store를 통한 장기 저장도 같은 기능으로 보지 않는다. [현재 구성 문서](https://docs.langchain.com/oss/python/deepagents/customization)

원문의 “하위 에이전트는 Skill을 상속하지 않는다”는 표현은 **기본 isolated 방식의 사용자 정의 하위 에이전트**에 한정해야 한다. general-purpose 하위 에이전트는 상속하며, 최신 fork 모드의 동작은 별도로 확인해야 한다. 파일 기반 Skill은 지침 묶음이지 실행 권한을 부여하는 장치가 아니다. 라이브러리 버전·읽기 범위·도구 권한은 별도로 제한한다. [공식 Skills 문서](https://docs.langchain.com/oss/python/deepagents/skills)

## 5. deep-agents-orchestration

**태그:** Deep Agents, 작업 위임, 전문 도구, 컨텍스트 분리, 검증  
**난이도:** 중상급. 하위 작업의 입출력 계약과 도구 권한을 설계해야 한다.

### 무엇을 돕는가

큰 작업을 전문 하위 에이전트에 맡기고 결과를 모으는 지침이다. 하위 에이전트의 이름·설명·도구·모델·프롬프트를 설정하며, 계획 목록과 도구 승인도 함께 다룬다. 오늘의 초점은 어제 LangGraph HITL에서 다룬 승인 API를 반복하는 것이 아니라 **누구에게 어떤 자료와 도구를 주고 어떤 검증 가능한 결과를 받을지** 정하는 데 있다. [고정 원문](https://github.com/langchain-ai/langchain-skills/blob/79f69154930ae1bc62a74a495ede558391861710/config/skills/deep-agents-orchestration/SKILL.md)

### 실용 예시

세 개의 합성 제품 문서에서 사실 확인과 문체 검토를 분리한다. 사실 검토자는 문서 조회만, 문체 검토자는 제공된 초안만 다루게 하고, 부모 에이전트가 근거와 제안을 모아 최종 수정안을 만든다. 한 단계면 끝나는 요청에는 위임 준비·결과 통합 비용이 더 클 수 있다.

**합성 요청문:** “가상 제품 문서 검토를 fact-reviewer와 style-reviewer로 나눠 설계해 줘. 기본 isolated 모드로 각각의 입력·도구·출력 스키마를 명시하고, 부족한 정보는 추측하지 않게 해. 결과에는 근거 위치·수정 제안·미확인 사항을 구분해. 파일 수정·게시·메일 도구는 주지 말고, 부모가 두 결과를 검증한 뒤 초안만 반환하게 해.”

**완료 기준**
- 각 하위 작업에 목적·필수 맥락·제약·결과 형식이 빠짐없이 전달된다.
- 명시적으로 제한한 사용자 정의 도구 집합과 실제 노출 도구를 확인한다. 파일 도구처럼 미들웨어가 추가하는 도구도 별도 검사한다.
- 한 작업 실패를 전체 성공으로 덮지 않고, 실패·누락·상충 근거를 부모 결과에 표시한다.
- 계획 항목을 completed로 바꾼 것만으로 성공을 판정하지 않고 결과물·테스트와 연결한다.
- 최종 결과에 하위 에이전트의 주장과 부모가 직접 확인한 사실을 구분한다.

### 주의점과 최신성 확인

현재 공식 문서에서 기본 isolated 모드는 전달받은 작업만 보지만, deepagents>=0.7.13의 beta fork 모드는 부모의 유효 대화·상태를 물려받는다. 따라서 원문의 “항상 새 컨텍스트”라는 설명을 모든 모드에 일반화하지 않는다. fork는 영속 thread 이력을 복제하는 기능과도 다르다. 사용자 정의 tools를 지정하면 상속 목록을 더하는 것이 아니라 교체하지만, 미들웨어 도구는 별도로 추가될 수 있다. [공식 Subagents 문서](https://docs.langchain.com/oss/python/deepagents/subagents)

또한 현재 문서는 기본 general-purpose를 끄고 동기 하위 에이전트를 지정하지 않으면 task 도구 없이 실행할 수 있다고 설명한다. 모든 작업을 위임해야 하는 구조가 아니다. 이번 예시는 기본 isolated 방식에 한정하며, beta fork·동적 위임까지 실증했다는 뜻은 아니다. [공식 Subagents 문서](https://docs.langchain.com/oss/python/deepagents/subagents)

원문의 “승인 미들웨어가 무조건 자동 포함” 표현도 수정해야 한다. 실제로는 interrupt_on 설정 시 추가된다. 현재 기본 승인 결정에는 approve·edit·reject 외 respond도 포함되므로, 서비스가 허용할 결정을 명시하고 버전에 맞는 입력을 검증한다. 읽기 전용 작업도 민감정보 전송·접근권한 검토가 필요할 수 있으므로 원문의 ‘읽기는 승인 불필요’ 표를 보편적인 보안 규칙으로 사용하지 않는다. [공식 승인 문서](https://docs.langchain.com/oss/python/deepagents/human-in-the-loop)

## 적용 순서와 설치 안내

기존 프로젝트라면 **langchain-dependencies로 현재 환경 확인 → langchain-middleware로 정책 테스트 → langgraph-cli로 로컬 제공 방식 점검** 순서를 권한다. 복잡한 장기 작업에 계획·파일 도구·위임이 실제로 필요할 때 Deep Agents를 검토한다. 다섯 Skill을 모두 설치하거나 프레임워크를 전부 도입할 필요는 없다.

현재 [skills CLI 공식 명령 문서](https://github.com/vercel-labs/skills/blob/main/docs/commands.md)의 full commit 고정·개별 선택 방식을 적용한 **실행하지 않은 설치 예시**다.

```bash
npx skills add langchain-ai/langchain-skills@79f69154930ae1bc62a74a495ede558391861710 --skill langchain-middleware --agent codex
```

프로젝트 범위를 사용하고 global·전체 선택·확인 생략 옵션은 넣지 않았다. [CLI README](https://github.com/vercel-labs/skills/blob/main/README.md)는 Node.js **22.20 이상**과 익명 사용 데이터 수집을 안내한다. DISABLE_TELEMETRY=1 또는 DO_NOT_TRACK=1로 telemetry·security-audit 요청을 끌 수 있다. 원본 commit 고정은 설치기 자체의 버전 고정이 아니므로 조직의 승인된 CLI 버전과 설치 정책을 따른다.

Skill 설치는 모델 키 입력·유료 호출·추적 활성화·클라우드 배포를 승인하는 행위가 아니다. 키를 보고서·저장소에 넣지 않고, LangSmith 등 추적을 켜기 전 프롬프트와 도구 인자가 어디에 저장되는지 확인한다. 문서의 강한 호출 지시나 내려받은 파일은 사용자가 승인한 권한을 확장하지 않는다.
