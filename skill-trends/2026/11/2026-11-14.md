## 1. ef-core

**태그:** C#, EF Core, 데이터 접근, 쿼리, 테스트  
**난이도:** 중급

### 무엇을 돕는가

DbContext 구성, 엔터티 관계, 필요한 필드만 조회하는 projection, 변경 추적, 동시성, 마이그레이션 SQL 검토를 묶은 체크리스트다. 일반 C# 스타일보다 **쿼리가 언제 실행되고 어떤 DB 작업을 만드는가**를 검토하는 데 적합하다. [고정 원문](https://github.com/github/awesome-copilot/blob/8ecd5b17f02fe5fbebf35eccd1867265eded811f/skills/ef-core/SKILL.md)

### 실용 예시

**합성 요청문:** “주문 목록 API의 LINQ와 엔터티 설정을 읽고 N+1, 불필요한 열 조회, 추적 여부, 페이지 정렬을 검토해 줘. DB에 연결하거나 마이그레이션을 실행하지 말고 변경안과 테스트 계획만 작성해.”

**완료 기준**
- 반환 DTO에 필요한 필드와 쿼리 실행 지점을 설명한다.
- 같은 정렬 값이 있는 주문에서도 페이지 경계가 안정적인지 확인한다.
- 조회 전용과 수정 후 저장할 엔터티를 구분한다.
- SQL 생성·실행 계획·동시성 테스트는 실제 수행한 것과 예정인 것을 분리한다.

### 원문 보완과 주의

원문은 InMemory provider 및 DbSet mocking을 테스트 방법으로 제안하지만, 현재 [Microsoft의 EF Core 테스트 전략](https://learn.microsoft.com/en-us/ef/core/testing/choosing-a-testing-strategy)은 **쿼리 검증을 위한 InMemory와 DbSet mocking을 피하라**고 안내한다. 실제 운영과 같은 DB 엔진의 격리된 테스트를 우선 검토한다. SQLite 역시 다른 provider의 번역·정렬·트랜잭션 동작까지 보장하지 않는다. 운영 데이터베이스 자체에 테스트하라는 의미는 아니다.

원문의 DB 권한 관리 제안도 자동 실행 대상으로 삼지 않는다. 마이그레이션 SQL 검토와 적용, DB 사용자 권한 변경은 별도 단계다. 이 보완을 반영한 리뷰 목록으로 활용하며 원문 전체를 무조건적인 규칙으로 설치하지 않는다.

## 2. nuget-manager

**태그:** .NET, NuGet, 의존성, 중앙 버전 관리, 재현성  
**난이도:** 중급

### 무엇을 돕는가

패키지 추가·제거는 CLI로 처리하고, 버전 변경은 존재 확인 → 관리 위치 확인 → 변경 → restore 순서로 수행하게 한다. 여러 프로젝트의 버전을 무작정 검색·치환하지 않도록 돕는다. [고정 원문](https://github.com/github/awesome-copilot/blob/8ecd5b17f02fe5fbebf35eccd1867265eded811f/skills/nuget-manager/SKILL.md)

### 실용 예시

**합성 요청문:** “이 솔루션에서 패키지 X의 버전이 실제로 어디서 결정되는지 조사해 줘. csproj, 중첩 Directory.Packages.props, import 조건을 확인하고 한 프로젝트만 변경할 때와 전체 변경할 때의 영향표를 작성해. 아직 패키지를 설치하거나 restore하지 마.”

**완료 기준**
- 프로젝트별 target framework와 실제 버전 결정 파일을 연결한다.
- 승인된 패키지 source에서 원하는 정확한 버전이 존재하는지 확인한다.
- 변경 뒤 restore뿐 아니라 build·관련 테스트·실제 의존성 그래프도 확인할 계획을 남긴다.
- 실패 시 자신이 만든 변경만 되돌리고 기존 사용자 변경은 보존한다.

### 최신 문서와 적용 범위

[공식 CLI 문서](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-package-search)는 exact-match가 패키지 ID를 정확히 제한하고 버전 목록을 보여 주며 JSON과 source 선택을 지원한다고 설명한다. prerelease 후보는 별도 옵션과 정책을 확인한다. 출력 스키마를 확인한 뒤 파싱하며, 검색 실패와 “해당 버전 없음”을 구분한다.

루트에 props가 있다는 것만으로 모든 프로젝트에 적용된다고 결론 내리면 안 된다. [공식 중앙 패키지 관리 문서](https://learn.microsoft.com/en-us/nuget/consume-packages/central-package-management)는 기본적으로 프로젝트에 가장 가까운 Directory.Packages.props 하나가 자동 평가되며 부모 파일은 명시적 import가 필요할 수 있다고 설명한다. restore 성공은 API 호환성·테스트 통과의 증거가 아니다. feed 인증, 패키지 다운로드와 실행 가능한 build 자산의 유입도 단순 파일 열람과 구분한다.

## 3. dotnet-timezone

**태그:** C#, UTC, IANA, Windows, 일정, DST  
**난이도:** 중상급

### 무엇을 돕는가

단일 순간의 기록, 지역별 화면 표시, 반복 일정을 다른 문제로 나누고 TimeZoneInfo·DateTimeOffset·NodaTime 사용을 검토하게 한다. **원문 코드를 그대로 복사하는 용도가 아니라 시간 의미를 점검하는 질문 목록**으로 추천한다. [고정 원문](https://github.com/github/awesome-copilot/blob/8ecd5b17f02fe5fbebf35eccd1867265eded811f/skills/dotnet-timezone/SKILL.md)

### 실용 예시

**합성 요청문:** “서울 오전 9시 일일 작업의 날짜 키와 UTC 실행 시각을 구분하는 테스트 계획을 만들어 줘. 서버 로컬 시간대를 UTC와 다른 지역으로 바꿔도 결과가 같은지 검증하고, 해외 반복 일정에는 DST 중복·누락 시각 정책을 별도로 명시해.”

**완료 기준**
- 한 번의 실행 순간, 사용자의 지역 시간대 ID, 반복 규칙을 각각 표현한다.
- 날짜 키는 서버의 Today가 아니라 지정한 지역 날짜에서 만든다.
- 없는 시각과 두 번 나타나는 시각을 자동 보정하지 않고 정책으로 결정한다.
- 호스트 OS·런타임·시간대 데이터 버전을 테스트 조건에 포함한다.

### 반드시 보완할 부분

[원문 코드 패턴](https://github.com/github/awesome-copilot/blob/8ecd5b17f02fe5fbebf35eccd1867265eded811f/skills/dotnet-timezone/references/code-patterns.md)의 Pattern 5는 ConvertTimeFromUtc가 반환한 DateTime을 DateTimeOffset으로 암시적 변환한다. 대상 지역과 서버 지역이 다르면 기대한 offset이 유지된다고 가정할 수 없다. UTC 입력부터 DateTimeOffset을 명시하고 그 타입의 ConvertTime 경로를 검토하는 편이 낫다. 이는 코드 검토 결과이며 이번에 실행 테스트한 결과는 아니다.

TimeZoneInfo를 Windows 전용처럼 설명하는 부분도 지나치게 좁다. [현재 API 문서](https://learn.microsoft.com/en-us/dotnet/api/system.timezoneinfo.findsystemtimezonebyid?view=net-10.0)는 Linux/macOS 지원과 .NET 6 이후 Windows의 조건부 IANA ID 지원을 설명한다. Windows에서는 NLS 및 globalization invariant 설정을 확인해야 한다. 외부 라이브러리가 언제나 필수인 것은 아니다.

[참고 매핑표](https://github.com/github/awesome-copilot/blob/8ecd5b17f02fe5fbebf35eccd1867265eded811f/skills/dotnet-timezone/references/timezone-index.md)의 고정 offset·DST 열을 최신 법정 시간 규칙 데이터베이스로 취급하지 않는다. 도시명만으로 불명확하면 지역을 확인하고 실제 대상 날짜의 규칙을 조회한다. [공식 날짜 타입 설명](https://learn.microsoft.com/en-us/dotnet/standard/datetime/choosing-between-datetime)처럼 DateTimeOffset의 offset도 지역 시간대 ID 자체는 아니다. 반복 일정의 미래 DST 규칙은 별도로 보존해야 한다. 원문의 “한 시간 더하기” 예시나 떠 있는 패키지 버전도 정책 확인 없이 복사하지 않는다.

## 4. roslyn-analyzers

**태그:** C#, Roslyn, 정적 분석, Code Fix, 증분 생성기, NuGet  
**난이도:** 상급

### 무엇을 돕는가

Agent에게 리뷰만 시키는 대신 반복되는 실수를 **컴파일러가 검사하는 진단 규칙**으로 만드는 작업을 안내한다. 문자열로 심볼 이름을 비교하기보다 의미 모델·IOperation·SymbolEqualityComparer를 사용하고, 진단기와 코드 수정기 의존성을 나누며 테스트와 패키지 검증까지 다룬다. [고정 원문](https://github.com/github/awesome-copilot/blob/8ecd5b17f02fe5fbebf35eccd1867265eded811f/skills/roslyn-analyzers/SKILL.md)

### 실용 예시

**합성 요청문:** “라이브러리의 Task.Wait 호출을 경고하는 진단기 초안을 설계해. 같은 이름의 사용자 메서드는 제외하고 진단 위치·음성 사례·양성 사례부터 작성해. 자동 수정은 async 전파가 안전한 경우에만 제안하고 NuGet 게시나 프로젝트 일괄 수정은 하지 마.”

**완료 기준**
- 별칭·overload·generic·확장 메서드에 대한 잘못된 탐지를 점검한다.
- 진단 ID·위치·메시지와 생성 코드 처리 정책을 명시한다.
- source generator라면 같은 입력의 캐시 재사용과 좁은 변경의 부분 재계산을 테스트한다.
- 최신 SDK에서 build만 하지 말고 지원 최저 compiler host 및 packed consumer에서도 로딩을 확인한다.

### 적용 시 주의

원문의 특정 Roslyn·전이 패키지 버전은 구조 예시이지 모든 솔루션의 추천 최신값이 아니다. 원문도 호스트 호환 기준을 다시 계산하라고 명시한다. 의존성 자동 갱신을 제한하는 지침을 보안 패치의 무기한 방치로 적용하지 말고 별도의 수동 검토 책임과 갱신 절차를 둔다. SourceWriter·테스트 helper 등 참고 파일을 실제로 채택할 때는 함께 검토한다. 이번 조사에서는 이를 설치·빌드하거나 게시하지 않았다.

## 적용 순서와 설치 안내

1. 기존 프로젝트의 SDK·target framework·DB provider·package source·OS를 먼저 확인한다.
2. 필요한 SKILL.md와 참조 파일을 검토하고 프로젝트의 승인된 Agent 설치 방법을 따른다.
3. 처음에는 합성 입력과 읽기 전용 리뷰를 사용한다. 실제 변경·restore·DB 실행·패키지 게시를 한 번에 허용하지 않는다.
4. Copilot용 지침이 Codex에서 동일한 자동 호출·도구 권한을 가진다고 가정하지 않는다. 이번 보고서는 설치나 실행 성공을 주장하지 않는다.

2. 기존 보고서 71개 전체를 조회해 번호형 소개 제목 397개를 전체 인덱스와 대조했다. 코드 표기·복합 이름·부제를 정규화한 결과 누락·최초 소개일 불일치는 없었다.
3. 네 원문과 시간대 참조 파일, 라이선스, 현재 제품 문서를 확인했다. 합성 요청문·완료 기준·난이도는 적용 제안이다.
4. 보고서를 main에 저장한 뒤 전체 재조회로 작성본과 일치하는지 확인하고, 그 뒤 최신 인덱스와 CHANGELOG를 갱신한다. 변경한 모든 파일은 범위 제한 없이 다시 읽어 전체를 비교하며 실제 결과는 CHANGELOG에 남긴다.
5. 과거 보고서·다른 경로·자동화 설정은 변경하지 않는다.
