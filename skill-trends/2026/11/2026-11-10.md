## 1. convex-authz

**태그:** Convex · 인가 · 멀티테넌트 · 코드 검토  
**난이도:** 중상급

### 무엇을 돕는가

클라이언트가 보낸 사용자 ID를 그대로 신뢰하는 코드, 문서 소유권을 확인하지 않는 읽기·수정, ID만 알면 노출되는 비공개 데이터, 다른 사람의 프로젝트에 하위 문서를 추가하는 코드를 집중적으로 찾는다. 특히 **로그인 확인과 해당 문서·컨테이너 접근 권한은 다르다**는 점을 드러낸다. 원문은 검색 결과의 파일·행·문제 유형을 남기고 수정 후 타입 검사·재검색을 하도록 한다. [고정 SKILL.md](https://github.com/convex/agent-skills/blob/f60629d7c6c1f27eb58a56260546d2445049274d/skills/convex-authz/SKILL.md)

### 실용 예시

가상의 createTask가 userId·projectId·title을 입력받아 task를 추가한다. userId를 서버의 인증 정보로 바꿔도 projectId의 소유권을 확인하지 않으면 다른 팀의 프로젝트에 쓰기가 가능할 수 있다.

> “합성 팀 작업 앱의 createTask와 listTasks를 검토해 줘. 사용자 신원 위조, 다른 팀 문서 조회, 다른 팀 프로젝트에 자식 문서 추가를 구분해 파일·행·근거와 테스트 계획을 제시해. 현재는 검토만 하고 공개 함수를 internal로 바꾸거나 인증 설정을 수정하지 마.”

**완료 기준:** 비로그인, 정상 소유자·허용된 팀원, 다른 팀 사용자로 각각 접근 결과를 정의한다. 거절된 쓰기 뒤에는 실제로 문서가 추가되지 않았는지도 확인한다. ownerId가 users 문서 ID라면 인증 subject 문자열과 직접 비교하지 않고 프로젝트의 신원 매핑을 거친다. 역할·공유·팀 탈퇴 같은 예외도 현재 정책을 따른다.

### 원문을 그대로 자동 수정에 쓰면 안 되는 이유

1. **인증 전제의 과도한 일반화:** 원문은 subject 기반 사용자 테이블이 없으면 getUserIdentity가 항상 null이라고 설명한다. 사용자 테이블 존재 자체가 인증된 identity를 결정하지는 않는다. 실제 토큰·인증 설정과 앱의 사용자 매핑을 구분해야 한다. 여러 issuer를 쓰는 경우 subject만으로 신원을 합치지 않는다. [공식 함수 내 인증 문서](https://docs.convex.dev/auth/functions-auth)는 tokenIdentifier가 subject와 issuer를 결합해 식별한다고 설명한다.
2. **정규식은 후보 탐색:** 함수 본문에 ctx.auth가 없다는 이유만으로 취약하다고 확정할 수 없다. 공통 helper에서 올바르게 검사할 수도 있다. 반대로 문자열이 존재해도 정확한 객체 권한 검사를 보장하지 않는다. 타입 검사 성공·검색 0건은 권한 테스트를 대신하지 않는다.
3. **참조 파일 누락:** 원문이 그대로 재사용하라고 요구하는 content/convex-expert.md는 이 snapshot에 없다. 임의의 helper를 만들어 “공식 패턴 그대로 적용했다”고 표현하지 않는다. 검증된 현재 코드·공식 인증 문서를 기준으로 별도 설계가 필요하다.
4. **공개 API 변경:** public 함수를 internal로 전환하면 기존 호출자가 끊길 수 있다. 감사 요청을 자동 수정·API 폐쇄·인증 제공자 교체 허가로 확대하지 않는다.

따라서 추천 범위는 **네 가지 권한 결함의 검토 체크리스트와 교차 사용자 테스트 설계**다. 원문의 결함 통계·자동 수정 흐름을 독립 검증된 보안 성능으로 소개하지 않는다.

## 2. convex-migrate

**태그:** Convex · 스키마 변경 · 백필 · 데이터 검증  
**난이도:** 중상급

### 무엇을 돕는가

새 필드를 바로 필수로 만들어 기존 문서가 검증에 실패하는 문제를 피하도록, **선택 필드 추가 → 기존 데이터 채우기 → 검증 → 필수 필드로 강화** 순서를 제시한다. @convex-dev/migrations 사용과 전후 행 수 확인을 안내하는 짧은 workflow다. 기존 SQL 엔진의 migration 명령 소개와 달리 Convex 문서 validator·점진적 백필에 초점이 있다. [고정 SKILL.md](https://github.com/convex/agent-skills/blob/f60629d7c6c1f27eb58a56260546d2445049274d/skills/convex-migrate/SKILL.md)

### 실용 예시

기존 주문 문서에 status가 없고 결제 상태는 별도 데이터로 기록되어 있다고 가정한다.

> “주문 status를 pending 또는 paid로 도입하는 이관 계획을 만들어 줘. 기존 문서는 선택 필드로 허용하고, 확인된 결제 근거로만 값을 채워. 결제 정보가 없는 주문은 임의로 paid 처리하지 마. 실제 연결·설치·백필·배포 없이 재시작, 동시 생성, 검증과 복구 계획을 먼저 제시해.”

**완료 기준:** 구형·신형 문서를 함께 읽는 동안의 동작, 새 주문 쓰기 경로, 이미 올바른 값을 가진 문서를 보존하는 규칙이 있다. 중단 후 재개와 재실행에도 값이 잘못 바뀌지 않으며, 최종적으로 누락·잘못된 값·업무 불변조건 위반을 확인한다. 행 수가 같다는 사실만으로 결제 상태가 정확하다고 결론 내리지 않는다.

### 보완해야 할 실행 설계

- 선택 필드 전략은 **새 필드 추가**의 기본 출발점이다. 기존 필드의 타입을 호환되지 않게 바꾸면서 optional만 붙여도 기존 값이 유효해지는 것은 아니다. 새 필드·전환용 타입·읽기·쓰기의 단계별 호환성을 설계한다.
- 원문에는 구현 코드, 버전 고정, 동시 쓰기 대책, 복구 검증이 없다. 짧은 Skill만으로 무중단이나 무손실을 보장하지 않는다. migration component의 배치·진행 상태 기능과 애플리케이션의 의미 보존은 다른 문제다.
- 연관 [리허설 지침](https://github.com/convex/agent-skills/blob/f60629d7c6c1f27eb58a56260546d2445049274d/skills/convex-migrate-rehearse/SKILL.md)은 snapshot을 preview에 복사하는 흐름을 제시한다. 운영 데이터를 개발 환경으로 옮길 때도 접근·보관 범위를 검토해야 한다. 합성 데이터로 검증 가능한 부분은 먼저 분리한다.
- snapshot으로 전체 교체하는 복구는 snapshot 이후의 쓰기를 잃을 수 있다. “백업이 있다”를 무손실 rollback이라고 표현하지 않는다. 복구 지점·허용 손실·백업 보관·복원 시험을 따로 정한다.
- 실제 실행은 대상 배포·데이터 범위·비용·파괴적 작업 여부를 확인한 별도 단계다. [배포 대상 확인 지침](https://github.com/convex/agent-skills/blob/f60629d7c6c1f27eb58a56260546d2445049274d/skills/convex-deploy-guard/SKILL.md)을 읽는 것만으로 기술적 접근 제한이 생기지는 않는다.

## 3. convex-agent

**태그:** Convex · AI Agent · 대화 상태 · RAG · 스트리밍  
**난이도:** 중상급

### 무엇을 돕는가

@convex-dev/agent component를 앱에 등록하고 모델·도구·지침을 연결한 뒤, 스레드·메시지를 저장하고 스트리밍하는 절차다. AI 코딩 도구의 기능을 늘리는 Skill을 이용해 **사용자 앱 안의 AI Agent 백엔드**를 만드는 경우다. 모델 호출은 action에서 수행하고 공급자 키가 필요한 경로에서는 브라우저에 노출하지 않도록 안내한다. [고정 SKILL.md](https://github.com/convex/agent-skills/blob/f60629d7c6c1f27eb58a56260546d2445049274d/skills/convex-agent/SKILL.md)

### 실용 예시

> “공개 합성 도움말 20개만 참조하는 고객지원 챗의 개발 계획을 만들어 줘. 대화 새로고침 후에도 기록을 이어가고, 근거가 없으면 모른다고 답하게 해. 다른 사용자의 thread·문서는 조회하지 못해야 해. 지금은 설치·문서 업로드·모델 호출 없이 모델 경로, 저장 범위와 테스트를 설계해.”

**완료 기준:** 같은 사용자의 스레드가 복구되고 다른 사용자의 스레드는 거절된다. 고정 질문 세트로 검색 근거·답변·모름 처리를 확인한다. 취소·타임아웃·재시도에서 중복 메시지와 중복 도구 실행을 점검하고 비용 상한을 둔다. RAG 자료가 존재한다는 사실만으로 답변 정확도나 자료별 접근 제어가 보장되지는 않는다.

### 현재 문서와 다른 원문 전제

검토한 Skill은 Gateway가 임베딩을 지원하지 않고 로컬 backend에서는 사용할 수 없다고 쓴다. **현재 제품 문서와 다르므로 그대로 적용하지 않는다.**

| 항목 | 조사 시점 공식 문서로 보완한 조건 |
|---|---|
| 임베딩 | Gateway는 embeddings endpoint와 convexGateway.embeddingModel을 지원한다. 임베딩 때문에 별도 공급자 키가 항상 필요한 것은 아니다. |
| 버전 | token helper에는 convex 1.45+가 필요하지만 현재 Agent·RAG component 경로는 convex 1.46+를 요구한다. |
| SDK | 현재 Vercel AI SDK 경로는 @convex-dev/ai-sdk-provider 0.2.1+ 및 AI SDK 7.0.105+를 안내한다. 프로젝트 의존성·peer 조건을 함께 확인한다. |
| 실행 환경 | 유료 팀의 Cloud 개발·운영 배포와 프로젝트에 연결된 local deployment가 지원된다. 익명·오래된 local과 self-hosted를 같은 지원 상태로 묶지 않는다. |

근거는 [현재 Gateway 설정](https://docs.convex.dev/ai-gateway/setup)과 [지원 범위](https://docs.convex.dev/ai-gateway/overview)다. 버전 숫자는 이 보고서가 확인한 현재 경로의 조건이지 모든 과거 component 버전에 대한 일반 법칙이 아니다. 구현 시 설치된 타입·문서와 다시 대조한다.

공급자 키를 직접 관리하지 않는 Gateway라도 무료·오프라인이라는 뜻은 아니다. 문서·대화가 모델 서비스로 전달되는 범위, 비용, 보관 정책을 확인한다. 모델 도구의 데이터 수정·외부 전송도 별도 권한 검사가 필요하다. action 전체를 하나의 DB transaction으로 가정하지 않는다. [공식 함수 구분](https://docs.convex.dev/functions/overview)은 query·mutation의 transaction과 action의 외부 API 호출을 구분한다.

## 4. convex-insights

**태그:** Convex · 로그 분석 · 관측성 · 장애 조사  
**난이도:** 중급

### 무엇을 돕는가

공식 MCP의 status·functionSpec으로 배포와 함수명을 먼저 확인하고, 실패 묶음·건강 지표·특정 실행 추적 중 하나를 골라 좁게 조사한다. 원시 로그를 쏟기보다 결론, 집계, 대표 증거와 확인 경로를 남기는 **읽기 전용 조사**가 목적이다. 배포 이후 오류가 늘어도 시간상 연관과 원인을 구분한다. [고정 SKILL.md](https://github.com/convex/agent-skills/blob/f60629d7c6c1f27eb58a56260546d2445049274d/skills/convex-insights/SKILL.md)

### 실용 예시

> “이미 읽기 접근이 승인된 개발 배포에서 최근 로그 500개를 대상으로 webhook 실패를 함수·오류별로 묶어 줘. 실제 함수명을 먼저 확인하고 대표 증거에서 토큰·개인정보는 제외해. 코드를 수정하거나 운영 권한을 추가하지 마.”

**완료 기준:** 대상 배포, 조회 개수, 실제 포함된 시간 범위, 로컬 필터 기준을 명시한다. 찾은 오류 수를 표본 안의 수치로 보고하며, 자료가 없거나 권한이 부족한 상태를 “전체 시스템 오류 0건”으로 표현하지 않는다. 대시보드 링크는 실제 열리는 정확한 대상이 확인될 때만 제공한다.

### 표본과 권한을 구분하기

- 원문에서 logs의 history는 **기간이 아니라 개수**다. CLI 옵션을 MCP 인자처럼 그대로 복사하지 말고 실제 노출된 도구 스키마를 확인한다. 함수·requestId·시간을 서버에서 모두 걸러 준다고 가정하지 않는다. 제한된 최근 자료를 가져와 로컬 필터링하는 경우 기간 전체를 보장할 수 없다.
- insights는 최근 **72시간**의 읽기 한도·OCC 관련 건강 지표를 제공한다. 전체 장애·비용·성능의 모든 원인을 포괄하는 시스템이 아니다.
- [현재 MCP 보안 표](https://docs.convex.dev/ai/convex-mcp-server#security)는 운영 배포의 비민감 읽기와 logs 등 개인정보가 포함될 수 있는 읽기, 비밀값 읽기·쓰기 권한을 나눈다. 로그를 보기 위해 광범위한 production 변경 권한까지 켜지 않는다. 같은 문서 앞부분의 포괄적인 운영 접근 설명과 표가 다르므로 설치된 버전·옵션도 확인한다.
- project-dir 설정은 다른 프로젝트 접근을 막는 보안 경계가 아니다. 또한 deploy key로 범위를 제한한 MCP에서는 insights가 지원되지 않는다고 문서에 명시되어 있다. 조회가 막혔다고 더 넓은 자격증명으로 자동 전환하지 않는다.
- 보고서용 finding schema·연계 경로가 이 snapshot에 모두 들어 있지는 않다. 이 Skill 하나를 설치하면 종합 감사 파이프라인까지 완성된다고 가정하지 않는다.

읽기 전용이어도 로그 내용은 민감할 수 있다. 필요한 집계와 최소 증거만 남기고, 장애 분석을 자동 수정·미래 모니터링·외부 발송으로 확대하지 않는다.

## 5. convex-test

**태그:** Convex · Vitest · 회귀 테스트 · 인증 모의 · 예약 작업  
**난이도:** 중급

### 무엇을 돕는가

convex-test와 Vitest로 메모리 기반 backend에서 함수의 입력·반환·권한·오류·예약 작업을 테스트한다. t.run으로 합성 데이터를 준비하고 t.query·t.mutation 결과를 검증하며, withIdentity로 서로 다른 사용자를 흉내 낸다. 실배포를 사용하지 않고 시간·네트워크를 통제하라는 경계가 분명해 작은 회귀 테스트부터 시작하기 좋다. [고정 SKILL.md](https://github.com/convex/agent-skills/blob/f60629d7c6c1f27eb58a56260546d2445049274d/skills/convex-test/SKILL.md)

### 실용 예시

> “합성 두 팀의 task fixture로 createTask/listTasks 테스트를 작성해 줘. 정상 생성, 비로그인 거절, 다른 팀 조회 차단, 다른 팀 projectId로 생성 차단, 잘못된 입력을 포함해. 예약 정리 작업은 가짜 시간으로 검증하고 실제 배포·네트워크를 사용하지 마.”

| 검증 대상 | 기대 결과 |
|---|---|
| 허용된 팀원 생성·조회 | 자신의 팀에만 추가되고 반환된다. |
| 비로그인·다른 팀의 쓰기 | 거절되며 기존 데이터와 개수가 유지된다. |
| 다른 팀의 조회 | 다른 팀 문서가 노출되지 않는다. |
| 잘못된 입력 | 지정한 검증 오류가 발생하고 부분 쓰기가 없다. |
| 예약 정리 | 통제한 시간 전에는 유지되고, 작업 완료 후 대상만 처리된다. |

이는 이번 조사에서 실행한 결과가 아니라 제안하는 assertion이다. **완료 기준**은 각 분기를 실제로 호출하는 테스트, 반복 실행의 같은 결과, 실패 출력과 수행 범위의 기록이다. 수정 작업이라면 먼저 결함이 재현되는지 확인하고 수정 후 통과와 인접 회귀를 분리해 남긴다.

### 짧은 Skill에서 빠진 설정과 한계

[공식 convex-test 문서](https://docs.convex.dev/testing/convex-test)는 테스트 의존성·Vitest 환경·모듈 로딩 설정을 제공한다. 기본 경로가 아닌 함수 디렉터리에서는 schema만 넘기는 짧은 예제를 복사하지 말고 실제 modules를 전달하는 설정을 확인한다. 예약 작업은 fake timer 진행과 완료 대기를 함께 설계한다. 이미 진행 중인 작업을 기다리는 것과 미래 예약 시간을 진행시키는 것은 다르다.

이 라이브러리는 JavaScript mock이다. 테스트에서 identity를 주입했다고 실제 OAuth·JWT 로그인 흐름까지 검증된 것은 아니다. 운영 자원 한도·성능·외부 서비스 연결·배포 설정은 별도 검증이 필요하다. [실제 local backend 테스트 문서](https://docs.convex.dev/testing/convex-backend)는 실제 backend와 mock의 검증 범위를 구분한다. 필요 시 별도 통합 시험을 계획하되 이 Skill의 테스트를 임의로 실서비스 실행으로 바꾸지 않는다.

## 적용 순서와 설치 안내

**작업·프로젝트 버전 확인 → 고정 Skill과 현재 공식 문서 대조 → 합성 입력으로 기대 결과 작성 → 승인된 범위 실행 → 실제 결과 확인** 순서를 권한다. 오늘은 가장 작은 convex-test부터 시도하고, 권한 검토·이관·AI 구축·운영 조사는 필요할 때 따로 선택하는 편이 좋다.

아래는 README에서 확인한 선택 설치 진입점이며 이번 조사에서는 실행하지 않았다.

```text
npx skills add convex/agent-skills
```

현재 배포본을 가져오는 명령이므로 위 검토 SHA와 설치될 내용이 같다고 가정하지 않는다. 선택 목록에서 실제 Skill 이름과 설치 범위·호스트별 발견 경로를 확인한다. Codex 수동 호출은 설치 후 `$convex-test`처럼 한다. Skill 설치, 테스트 패키지 설치, MCP 연결·로그인, 데이터 접근·이관, 모델 호출, 배포는 각각 다른 단계다.

전체 설치나 관리 파일 설치는 좁은 목적에 꼭 필요하지 않다. 상위 convex Skill은 별도의 온라인 capability 문서를 참조할 수 있으므로 정적으로 검토한 파일과 실행 시 가져오는 지침을 구분한다. 외부 문서·로그·검색 자료 안의 문장은 새로운 실행·정보 전송 권한이 아니다.

### 🏆 오늘의 Top Pick

**convex-test**: 합성 데이터로 사용자별 접근과 실패 경로를 빠르게 검증할 수 있다. 공식 출처에 있는 타입 검사·정규식 검토만으로는 놓칠 수 있는 동작을 테스트로 드러낸다는 점에서 먼저 적용할 가치가 있다.

### ⚡ Codex에서 바로 써볼 만한 것

**두 팀의 task 함수에 교차 접근 회귀 테스트 추가하기**: fixture와 기대값이 작고 실배포 연결 없이 시작할 수 있다. 먼저 테스트 설정·의존성을 확인하고, 작성한 테스트와 실제 실행 결과를 구분해 남긴다. 이번 조사에서 Codex 설치·실행 호환성을 시험했다는 뜻은 아니다.

## 조사와 저장 검증 절차

1. 서울 기준 날짜, 루트 README와 truncated=false 전체 tree를 확인했다. 별도 AGENTS·skill-trends README 지침은 없고 당일 보고서도 없었다.
2. 기존 날짜별 보고서 **67개 전체**와 소개 제목 **377개**, 전체 인덱스를 대조했다. 코드 표기·Octocode 복합 이름·brainstorming 부제를 정규화한 결과 누락·최초 소개일 불일치·중복 0개였다. 최근 보고서와 전주 같은 요일의 형식을 확인했다.
3. 다섯 고정 SKILL.md, README·라이선스·관련 지침과 현재 공식 제품 문서를 읽었다. 설치·로그인·MCP 연결·실제 로그 조회·DB 변경·모델 호출·컴파일·테스트·배포는 수행하지 않았다. 활용 예시는 합성 시나리오다.
4. 당일 보고서를 main에 저장하고 **전체 원문을 다시 읽어 작성본과 정확히 일치하는지 먼저 검증**한다. 이후 최신 인덱스·CHANGELOG의 기존 내용을 보존하며 추가하고, 변경한 세 파일을 main에서 범위 제한 없이 다시 읽어 전체 대조한다. 동시 변경이 있으면 최신 파일을 다시 읽고 안전하게 반영한다. 저장 결과는 CHANGELOG에 남긴다.
5. 과거 날짜 보고서, 다른 보고서 경로, 자동화 설정은 변경하지 않는다.
