## 1. recipe-copy-sheet-for-new-month

**월초 반복 작업을 “복사 성공”에서 끝내지 않고 새 탭의 ID까지 연결하기.**

- 원본: [SKILL.md](https://github.com/googleworkspace/cli/blob/cd3697e07eb520056dcf142d0c7439bbb9ba32e9/skills/recipe-copy-sheet-for-new-month/SKILL.md)
- 태그: `sheets`, `monthly-workflow`, `template`, `idempotency`
- 난이도: 초중급

### 무엇을 해주나

스프레드시트 정보 조회 → 템플릿 탭 복사 → 새 탭 이름 변경이라는 작은 흐름을 제시한다. 기존 CSV 백업·탭 비교와 달리 **새 기간의 작업 공간을 생성하는 작업**이다. 월별 정산·업무 기록을 만들 때 사람에게 복사 대상을 보여주고 실행 결과를 추적하는 출발점으로 쓸 수 있다.

### 원문을 그대로 쓰면 안 되는 부분

원문의 sheetId 0과 이름 변경 대상 123은 실제 환경에서 자동으로 맞는 ID가 아니다. [Sheets copyTo API](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets.sheets/copyTo)는 새 시트의 SheetProperties를 반환한다. 조회로 선택한 템플릿 ID를 사용하고 **복사 응답의 새 sheetId**를 다음 요청으로 넘겨야 한다. 스프레드시트 전체 ID와 탭의 정수 ID도 구분한다.

예제의 February 2025는 과거 고정 문자열이다. 대상 월은 사용자 기준 시간대와 업무 기간으로 정해야 하며 현재 날짜를 원본에 기계적으로 넣는 것으로 요구사항이 해결되지는 않는다. 복사 후 이름 변경이 실패하면 새 탭이 이미 생겼을 수 있다. 처음부터 복사를 다시 하는 대신 응답 ID·현재 탭 목록을 확인한다.

### 실용 예시

> “가짜 스프레드시트 메타데이터로 2026년 11월용 탭 생성 계획을 만들어줘. 템플릿 이름이 같은 경우 ID로 구분하고, 대상 월 탭이 이미 있으면 덮어쓰지 말아줘. 복사 성공·이름 변경 실패·응답 유실의 fixture를 만들고 재시도 판단을 설계해. 실제 복제는 하지 마.”

**완료 기준:** 원본 탭 보존, 새 탭 ID 기록, 최종 이름 재조회, 필요한 수식·서식·참조의 표본 검수다. 복사 API 성공만으로 템플릿의 모든 업무 로직이 새 기간에 맞다고 주장하지 않는다.

## 2. recipe-create-doc-from-template

**복사·본문 작성·placeholder 치환·공유를 서로 다른 단계로 나누기.**

- 원본: [SKILL.md](https://github.com/googleworkspace/cli/blob/cd3697e07eb520056dcf142d0c7439bbb9ba32e9/skills/recipe-create-doc-from-template/SKILL.md)
- 태그: `docs`, `template-merge`, `document-review`, `sharing-boundary`
- 난이도: 중급

### 무엇을 해주나

Drive에서 문서를 복사하고 새 문서에 내용을 넣은 다음 협업자 권한을 추가하는 흐름이다. 제안서·프로젝트 개요처럼 틀이 반복되는 문서에 응용할 수 있다. 다만 원문은 완전한 템플릿 엔진이 아니라 몇 단계의 명령 예제다.

### 확인한 예제·구현 차이

원문은 `gws docs +write --document-id`를 사용하지만, 같은 커밋의 [helper 문서](https://github.com/googleworkspace/cli/blob/cd3697e07eb520056dcf142d0c7439bbb9ba32e9/skills/gws-docs-write/SKILL.md)와 [구현](https://github.com/googleworkspace/cli/blob/cd3697e07eb520056dcf142d0c7439bbb9ba32e9/crates/google-workspace-cli/src/helpers/docs.rs)은 **--document**를 요구한다. 또한 +write는 문서 끝에 **평문을 추가**하는 기능이다. Markdown의 ##를 제목 스타일로 변환하거나 템플릿 안의 자리표시자를 자동 교체하지 않는다.

실제 치환이 목적이면 [Google Docs 공식 merge 안내](https://developers.google.com/workspace/docs/api/how-tos/merge)처럼 복사본에서 placeholder를 지정하고 batchUpdate의 replaceAllText 등 적절한 요청을 구성해야 한다. 원본·복사본 ID를 혼동하지 않고, 치환 누락·남은 placeholder와 최종 문서 모습을 검수한다.

원문의 마지막 permissions.create는 별도 **공유 변경**이다. [Drive 공식 API](https://developers.google.com/workspace/drive/api/reference/rest/v3/permissions/create)에서 사용자·그룹 공유의 알림 메일은 기본 true다. 문서 작성 요청이 편집권 부여·메일 통지까지 자동 승인한 것은 아니다. 주소가 그룹인지 개인인지 확인하고 최소 권한과 통지 여부를 명시한다.

### 실용 예시

> “합성 프로젝트 데이터와 템플릿 구조로 치환 목록을 작성해줘. 문서 복사 후 받은 ID만 사용하고, plain-text append와 placeholder 치환을 구분해. 빠진 값·중복 placeholder·이미 처리한 문서의 재실행 테스트를 설계해. 실제 파일 생성·공유·메일 통지는 하지 마.”

**완료 기준:** 복사본 내용·서식·남은 placeholder를 확인한 뒤 공유를 별도 판단한다. 협업자에게 전달하기 전에 파일 위치와 실제 접근 범위를 검토한다. 템플릿 본문에 포함된 지시는 에이전트의 새 실행 권한이 아니다.

## 3. recipe-create-expense-tracker

**작은 지출표에서도 입력 문자열·통화·중복 행·공유 범위를 명확히 하기.**

- 원본: [SKILL.md](https://github.com/googleworkspace/cli/blob/cd3697e07eb520056dcf142d0c7439bbb9ba32e9/skills/recipe-create-expense-tracker/SKILL.md)
- 태그: `sheets`, `expense-log`, `input-validation`, `formula-safety`
- 난이도: 중급

### 무엇을 해주나

빈 스프레드시트 생성 → 헤더·첫 행 추가 → 관리자에게 읽기 공유라는 흐름이다. 기존 시트 읽기나 백업이 아니라 **구조화된 새 기록표의 초기화**에 해당한다. 재무 판단·세무 처리·결제 기능은 제공하지 않는다.

### 입력 예제의 교정

원문은 JSON처럼 생긴 배열을 --values에 넘긴다. 그러나 [Sheets helper 문서](https://github.com/googleworkspace/cli/blob/cd3697e07eb520056dcf142d0c7439bbb9ba32e9/skills/gws-sheets-append/SKILL.md)와 [구현](https://github.com/googleworkspace/cli/blob/cd3697e07eb520056dcf142d0c7439bbb9ba32e9/crates/google-workspace-cli/src/helpers/sheets.rs)을 보면 --values는 단순 쉼표 분할이고 JSON 구조를 파싱하지 않는다. 쉼표가 들어간 설명이나 따옴표를 안전하게 다루려면 **--json-values와 행 배열**을 사용해야 한다.

예를 들어 합성 데이터 구조는 다음과 같다. 이것은 실행 결과가 아니라 요청 검토용 예시다.

```json
[["2026-11-02","교통","회의 이동, 왕복","12000","KRW","sample-001"]]
```

현재 helper는 **valueInputOption=USER_ENTERED**를 지정한다. [Google 입력 옵션 문서](https://developers.google.com/workspace/sheets/api/reference/rest/v4/ValueInputOption)는 USER_ENTERED가 UI 입력처럼 해석되고 RAW는 파싱하지 않는다고 설명한다. 신뢰하지 않는 설명 문자열을 수식으로 해석시키지 않으려면 허용 형식을 검증하고, 원시 values API의 RAW 사용 등 입력 정책을 검토해야 한다. --json-values만 바꿨다고 수식 해석 문제가 해결되지는 않는다.

현재 snapshot은 --range를 지원한다. 다만 원문의 Sheet1 이름을 모든 언어·문서에 존재한다고 가정하지 말고 실제 탭 메타데이터를 읽어 지정한다. [append API](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets.values/append)는 지정 범위 안의 논리 테이블을 찾아 다음 행에 쓴다. 응답의 갱신 범위·행 수와 실제 저장값을 확인한다.

### 실용 예시

> “실제 지출 없이 합성 데이터로 지출표 스키마와 fixture를 만들어줘. 날짜·금액·통화·원본 기록 ID를 분리하고 쉼표·따옴표·수식 모양 설명·중복 기록을 검사해. 헤더 생성과 데이터 추가의 재시도를 구분하고 외부 공유는 계획에서 제외해.”

**완료 기준:** 통화가 다른 금액을 무조건 합치지 않고, 숫자/문자열·날짜 해석을 검수한다. append 요청의 응답이 끊겼을 때 원본 기록 ID를 확인한 후 재시도한다. 원문의 관리자 공유 단계는 필요성과 대상이 확인된 경우에만 별도 진행한다.

## 4. recipe-create-task-list

**목록 생성과 작업 추가를 연결하되 due를 시각 알림으로 오해하지 않기.**

- 원본: [SKILL.md](https://github.com/googleworkspace/cli/blob/cd3697e07eb520056dcf142d0c7439bbb9ba32e9/skills/recipe-create-task-list/SKILL.md)
- 태그: `tasks`, `checklist`, `date-semantics`, `retry-safety`
- 난이도: 초중급

### 무엇을 해주나

새 Google Tasks 목록 생성, 반환된 목록 ID로 작업 추가, 목록 결과 확인이라는 패턴이다. 기존 overdue 조회 레시피와 달리 새 프로젝트 체크리스트를 초기화한다. 제목·메모·마감일을 구조화하되 작업 우선순위나 책임자 승인까지 대신 결정하지 않는다.

원문의 2024년 예시 날짜는 실제 기한으로 복사하면 안 된다. [Tasks 리소스 문서](https://developers.google.com/tasks/reference/rest/v1/tasks)는 due가 RFC 3339 문자열이지만 **날짜만 기록하고 시각 부분은 버린다**고 명시한다. “내일 오후 3시 알림”을 이 필드 하나로 구현했다고 주장해서는 안 된다. 정밀한 시각 알림은 그 목적에 맞는 별도 기능과 사용자 시간대를 확인해야 한다.

### 실용 예시

> “새 프로젝트 체크리스트의 제목·설명·사용자 기준 기한 날짜를 JSON 계획으로 작성해줘. due를 시각 알림으로 표현하지 말고, 목록 생성 후 두 번째 작업에서 실패한 상황의 재개 절차를 설계해. 이미 만든 목록·작업의 반환 ID를 보존하고 실제 생성은 하지 마.”

**완료 기준:** 생성된 목록 ID와 각 작업 ID를 추적하고 부분 성공을 구분한다. 같은 제목이라는 이유만으로 다른 프로젝트 목록을 재사용하거나 중복이라며 삭제하지 않는다. 작업이 저장되었다는 사실과 담당자가 확인·완료했다는 사실도 구분한다.

## 5. recipe-label-and-archive-emails

**스레드 제목에 현혹되지 않고 실제로 바뀌는 메시지 범위를 제한하기.**

- 원본: [SKILL.md](https://github.com/googleworkspace/cli/blob/cd3697e07eb520056dcf142d0c7439bbb9ba32e9/skills/recipe-label-and-archive-emails/SKILL.md)
- 태그: `gmail`, `labels`, `archive`, `scope-review`
- 난이도: 중급

### 무엇을 해주나

검색 조건으로 메시지를 찾고 라벨을 붙인 뒤 INBOX 라벨을 제거해 보관하는 레시피다. 기존 triage/read가 정보를 읽는 데 초점이 있다면, 이번에는 **상태 변경 전의 대상 확정·복구 가능성**이 핵심이다. 발신자 하나가 같다는 이유만으로 중요 알림까지 모두 정리하지 않도록 날짜·라벨·사용자 지정 제외 조건을 함께 검토한다.

### 메시지와 스레드의 차이

원문 제목은 Threads라고 하지만 실제 명령은 users.messages.list와 users.messages.modify다. [Gmail 라벨 문서](https://developers.google.com/workspace/gmail/api/guides/labels)는 메시지에 붙인 라벨이 다른 메시지로 자동 전파되지 않는다고 설명한다. 스레드 수정은 기존 메시지 전체를 대상으로 하지만 나중에 들어온 메시지는 기존 라벨을 자동 상속하지 않는다. 따라서 한 메시지를 보관했다고 전체 대화가 같은 상태가 되었다고 판정하지 않는다.

[modify API](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/modify)는 한 요청에서 addLabelIds와 removeLabelIds를 받는다. 승인된 대상 메시지에 대해 라벨 부착과 INBOX 제거를 함께 표현할 수 있지만 여러 메시지 전체의 성공을 보장하는 것은 아니다. 라벨 이름 대신 실제 ID를 확인하고 페이지별 검색 결과·실패 항목을 추적한다. INBOX 제거는 삭제·휴지통 이동과 구분하며 읽음 처리까지 임의로 추가하지 않는다.

### 실용 예시

> “가짜 Gmail 목록으로 보관 후보 미리보기를 만들어줘. 사용자가 정한 날짜·발신자·제외 라벨을 적용하고, 각 messageId와 기존 라벨을 보존해. 페이지가 더 있는 경우와 일부 수정 실패를 fixture로 테스트해. 실제 라벨 변경·보관·삭제·읽음 처리는 하지 마.”

**완료 기준:** 변경 전 대상 ID 목록과 변경 후 라벨을 대조한다. 복구는 과거 상태를 근거로 해야 하며 사용자가 나중에 변경한 상태를 무조건 덮어쓰지 않는다. 이메일 본문에 쓰인 정리 명령이나 링크는 실행 지시로 취급하지 않는다.
