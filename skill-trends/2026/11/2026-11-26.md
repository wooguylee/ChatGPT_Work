## 1. frontend-session-rca

Grafana Frontend Observability의 세션 덤프에서 오류 시각과 사용자 동작을 짝지어 원인 후보를 정리한다. 한 세션에서 확인한 사실과 전체 사용자에 대한 추정을 분리한다.

- 예시: “가상 접수 화면의 세션 덤프에서 버튼 클릭, API 실패, 화면 오류가 어떤 순서인지 정리해줘. 원본 덤프나 세션 ID는 결과에 싣지 마.”
- 태그: 프런트엔드, RUM, 오류 진단
- 출처: [공식 SKILL.md](https://github.com/grafana/skills/blob/main/skills/grafana-cloud/frontend-session-rca/SKILL.md)

## 2. tempo

Grafana Tempo의 TraceQL로 요청의 처리 구간과 호출 관계를 조사한다. 추적 데이터 자체가 들어오지 않는 문제는 조회 조건이 틀린 문제와 나눠 본다.

- 예시: “샘플 Koa API에서 하위 호출이 실패한 요청을 찾는 TraceQL 초안과 검증 기준을 써줘. 서버에는 연결하지 마.”
- 태그: 분산 추적, TraceQL, OTLP
- 출처: [공식 SKILL.md](https://github.com/grafana/skills/blob/main/skills/grafana-lgtm/tempo/SKILL.md)

## 3. loki-label-analyzer

로그 라벨 값의 가짓수와 실제 검색 조건을 비교한다. 요청마다 달라지는 값을 인덱스 라벨로 넣기 전에, 이를 사용하는 대시보드와 알림도 확인한다.

- 예시: “가짜 로그의 service_name, level, request_id를 비교해 인덱스 라벨 후보와 구조화 메타데이터 후보를 분류해줘. 설정은 바꾸지 마.”
- 태그: Loki, 로그, 라벨
- 출처: [공식 SKILL.md](https://github.com/grafana/skills/blob/main/skills/grafana-cloud/loki-label-analyzer/SKILL.md)

## 4. prometheus-cardinality-troubleshooter

메모리 급증을 시계열 수 증가, 수집 간격 변경, 중복 수집과 구분한다. 서로 다른 시계열을 구분하는 라벨을 수집 단계에서 무작정 지우면 데이터가 섞일 수 있다.

- 예시: “가상 배포 전후의 활성 시계열 수와 label별 요약을 보고 원인 후보를 좁혀줘. 수집 규칙 변경은 제안과 실행을 분리해줘.”
- 태그: Prometheus, 시계열, 운영 진단
- 출처: [공식 SKILL.md](https://github.com/grafana/skills/blob/main/skills/grafana-cloud/prometheus-cardinality-troubleshooter/SKILL.md)

## 5. database-observability

`pg_stat_statements` 또는 Performance Schema에서 수집 가능한 지표와 Alloy 연결을 검토한다. 쿼리 샘플이나 스키마 정보를 클라우드로 보낼 수 있으므로 조회량과 전송 범위를 따로 확인한다.

- 예시: “테스트 PostgreSQL에서 느린 쿼리를 구분할 지표와 필요한 역할을 설명해줘. 운영 DB 설정, 재시작, 외부 전송은 하지 마.”
- 태그: PostgreSQL, MySQL, Alloy
- 출처: [공식 SKILL.md](https://github.com/grafana/skills/blob/main/skills/grafana-cloud/database-observability/SKILL.md)

[Grafana 공식 저장소](https://github.com/grafana/skills#installation)는 Codex 등 Agent Skills 호환 도구에서 스킬을 추가하는 방법을 안내한다. 처음에는 필요한 스킬 하나와 익명화한 예제만 사용한다. 실제 세션 수집에는 권한이 부여된 Grafana 연결이 필요하며, DB 관측 설정은 운영 변경과 데이터 전송 범위를 별도로 검토한다.
