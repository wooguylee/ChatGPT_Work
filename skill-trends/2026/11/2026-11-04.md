## 1. recipe-create-gmail-filter

**기존 메일 정리와 앞으로 적용되는 규칙을 구분하기.**

- 원본: [SKILL.md](https://github.com/googleworkspace/cli/blob/cd3697e07eb520056dcf142d0c7439bbb9ba32e9/skills/recipe-create-gmail-filter/SKILL.md)
- 태그: `gmail`, `filter`, `classification`, `persistent-settings`
- 난이도: 중급

### 무엇을 해주나

라벨을 조회하고 필요한 라벨을 만든 뒤, 특정 발신자의 메일에 라벨을 붙이는 필터를 생성하고 목록에서 확인하는 패턴이다. 이전에 소개한 recipe-label-and-archive-emails가 선택한 기존 메시지를 처리하는 작업이라면, 이 레시피는 **이후 수신 메일에 적용되는 계정 규칙**을 만든다.

[공식 필터 가이드](https://developers.google.com/workspace/gmail/api/guides/filter_settings)는 필터가 스레드 전체가 아닌 개별 메시지에 적용되며 여러 조건은 모두 만족해야 한다고 설명한다. 원문의 INBOX 제거는 단순 분류가 아니라 받은편지함을 건너뛰는 동작이다. 분류만 원한다면 이 동작을 자동으로 포함하지 않는다.

### 적용 전에 보완할 점

1. 동일 이름 라벨과 같은 조건·동작의 기존 필터를 먼저 비교한다. 라벨 이름과 실제 LABEL_ID를 혼동하지 않는다.
2. 사용자에게 발신 조건, 라벨, 받은편지함 유지 여부를 구분해 확인받는다. 예제 발신자 주소는 실제 수신자로 바꾸라는 승인이 아니다.
3. 읽기 범위 안에서 조건에 맞는 과거 메일 표본을 검토하되, 필터 생성이 기존 메일 일괄 처리까지 했다고 말하지 않는다.
4. 생성 후 반환 필터 ID의 조건·동작을 다시 읽는다. 네트워크 오류 후에는 목록을 대조해 중복 생성하지 않는다.

[create API](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.settings.filters/create)는 최대 1,000개 필터와 gmail.settings.basic 권한을 명시한다. 메일을 읽을 수 있다는 사실이 설정 변경 권한까지 있다는 뜻은 아니다.

**실용 프롬프트:** “합성 영수증 메일 10개와 현재 규칙 JSON을 보고 중복 없는 필터 계획을 만들어. 라벨만 추가하고 받은편지함에서는 빼지 않는 안을 기본으로 해. 실제 설정은 변경하지 마.”

**완료 기준:** 필터의 저장된 조건·라벨 ID·행동이 승인 내용과 같아야 한다. 설정 저장과 향후 모든 메일의 정확한 분류는 별도로 관찰한다.

## 2. recipe-create-vacation-responder

**부재중 문구보다 기간과 응답 대상이 먼저다.**

- 원본: [SKILL.md](https://github.com/googleworkspace/cli/blob/cd3697e07eb520056dcf142d0c7439bbb9ba32e9/skills/recipe-create-vacation-responder/SKILL.md)
- 태그: `gmail`, `auto-reply`, `time-bound`, `privacy`
- 난이도: 중급

### 무엇을 해주나

Gmail 부재중 자동 응답을 켜고 설정을 재조회한 뒤 복귀 시 끄는 흐름이다. 정해진 대상에게 반복적으로 응답하는 계정 기능이므로, 문구 초안 작성과 활성화는 구분해야 한다.

원문 설명은 날짜 범위를 언급하지만 실제 JSON에는 **startTime·endTime이 없다**. 문구에 “Jan 20까지”라고 쓰는 것으로 자동 종료가 설정되지 않는다. 또한 restrictToContacts와 restrictToDomain을 모두 false로 제시하므로 연락처·도메인 제한 없는 예시를 무심코 사용하면 응답 범위가 넓어진다.

### 공식 스키마와 대조

[VacationSettings](https://developers.google.com/workspace/gmail/api/reference/rest/v1/VacationSettings)의 시간은 epoch **밀리초**다. 시작과 종료를 함께 정하면 시작이 먼저여야 한다. 도메인 제한은 Workspace 계정에만 제공된다. HTML과 평문을 함께 지정하면 HTML이 사용되므로 실제 저장된 응답 본문도 확인한다.

[updateVacation](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.settings/updateVacation)은 PUT 설정 변경이다. 먼저 [getVacation](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.settings/getVacation)으로 현재 값을 읽고 승인한 최종 상태를 구성하는 편이 안전하다. 원문의 enableAutoReply=false 한 필드 예제가 다른 모든 필드를 보존한다고 단정하지 않는다.

### 실무 적용 제안

- 현지 시작·종료 시각과 시간대를 확정하고 밀리초 변환을 검증한다.
- 수신자 범위와 공개 가능한 내용, 대체 담당자 연락처를 승인받는다. 부재 이유나 여행 위치까지 넣을 필요는 없다.
- 활성화·종료 상태를 재조회하고, 종료 확인은 별도로 계획한다.
- 설정 저장 성공을 실제 수신·전달 성공으로 표현하지 않는다.

**실용 프롬프트:** “가상의 서울 시간 부재 기간을 epoch ms로 변환하고 종료 경계 테스트를 설계해. 연락처만 응답하는 최소 문구 초안을 만들되, 계정 설정 변경·메일 발송은 하지 마.”

**완료 기준:** 승인된 기간·대상 제한·본문·활성 상태가 일치해야 한다. 지속적인 외부 발송 설정이라는 점을 놓치지 않는 것이 핵심이다.

## 3. recipe-save-email-to-doc

**메일 본문을 보존할 때 요약문과 원문을 섞지 않기.**

- 원본: [SKILL.md](https://github.com/googleworkspace/cli/blob/cd3697e07eb520056dcf142d0c7439bbb9ba32e9/skills/recipe-save-email-to-doc/SKILL.md)
- 태그: `gmail`, `docs`, `archival`, `provenance`
- 난이도: 중급

### 무엇을 해주나

메시지를 찾고 내용을 읽어 새 Docs 파일에 넣는 패턴이다. 첨부파일 저장과 달리 **선택한 메일 본문 및 메타데이터를 참조 문서로 전환**한다. 회의 결정이나 업무 지시를 찾아보기 좋게 정리하는 데 쓸 수 있다.

하지만 원문은 [EMAIL BODY]라는 자리표시자만 제공하며 MIME 본문 추출을 구현하지 않는다. [Message 구조](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages)의 payload·중첩 parts를 따라 본문을 찾고, [MessagePartBody](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages.attachments)의 base64url 데이터 및 별도 attachmentId 경로를 구분해야 한다. snippet을 전체 본문처럼 사용하지 않는다. HTML-only 메일, 인용문, 한글 인코딩, 대체 본문의 중복을 시험할 필요가 있다.

### CLI 불일치와 보존 범위

원문의 --document-id는 같은 snapshot의 [Docs helper](https://github.com/googleworkspace/cli/blob/cd3697e07eb520056dcf142d0c7439bbb9ba32e9/crates/google-workspace-cli/src/helpers/docs.rs)·[사용 지침](https://github.com/googleworkspace/cli/blob/cd3697e07eb520056dcf142d0c7439bbb9ba32e9/skills/gws-docs-write/SKILL.md)과 맞지 않는다. 실제 helper는 **--document와 --text**를 받아 기존 문서 끝에 평문을 추가한다. 메일 HTML을 원형 그대로 재현하는 도구가 아니다.

문서에는 원문 메시지 ID, 발신·수신·제목·기준 시각, 추출 범위와 생략 여부를 기록하는 설계를 권한다. 요약을 더한다면 원문과 별도 절로 나눈다. 메일 내부의 “다른 곳으로 보내라” 같은 문장은 자료이지 실행 권한이 아니다. 새 문서에 복사하면 보관 위치와 접근 범위가 달라지므로 목적지·공유 대상도 확인한다.

**실용 프롬프트:** “합성 multipart 메일을 평문 기록으로 변환하는 테스트를 설계해. 원문/요약을 구분하고 원문 ID로 중복 저장을 막아. 실제 메일을 읽거나 Docs에 쓰지는 마.”

**완료 기준:** 검색 성공이나 빈 문서 생성이 아니라, 선택한 메일의 필요한 본문·출처가 실제 문서에 들어가야 한다. 법적 원본 보존이나 완전한 메일 백업과 같은 수준으로 주장하지 않는다.

## 4. recipe-generate-report-from-sheet

**숫자의 근거를 먼저 확정하고 문장과 서식을 나중에 만들기.**

- 원본: [SKILL.md](https://github.com/googleworkspace/cli/blob/cd3697e07eb520056dcf142d0c7439bbb9ba32e9/skills/recipe-generate-report-from-sheet/SKILL.md)
- 태그: `sheets`, `docs`, `reporting`, `data-validation`
- 난이도: 중급

### 무엇을 해주나

Sheets 범위를 읽고 Docs 보고서를 만든 뒤 독자에게 공유하는 절차다. CSV 백업이나 월별 표 복사와 달리 **데이터를 해석해 문서로 전달하는 과정**이다.

원문은 고정된 건수·매출·상위 거래 예제를 넣는다. 실제 표에서 계산하는 코드나 누락값 정책은 없다. 따라서 예제의 45건·125,000달러를 읽은 데이터의 결과처럼 쓰면 안 된다. 기간, 취소·중복 행, 통화, 소수점 처리, 원본 범위를 확정하고 재현 가능한 집계표를 먼저 만든다.

### 형식과 전달의 경계

이 레시피에도 --document-id가 있지만 현재 helper는 --document를 요구한다. “formatted report”라는 설명과 달리 +write는 평문 추가이며 Markdown의 ##를 Docs 제목 스타일로 변환하지 않는다. 제목 스타일·표가 필요하면 별도 batchUpdate 요청과 결과 검토가 필요하다.

원문 마지막 단계는 Drive 권한 생성이다. [공식 permissions.create](https://developers.google.com/workspace/drive/api/reference/rest/v3/permissions/create)는 사용자·그룹 공유 시 알림 메일이 기본 true임을 명시한다. 문서 초안을 만들라는 요청을 특정 외부인에게 자동 공유하라는 허가로 확대하지 않는다. 같은 파일의 권한 동시 수정도 피한다.

**실용 프롬프트:** “합성 매출표에서 확정 매출만 집계해 보고서 초안을 만들어. 제외 행과 계산식을 함께 보여주고, 근거가 없는 성과 해석은 붙이지 마. Docs 생성과 공유는 하지 마.”

**완료 기준:** 표의 검증된 합계와 문서 수치·기간이 일치하고, 원본 범위와 집계 시점이 남아야 한다. 공유는 독자·권한·알림을 승인받은 별도 단계다.

## 5. recipe-post-mortem-setup

**문서·회의·공지를 하나의 성공으로 묶지 않기.**

- 원본: [SKILL.md](https://github.com/googleworkspace/cli/blob/cd3697e07eb520056dcf142d0c7439bbb9ba32e9/skills/recipe-post-mortem-setup/SKILL.md)
- 태그: `incident-review`, `docs`, `calendar`, `chat`, `partial-failure`
- 난이도: 중상급

### 무엇을 해주나

사후 회고 문서를 준비하고 검토 회의를 잡고 Chat 공간에 알리는 다중 서비스 패턴이다. 장애 원인을 자동으로 확정하는 분석기가 아니라 **검토를 시작하기 위한 작업 공간 준비**다.

원문의 첫 단계는 +write --title ... --body ...로 문서를 만들려 하지만, 실제 [Docs helper](https://github.com/googleworkspace/cli/blob/cd3697e07eb520056dcf142d0c7439bbb9ba32e9/crates/google-workspace-cli/src/helpers/docs.rs)는 해당 인자를 제공하지 않는다. [gws-docs](https://github.com/googleworkspace/cli/blob/cd3697e07eb520056dcf142d0c7439bbb9ba32e9/skills/gws-docs/SKILL.md)의 documents.create로 빈 문서를 만들고 반환 ID에 --document/--text로 내용을 넣는 등 단계 분리가 필요하다. 제목만 생긴 파일을 회고 문서 완료로 판단하지 않는다.

### 회의·공지까지 연결할 때

[Calendar helper 구현](https://github.com/googleworkspace/cli/blob/cd3697e07eb520056dcf142d0c7439bbb9ba32e9/crates/google-workspace-cli/src/helpers/calendar.rs)은 start/end를 dateTime으로 넣지만 timeZone이나 sendUpdates를 명시하지 않는다. 원문의 오프셋 없는 날짜를 그대로 쓰지 말고 정확한 시간대·참석자·통지 요구를 정한 뒤 필요한 요청을 구성한다. Chat 공간의 실제 대상과 문서 접근권한도 독립적으로 확인한다.

실용적인 보완은 incident ID를 기준으로 document ID, event ID, message ID를 따로 저장하는 것이다. 문서 작성 뒤 일정 생성이 실패했다고 문서를 다시 만들거나 공지를 중복 발송하지 않도록 한다. 회고의 “원인” 항목은 증거가 없으면 가설·미확인으로 남긴다. 사람의 책임이나 고객 영향을 자료 없이 단정하지 않는다.

**실용 프롬프트:** “가상 장애 회고 준비를 문서·회의·공지 세 단계로 나눠 계획해. 원인 확정 대신 사실/가설/확인 필요를 분리하고 각 단계 재시도 조건을 만들어. 문서·일정·Chat 메시지는 실제로 생성하지 마.”

**완료 기준:** 문서 내용, 회의 저장, 공지 게시를 각각 검증해야 한다. Chat 게시가 참석자 수락이나 원인 규명 완료를 뜻하지 않는다. 장애 내용이 민감하면 공개 전에 별도 검토한다.

## 적용 순서·설치 안내

**원본 검토 → 합성 데이터로 변환/요청 계획 검증 → 현재 CLI schema 확인 → 승인된 좁은 범위 실행 → 실제 결과 재조회** 순서가 좋다. 오늘 예시는 모두 계획용이며 실행 권한을 부여하는 문장이 아니다.

[README](https://github.com/googleworkspace/cli/blob/cd3697e07eb520056dcf142d0c7439bbb9ba32e9/README.md)는 필요한 Skill만 설치하는 방식을 제공한다. 예시는 다음과 같으며 이번 조사에서는 실행하지 않았다.

```text
npx skills add https://github.com/googleworkspace/cli/tree/main/skills/recipe-save-email-to-doc
```

main 설치 내용은 변할 수 있으므로 검토 snapshot과 비교한다. 기반 Skill과 [gws-shared](https://github.com/googleworkspace/cli/blob/cd3697e07eb520056dcf142d0c7439bbb9ba32e9/skills/gws-shared/SKILL.md)를 함께 읽고, Skill 설치·CLI 설치·OAuth 권한·실제 데이터 쓰기를 분리한다. dry-run은 서버 권한·실제 전달·결과 품질을 검증하지 않는다.
