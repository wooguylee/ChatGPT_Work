## 1. langchain-fundamentals

### 무엇을 돕는가

LangChain 에이전트를 처음 만들거나, 임시로 이어 붙인 도구 호출 코드를 정리할 때 유용한 스킬입니다. Python의 create_agent와 TypeScript의 createAgent를 중심으로 도구 정의, 대화 상태, 승인 미들웨어, 구조화된 출력을 다룹니다. 핵심은 “모델이 답변한다”에서 끝나지 않고, 어떤 도구를 호출하며 언제 사람의 판단을 기다릴지 명시하는 것입니다. [고정 원문](https://github.com/langchain-ai/langchain-skills/blob/126c384d8552dcb476b226c244172186cc3f4328/config/skills/langchain-fundamentals/SKILL.md)

**태그**  
#LangChain #에이전트 #도구호출 #HITL #상태관리

**난이도: 중급**  
Python 함수·타입 또는 TypeScript·Zod를 이해하면 시작할 수 있습니다. 다만 재시작 후 복구, 여러 사용자 간 상태 분리, 외부 변경 작업의 승인까지 다루면 중급 수준입니다.

### 실용 예시

상품 정보 조회와 계산을 조합하는 상담 보조, 내부 시스템을 읽고 변경안을 제안하는 운영 도우미, 일정한 스키마로 결과를 반환하는 추출 작업에 적합합니다. 단순한 정보 추출이라면 에이전트 루프 없이 모델 수준의 구조화된 출력으로 충분할 수도 있습니다. 현재 공식 문서도 create_agent를 작은 실행 구조를 직접 구성하는 선택지로 설명합니다. [공식 에이전트 문서](https://docs.langchain.com/oss/python/langchain/agents)

**합성 프롬프트 예시:** “가상의 재고 데이터만 사용하는 Python 데모를 설계해 줘. 재고 조회와 합계 계산은 자동으로 처리하되, 발주 등록 모의 도구는 반드시 사람의 승인 뒤에만 실행하도록 해 줘. 서로 다른 두 thread_id의 대화가 섞이지 않게 하고, 도구 오류와 승인 거절을 테스트해 줘. 외부 서비스나 실제 고객 데이터는 사용하지 마.”

**테스트 가능한 완료 기준**
- 조회·계산 도구의 입력 스키마와 설명이 명확하고, 정상 입력의 예상 결과가 일치한다.
- 발주 등록 모의 도구는 승인 전 실행 횟수가 0이고, 거절 후에도 실행되지 않는다.
- 승인 후에는 대상 작업이 한 번만 반영되며, 재시도 시 중복 처리 방식을 설명한다.
- 같은 thread_id에서는 앞선 대화를 이어가고, 다른 thread_id에는 해당 내용이 노출되지 않는다.
- 구조화된 출력과 도구 오류 경로에 대한 검증 결과를 남긴다.

### 주의점과 최신성 확인

원문의 MemorySaver 예제를 영속 데이터베이스로 오해하면 안 됩니다. 현재 공식 문서는 InMemorySaver를 시험용으로, 운영에는 데이터베이스 기반 체크포인터를 권장합니다. 사람의 승인 흐름에는 체크포인터와 thread_id가 필요하며, 승인 UI를 붙이는 것만으로 접근 권한이나 중복 실행 문제가 해결되지는 않습니다. [단기 메모리](https://docs.langchain.com/oss/python/langchain/short-term-memory), [사람의 승인 흐름](https://docs.langchain.com/oss/python/langchain/human-in-the-loop)

원문의 “다른 모든 방식은 구식”이라는 표현은 과도합니다. create_agent는 유용한 기본 선택지지만 모든 작업에 에이전트가 필요한 것은 아닙니다. 샘플의 모델명도 그대로 고정하지 말고 실제 공급자의 지원 여부를 확인해야 합니다. 날씨 예제는 실시간 조회가 아니라 고정 문자열을 반환하는 모의 도구입니다.

## 2. langchain-rag

### 무엇을 돕는가

문서를 불러오고, 청크로 나누고, 임베딩을 만들어 저장한 뒤, 질문과 관련된 내용을 검색해 답변에 제공하는 RAG의 전체 흐름을 정리한 스킬입니다. PDF·웹·디렉터리 로더, RecursiveCharacterTextSplitter, OpenAI 임베딩, 메모리 저장소·Chroma·FAISS, 유사도 검색·MMR·메타데이터 필터를 다룹니다. 검색기를 에이전트의 도구로 연결하는 예제도 있습니다. [고정 원문](https://github.com/langchain-ai/langchain-skills/blob/126c384d8552dcb476b226c244172186cc3f4328/config/skills/langchain-rag/SKILL.md)

**태그**  
#RAG #문서검색 #임베딩 #벡터저장소 #검색평가

**난이도: 중급**  
기본 구현은 짧지만, 좋은 결과를 내려면 문서 추출 품질과 검색 성능을 따로 확인해야 합니다. 모델이 자연스럽게 답했다는 이유만으로 검색이 정확했다고 판단하면 안 됩니다.

### 실용 예시

제품 매뉴얼 질의응답, 공개 정책 문서 검색, 개발 문서 보조에 적합합니다. 질문마다 검색 후 답변하는 2단계 RAG는 흐름을 예측하기 쉽고, 여러 검색 수단 중 필요한 것을 모델이 고르는 에이전트형 RAG는 더 유연합니다. 이미 검색 가능한 데이터베이스가 있다면 무조건 새 벡터 저장소부터 만들 필요도 없습니다. [공식 검색·RAG 문서](https://docs.langchain.com/oss/python/deepagents/retrieval)

**합성 프롬프트 예시:** “가상의 공개 제품 매뉴얼 10개로 RAG 데모를 설계해 줘. 문서명·절 번호·버전을 메타데이터에 보존하고, 답변마다 근거 문서를 표시해 줘. 정답이 있는 질문 15개와 자료에 답이 없는 질문 5개를 만들어 검색과 답변을 따로 평가해 줘. 근거가 없으면 추측하지 말고 확인할 수 없다고 답하게 해 줘.”

**테스트 가능한 완료 기준**
- 각 청크에서 원문 문서와 위치를 역추적할 수 있다.
- 정답 근거가 표시된 평가 질문 15개 중 최소 12개에서 해당 근거가 상위 4개 검색 결과에 포함된다. 이 수치는 합성 데모의 임시 합격선이며 제품 성능 주장이나 모든 RAG의 권장 기준은 아니다.
- 답이 없는 질문 5개 모두에서 출처나 사실을 지어내지 않는다.
- 답변의 출처가 실제 검색된 청크와 일치한다.
- 영속 저장소를 선택했다면 재시작 후에도 문서 수와 검색 결과를 점검한다.
- 임베딩 모델·차원·분할 설정·사용한 패키지 버전을 기록한다.

### 주의점과 최신성 확인

원문의 “임베딩 차원을 설정할 수 없다”는 설명은 수정이 필요합니다. 공식 OpenAIEmbeddings 문서는 text-embedding-3 계열의 dimensions 설정을 지원합니다. 인덱스와 질의에 같은 임베딩 설정을 사용하고, 저장소 차원도 맞춰야 합니다. 최신 공식 예제의 Python InMemoryVectorStore 경로는 langchain_core.vectorstores입니다. 원문의 community 경로를 그대로 복사하기보다 현재 버전에서 확인하는 편이 안전합니다. [공식 임베딩 통합 문서](https://docs.langchain.com/oss/python/integrations/embeddings/openai)

청크 500~1,500자와 겹침 10~20%는 출발점이지 보편적인 정답이 아닙니다. 기본 길이는 토큰이 아니라 문자 기준이며, 문서 구조와 언어에 맞춰 평가해야 합니다. [공식 분할 문서](https://docs.langchain.com/oss/python/integrations/splitters/recursive_text_splitter)

FAISS의 allow_dangerous_deserialization은 신뢰할 수 없는 저장 파일에서 임의 코드 실행 위험을 만들 수 있습니다. 오류를 없애려고 켜지 말고, 자신이 만들고 계속 통제해 변조되지 않은 인덱스인지 먼저 확인해야 합니다. 검색 문서 속 지시문을 실행 지시로 취급하지 말고, 개인정보가 임베딩·모델 공급자로 전송되는 범위를 먼저 확인하는 것도 실무 점검 사항입니다.

## 3. langgraph-fundamentals

**태그:** LangGraph, 워크플로, 상태 관리, 병렬 처리, Python, TypeScript  
**난이도:** 중급. 함수·타입·비동기 처리의 기본 지식이 있으면 접근하기 좋습니다.

### 무엇을 배우나

여러 단계로 움직이는 AI 기능을 공유 상태, 작업 노드, 실행 경로로 나누는 스킬입니다. 조건에 따라 다른 작업을 실행하거나, 여러 자료를 동시에 처리한 뒤 결과를 합치는 흐름에 적합합니다. 핵심 범위는 StateGraph, 상태 스키마와 reducer, 조건부 경로, Command, Send, 실행·스트리밍, 오류 처리입니다. 단순한 한 번의 모델 호출보다 흐름을 직접 제어해야 할 때 가치가 큽니다. [고정 버전 원문](https://github.com/langchain-ai/langchain-skills/blob/126c384d8552dcb476b226c244172186cc3f4328/config/skills/langgraph-fundamentals/SKILL.md)

### 어디에 쓰나

문의 내용을 먼저 분류하고, 문서 검색이 필요한 문의만 검색 단계로 보내는 고객지원 초안 생성기가 좋은 예입니다. 여러 문서를 병렬로 요약한 뒤 최종 초안을 만드는 작업에도 응용할 수 있습니다. 처음부터 실제 모델과 외부 API를 연결하기보다, 고정 입력을 반환하는 가짜 노드로 분기·합류·종료를 확인하면 구조 문제를 모델 API 호출 비용 없이 찾기 쉽습니다. 그래프는 실행 전에 compile이 필요하며, 노드는 상태 전체를 직접 수정하기보다 변경할 부분만 반환하도록 설계합니다. [공식 Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api)

### 요청 예시 · 설명용 가상 프롬프트

“Python으로 고객 문의 초안 생성 그래프를 설계해 줘. 일반 문의는 바로 답변 초안을 만들고, 제품 문의는 가짜 문서 세 개를 Send로 병렬 분석한 뒤 합쳐 줘. 외부 API·메일 전송은 쓰지 말고, 상태 스키마와 reducer를 명시해 줘. 빈 문서 목록, 한 작업의 일시 오류, 정상 종료를 검증하는 테스트와 단계별 진행 표시도 포함해 줘.”

### 완료 판정 기준

- 일반 문의와 제품 문의가 각각 지정한 노드만 통과한다.
- 문서 세 개의 결과가 누락·중복 없이 합쳐지고, 빈 목록도 종료한다.
- 임시 오류만 설정한 횟수까지 재시도하며, 예상하지 못한 오류는 숨기지 않는다.
- 반복 경로에 종료 조건이 있고, 진행 표시와 최종 결과를 구분한다.
- 실행 결과를 실제 검증했는지, 설계만 제시했는지 명확히 밝힌다.

### 주의할 점과 원문 보완

Command의 goto는 기존 정적 경로를 취소하지 않습니다. 같은 노드에 정적 경로까지 남기면 양쪽이 실행될 수 있습니다. 또한 [원문 Python 참조](https://github.com/langchain-ai/langchain-skills/blob/126c384d8552dcb476b226c244172186cc3f4328/config/skills/langgraph-fundamentals/references/python.md)의 “reducer가 없으면 마지막 병렬 결과가 덮어쓴다”는 설명은 부정확합니다. 같은 단계에서 여러 노드가 일반 상태 필드에 쓰면 동시 업데이트 오류가 발생할 수 있으므로, 순차 덮어쓰기와 병렬 병합을 구별해야 합니다. [공식 동시 업데이트 오류 설명](https://docs.langchain.com/oss/python/langgraph/errors/INVALID_CONCURRENT_GRAPH_UPDATE)

메시지 이력에는 단순 리스트 연결보다 메시지 ID 기반 수정·삭제를 지원하는 reducer가 유용합니다. TypeScript의 StateSchema·ReducedValue·MessagesValue는 현재 공식 문서에도 등장하지만, 기존 프로젝트의 설치 버전과 타입을 먼저 확인해야 합니다. [공식 TypeScript 상태 정의](https://docs.langchain.com/oss/javascript/langgraph/graph-api)

## 4. langgraph-persistence

**태그:** LangGraph, 체크포인트, 대화 기억, PostgreSQL, 재개, 상태 이력  
**난이도:** 중상급. 그래프 상태와 저장소 연결을 이해하면 활용하기 좋습니다.

### 무엇을 배우나

한 번 실행하고 끝나는 그래프를 대화를 이어가고 실패에서 복구할 수 있는 애플리케이션으로 확장합니다. Checkpointer는 특정 thread의 그래프 상태를 기록하고, Store는 여러 thread에서 공유할 사용자 선호나 애플리케이션 데이터를 보관합니다. 이 둘은 역할이 다르므로 “기억 기능” 하나로 묶어 생각하지 않는 것이 중요합니다. 상태 이력 조회, 과거 체크포인트에서 재실행·분기하기, 하위 그래프의 저장 범위도 다룹니다. [고정 버전 원문](https://github.com/langchain-ai/langchain-skills/blob/126c384d8552dcb476b226c244172186cc3f4328/config/skills/langgraph-persistence/SKILL.md), [공식 Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)

### 어디에 쓰나

상담 중 새 질문을 받아도 앞선 맥락을 유지하거나, 오래 걸리는 자료 조사에서 실패한 단계를 다시 실행할 때 유용합니다. 사용자의 응답 언어처럼 대화가 바뀌어도 필요한 정보는 Store에 분리할 수 있습니다. 운영 환경에서는 메모리 저장소만으로 재시작 후 복구를 기대하면 안 됩니다. PostgreSQL 같은 영속 저장소를 쓰고 실제 프로세스 재시작 테스트를 해야 합니다. Agent Server를 사용하는 경우에는 저장 인프라가 자동 관리되므로, 별도 구성이 필요한 배포인지 먼저 구별합니다. [공식 메모리 안내](https://docs.langchain.com/oss/python/langgraph/add-memory), [공식 Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)

### 요청 예시 · 설명용 가상 프롬프트

“가짜 사용자 A·B만 사용하는 상담 그래프의 저장 설계를 만들어 줘. 대화 상태는 thread별로, 응답 언어는 사용자별 Store에 분리해 줘. 개발용 메모리 저장소와 테스트용 PostgreSQL 구성을 구별하고, 재시작 후 복원·사용자 간 분리·과거 상태에서의 분기 테스트를 제시해 줘. 실제 개인정보나 운영 DB는 사용하지 말고, 외부 전송은 가짜 함수로 대체해 줘.”

### 완료 판정 기준

- 같은 thread에는 이전 상태가 이어지고 다른 thread의 대화는 섞이지 않는다.
- 같은 사용자의 다른 thread에서 승인된 선호 정보만 공유된다.
- 영속 저장소 구성은 프로세스를 다시 시작해도 상태가 복원된다.
- 새 입력, 오류 후 재개, interrupt 응답, 과거 체크포인트 재실행을 구분해 테스트한다.
- reducer가 있는 필드를 수정할 때 추가와 완전 교체가 각각 기대대로 동작한다.

### 주의할 점과 원문 보완

thread_id를 같게 주는 것만으로 “중단 지점부터 재개”되는 것은 아닙니다. 새 입력은 기존 상태에 적용된 뒤 진입점부터 실행하고, 미완료 작업 재개와 interrupt 응답은 다른 호출 방식을 사용합니다. 과거 체크포인트 이후의 모델 호출·API 요청도 다시 실행되므로 외부 부작용의 중복 방지가 필요합니다. [공식 Checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers)

상위 그래프에 checkpointer가 있는 경우 하위 그래프의 기본 설정(None)은 호출별 상태, True는 같은 thread의 호출 간 상태, False는 체크포인트 없음에 해당합니다. True로 만든 같은 하위 그래프를 병렬 호출하면 저장 영역이 충돌할 수 있습니다. [공식 Subgraphs](https://docs.langchain.com/oss/python/langgraph/use-subgraphs)

원문의 Python 초기화 주석처럼 from_conn_string 반환값에 곧바로 setup을 연결하지 말고, 공식 예시처럼 컨텍스트 관리자 안에서 초기화해야 합니다. 또 원문의 병렬 하위 에이전트 예시는 Python create_agent에 prompt를 넘기지만, 현재 공식 예시는 system_prompt를 사용합니다. 이 스킬은 복사해 바로 실행하는 완성 코드보다 저장 범위와 검증 항목을 정하는 안내서로 쓰는 편이 안전합니다. [공식 메모리 예시](https://docs.langchain.com/oss/python/langgraph/add-memory), [공식 하위 에이전트 예시](https://docs.langchain.com/oss/python/langgraph/use-subgraphs)

thread_id와 Store namespace는 데이터 구분 키이지 사용자 인증 자체가 아니다. 서버가 검증한 신원에 따라 소유권을 검사하고, 클라이언트가 임의의 사용자 ID·thread를 선택해 다른 사람의 상태를 읽지 못하게 해야 한다. 보관 기간·삭제·백업 접근 범위도 별도로 정한다.

## 5. langgraph-human-in-the-loop

### 무엇을 돕는가

에이전트가 작업 도중 멈춰 사람의 승인이나 수정 입력을 받은 뒤 이어서 진행하도록 만드는 구현 스킬입니다. 핵심은 interrupt()로 검토할 내용을 전달하고, 같은 thread_id에 Command(resume=...)를 보내 재개하는 흐름입니다. 중단 상태를 저장하는 checkpointer와 JSON 직렬화 가능한 검토 데이터가 필요합니다. 승인·거절 분기, 잘못된 입력 재요청, 병렬 작업별 승인까지 다룹니다. [고정 원문](https://github.com/langchain-ai/langchain-skills/blob/126c384d8552dcb476b226c244172186cc3f4328/config/skills/langgraph-human-in-the-loop/SKILL.md)

**태그**  
LangGraph · 사람 승인 · 상태 복원 · 안전한 자동화

**난이도: 중상급**  
그래프의 상태·노드·체크포인트 개념을 알고 있다면 활용하기 좋습니다. 실서비스에서는 승인 화면보다 재실행과 중복 처리 방지가 더 어렵습니다.

### 실용 예시

고객 답변 초안을 담당자가 수정한 다음 발송하는 흐름, 운영 설정 변경 전 검토, 필수 입력이 빠진 업무를 사용자에게 되돌려 보내는 흐름에 적합합니다. 단순히 “승인하시겠습니까?”라고 묻는 프롬프트가 아니라, 실제 실행 경로를 승인 지점에서 중단한다는 것이 핵심입니다.

**합성 프롬프트 예시:** “Python LangGraph로 고객 답변 검토 예제를 만들어줘. 실제 메일 대신 호출 횟수를 기록하는 가짜 발송 도구를 사용해. 초안과 수신자를 보여주고 승인·수정·거절을 받아. 잘못된 승인 데이터는 다시 질문하고, 같은 작업을 재개해도 중복 발송하지 않게 해. 테스트와 실패 시나리오도 포함해.”

**테스트 가능한 완료 기준**
- 최초 실행은 승인 요청을 반환하며 발송 횟수가 0이다.
- 거절하면 발송 없이 종료하고, 수정 승인하면 수정된 내용만 발송한다.
- 올바른 thread_id로 재개되고, 다른 작업의 승인 응답이 섞이지 않는다.
- 재시도와 복구 테스트에서 동일 작업의 발송 기록이 중복되지 않는다.

### 주의점과 최신성 확인

재개할 때는 중단한 노드가 처음부터 다시 실행됩니다. 따라서 interrupt() 이전의 외부 쓰기는 멱등성을 보장해야 합니다. 원문의 “중단 뒤에 두면 한 번만 실행”이라는 주석도 장애·재시도 전체에 대한 정확히 한 번 실행 보장으로 확대하면 안 됩니다. 승인 이후 발송에도 작업별 중복 방지가 필요합니다.

현재 문서는 interrupt를 포괄적 예외 처리로 삼키지 말고, 한 노드 안의 interrupt 순서를 바꾸지 말라고 추가로 강조합니다. 기본 invoke()의 __interrupt__ 방식은 여전히 유효하며, 현재 문서는 v3 이벤트 스트리밍도 안내합니다. 원문 설명에 언급된 전체 4단계 오류 처리 전략은 본문에서 별도 fundamentals 스킬로 넘깁니다. [공식 Interrupts 문서](https://docs.langchain.com/oss/python/langgraph/interrupts)

승인 응답은 신뢰할 수 있는 사용자·작업에 연결해야 한다. 승인 대상의 수신자·본문·인자가 바뀌면 오래된 승인으로 실행하지 않도록 작업 버전도 확인한다. interrupt 자체가 승인자의 신원이나 업무 권한까지 검증해 주는 것은 아니다.

## 6. deep-agents-memory

### 무엇을 돕는가

Deep Agents의 파일 접근과 기억 저장 위치를 설계하는 스킬입니다. StateBackend로 한 스레드의 작업 파일을 관리하고, StoreBackend로 여러 스레드에서 사용할 정보를 저장하며, CompositeBackend로 경로별 저장소를 나눕니다. 예를 들어 초안은 기본 작업 공간에 두고, 명시적으로 저장한 선호만 /memories/ 아래에 보관할 수 있습니다. [고정 원문](https://github.com/langchain-ai/langchain-skills/blob/126c384d8552dcb476b226c244172186cc3f4328/config/skills/deep-agents-memory/SKILL.md)

**태그**  
Deep Agents · 장기 기억 · 파일시스템 · 저장소 분리

**난이도: 중상급**  
로컬 데모는 비교적 간단하지만, 운영용으로 만들려면 저장 수명과 사용자별 접근 범위를 설계해야 합니다.

### 실용 예시

매번 다시 설명하기 번거로운 문서 형식이나 명시적인 사용자 선호를 다음 대화에서도 활용하는 비서, 작업 중간 결과와 프로젝트 지식을 분리하는 조사 에이전트에 적합합니다. 모든 대화를 무조건 기억하게 만드는 기능으로 보기보다는, 무엇을 어디에 저장하고 다시 읽을지 통제하는 구조로 이해하면 좋습니다.

**합성 프롬프트 예시:** “Deep Agents로 합성 사용자 A와 B의 문서 작성 비서를 설계해줘. /drafts/는 스레드별 임시 영역, /memories/는 사용자별 장기 영역으로 분리해. A가 명시적으로 저장한 ‘요약은 세 문장’ 선호는 A의 새 스레드에서 읽되 B에게는 보이지 않아야 해. 개발용 메모리 저장소와 운영용 영속 저장소를 구분하고, 현재 버전 API로 테스트를 작성해.”

**테스트 가능한 완료 기준**
- A의 새 스레드는 A의 저장된 선호를 읽고, 이전 스레드의 임시 초안은 읽지 못한다.
- B는 A의 기억을 조회하거나 수정할 수 없다.
- 경로별 라우팅 테스트로 /memories/와 기본 영역의 저장소가 구분된다.
- 운영용 저장소에서는 프로세스 재시작 뒤에도 기억이 남는다.
- 사용자 요청에 따른 수정·삭제 후 이전 내용이 계속 사용되지 않는지 검사한다.

### 주의점과 최신성 확인

원문의 backend=lambda rt: ... 및 StateBackend(rt), StoreBackend(rt) 패턴은 현재 공식 문서상 deepagents 0.5.0부터 deprecated입니다. 새 구현은 backend 인스턴스를 직접 전달하는 방식으로 작성하는 것이 권장됩니다. 문서는 기존 factory가 아직 동작하며 deprecation warning을 낸다고 설명하므로 이미 제거된 API라고 표현하지 않습니다. InMemoryStore는 스레드 간 공유 데모에는 쓸 수 있지만 재시작을 견디는 영속 저장소는 아닙니다. 또한 StateBackend를 “대화가 끝나면 무조건 삭제”로 해석하면 부정확합니다. 같은 스레드에서의 복원은 checkpointer 구성에 달려 있습니다. [공식 Backends 문서](https://docs.langchain.com/oss/python/deepagents/backends)

namespace callback은 여전히 필요할 수 있으며, 폐기 권고 대상인 backend factory와 다른 개념입니다. 사용자별 namespace는 검증된 신원에서 만들고 실행 중 바뀌지 않게 해야 합니다.

기억을 지워도 과거 checkpoint·백업·모델 입력에 남은 사본이 자동으로 모두 삭제되는 것은 아닙니다. 삭제 검증은 기억 파일뿐 아니라 관련 보관 범위까지 따로 정해야 합니다.

기억 저장과 자동 활용도 구분해야 합니다. 현재 문서는 memory=로 읽을 파일을 지정하는 방식과 사용자별 namespace 격리를 설명합니다. 다중 사용자 서비스에서 공유 namespace를 그대로 쓰면 개인 정보가 섞일 수 있습니다. 로컬 파일 접근의 virtual_mode는 경로 제한이며, 별도의 셸 실행까지 격리하는 보안 경계로 간주하면 안 됩니다. [공식 Memory 문서](https://docs.langchain.com/oss/python/deepagents/memory)

## 적용 순서와 설치 안내

**작은 도구 하나 → 상태와 분기 → 재시작 복구 → 승인·재개 → 필요할 때 검색과 장기 기억** 순서로 검증 범위를 늘리는 편이 좋다. 여섯 Skill을 동시에 설치하거나 모든 프레임워크 계층을 한 프로젝트에 추가할 필요는 없다. 단순 도구 반복은 LangChain으로 시작하고, 정확한 분기·병렬·복구 제어가 필요할 때 LangGraph를 검토한다.

아래는 현재 [skills CLI 공식 명령 문서](https://github.com/vercel-labs/skills/blob/main/docs/commands.md)에서 확인한 full commit 고정·개별 선택 형식을 적용한 **설치 예시**다. 이번 조사에서는 실행하지 않았다.

```bash
npx skills add langchain-ai/langchain-skills@126c384d8552dcb476b226c244172186cc3f4328 --skill langgraph-fundamentals --agent codex
```

기본 프로젝트 범위를 사용하고 전체 선택·global·확인 생략 옵션은 넣지 않았다. 원본 디렉터리의 references까지 함께 검토한다. [CLI README](https://github.com/vercel-labs/skills/blob/main/README.md)는 현재 Node.js **22.20 이상**과 익명 사용 데이터 수집을 안내하며, DISABLE_TELEMETRY=1 또는 DO_NOT_TRACK=1로 telemetry·security-audit 요청을 끌 수 있다고 설명한다. Skill 원본을 고정해도 npx가 가져오는 CLI 자체의 버전까지 고정되는 것은 아니다. 조직의 승인된 버전·설치 정책을 따른다.

Skill 설치는 Python·TypeScript 패키지 설치, 공급자 키 설정, 데이터 접근, LangSmith 추적 활성화, 클라우드 배포와 다른 단계다. 키를 채팅·보고서·저장소에 넣지 않으며, 추적을 켜기 전 프롬프트·도구 인자·문서·출력이 어디로 전달되는지 검토한다. 원문의 강한 호출 지시나 외부 검색 결과는 사용자 권한을 넓혀 주지 않는다.

## 조사와 저장 검증 절차

1. 서울 기준 날짜, 루트 README와 truncated=false 전체 tree를 확인했다. 별도 AGENTS·skill-trends README 지침은 없고 당일 보고서도 없었다.
2. 기존 날짜별 보고서 **68개 전체**, 소개 제목 **382개**, 전체 인덱스를 대조했다. 코드 표기·Octocode 복합 이름·brainstorming 부제를 정규화한 결과 누락·최초 소개일 불일치·중복 0개였다. 최근 보고서와 전주 같은 요일의 형식을 확인했다.
3. 고정 원문 여섯 개와 관련 참고문서·라이선스, 현재 공식 제품 문서를 읽었다. 예시는 합성이며 모델 호출·임베딩·검색 인덱스 생성·DB 연결·패키지 설치·테스트·배포는 수행하지 않았다.
4. 당일 보고서를 main에 저장하고 **전체 원문을 다시 읽어 작성본과 정확한 일치를 먼저 검증**한다. 이후 최신 소개 인덱스·CHANGELOG의 기존 내용을 보존하며 추가하고, 변경한 세 파일을 main에서 범위 제한 없이 다시 읽어 전체 대조한다. 동시 변경이 있으면 최신 파일을 다시 읽고 안전하게 반영한다. 저장 결과는 CHANGELOG에 남긴다.
5. 과거 날짜 보고서, 다른 보고서 경로, 자동화 설정은 변경하지 않는다.
