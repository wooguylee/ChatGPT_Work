## 1. aws-containers

ECS Express Mode, 서비스·태스크 정의, ECR 등 컨테이너 배포의 선택지를 구분하고 필요한 하위 지침을 불러오는 스킬이다. 배포 롤백과 배치 실패는 ECS 서비스 이벤트·중단 사유를 먼저 보고, 오케스트레이션 판단 근거가 부족할 때만 ECS Action Logs를 살핀다. 이미지 풀 실패부터 Action Logs로 쫓는 방식은 적합하지 않다.

- 예시: “Koa 이미지의 Express Mode와 일반 ECS/Fargate 배포안을 비교해줘. 태스크 역할과 실행 역할을 구분하고, 실패 진단 순서를 적되 배포하지 마.”
- 태그: ECS, Fargate, ECR, Docker
- 출처: [SKILL.md](https://github.com/aws/agent-toolkit-for-aws/blob/main/skills/core-skills/aws-containers/SKILL.md) · [ECS Action Logs 지침](https://github.com/aws/agent-toolkit-for-aws/blob/main/skills/core-skills/aws-containers/references/action-logs.md)

## 2. aws-networking

Route 53, CloudFront, WAF 등에서 요청이 어느 계층의 문제인지 먼저 가르고 서비스별 스킬로 넘기는 라우터다. CloudFront의 VPC Origin은 분류 대상이지만 VPC 서브넷·보안 그룹·ALB 자체 설계까지 이 스킬 하나가 구현하지는 않는다.

- 예시: “CloudFront의 /api 경로에서 간헐적인 502가 나. 캐시 동작·오리진 연결·ALB 대상 상태 중 각각 무엇을 확인해야 하는지 분리해줘. 변경은 하지 마.”
- 태그: CloudFront, Route 53, WAF, DNS
- 출처: [SKILL.md](https://github.com/aws/agent-toolkit-for-aws/blob/main/skills/core-skills/aws-networking/SKILL.md) · [CloudFront VPC Origin 공식 문서](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-vpc-origins.html)

## 3. aws-storage

저장소를 정하기 전에 애플리케이션이 객체 API를 호출하는지, 공유 파일시스템이 필요한지, 인스턴스에 붙는 블록 디스크가 필요한지 확인한다. 저장 단가만이 아니라 요청·전송·수명주기 비용과 복구 요구를 함께 본다. 관리형 DB 엔진 선택은 범위 밖이다.

- 예시: “PDF 보관 서비스의 객체 크기·조회 빈도·보존 기간을 전제로 S3 저장 클래스 후보를 비교해줘. 요금은 도쿄가 아니라 서울 리전 공식 페이지로 확인하고 미확인 수치는 빼줘.”
- 태그: S3, EFS, EBS, 수명주기
- 출처: [SKILL.md](https://github.com/aws/agent-toolkit-for-aws/blob/main/skills/core-skills/aws-storage/SKILL.md) · [S3 공식 요금](https://aws.amazon.com/s3/pricing/)

## 4. aws-observability

Classic CloudWatch와 CloudWatch Omni의 데이터와 쿼리 방식을 구분한 뒤 그 환경에서 사용 가능한 신호를 찾는다. 예컨대 Classic 로그 그룹에서 조회할 때는 Logs Insights 지침을 보고, 이미 구성된 Omni Space에서는 해당 데이터와 쿼리 지원 범위를 별도로 확인한다. 수집과 접근 권한의 첫 설정은 별도 스킬 영역이다.

- 예시: “ECS 서비스의 지연이 늘어난 30분 동안 기존 로그·지표·트레이스에서 확인할 순서를 만들어줘. 환경이 Classic인지 Omni인지 먼저 구분하고 알람은 생성하지 마.”
- 태그: CloudWatch, Logs Insights, X-Ray, OpenTelemetry
- 출처: [SKILL.md](https://github.com/aws/agent-toolkit-for-aws/blob/main/skills/core-skills/aws-observability/SKILL.md) · [CloudWatch Logs Insights 공식 문서](https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/AnalyzingLogData.html)

## 5. aws-well-architected-review

검토 시점의 AWS 프레임워크 문서를 불러와 코드·IaC의 실제 증거를 항목별로 연결한다. 빠른 질문 단위 검토와 모범 사례 단위의 전체 검토를 구분하며, 결과는 위험도와 우선순위를 기준으로 정리한다. 민감한 코드와 설정을 도구에 넘기기 전에는 마스킹과 읽기 권한 범위를 먼저 점검한다.

- 예시: “테스트 환경 IaC만 읽어서 빠른 Well-Architected 검토를 해줘. 각 개선점에 근거 파일·위험도·다음 단계와 미확인 항목을 붙이고 리소스는 수정하지 마.”
- 태그: Well-Architected, IaC, 근거 검토
- 출처: [SKILL.md](https://github.com/aws/agent-toolkit-for-aws/blob/main/skills/core-skills/aws-well-architected-review/SKILL.md) · [스킬의 데이터 보호 지침](https://github.com/aws/agent-toolkit-for-aws/blob/main/skills/core-skills/aws-well-architected-review/references/security-considerations.md)

## 오늘의 Top Pick: aws-containers

컨테이너 하나를 올릴 때는 배포 경로부터 정하는 게 먼저지만, 운영에서는 앱 로그와 배포 제어 영역의 신호를 구분하는 게 더 중요해진다. 이 스킬은 선택과 진단 양쪽에 쓸 수 있고, 필요 없는 로그 수집부터 권하지 않는 점이 좋다.

## Codex에서 바로 써볼 만한 것: aws-well-architected-review

테스트 환경의 IaC만 열어 빠른 검토부터 시도해 볼 만하다. 개선 목록뿐 아니라 파일 근거와 확인하지 못한 항목을 같이 받으면 추측에 따른 변경을 줄일 수 있다.

## 관찰 메모

이 묶음의 공통점은 범용 스킬이 모든 답을 바로 만들기보다 문제의 계층을 먼저 정한 뒤 필요한 서비스 지침만 불러온다는 점이다. 최근 보고서의 Worker 배포·로컬 검증과 달리 오늘은 AWS에서 배포와 운영 신호를 구분하는 데 초점을 맞췄다. 공식 파일과 설치 안내를 확인했으며 개별 출시일·인기도·설치 수는 집계하지 않았다. 실제 AWS 계정 접근, 설치, 배포 및 성능 테스트는 하지 않았다.
