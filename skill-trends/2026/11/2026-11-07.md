## 1. using-dbt-for-analytics-engineering

**태그:** 데이터 엔지니어링 · SQL 모델링 · dbt · 테스트 · 영향 분석  
**난이도:** 중급. SQL 문법뿐 아니라 모델의 데이터 단위와 조인 관계를 이해해야 한다.

**무엇을 돕는가**

dbt 모델을 만들거나 수정할 때 결과부터 설계하고, 기존 변환 로직을 재사용하며, 실제 데이터로 가정을 확인하도록 안내한다. 원하는 출력의 기본키와 grain, 즉 한 행이 무엇을 의미하는지 먼저 정하고 입력 모델을 거꾸로 찾는다. 기존 SQL뿐 아니라 YAML의 모델·열 설명과 소유권 정보를 읽게 하는 점이 실용적이다. 같은 이름의 열을 같은 의미로 오해하거나, 이미 있는 중간 모델을 다시 만드는 일을 줄일 수 있다. `ref()`와 `source()`를 사용하고 입력·출력을 `dbt show`로 점검하는 흐름이다. 열 이름 변경·삭제·타입 변경처럼 소비자를 깨뜨릴 수 있는 작업은 Mesh 스킬의 버전 전략으로 넘긴다. [고정 원문](https://github.com/dbt-labs/dbt-agent-skills/blob/b8facde20b7a92c40ce3e6b86b71c4b92aa44040/skills/dbt/skills/using-dbt-for-analytics-engineering/SKILL.md)

**사전 조건과 적용 범위**

기존 dbt 프로젝트, 해당 웨어하우스 어댑터, 개발용 target과 승인된 데이터 접근이 필요하다. 요구 지표의 정의, 날짜 기준과 시간대, 예상 데이터 단위도 먼저 정해야 한다. dbt MCP는 있으면 활용하는 도구이지 필수 설치 조건은 아니다. 단순 SQL 초안은 데이터 접속 없이 작성할 수 있지만, 실제 입력 확인과 실행 결과 검증이 빠졌다면 실제 데이터 검증은 미완료로 표시한다. 원문은 새 모델을 요청받으면 기존 모델 확장으로 해결할 수 있는지 먼저 검토하도록 한다. [모델 설계 참고](https://github.com/dbt-labs/dbt-agent-skills/blob/b8facde20b7a92c40ce3e6b86b71c4b92aa44040/skills/dbt/skills/using-dbt-for-analytics-engineering/references/planning-dbt-models.md)

**실용 예시와 요청문**

가상의 주문 모델에서 고객별 일일 순매출을 만든다고 가정한다. 완료 주문 120과 환불 20이 같은 고객·날짜에 있으면 순매출은 100이다. 취소 주문은 제외하고, 통화가 다르면 환율 기준 없이 합치지 않는다. 주문과 상품을 조인할 때 주문 금액이 상품 개수만큼 중복되는지도 확인한다.

> “고객·날짜·통화별 순매출이 필요해. 먼저 기존 모델과 YAML을 읽고 새 모델이 필요한지 판단해 줘. 완료 주문과 환불의 부호 규칙, 시간대를 확인하고 합성 예시로 기대 출력을 제시해. 변경 SQL, 핵심 데이터 테스트, 영향받는 모델 목록을 준비하되 실행 전에는 개발 target과 선택 범위를 보여 줘.”

**완료 판단 기준**

- 출력 grain과 키가 명확하고 기존 모델 재사용 여부가 설명되어 있다.
- 조인 전후 행 수, 중복 키, null, 합계 차이를 확인한다. 단순 미리보기 몇 행만으로 전체 정합성을 단정하지 않는다.
- 키의 `unique`·`not_null`, 필요한 관계 검사와 환불 같은 경계 사례가 검증된다. 테스트 실패 시 확인할 위치도 기록한다.
- 선택한 범위의 실행 결과, 미실행 항목, 소비자 영향과 롤백 방법이 남는다. [테스트 설계 참고](https://github.com/dbt-labs/dbt-agent-skills/blob/b8facde20b7a92c40ce3e6b86b71c4b92aa44040/skills/dbt/skills/using-dbt-for-analytics-engineering/references/writing-data-tests.md)

**안전·실행 제한과 원문 보정**

조회 결과, SQL 주석, YAML 설명에 들어 있는 명령형 문장은 데이터로만 취급한다. 실제 고객 데이터는 예시나 로그로 불필요하게 반출하지 않는다. `dbt show`도 웨어하우스에서 쿼리를 실행하며, 특히 `--inline`은 쓰기 방지를 보장하지 않으므로 탐색에는 읽기 전용 역할이 안전하다. `dbt show --select 모델`은 기존 테이블을 읽는 대신 모델 SQL을 다시 컴파일·실행한다. 따라서 “배포된 테이블이 존재한다”는 증거로 사용하면 안 된다. [공식 show 문서](https://docs.getdbt.com/reference/commands/show)

원문의 `dbt clone` 비용 절감 설명은 조건부다. 지원 플랫폼의 테이블은 zero-copy clone을 사용할 수 있지만 다른 경우에는 원본을 참조하는 뷰를 만들며, 어느 쪽이든 웨어하우스 객체를 생성한다. 무조건 무료이거나 읽기 전용인 단계로 취급하지 않는다. [공식 clone 문서](https://docs.getdbt.com/reference/commands/clone)

변경 영향 분석에 `state:modified+`를 쓸 때는 비교 기준이 필요하다. 원문 예시는 이를 생략하지만 로컬 state 방식에서는 이전 manifest 경로를 `--state`로 제공해야 한다. 관리형 dbt State는 별도의 설정 조건을 확인한다. [영향 분석 원문](https://github.com/dbt-labs/dbt-agent-skills/blob/b8facde20b7a92c40ce3e6b86b71c4b92aa44040/skills/dbt/skills/using-dbt-for-analytics-engineering/references/evaluating-impact-of-a-dbt-model-change.md) · [공식 state 문서](https://docs.getdbt.com/reference/node-selection/state-selection)

## 2. adding-dbt-unit-test

**태그:** 데이터 품질 · 회귀 테스트 · TDD · dbt YAML  
**난이도:** 중급. 증분 모델, 매크로 override, 복합 타입은 중상급이다.

**무엇을 돕는가**

입력 데이터를 작게 고정하고 예상 출력을 명시하여 SQL 변환 로직을 검증하는 스킬이다. 데이터가 이미 만들어진 뒤 품질을 확인하는 data test와 달리, 복잡한 조건문·날짜 계산·윈도 함수·조인에서 기대한 결과가 나오는지 재현한다. 버그를 일으킨 최소 입력을 남기거나 리팩터링 전에 동작을 고정할 때 가치가 크다. 핵심 구조는 `model`, `given`, `expect`다. 테스트 수를 늘리는 것보다 누락 주문, 중복, null, 경계 날짜처럼 실제로 틀릴 수 있는 사례를 고르는 편이 좋다. [고정 원문](https://github.com/dbt-labs/dbt-agent-skills/blob/b8facde20b7a92c40ce3e6b86b71c4b92aa44040/skills/dbt/skills/adding-dbt-unit-test/SKILL.md)

**사전 조건과 적용 범위**

공식 문서상 unit test는 dbt v1.8부터 제공된다. 현재 프로젝트의 SQL 모델이 대상이며 Python 모델, snapshots·seeds 자체, materialized view, 재귀 SQL 등에는 동일하게 적용할 수 없다. 테스트 YAML은 기본적으로 `models/`에 놓고 외부 CSV·SQL fixture는 `tests/fixtures/`에 둔다. 기본 `dict` 형식은 관련 열만 간결하게 작성할 수 있다. ephemeral 입력에는 SQL 형식이 필요하며 SQL fixture는 모든 열을 정의해야 한다. 웨어하우스와 어댑터별 타입 제한도 확인한다. [공식 unit test 문서](https://docs.getdbt.com/docs/build/unit-tests), [입력 형식](https://docs.getdbt.com/reference/resource-properties/data-formats)

**실용 예시와 요청문**

가상의 `fct_customer_net` 모델이 완료 주문은 양수, 환불은 음수로 합산하고 취소 주문은 제외한다고 가정한다. 다음은 그 규칙만 검증하는 합성 입력이다. 실제 프로젝트의 추가 의존성이 있다면 모두 명시해야 한다.

```yaml
unit_tests:
  - name: refunds_reduce_customer_net
    model: fct_customer_net
    given:
      - input: ref('stg_orders')
        rows:
          - {customer_id: 101, status: completed, amount: 120}
          - {customer_id: 101, status: refunded, amount: 20}
          - {customer_id: 101, status: cancelled, amount: 50}
    expect:
      rows:
        - {customer_id: 101, net_amount: 100}
```

> “이 모델에 합성 입력 기반 unit test를 추가할 계획을 만들어 줘. 환불·취소·빈 입력·null 금액의 규칙을 먼저 확인하고, 기존 버그를 재현하는 최소 사례를 포함해. 개발 환경의 부모 모델 존재 여부와 테스트 선택 범위를 확인하기 전에는 명령을 실행하지 마.”

**완료 판단 기준**

테스트가 정상 사례와 합의된 경계 사례를 구분하고 기대값의 근거를 설명해야 한다. 버그 재현 테스트는 수정 전 실패하고 수정 후 통과하는지 확인한다. 승인된 환경에서 `dbt test --select "fct_customer_net,test_type:unit"`처럼 범위를 좁혀 실제 결과를 남긴다. 빌드까지 요청된 경우 공식 문서의 일반 순서는 unit test, 모델 materialization, data test다. 단순 YAML 생성과 실행 통과는 서로 다른 완료 상태다. [공식 build 문서](https://docs.getdbt.com/reference/commands/build)

**안전·실행 제한과 원문 보정**

fixture에는 실사용자 정보 대신 합성값을 쓴다. `--empty`는 실행 없는 검사가 아니다. 입력을 0행으로 제한해도 웨어하우스에서 모델 SQL을 실행하므로 개발용으로 격리하고 기존 데이터를 보존해야 하는 대상에는 무심코 적용하지 않는다. 원문의 “`dbt build --select my_model`이면 부모 준비를 생략”은 그대로 따르면 위험하다. bare 모델 selector는 부모까지 자동 선택하지 않으며 부모를 포함하려면 `+` 등의 선택 전략이 필요하다. 먼저 실제 부모 테이블·뷰의 존재와 선택 범위를 확인해야 한다. [선택 연산자](https://docs.getdbt.com/reference/node-selection/graph-operators)

증분 모델에서는 `is_incremental`을 명시적으로 override하고 필요하면 `this` 입력을 제공한다. 예상값은 삽입·병합할 행이지 병합 후 최종 테이블 전체가 아니다. [증분 모델 참고](https://github.com/dbt-labs/dbt-agent-skills/blob/b8facde20b7a92c40ce3e6b86b71c4b92aa44040/skills/dbt/skills/adding-dbt-unit-test/references/special-cases-incremental-model.md) 원문의 `references/spec.md`에는 `versions`가 `model` 아래로 잘못 들여쓰기된 예시가 있다. 버전 제한 시 두 키를 같은 수준에 둔 공식 예시를 따른다. [버전별 unit test](https://docs.getdbt.com/reference/resource-properties/unit-testing-versions)

## 3. working-with-dbt-mesh

**태그:** 데이터 계약 · 모델 버전 · 거버넌스 · 다중 프로젝트 · 변경 관리  
**난이도:** 고급. 배포 절차와 소비자 의존성, 웨어하우스 객체 이름까지 함께 판단해야 한다.

**무엇을 돕는가**

다른 팀이나 BI가 사용하는 모델을 변경할 때 소비자가 갑자기 깨지지 않도록 계획하는 스킬이다. Mesh라는 이름이지만 단일 프로젝트의 모델 버전, 계약, 그룹과 접근 범위에도 쓸 수 있다. 열 삭제·이름 변경·타입 변경 전에 소비자를 찾고, 새 버전 도입과 기본 버전 승격을 분리하도록 강조한다. 특히 `latest_version`을 새 버전 추가와 동시에 올리면 버전을 지정하지 않은 참조와 기본 이름의 포인터를 읽는 소비자가 배포 후 새 구조를 받게 된다는 경고가 유용하다. [고정 원문](https://github.com/dbt-labs/dbt-agent-skills/blob/b8facde20b7a92c40ce3e6b86b71c4b92aa44040/skills/dbt/skills/working-with-dbt-mesh/SKILL.md)

**사전 조건과 적용 범위**

프로젝트 내부의 governance와 관리형 cross-project dependency를 구분해야 한다. 공식 문서상 프로젝트 간 참조는 dbt Enterprise 또는 Enterprise+ 대상이다. 상위 프로젝트의 public 모델, 성공한 production 배포의 manifest, 하위 프로젝트의 `dependencies.yml`, 정확한 프로젝트 이름이 필요하다. 상위 모델은 `ref('프로젝트', '모델')`로 참조한다. `public`은 dbt 모델 참조 범위이며 인터넷 공개나 웨어하우스 사용자 권한을 뜻하지 않는다. [프로젝트 의존성](https://docs.getdbt.com/docs/mesh/govern/project-dependencies), [모델 접근 범위](https://docs.getdbt.com/docs/mesh/govern/model-access)

계약은 모든 출력 열의 이름과 타입을 선언하고 빌드에서 확인한다. 데이터의 모든 의미나 정확성을 보장하지 않으며 constraints의 실제 강제 여부는 웨어하우스마다 다르다. views에서는 이름·타입은 검사하지만 constraints는 지원하지 않는다. [공식 계약 문서](https://docs.getdbt.com/docs/mesh/govern/model-contracts)

**실용 예시와 요청문**

가상의 재무 모델 `fct_orders`에서 `order_total`을 `net_amount`로 바꾸되 BI의 기존 조회를 유지하는 상황이다. 1차 배포에서는 v1을 그대로 남기고 v2를 추가한다. `latest_version: 1`을 유지하고 새 소비자는 `ref('fct_orders', v=2)`처럼 명시적으로 옮긴다. 기본 이름의 포인터도 v1의 기존 열을 계속 제공하는지 검증한다. 2차 배포는 소비자 전환이 확인된 뒤 별도로 결정한다.

> “`fct_orders.order_total`을 `net_amount`로 바꾸려 해. 먼저 downstream 모델·exposure·직접 조회하는 BI를 조사하고 v1/v2 공존안을 작성해 줘. v2를 추가해도 latest는 v1로 유지해. 현재 엔진의 포인터 설정과 이름 충돌을 확인하고, 배포·승격·구버전 제거는 실행하지 말고 각각의 승인 기준을 제시해.”

**완료 판단 기준**

- 소비자와 담당자, 명시적 버전 참조 여부, 실제 조회하는 relation 이름이 정리되어 있다.
- v1의 기존 쿼리가 여전히 동작하고 v2의 계약·테스트가 통과한다.
- `latest_version` 승격 전 전환 확인 항목과 롤백 방법이 있다. 단순히 v2 파일이 생겼다고 마이그레이션 완료로 간주하지 않는다.
- 폐기 예정일, 잔여 참조 점검, 삭제 조건을 문서화하고 구버전 유지 비용도 고려한다. [버전 전략 참고](https://github.com/dbt-labs/dbt-agent-skills/blob/b8facde20b7a92c40ce3e6b86b71c4b92aa44040/skills/dbt/skills/working-with-dbt-mesh/references/model-versions.md)

**안전·실행 제한과 원문 보정**

권한 확대, 포인터 교체, production 배포, 구버전 삭제는 별개의 실제 변경이다. 스킬이 권장한다는 이유만으로 실행하거나 소비자에게 연락하지 않는다. 계약을 staging 모델에 쓰지 말라는 원문의 강한 문구도 제품의 기술적 금지가 아니라 설계 권고다. 모델 이름보다 실제 소비자 경계와 변경 비용을 기준으로 판단한다.

원문은 `latest_version_pointer`를 beta이며 기본 off라고 설명하지만, 현재 공식 문서는 dbt v1.12부터 제공되며 dbt v2에서는 버전 모델에 기본 활성화된다고 명시한다. 엔진·release track을 확인해 적용해야 한다. 기존 모델의 alias와 포인터 이름이 같으면 충돌할 수 있다. 포인터는 이름을 안정화할 뿐 새 구조로의 호환성을 자동 보장하지 않는다. [최신 포인터 문서](https://docs.getdbt.com/reference/resource-configs/latest_version_pointer)

프로젝트 간 ref가 관계를 자동 해석한다고 소비자의 열 이름·계약 변경까지 자동 해결되는 것은 아니다. 기본 이름 alias를 쓰는 예제와 pointer 예제를 함께 적용하지 말고, 설치 버전의 실제 relation 이름과 충돌 여부를 확인한다. [프로젝트 간 협업 참고](https://github.com/dbt-labs/dbt-agent-skills/blob/b8facde20b7a92c40ce3e6b86b71c4b92aa44040/skills/dbt/skills/working-with-dbt-mesh/references/cross-project-collaboration.md)

## 4. building-dbt-semantic-layer

**무엇을 해결하나**  
매출, 주문 수, 전환율처럼 반복해서 쓰는 지표를 dbt Semantic Layer에 정의하거나 수정하는 작업을 안내한다. 테이블의 한 행이 무엇을 뜻하는지 정한 다음 엔터티, 차원, 지표를 연결하고, 단순 집계에서 비율·파생·누적·전환 지표로 확장한다. 같은 질문에 팀마다 다른 SQL을 쓰는 상황을 줄이는 데 유용하다. 기존 지표 정의를 읽고 필요한 부분만 바꾸도록 요구한다는 점도 실무적이다. 비즈니스 질문에서 시작하면 후보 모델을 먼저 제시하고, 모델이 지정되면 SQL·YAML과 데이터 단위를 확인하도록 구성되어 있다. [고정 원문](https://github.com/dbt-labs/dbt-agent-skills/blob/b8facde20b7a92c40ce3e6b86b71c4b92aa44040/skills/dbt/skills/building-dbt-semantic-layer/SKILL.md)

**태그·난이도**  
dbt / Semantic Layer / MetricFlow / 지표 거버넌스 / YAML. 난이도는 중상이다. SQL 집계, 조인 중복, 시간 단위와 dbt 모델 구조를 이해해야 한다.

**준비 조건과 버전 주의**  
프로젝트의 dbt 버전, 어댑터, 기존 Semantic Layer 문법, 지표 소유자가 합의한 정의가 필요하다. 원문은 Core 1.6~1.11을 legacy, Core 1.12 이상과 Fusion을 latest로 구분한다. 현재 문서는 latest 지원 환경을 dbt v1.12, dbt v2, 플랫폼 v1 Latest로 안내한다. 특히 **Semantic Layer에서 다른 프로젝트 모델을 직접 참조하는 구성은 latest YAML에서 아직 지원되지 않으므로** 버전이 높다는 이유만으로 전환하면 안 된다. [현재 마이그레이션 안내](https://docs.getdbt.com/docs/build/latest-metrics-spec)

legacy에서는 최상위 semantic_models와 measures를 사용하고, latest에서는 모델·컬럼에 의미 정보를 붙이고 simple metric을 직접 정의한다. 원문 참조의 “primary entity가 정확히 하나 필요”라는 표현도 물리적 PK 컬럼을 반드시 만들라는 뜻으로 읽으면 안 된다. 공식 문서는 물리적 primary 컬럼이 없을 때 primary_entity를 지정하는 방식을 설명한다. [최신 문법 참조](https://github.com/dbt-labs/dbt-agent-skills/blob/b8facde20b7a92c40ce3e6b86b71c4b92aa44040/skills/dbt/skills/building-dbt-semantic-layer/references/latest-spec.md), [공식 semantic model 설명](https://docs.getdbt.com/docs/build/semantic-models)

**합성 실무 예시와 프롬프트**  
주문당 한 행인 fct_orders에 order_id, ordered_at, status, net_amount가 있다고 가정한다. 완료 주문 세 건의 금액은 100·200·50이고 취소 주문 한 건은 90이다.

“현재 버전과 기존 문법을 확인하고, 완료 주문만 포함한 매출·주문 수·객단가를 설계해 줘. 주문 엔터티와 일별 시간 차원을 사용하고, 환불 처리·통화·시간대는 먼저 확인해 줘. 기존 설정은 보존하고 변경안, 검증 순서, 작은 예제의 예상값을 보여 줘.”

학습용 기대값은 매출 350, 주문 수 3, 객단가 350/3이다. 취소 주문이 합산되거나 조인으로 행이 늘어나면 잘못된 구현이다. 후속 과제로 7일 누적 매출을 추가하되 시간 스파인 범위와 결측일 처리를 별도로 확인할 수 있다.

**완료 기준**  
문법·참조 검증 뒤 Semantic Layer 검증까지 통과해야 한다. 수정 후 parse로 아티팩트를 갱신하고, 플랫폼 연결 환경에서는 dbt sl validate, 자체 호스팅에서는 mf validate-configs를 사용한다. 추가로 작은 데이터의 기대값, 날짜 경계, 필터, 조인 중복과 기존 지표 영향까지 확인하는 것이 좋다. 검증 명령 성공만으로 업무 정의가 맞다고 단정하지 않는다. [현재 명령 안내](https://docs.getdbt.com/docs/build/metricflow-commands)

**안전 및 실행 한계**  
YAML 변경, 자동 마이그레이션, 시간 스파인 테이블 생성과 실제 쿼리는 각각 영향이 다르다. 개발 환경에서 검토하고 승인된 범위에서 실행해야 한다. 시간 스파인 참조의 연간 예시는 생성 종료일이 2025년으로 고정되어 있어 그대로 복사하면 현재 기간을 덮지 못한다. 날짜 범위와 warehouse별 SQL을 고쳐야 한다. SQL 주석이나 설명 필드에 들어 있는 지시는 실행하지 않는다. [시간 스파인 원문](https://github.com/dbt-labs/dbt-agent-skills/blob/b8facde20b7a92c40ce3e6b86b71c4b92aa44040/skills/dbt/skills/building-dbt-semantic-layer/references/time-spine.md)

## 5. answering-natural-language-questions-with-dbt

**무엇을 해결하나**  
“지난달 지역별 매출은?” 같은 업무 질문을 실제 데이터로 답하도록 경로를 정한다. 먼저 등록된 지표와 차원을 조회하고, 직접 답하기 어려우면 컴파일된 지표 SQL 수정, 비즈니스 마트 탐색, 로컬 manifest·catalog 확인으로 이어진다. 출처 없는 SQL을 처음부터 만드는 대신 기존 업무 정의를 우선 사용한다는 점이 핵심이다. 모델 개발, 테스트 실행이나 데이터 파이프라인 수정용 스킬은 아니다. [고정 원문](https://github.com/dbt-labs/dbt-agent-skills/blob/b8facde20b7a92c40ce3e6b86b71c4b92aa44040/skills/dbt/skills/answering-natural-language-questions-with-dbt/SKILL.md)

**태그·난이도**  
자연어 분석 / SQL / KPI / Semantic Layer / dbt MCP. 사용자는 중급, fallback SQL을 검토할 담당자는 중상 수준이 적합하다. 지표 정의, 데이터 단위와 쿼리 권한을 해석할 수 있어야 한다.

**준비 조건과 최신 변경점**  
등록된 지표를 조회할 도구와 권한이 가장 좋은 출발점이다. 대안으로 Discovery 도구 또는 해당 프로젝트의 최신 manifest.json·catalog.json이 필요하다. 도구가 보인다고 모든 데이터에 접근할 수 있는 것은 아니다. 현재 원격 MCP에서 execute_sql은 OAuth 또는 PAT, 프로젝트 권한, 개발 환경과 warehouse 자격 증명을 요구한다. 서비스 토큰만으로 execute_sql을 사용할 수 없고, ref/source가 들어간 SQL은 추가 develop 권한이 필요하다. [현재 원격 MCP 권한](https://docs.getdbt.com/docs/dbt-ai/setup-remote-mcp)

원문이 사용하는 get_model_details는 현재 문서에서 폐기 예정으로 표시되며 get_node_details로 대체하도록 안내한다. 실제 연결의 도구 목록을 확인해 이름과 매개변수를 맞춰야 한다. get_metrics_compiled_sql은 실행하지 않고 SQL을 반환하지만 query_metrics와 execute_sql은 데이터 조회를 수행한다. [현재 도구 목록](https://docs.getdbt.com/docs/dbt-ai/mcp-available-tools)

**합성 실무 예시와 프롬프트**  
온라인 상점의 2026년 10월 매출을 지역별로 비교하는 연습이다.

“2026-10-01 이상 2026-11-01 미만의 결제완료 순매출을 지역별로 보여 줘. 기준 시간대는 Asia/Seoul, 통화는 KRW로 가정해. 우선 등록된 지표와 사용 가능한 차원을 확인하고, 환불 반영 방식이 불명확하면 먼저 질문해 줘. 사용할 지표명, 필터, 데이터 갱신 시점과 결과의 한계를 함께 설명해 줘. 실행 권한이 없으면 검토 가능한 SQL만 작성해 줘.”

등록된 revenue가 총매출이라면 이름이 비슷하다는 이유로 순매출로 답하면 안 된다. 지역 차원이 없다면 먼저 실제 모델에 필요한 키와 컬럼이 있는지 확인한다. 컴파일 SQL에 지역 테이블을 조인하는 대안은 가능하지만, 주문 한 건이 여러 지역 행과 연결되어 금액이 부풀지 않는지 검증해야 한다. 이는 등록 지표를 그대로 조회한 결과가 아니라 별도 분석 로직임을 표시한다.

**완료 기준**  
답에는 사용한 지표나 모델, 기간·시간대·통화·필터, 실제 실행 여부가 드러나야 한다. 빈 결과를 매출 0으로 단정하지 않고, 권한 문제나 적재 지연과 구분한다. SQL만 작성한 경우 숫자를 만들어 답하지 않는다. 재사용할 수정이라면 Semantic Layer 개선안을 제안하되, 질문 하나를 처리하기 위해 정의를 자동으로 바꾸지는 않는다.

**안전 및 실행 한계**  
“모든 대안을 시도하라”는 원문은 권한 거절을 우회하거나 무제한 쿼리를 실행하라는 허가가 아니다. 승인된 데이터와 읽기 전용 자격 증명을 사용하고, 개인정보 노출과 조회 비용을 줄이는 필터를 적용한다. 결과 행 수 제한만으로 스캔 비용이 제한되지는 않는다. 로컬 아티팩트는 필요한 노드만 필터링하고 생성 시점·환경을 확인한다. 실제로 실행하지 않은 SQL은 검증되지 않은 검토용 SQL 초안임을 명시해야 한다.

## 6. troubleshooting-dbt-job-errors

**무엇을 해결하나**  
dbt Cloud 또는 플랫폼에서 실패한 배치 작업을 로그, 실행 아티팩트, 코드 변경과 데이터 증거로 조사한다. 인프라·연결 문제, 코드·컴파일 문제, 데이터·테스트 실패를 구분해 다음 조사를 정한다. 가장 중요한 원칙은 원인을 모른 채 테스트 조건을 느슨하게 만들어 통과시키지 않는 것이다. 간헐적 실패나 배포 직후 장애에 적합하며, 로컬 개발 오류 전반을 다루는 스킬은 아니다. [고정 원문](https://github.com/dbt-labs/dbt-agent-skills/blob/b8facde20b7a92c40ce3e6b86b71c4b92aa44040/skills/dbt/skills/troubleshooting-dbt-job-errors/SKILL.md)

**태그·난이도**  
dbt Cloud / 장애 진단 / 데이터 품질 / Admin API / 회귀 테스트. 난이도는 중상이다. 로그 해석, Git 비교, dbt 테스트와 warehouse 권한에 대한 이해가 필요하다.

**준비 조건**  
대상 계정·프로젝트·환경·job·run ID와 실패한 step을 특정해야 한다. 가능한 경우 해당 작업의 실행 이력과 오류를 Admin API로 읽고, 없으면 로그와 실패 step의 run_results.json을 받는다. run_results에는 해당 invocation에서 실행된 노드만 들어가므로, 다른 step의 파일이나 현재 로컬 결과로 사고 당시 상태를 대신해서는 안 된다. unique_id로 manifest의 노드 정의와 연결할 수 있다. [공식 run results 설명](https://docs.getdbt.com/reference/artifacts/run-results-json)

현재 MCP에는 get_job_run_details, get_job_run_artifacts 등 직접 아티팩트를 읽는 도구도 있다. 원문의 도구명 예시를 그대로 호출하기보다 실제 목록을 확인하고, 목록 조회가 다른 프로젝트·환경을 섞지 않도록 범위를 제한한다. 현재 문서는 list_jobs의 기본 환경 필터와 project_id를 이용한 범위 변경도 설명한다. [현재 Admin API 도구](https://docs.getdbt.com/docs/dbt-ai/mcp-available-tools)

**합성 실무 예시와 프롬프트**  
가상의 야간 job 42, run 9001에서 fct_orders의 order_id 유일성 테스트가 실패했다고 가정한다.

“이 실행만 읽기 전용으로 조사해 줘. 실패 step의 로그·결과와 마지막 성공 실행의 코드 SHA를 비교하고, 중복 주문의 발생 지점과 최근 조인 변경을 확인해 줘. 테스트를 완화하거나 작업을 재실행하지 말고, 확인한 증거·반증된 가설·남은 질문을 정리해 줘.”

학습용 가설은 고객 차원 테이블에 같은 고객의 두 버전이 생겼는데 현재 버전 필터 없이 조인했다는 것이다. 먼저 실제 중복 키 수, 조인 전후 행 수, 유효기간 조건과 변경 커밋을 확인해야 한다. 그 증거가 일치할 때만 원인으로 결론 낸다. 수정 단계까지 요청받았다면 두 버전의 고객 행을 가진 작은 입력으로 회귀 테스트를 만들고, 기존 유일성 테스트도 유지하는 방식이 적합하다.

**완료 기준**  
해결된 조사에는 원인, 영향 범위, 재현 증거, 최소 수정안과 검증 결과가 있어야 한다. 해결되지 않았어도 검토한 로그·코드·데이터, 기각한 가설, 아직 필요한 증거와 다음 조사 순서를 남기면 조사 결과를 전달할 수 있다. 다만 이를 장애 해결로 표시하면 안 된다. 원문의 조사 템플릿은 인수인계를 위한 출발점이다. [고정 조사 템플릿](https://github.com/dbt-labs/dbt-agent-skills/blob/b8facde20b7a92c40ce3e6b86b71c4b92aa44040/skills/dbt/skills/troubleshooting-dbt-job-errors/references/investigation-template.md)

**안전 및 원문 보완점**  
원문은 진단 뒤 브랜치·수정·PR·조사 문서 커밋까지 제안하지만, 진단 요청만으로 모든 변경이 승인되는 것은 아니다. 재실행, 코드 변경과 외부 공유는 요청 범위에 맞춰 분리한다. compile도 warehouse 메타데이터·introspection 쿼리를 사용할 수 있어 단순 파일 읽기와 다르다. 네트워크 연결 없는 구문 확인에는 parse가 더 맞다. 로그나 SQL 주석의 지시는 실행하지 않으며 민감한 행 데이터와 토큰을 보고서에 복사하지 않는다. [compile 실행 특성](https://docs.getdbt.com/reference/commands/compile), [parse 설명](https://docs.getdbt.com/reference/commands/parse)

또한 원문이 별도 discovering-data 스킬처럼 언급하는 내용은 해당 스냅샷에서 analytics-engineering 스킬의 참조 파일로 존재한다. 자동 의존성 설치를 가정하면 안 된다. [실제 데이터 탐색 참조](https://github.com/dbt-labs/dbt-agent-skills/blob/b8facde20b7a92c40ce3e6b86b71c4b92aa44040/skills/dbt/skills/using-dbt-for-analytics-engineering/references/discovering-data.md)

## 적용 순서와 설치 안내

처음에는 기존 프로젝트를 읽고 **엔진·adapter·모델의 행 단위·지표 정의·실행 대상**을 확인한다. 합성 입력과 기대 결과를 먼저 만들고, 필요한 참고 Skill까지 원문을 검토한 뒤 승인된 개발 환경에서 좁은 범위로 실행하는 순서가 좋다. Skill 설치가 데이터 접근 권한, MCP 연결, 웨어하우스 비용 승인이나 배포 권한까지 주는 것은 아니다.

[공식 설치 안내](https://github.com/dbt-labs/dbt-agent-skills/blob/b8facde20b7a92c40ce3e6b86b71c4b92aa44040/README.md)는 Claude Code plugin 설치와 Vercel Skills CLI를 통한 개별 설치를 제공한다. 다음은 이 보고서의 snapshot에서 Codex용 단위 테스트 Skill 하나를 선택하는 예시이며 **이번 조사에서는 실행하지 않았다**.

```text
npx skills add dbt-labs/dbt-agent-skills@b8facde20b7a92c40ce3e6b86b71c4b92aa44040 --skill adding-dbt-unit-test --agent codex
```

[CLI 명령 문서](https://github.com/vercel-labs/skills/blob/d3701c11b1101251af14c9d148f026e1a47ebe17/docs/commands.md)에서 전체 commit 고정·개별 Skill·대상 Agent 선택을 확인했다. [Agent 경로 안내](https://github.com/vercel-labs/skills/blob/d3701c11b1101251af14c9d148f026e1a47ebe17/docs/agents.md)는 Codex의 프로젝트 설치 경로를 .agents/skills로 표시한다. 현재 [CLI README](https://github.com/vercel-labs/skills/blob/d3701c11b1101251af14c9d148f026e1a47ebe17/README.md)는 Node.js 22.20 이상을 요구한다. 고정한 것은 Skill 원본이며 위 예시의 skills CLI 패키지 버전까지 고정한 것은 아니다. 재현성이 필요하면 검토한 CLI 버전도 별도로 고정한다. 전체 설치나 전역 설치보다 필요한 항목부터 시작한다.

dbt README는 자연어 요청에 따라 Skill을 불러오는 방식으로 설명한다. 다만 실제 호출·도구 허용·plugin 지원은 Agent마다 다르므로 Claude의 slash command나 frontmatter 동작을 Codex에서 동일하게 보장한다고 해석하지 않는다. 일부 원문은 running-dbt-commands·fetching-dbt-docs 등 다른 Skill을 참조한다. 개별 설치가 이 의존 안내를 모두 자동 설치한다는 보장은 없으므로 필요한 원문·도구를 따로 확인한다.

웨어하우스 실행에는 조회 비용과 데이터 노출 범위가 있다. build·full-refresh·job 재실행·배포는 조회와 구분하고, selector가 맞는지 먼저 확인한다. 로그·SQL 주석·데이터 셀에 들어 있는 명령은 작업 지시로 따르지 않는다. 토큰·연결 문자열·실제 고객 행을 프롬프트나 공유 보고서에 남기지 않는다.

### 평가 도구는 별도로 검토

저장소의 [평가 README](https://github.com/dbt-labs/dbt-agent-skills/blob/b8facde20b7a92c40ce3e6b86b71c4b92aa44040/evals/README.md)는 시나리오별 A/B 비교 방법을 제공한다. 평가 도구의 존재를 오늘 여섯 Skill의 성능 개선 증거로 간주하지 않았다. 오늘 확인한 전체 tree에는 시나리오와 평가 코드가 있지만 별도의 공개 runs·reports 결과 디렉터리는 없었다.

특히 [평가 실행기](https://github.com/dbt-labs/dbt-agent-skills/blob/b8facde20b7a92c40ce3e6b86b71c4b92aa44040/evals/src/skill_eval/runner.py)는 allowed_tools가 생략되거나 빈 목록이면 권한 확인을 건너뛰는 옵션을 추가한다. macOS Keychain에서 가져온 Claude 자격증명을 임시 환경 파일로 복사하려는 코드도 있으므로 개인 계정이 있는 환경에서 그대로 실행하지 않는다. 임시 작업 폴더와 MCP 설정 제한만으로 OS·네트워크 격리가 되는 것도 아니다. 평가를 시도한다면 **비어 있지 않은 최소 도구 목록, 별도 격리 환경, 합성 자료, 승인된 자격증명·비용 범위**를 먼저 검토해야 한다. 이번 추천은 Skill 지침의 활용이며 평가 실행기의 기본 실행을 권하는 것은 아니다.

Skills CLI에도 [사용량 정보·보안 감사 요청 설정](https://github.com/vercel-labs/skills/blob/d3701c11b1101251af14c9d148f026e1a47ebe17/docs/troubleshooting.md)이 있다. DO_NOT_TRACK=1 또는 DISABLE_TELEMETRY=1은 둘 다 비활성화하므로, 사용량 정보 전송만 끄면서 동일한 감사 결과가 유지된다고 설명하지 않는다. 이러한 설정 검토나 Skill 설치는 이번에 수행하지 않았다.

### 🏆 오늘의 Top Pick

**adding-dbt-unit-test**: 작은 합성 입력과 명시적 기대 결과를 남기면 Agent가 바꾼 SQL의 의미를 검토하기 쉽다. NULL, 중복 조인, 경계 시각, 증분 처리처럼 눈으로 보기 어려운 경우부터 시작한다. 단위 테스트 통과는 실제 데이터 품질·성능·운영 안전성 전체의 보장이 아니다.

### ⚡ Codex에서 바로 써볼 만한 것

**using-dbt-for-analytics-engineering의 모델 검토 계획**: 데이터에 연결하지 않고도 제공된 SQL과 schema YAML에서 행 단위, join의 다대다 가능성, 필수 테스트, 변경 영향 가설을 정리할 수 있다. 그 결과를 실제 스키마·계보·승인된 표본으로 확인하는 단계는 별도로 남긴다. 설치·인증 없이 작성한 계획을 실행 성공으로 표현하지 않는다.

## 전주 비교와 중복 검토

- [전주 같은 요일 2026-10-31](../10/2026-10-31.md)은 텍스트 분석·문서/텍스트 번역·실시간 통신·Data Lake 작업 **5개**였다. 오늘은 **6개**이며 분석 결과의 의미, 모델 변경과 테스트, 실패 조사로 범위를 옮겼다.
- 5→6은 저장소의 편집 비교이며 설치 수·점유율·성장률 시계열이 아니다. 공식 저장소를 오늘 조회했다는 사실과 최근 출시를 구분한다.
- 기존 query·read-file은 DuckDB의 조회·파일 분석, 오늘의 dbt 모델·Mesh는 프로젝트 변환과 소비자 계약을 다룬다. 기존 tdd·property-based-testing과 adding-dbt-unit-test는 공통 검증 원칙을 공유하지만 dbt의 fixture·ref/source·증분 모델 조건이 구체적인 적용 차이다.
- Semantic Layer 작성과 자연어 질문은 각각 **지표 정의의 생성·검증**과 **기존 정의의 조회·해석**이어서 따로 선정했다. 여섯 이름 모두 기존 360개 인덱스와 과거 보고서 소개 제목에 없었다.
- dbt 버전 마이그레이션과 MCP 서버 설정은 오늘의 신규 소개 범위에 넣지 않았다. 관련 안내를 참조했다는 이유만으로 추가 소개 수나 인덱스에 넣지 않는다.

## 조사와 저장 검증 절차

1. 서울 기준 날짜, 루트 README와 truncated=false 전체 tree를 확인했다. 별도 AGENTS·skill-trends README 지침은 없었고 당일 파일도 없었다.
2. 기존 날짜별 보고서 64개를 범위 제한 없이 조회하고 소개 제목 360개를 전체 인덱스와 대조했다. 코드 표기·Octocode 복합 이름·brainstorming 부제를 정규화한 결과, 누락·최초 소개일 불일치·중복은 0개였다.
3. 선정한 여섯 SKILL.md와 필요한 참고문서, 공식 제품 문서, 설치·평가 자료를 검토했다. 정적 검토와 실제 실행을 구분했다. 패키지 설치·dbt 실행·웨어하우스 조회·MCP 인증·job 재실행·배포·평가 실행은 하지 않았다.
4. 당일 보고서를 main에 저장한 뒤 전체 원문을 다시 읽어 작성본과 정확히 일치하는지 먼저 확인한다. 그 뒤 최신 소개 인덱스와 CHANGELOG의 기존 내용을 보존하며 추가하고, 변경된 세 파일을 모두 main에서 범위 제한 없이 재조회한다. 저장 결과는 CHANGELOG에 기록한다. 과거 날짜·다른 보고서 경로·자동화 설정은 변경하지 않는다.
