## 2. azure-mgmt-apimanagement-py

**게이트웨이 정책 수정이 상위 정책을 지우거나 비밀을 노출하지 않는지 점검하기.**

- 원본: [SKILL.md](https://github.com/microsoft/skills/blob/3f5b461b2314e01c400564051e92469114c5b68f/.github/plugins/azure-sdk-python/skills/azure-mgmt-apimanagement-py/SKILL.md)

- 대상 패키지: `azure-mgmt-apimanagement`
- 난이도: 중상급

### 무엇을 해주나

ApiManagementClient를 통해 서비스·API·product·subscription·policy·backend 등을 관리하는 방법을 설명한다. 기존 Maton의 api-gateway가 외부 SaaS 인증·호출 연결이었다면, 이 항목은 **Azure APIM 관리 평면의 구성 검토**다. 앞의 API Center 인벤토리 등록과도 다르며 실제 트래픽 동작에 영향을 줄 수 있다.

### 정책 상속과 비밀 출력은 수정이 필요하다

원문 XML에는 `base`가 없고 subscription 예제는 primary key를 출력한다. [공식 정책 문서](https://learn.microsoft.com/en-us/azure/api-management/api-management-howto-policies)는 상위 scope 정책의 상속·실행 순서를 `base` 위치로 제어한다고 설명한다. 따라서 원문 XML을 기존 환경에 덮어쓰기 전에 유효 정책과 상위 인증·제한 규칙을 확인해야 한다. 모든 scope·정책에 동일한 지원 범위를 가정하지 않는다.

구독 키는 로그에 남기지 않는다. 원문의 secret named value 생성이나 subscription 생성은 “설정 검토”의 일부로 자동 실행할 일이 아니다. [공식 Python SDK 개요](https://learn.microsoft.com/en-us/python/api/overview/azure/mgmt-apimanagement-readme?view=azure-python)도 관리 클라이언트와 인증 전제를 구분한다.

### 실용 예시

> “저장소에 있는 가짜 APIM 정책 XML을 읽고 inbound·backend·outbound·on-error의 상속 경계를 검토해줘. base 누락, 키 출력, secret 하드코딩, 전체 서비스에 영향을 주는 변경을 표시해. 권장 diff와 승인 전 확인사항만 작성하고 실제 policy 쓰기·subscription 생성·키 조회는 하지 마.”

**완료 기준:** 원본 보존, 적용 scope, 예상 영향, 테스트·복구 계획이 분리돼야 한다. SDK 호출 성공만으로 게이트웨이 동작이 검증됐다고 하지 않는다. 인증이나 접근 범위를 넓히는 변경은 별도의 명확한 승인·검증이 필요하다.

## 3. azure-ai-ml-py

**학습 요청 접수와 학습 성공·검증된 모델 등록을 분리하기.**

- 원본: [SKILL.md](https://github.com/microsoft/skills/blob/3f5b461b2314e01c400564051e92469114c5b68f/.github/plugins/azure-sdk-python/skills/azure-ai-ml-py/SKILL.md)

- 대상 패키지: `azure-ai-ml` — Azure ML SDK v2
- 난이도: 중상급

### 무엇을 해주나

workspace, data asset, model registry, compute, command job, pipeline, environment의 작업 관계를 정리한다. 기존 huggingface-llm-trainer의 특정 모델 학습 흐름과 달리 **Azure ML 작업·자산 관리 계약**에 초점을 둔다. 에이전트가 학습 job을 만들 때 데이터·코드·환경·모델의 출처가 연결되는지 검토하기 좋다.

### 공통 예제를 그대로 적용하면 안 되는 이유

원문은 `with MLClient(...)`와 async MLClient 사용을 일반 규칙으로 제시한다. 그러나 확인한 [공식 MLClient 소스](https://github.com/Azure/azure-sdk-for-python/blob/bc38a4386dd702cb67039f12291655282d3c2819/sdk/ml/azure-ai-ml/azure/ai/ml/_ml_client.py)의 클래스에는 `__enter__`·`__exit__`·`__aenter__`가 없다. [공식 MLClient 참조](https://learn.microsoft.com/en-us/python/api/azure-ai-ml/azure.ai.ml.mlclient?view=azure-python)와 설치 버전을 기준으로 수명주기를 작성해야 하며 다른 Azure SDK의 context-manager 패턴을 기계적으로 복사하지 않는다. 이는 소스 검토 결과이고 실제 설치·실행 시험은 아니다.

또한 원문의 pipeline은 prep_component·train_component가 따로 정의돼야 하는 골격이다. 오래된 환경 이름과 `@latest`를 그대로 재현 가능한 실행 환경으로 간주하지 않는다.

### 실용 예시

> “클라우드 접속 없이 학습 job manifest를 검토해줘. 데이터·코드·환경·모델 버전을 연결하고, 준비·제출·실행·성공·실패·취소를 구분해. 최신 버전 별칭 대신 검증된 버전 기록을 제안하고, job 실패 때 모델 등록이 진행되지 않는 테스트를 mock으로 설계해. compute 생성·job 제출·파일 업로드는 하지 마.”

**완료 기준:** 작업 접수 ID가 생긴 상태와 학습 산출물이 검증된 상태를 구분한다. 실패한 모델이나 다른 실행의 artifact를 성공 결과로 등록하지 않으며 재시도 시 중복 작업·비용 발생을 확인한다. 자원 자동 축소 설정이 모든 비용을 없애 주는 것으로 설명하지 않는다.

### 무엇을 해주나

ImageAnalysisClient의 이미지 파일·URL 입력, caption, tag, object, OCR, crop 결과를 다룬다. 문서 구조 추출 중심의 Document Intelligence와는 결과 계약이 다르다. 필요한 visual feature를 고르고 결과가 없을 때의 처리, 이미지 크기와 좌표의 대응을 검토할 수 있다. 사람 검출을 신원 확인이나 민감한 속성 추론으로 확대하지 않는다.

### 반드시 먼저 볼 서비스 수명주기

[Microsoft 공식 이관 안내](https://learn.microsoft.com/en-us/azure/ai-services/computer-vision/migration-options)는 **Image Analysis API의 종료일을 2028-09-25**로 명시한다. 이 공지는 /imageanalysis endpoint와 지원 버전 v3.2·v4.0을 대상으로 한다. 따라서 이 Skill을 새 장기 시스템의 무조건적 추천으로 소개하지 않는다. **기존 호출·출력 계약을 파악해 대체 구현을 평가하는 용도**가 오늘의 선정 이유다. 문서의 “2026년까지 계획” 문구를 서비스 종료일과 혼동하지 않는다.

[공식 SDK 개요](https://learn.microsoft.com/en-us/python/api/overview/azure/ai-vision-imageanalysis-readme?view=azure-python)는 Caption·Dense Captions에 지원 지역 조건이 있음을 설명한다. 원문이 모든 feature를 한꺼번에 나열했다고 해서 모든 리소스·언어에서 같은 결과를 받을 수 있는 것은 아니다.

### 실용 예시

> “실제 이미지 업로드 없이 기존 ImageAnalysisClient 호출 위치와 사용 feature를 찾아줘. 저장된 합성 결과 fixture에서 OCR 텍스트·polygon, object box, caption의 소비 코드를 목록화하고 대체 서비스 비교용 출력 계약을 작성해. 빈 결과·경계 좌표·회전 이미지·부분 기능 실패 테스트를 설계하고 서비스 이관 체크리스트를 만들어줘.”

**완료 기준:** provider별 응답을 바로 바꾸지 않고 원래 이미지 크기·좌표계·소비자 기대값을 기록한다. 대체 서비스의 결과 품질은 별도 표본 평가로 확인해야 한다. 기존 모델이 반환한 confidence와 다른 모델의 점수를 같은 척도로 간주하지 않는다. URL 입력도 외부 서비스에 이미지 위치를 전달하는 작업임을 인식한다.

## 적용 순서와 설치 안내

[공식 README](https://github.com/microsoft/skills/blob/3f5b461b2314e01c400564051e92469114c5b68f/README.md)의 설치 진입점은 다음과 같다. 이번 조사에서는 실행하지 않았다.

```text
npx skills add microsoft/skills
```

필요한 Skill만 선택하고 설치된 파일과 위 검토 커밋을 비교한다. 이 명령이 검토 snapshot에 자동 고정된다는 뜻은 아니다. Skill 설치, SDK 설치, 계정 인증, 리소스 생성은 서로 다른 단계다. 원문의 `DefaultAzureCredential(require_envvar=True)` 예제는 실제 azure-identity 버전과 환경 변수 전제를 확인해야 한다.

권장 순서는 **원본·설치 버전 확인 → fixture 기반 정적 검토 → 승인된 좁은 범위 시험 → 결과 재조회**다. 오늘 소개한 다섯 항목을 모두 설치하거나 Azure로 이전할 필요는 없다.

## 전주 비교·중복 검토

- [전주 같은 요일 2026-10-25](../10/2026-10-25.md)는 Cosmos·Tables·Event Grid·Event Hubs·Storage Queue **5개**로 상태 저장과 비동기 메시징에 집중했다. 오늘도 **5개**지만 API 거버넌스와 ML·인식 결과의 검증 및 이관으로 초점이 이동했다.
- 선정 수 5→5는 보고서 간 비교일 뿐 설치량·채택률·시장 인기 변화가 아니다. 동일 조건의 주간 순위 자료를 확보하지 않았다.
- API Center의 목록·정의 관리와 APIM의 실행 정책 관리는 별개다. APIM은 기존 Maton api-gateway·모델 호출용 AI gateway의 재소개가 아니다. CLU는 일반 NLP, Azure ML은 특정 학습 레시피, Image Analysis는 문서 전용 추출과 구분했다.
- 동일 서비스의 .NET·Java·TypeScript 버전은 수량을 늘리기 위해 추가하지 않았다. 미검증 후보를 여섯 번째 항목으로 채우지 않았다.
