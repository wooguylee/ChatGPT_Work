## 1. clickhouse-best-practices

**태그:** ClickHouse · SQL 검토 · 스키마 설계 · 쿼리 비용  
**난이도:** 중상급

### 무엇을 돕는가

정렬 키, 자료형, JOIN, 파티셔닝, 대량 삽입과 mutation 대안을 ClickHouse의 특성에 맞춰 검토한다. “쿼리를 빠르게 해줘”라는 요청을 확인한 규칙, 현재 문제, 수정 근거와 우선순위로 바꾸는 데 유용하다. 관련 규칙 파일을 읽고 이름을 인용하며, 결과를 Rules Checked / Findings / Recommendations로 나누도록 한다. [고정 SKILL.md](https://github.com/ClickHouse/agent-skills/blob/d3b2b5ba43a8b80c2d08858b68d53edc701b5ace/skills/clickhouse-best-practices/SKILL.md)

SQL과 DDL 텍스트 검토만 한다면 서버 연결이 필요 없다. 실제 조회 단계에서는 데이터베이스·테이블·열·설명·정렬 키·skip index를 발견한 뒤 표본과 실행 계획을 확인하고 제한된 질의로 넘어간다. 기존 PostgreSQL·DuckDB Skill과 달리 MergeTree 계열의 저장·정렬과 ClickHouse 실행 특성이 핵심이다.

### 실용 예시

가상의 주문 이벤트 테이블과 tenant별 하루 매출 집계를 입력으로 준다. tenant_id와 시각 조건, country의 값 분포, 중복 주문의 의미, 한 행씩 전송하는 적재 방식을 함께 설명한다.

> “첨부한 합성 DDL과 지난 24시간 매출 상위 20개 SQL을 검토해 줘. 실제 DB에 연결하거나 DDL을 실행하지 말고, 정렬 키와 WHERE 조건의 관계, 자료형, 적재 배치를 확인해. 적용 규칙·문제·수정 초안과 EXPLAIN 검증 계획을 구분하고 모르는 데이터 분포는 추정하지 마.”

**완료 기준:** 권고마다 workload와 자료형 범위의 근거가 있고, 의미가 달라질 수 있는 JOIN·NULL·중복 처리 변경을 따로 표시한다. 성능 시험 단계에서는 같은 입력·설정으로 결과 동등성과 read_rows/read_bytes, 실행 계획을 비교한다. 문서 검토만으로 속도 개선 수치를 제시하지 않는다.

### 원문에서 보완할 점

- 원문은 31개 규칙을 소개하면서 일부 설명은 28개라고 쓴다. 숫자보다 실제로 읽은 규칙과 적용 범위를 기록한다.
- ORDER BY를 “변경 불가”라고 단순화하지만, 공식 문서에는 제한된 MODIFY ORDER BY가 있다. 이 명령은 일반적인 기존 데이터 재정렬 도구가 아니며 primary key와 새 정렬식에 제약이 있다. 초기에 조회 패턴을 보고 설계하되 기존 테이블은 이관 비용과 허용 변경을 확인한다. [공식 MODIFY ORDER BY](https://clickhouse.com/docs/reference/statements/alter/order-by)
- NULL을 기본값으로 바꾸거나 ANY JOIN을 쓰면 업무 의미가 달라질 수 있다. 일반 규칙을 일괄 수정 명령으로 취급하지 않는다.

**LIMIT은 비용 상한이 아니다.** 결과 20행이어도 대규모 집계는 많은 행을 읽을 수 있다. [질의 안전 규칙](https://github.com/ClickHouse/agent-skills/blob/d3b2b5ba43a8b80c2d08858b68d53edc701b5ace/skills/clickhouse-best-practices/rules/agent-query-safety.md)과 함께 읽기 권한, 서버측 settings profile·quota, 시간·읽기량 제한을 검토한다. 제한은 분산 환경의 서버별 처리나 데이터 part 처리 경계에 영향을 받으며 break 방식은 부분 결과일 수 있다. 부분 집계를 완전한 매출로 보고하지 않는다. [공식 쿼리 복잡도 제한](https://clickhouse.com/docs/concepts/features/configuration/settings/query-complexity)

## 2. elasticsearch-esql

**태그:** Elasticsearch · ES|QL · 로그 분석 · 스키마 탐색  
**난이도:** 중급

### 무엇을 돕는가

배포 종류와 버전, 실제 인덱스·mapping을 확인한 뒤 질문에 맞는 ES|QL을 작성하고 조회한다. ES|QL은 파이프로 명령을 이어 붙이는 언어이며 JSON Query DSL·SQL·EQL과 다르다. 로그가 어느 인덱스에 있고 상태 코드가 숫자인지부터 확인하게 하므로, 그럴듯한 필드명을 지어내는 분석을 줄이는 데 유용하다. [고정 SKILL.md](https://github.com/elastic/agent-skills/blob/09d879dfe23436684e11391a5e5a74a2aedd6b04/skills/elasticsearch/elasticsearch-esql/SKILL.md)

원문 기본 호환 대상은 Elasticsearch 8.14 이상이며 조회 인덱스의 _source 활성화를 전제로 한다. 원문이 요구하는 elastic CLI는 0.2 이상이며 실제 실행에는 인증된 endpoint가 필요하다. 연결 실패 시 자격증명·endpoint를 추측하거나 다른 HTTP 경로로 우회하도록 하지 않는다. CLI도 Technical Preview이며 현재 명령은 설치본의 help와 대조해야 한다. [현재 CLI README](https://github.com/elastic/cli/blob/main/README.md)

### 실용 예시

합성 logs-demo 인덱스의 mapping에서 아래 네 필드와 자료형을 확인했다고 가정한다. 숫자 상태 코드, keyword 서비스·환경, 날짜형 @timestamp를 사용한다.

> “제공한 staging 로그 mapping으로 최근 1시간의 서비스별 5xx 상위 10개 ES|QL 초안과 검증 순서를 만들어 줘. 연결·실행은 하지 말고 대상 버전에서 지원되는 기능만 써 줘. 원문 로그나 토큰은 출력하지 마.”

```esql
FROM logs-demo
| WHERE @timestamp > NOW() - 1 hour
  AND service.environment == "staging"
  AND http.response.status_code >= 500
  AND http.response.status_code < 600
| STATS errors = COUNT(*) BY service.name
| SORT errors DESC
| LIMIT 10
```

**완료 기준:** 같은 1시간 안에 staging checkout 500 두 건, checkout 200 한 건, production checkout 500 한 건을 둔 합성 fixture에서는 checkout 오류 수가 2여야 한다. 환경·시간 경계, NULL·누락 필드, 499·500·599·600을 별도로 확인한다. 이는 기대값이지 이번 조사에서 실행해 얻은 결과가 아니다. 동률 순서가 필요하면 서비스명 등 명시적 추가 정렬 기준도 정한다.

### 버전·집계·결과 해석

1. **기본 지원과 모든 기능 지원은 다르다.** 원문은 LOOKUP JOIN, INLINE STATS, time-series 기능 등에 별도 버전 조건을 둔다. Serverless·버전 고정 Stack·snapshot도 구분한다. 원문이 Serverless에서 폭넓은 기능 사용을 권하더라도 실제 배포의 지원·preview 상태·구독을 확인하고 필요한 기능만 선택한다. 단순 집계에 최신 실험 기능을 끼워 넣지 않는다.
2. **LIMIT의 위치가 의미를 바꾼다.** STATS 뒤 LIMIT 10은 필터에 맞는 문서를 집계한 후 출력 수를 제한한다. STATS 앞에 두면 집계 입력을 잘라 질문이 달라질 수 있다. 일반 FROM의 기본 출력 1,000행·기본 상한 10,000행도 처리한 원문서 수의 상한은 아니며 설정 가능하다. TS/PROMQL에는 별도 한도가 있다. [공식 제한 문서](https://www.elastic.co/docs/reference/query-languages/esql/limitations) · [LIMIT 문서](https://www.elastic.co/docs/reference/query-languages/esql/commands/limit)
3. **빈 결과와 실패를 구분한다.** 승인된 실행 단계에서는 대상·mapping·시간 범위와 응답 오류·경고·부분 결과 여부를 확인한다. 결과 일부가 없다는 사실을 서비스 장애가 없다는 결론으로 확대하지 않는다. 고유 사용자 수 같은 다른 질문에 COUNT(*)를 그대로 재사용하지 않는다.

실제 로그는 개인정보나 비밀값을 포함할 수 있다. 필요한 집계·열만 반환하고 최소 읽기 권한과 기간·비용 범위를 정한다. Skill 설치는 데이터 접근 허가나 읽기 전용 격리를 자동으로 만들지 않는다.

## 3. promql

**태그:** Prometheus · Grafana · 관측성 · 시계열 질의  
**난이도:** 중급, 운영 alert·수집 규칙 변경은 중상급

### 무엇을 돕는가

Prometheus·Mimir·Grafana Cloud Metrics의 rate, 오류 비율, histogram과 recording rule을 검토한다. counter를 먼저 rate로 변환한 뒤 합산하고, classic histogram에서는 le 경계를 보존하는 등 “문법이 맞는 식”을 넘어 수치 의미를 확인하는 데 유용하다. [고정 SKILL.md](https://github.com/grafana/skills/blob/8fb72a527961f05e708f53d2a0500709e12d7970/skills/grafana-core/promql/SKILL.md)

원래 workflow에는 curl을 통한 /api/v1/query·/api/v1/series 호출, Grafana Explore 확인, recording rule·dashboard 전환이 포함된다. **계획 전용 Skill은 아니다.** 초안만 필요하면 연결·실행·배포를 하지 않는 범위를 명시한다. 실행 단계에는 실제 endpoint와 허용된 조회 권한이 필요하며 인증값을 명령 기록·보고서에 남기지 않는다.

### 실용 예시

> “checkout classic histogram의 p95 식을 검토해 줘. scrape 주기는 30초이고 duration 단위는 초야. 실제 endpoint 호출, recording rule 배포, label 변경은 하지 말고 수정 식과 테스트 계획만 작성해 줘.”

합성 metric·label이 다음과 같이 정의되어 있다고 가정한 초안이다.

```promql
histogram_quantile(0.95,
  sum by (le, service) (
    rate(http_request_duration_seconds_bucket{service="checkout"}[5m])
  )
)
```

**완료 기준:** metric이 classic histogram인지, service·le 라벨과 단위가 맞는지, 5분 구간에 충분한 표본이 있는지 확인한다. counter reset을 다룰 수 있도록 rate 뒤에 합산하고, 같은 평가 시각·구간·fixture로 기존 식과 비교한다. native histogram이면 _bucket/le 식을 그대로 복사하지 않는다. p95는 분포 기반 추정치이며 이 식을 썼다는 사실이 실제 응답속도 개선을 뜻하지 않는다. [Prometheus 공식 함수 문서](https://prometheus.io/docs/prometheus/latest/querying/functions/)

### 원문에서 확인한 오류와 운영 경계

- [patterns.md](https://github.com/grafana/skills/blob/8fb72a527961f05e708f53d2a0500709e12d7970/skills/grafana-core/promql/references/patterns.md)는 changes(up[5m]) == 0을 stale exporter 탐지 예로 제시한다. 그러나 정상적으로 계속 1인 up도 변화가 0이다. **이 조건만으로 수집 중단을 판정하지 않는다.** 값 변화 없음, up=0, 시계열 부재는 서로 다른 상태다.
- 같은 파일의 Alloy labeldrop 예제는 prometheus.scrape 안에 rule을 두고 source_labels를 지정한다. 공식 relabel 문서의 prometheus.relabel 구성과 label 이름에 적용하는 regex를 기준으로 다시 작성해야 한다. 라벨을 지우면 별개 시계열이 같은 label set이 될 수 있으므로 차원·충돌·집계 의미도 검토한다. [공식 Alloy relabel](https://grafana.com/docs/alloy/latest/reference/components/prometheus/prometheus.relabel/)
- 원문의 분모 > 0 조건은 0인 series를 필터링하는 방식이다. **트래픽 없음이 자동으로 오류율 0이 되는 것은 아니다.** 비교 연산의 필터링과 bool 동작, 라벨 매칭을 구분하고 “no data”를 정책 없이 정상으로 표시하지 않는다. [공식 연산자 문서](https://prometheus.io/docs/prometheus/latest/querying/operators/)
- topk는 표시할 시계열 수를 줄여도 backend 계산 비용의 상한을 보장하지 않는다. 전체 metric을 훑는 cardinality 탐색은 좁은 범위부터 시작한다. recording rule·dashboard·ingestion label 변경을 쿼리 초안 검토에 자동으로 포함하지 않는다.

따라서 오늘의 추천 범위는 **공식 함수 문서와 대조하는 좁은 질의 검토·초안**이다. 참고 패턴 전체를 운영 설정에 자동 적용하는 용도로 추천하지 않는다.

## 4. svelte-code-writer

**태그:** Svelte · 공식 문서 · 반응성 · 코드 분석  
**난이도:** 중급

### 무엇을 돕는가

Svelte 5·SvelteKit 문서의 섹션을 찾고 필요한 부분을 읽은 뒤, .svelte 및 .svelte.ts/.svelte.js 작업을 분석하는 도구 흐름이다. @sveltejs/mcp CLI의 list-sections, get-documentation, svelte-autofixer를 연결한다. 기억에 의존해 문법을 섞는 대신 프로젝트 버전과 공식 문서를 근거로 수정하기 좋다. [고정 SKILL.md](https://github.com/sveltejs/ai-tools/blob/d3e755be770277d8c75fe61109b103b801b12775/tools/skills/svelte-code-writer/SKILL.md)

autofixer는 문제와 수정 제안을 내는 분석기다. 이름만 보고 모든 변경이 자동 적용되거나 전체 테스트가 끝난다고 해석하지 않는다. 원문은 검토·디버깅과 최종 확인에 이 도구를 사용하도록 안내한다.

### 실용 예시

> “합성 상품 목록을 쓰는 ProductFilter.svelte에서 최솟값을 바꿔도 상품 수가 갱신되지 않는다. package.json의 버전과 기존 컴포넌트 구조를 유지해 반응성 문제를 검토해 줘. 필요한 공식 문서, 최소 수정안, autofixer 확인과 프로젝트 테스트를 구분하고 새 프레임워크 버전은 설치하지 마.”

**완료 기준:** 입력의 최솟값·최댓값 경계, 결과 0건, 초기값 복원, 부모 props 갱신을 확인한다. 코드 수정안·참고 문서·분석 경고와 함께 실제 수행한 타입 검사·프로젝트 테스트를 구분해 남긴다. 분석기에서 문제를 찾지 못한 상태를 제품 동작 검증 성공으로 표현하지 않는다.

### 버전·쉘 입력·설치 범위

- --svelte-version은 major 4 또는 5를 받으며 기본값은 5다. 원문은 가능하면 package.json의 전체 버전을 전달하도록 안내한다. --async는 기본 비활성이므로 프로젝트 기능에 맞춰 선택한다.
- 원문의 get-documentation 예제는 큰따옴표 안의 $state 등을 쉘 변수로 해석할 수 있다. inline 코드 예제는 작은따옴표 안에 역슬래시를 넣어 실제 코드에 남길 수 있다. **달러 기호를 무조건 이스케이프하라는 지침보다 사용 중인 쉘의 인용 규칙이 우선**이며, 컴포넌트 분석에는 파일 경로 입력을 쓰는 편이 단순하다.
- Node/npm, npx·쉘 실행 환경과 대상 프로젝트가 필요하다. Skill 설치와 @sveltejs/mcp 패키지 실행은 별도 단계다. 설치·실행 시 실제 패키지 버전과 허용 범위를 확인하고, 미고정 npx 명령이 보고서의 검토 커밋과 같은 코드라고 가정하지 않는다.
- OpenCode 전체 플러그인의 기본 자동 업데이트 안내는 단일 Skill 설치와 다르다. 다른 도구까지 묶어 설치할 이유가 있는지 먼저 검토한다. [고정 OpenCode README](https://github.com/sveltejs/ai-tools/blob/d3e755be770277d8c75fe61109b103b801b12775/packages/opencode/README.md)

[공식 Skill 안내](https://svelte.dev/docs/ai/skills)는 개별 설치 경로를 제공한다. 설치만 했다고 모든 호스트에서 같은 CLI 권한·자동 발견·검증 흐름이 보장되지는 않는다.

## 5. angular-developer

**태그:** Angular · 버전 호환성 · Forms · 라우팅 · 테스트  
**난이도:** 중급

### 무엇을 돕는가

컴포넌트·signal 상태·HTTP·forms·라우팅·SSR·접근성·테스트의 참고문서를 작업에 맞게 선택하는 공식 지침이다. 먼저 프로젝트 Angular 버전을 분석하고 코드 생성 후 ng build로 오류를 확인하게 한다. 범용 프런트엔드 설계보다 Angular의 구체적인 API·CLI·검증 관례를 적용하는 데 초점이 있다. [고정 SKILL.md](https://github.com/angular/skills/blob/9274c6e0c832610eefcb2204951fc8ecaac21a35/angular-developer/SKILL.md)

신규 폼에서 Signal Forms를 우선하는 규칙은 **Angular v22 이상**이라는 조건이 있다. 기존 폼이나 이전 버전은 현재 앱의 전략과 호환성을 따르게 하므로 “최신 패턴으로 전부 바꾸는 Skill”로 쓰면 안 된다.

### 실용 예시

> “기존 Angular 관리 화면에 합성 데이터를 편집하는 폼과 저장하지 않은 변경의 이탈 경고를 추가하는 계획을 만들어 줘. 현재 Angular 버전과 폼 방식을 유지하고, forms·CanDeactivate·라우터 테스트 참고자료를 선택해. 서버 API 호출이나 배포 없이 구현 범위와 테스트를 먼저 보여 줘.”

승인된 구현 단계의 산출물은 최소 폼·guard 변경, 테스트, build 결과다. **완료 기준**은 변경 없는 이탈, 미저장 상태의 경고와 취소, 저장 성공 후 이탈, 저장 실패 후 초안 보존, 유효하지 않은 입력 차단이다. 반복 편집·뒤로 가기·다른 URL로 이동하는 흐름도 구분한다. [고정 guard 지침](https://github.com/angular/skills/blob/9274c6e0c832610eefcb2204951fc8ecaac21a35/angular-developer/references/route-guards.md)

현대 zoneless 테스트를 쓰는 프로젝트에서는 상태 변경 후 fixture.whenStable() 등 해당 환경의 안정화 흐름을 거쳐 DOM을 확인한다. 원문의 최신 Vitest 지침을 기존 테스트 러너 전면 교체 요청으로 해석하지 않는다. [고정 테스트 지침](https://github.com/angular/skills/blob/9274c6e0c832610eefcb2204951fc8ecaac21a35/angular-developer/references/testing-fundamentals.md)

### 적용 전에 확인할 점

- ng build 성공은 동작·접근성·보안 검사를 모두 통과했다는 뜻이 아니다. 컴포넌트·라우팅 테스트와 실제 사용자 흐름의 검증 결과를 따로 기록한다.
- 클라이언트 route guard는 서버의 사용자·객체별 권한 검사를 대신하지 않는다. 숨겨진 화면이나 이탈 경고만으로 API가 보호됐다고 결론 내리지 않는다.
- 새 프로젝트 생성 지침에는 사용자 요청 버전, 설치된 CLI 사용, 최신 CLI fallback이 구분된다. “최신을 권장”한다는 문구와 실제 실행할 CLI 버전이 다를 수 있으므로 기존 설치본을 확인한다. 요청하지 않은 업그레이드를 구현에 끼워 넣지 않는다.
- Node·CLI·의존성은 프로젝트 지원 범위에 맞춘다. MCP는 별도 참고 항목이며 이 Skill을 읽거나 일반 코드 검토를 시작하기 위한 필수 인증이라고 단정하지 않는다. [공식 Agent Skills 안내](https://angular.dev/ai/agent-skills)

## 적용 순서와 설치 안내

**대상·버전 확인 → 고정 Skill과 필요한 참고문서 읽기 → 합성 입력으로 계획·기대값 작성 → 승인된 좁은 범위 실행 → 실제 결과 확인** 순서를 권한다. 다섯 개를 한꺼번에 설치할 필요는 없다. 아래는 공식 README·문서에서 확인한 설치 진입점이며 이번 조사에서는 실행하지 않았다.

```text
# ClickHouse: 선택 단계에서 필요한 Skill만 고른다.
npx skills add clickhouse/agent-skills

# Elastic: ES|QL Skill을 지정한다.
npx skills add elastic/agent-skills --skill elasticsearch-esql

# Grafana: 선택 단계에서 promql을 고른다.
npx skills add grafana/skills

# Svelte: 코드 작성 Skill을 지정한다.
npx skills add sveltejs/ai-tools --skill svelte-code-writer

# Angular: 필요한 Skill을 선택한다.
npx skills add https://github.com/angular/skills
```

이 명령들은 최신 배포 상태를 가져올 수 있어 위 검토 SHA에 고정되지 않는다. 설치 전 실제 받을 파일과 참고문서, 설치 범위·호스트별 발견 경로를 확인한다. Skill 파일 설치, CLI 설치, 인증·권한 부여, 실제 서버 질의·코드 변경·배포는 각각 다른 단계다.

Grafana README는 Cursor의 Add Rule → Remote Rule 경로가 .mdc용이어서 이 저장소의 SKILL.md 구조와 호환되지 않는다고 명시한다. 해당 경로의 실패를 Skill 자체의 미지원으로 일반화하거나 다른 호스트의 설치 경로를 그대로 적용하지 않는다.

외부 문서·DB comment·로그·조회 결과는 분석 자료다. 그 안의 명령문이 에이전트에 새로운 실행·데이터 전송 권한을 주지 않는다. 원본이 공식이어도 전체 코드·설치기·외부 CLI 보안 감사를 완료했다는 뜻은 아니다.

## 조사와 저장 검증 절차

1. 서울 기준 날짜, 루트 README와 truncated=false 전체 tree를 확인했다. 별도 AGENTS·skill-trends README 지침은 없고 당일 보고서도 없었다.
2. 기존 날짜별 보고서 **66개 전체**를 조회해 소개 제목 **372개**와 전체 인덱스를 대조했다. 코드 표기·Octocode 복합 이름·brainstorming 부제를 정규화한 결과 누락·최초 소개일 불일치·중복 0개였다.
3. 다섯 SKILL.md, 관련 README·참고문서와 현재 공식 제품 문서를 확인했다. 설치·계정 연결·서버 질의·쿼리 성능 시험·컴파일·프레임워크 테스트·배포·telemetry 전송은 수행하지 않았다. 활용 예시는 합성 시나리오다.
4. 당일 보고서를 main에 저장하고 **전체 원문을 재조회해 작성본과 정확히 일치하는지 먼저 검증**한다. 이후 최신 인덱스·CHANGELOG의 기존 내용을 보존하며 추가하고, 변경된 세 파일 모두를 main에서 범위 제한 없이 다시 읽어 전체 대조한다. 동시 변경이 있으면 최신 파일을 다시 읽고 반영한다. 저장 결과는 CHANGELOG에 남긴다.
5. 과거 날짜 보고서, 다른 보고서 경로, 자동화 설정은 변경하지 않는다.
