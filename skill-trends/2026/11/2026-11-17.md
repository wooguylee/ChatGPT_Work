## 1. frameworks-on-cloudflare

- **출처:** [원문](https://github.com/cloudflare/skills/blob/cbf893b954222276bf1af57e5f23379231e0efb9/skills/frameworks-on-cloudflare/SKILL.md) · [Astro on Workers 공식 가이드](https://developers.cloudflare.com/workers/framework-guides/web-apps/astro/). **태그:** Astro, Vite, SSR, 정적 자산, 어댑터
- **무엇을 하나:** 현재 프레임워크·버전·패키지 매니저·렌더링 모드·설정을 먼저 읽고 그 조합에 맞는 연결 문서로 안내한다. Astro로 만든 홍보 사이트가 전부 정적이면 빌드 결과를 Workers Static Assets로 제공할 수 있고, 요청마다 서버 코드를 실행해야 하는 페이지에는 Cloudflare 어댑터를 검토한다.
- **주의:** 기존 Wrangler 설정이나 Pages 배포를 관련 없는 작업에서 바꾸지 않는다. 프레임워크 자동 감지가 빌드 가능성을 보증하지 않는다.
- **예시 요청:** “이 Astro 저장소에서 빌드 시 고정되는 페이지와 실행 중 서버가 필요한 라우트를 구분해 줘. 기존 배포 설정은 건드리지 말고 Workers에 필요한 최소 변경만 제안해.”

## 2. cloudflare-app-bootstrap

- **출처:** [원문](https://github.com/cloudflare/skills/blob/cbf893b954222276bf1af57e5f23379231e0efb9/skills/cloudflare-app-bootstrap/SKILL.md) · [Workers 로컬 개발](https://developers.cloudflare.com/workers/local-development/). **태그:** 바인딩, 로컬 테스트, D1, secrets, TypeScript
- **무엇을 하나:** 바인딩은 앱 코드에 연결된 D1·KV·R2 같은 리소스의 이름이다. 이 스킬은 코드에서 실제로 쓰는 바인딩을 찾아 설정과 맞추고, 로컬에서 필요한 최소 데이터만 넣은 뒤 대표 요청의 응답과 상태를 확인한다. 단순히 개발 서버가 켜졌다는 로그를 성공 기준으로 쓰지 않는다.
- **주의:** 로컬 Worker도 원격 바인딩을 사용하면 실제 서비스에 접근할 수 있다. 운영 ID나 마이그레이션을 변경하지 말고, 비밀 값은 출력·커밋하지 않는다.
- **예시 요청:** “D1을 사용하는 목록 API가 로컬 임시 데이터에 실제로 연결되는지 확인해. 정해진 프로젝트 스크립트로 실행하되 원격으로 연결된 바인딩이 하나라도 있으면 쓰기를 하지 말고 알려줘.”

## 3. workers-development

- **출처:** [원문](https://github.com/cloudflare/skills/blob/cbf893b954222276bf1af57e5f23379231e0efb9/skills/workers-development/SKILL.md) · [Local Explorer 공식 문서](https://developers.cloudflare.com/workers/local-development/local-explorer/). **태그:** 디버깅, 로컬 트레이스, 로그, OpenAPI
- **무엇을 하나:** 기존 `cf dev`·Wrangler·Cloudflare Vite 개발 흐름을 유지하며, 로컬 개발 서버의 `/cdn-cgi/local/explorer`에서 요청 추적과 바인딩 호출을 먼저 살핀다. 자동화가 필요하면 해당 개발 서버의 OpenAPI 설명에서 필요한 조회만 골라 설치 버전에 없는 기능을 추측하지 않는다.
- **주의:** 로컬 트레이스와 배포된 Worker 관측은 다른 경로다. 조회 목적으로 조사할 때는 데이터 삽입·삭제를 하지 않는다. 프로젝트의 기본 로그에 비밀 값이 포함돼 있는지 먼저 고려한다.
- **예시 요청:** “로컬 `GET /api/items` 한 건의 실패 트레이스를 읽고, 앱 코드 예외와 D1 바인딩 실패 중 어디서 먼저 끊겼는지 알려줘. 소스 수정은 하지 마.”

## 4. workers-profiling

- **출처:** [원문](https://github.com/cloudflare/skills/blob/cbf893b954222276bf1af57e5f23379231e0efb9/skills/workers-profiling/SKILL.md) · [운영 프로파일링 공식 가이드](https://developers.cloudflare.com/workers/observability/profiling-in-production/). **태그:** CPU, 힙, pprof, 소스맵, Durable Objects
- **무엇을 하나:** 응답 지연을 곧바로 CPU 문제로 해석하지 않고, 증상에 따라 CPU 또는 메모리 할당 프로파일을 고른다. 프로파일 결과를 함수·소스 위치와 연결해 가장 작은 개선을 검토한다. 생성된 번들만 보이면 소스맵 부재를 한계로 적는다.
- **주의:** 같은 Worker 이름이라도 계정·환경·배포 버전이 맞아야 한다. 대기 시간과 CPU 시간을 구분하며, 비슷한 부하 조건으로 변경 전후를 비교한다.
- **예시 요청:** “이미 수집한 pprof에서 CPU를 많이 쓰는 함수 세 개를 찾아줘. 번들 때문에 원본 줄을 확인할 수 없으면 추측하지 말고 표시하고, 재측정 조건을 제안해.”

## 5. cf-cli

- **출처:** [원문](https://github.com/cloudflare/skills/blob/cbf893b954222276bf1af57e5f23379231e0efb9/skills/cf-cli/SKILL.md) · [Cloudflare CLI 개요](https://developers.cloudflare.com/cf/). **태그:** CLI, 베타, 도구 선택, 스키마, 배포 검토
- **무엇을 하나:** 프로젝트의 `cloudflare.config.ts` 또는 Wrangler 설정을 보고 기존 개발·빌드·배포 도구를 결정한다. `cf`를 쓰는 프로젝트에서는 `cf cli search`, 도움말·스키마로 지원 명령을 찾고 해당 명령이 지원하면 미리보기로 요청 대상을 검토한다.
- **주의:** `cf`는 베타라 명령과 설정이 변할 수 있고, Wrangler 로그인을 그대로 재사용하지 않는다. 기존 Wrangler 프로젝트를 임의로 변환하지 않는다. `--dry-run` 가능 여부는 실제 버전과 명령에서 확인한다.
- **예시 요청:** “이 앱이 어떤 Cloudflare CLI 설정을 쓰는지 저장소에서 확인해 줘. 설치·로그인·마이그레이션·배포는 하지 말고 근거 파일과 확인용 명령만 알려줘.”
