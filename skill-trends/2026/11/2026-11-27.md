## 1. aws-ami-builder

Packer의 amazon-ebs 빌더로 베이스 AMI, 설치 단계, 결과 이미지 이름·태그를 정의한다. 컨테이너 이미지와 달리 EC2에 쓰는 머신 이미지다.

- 예시: “샘플 Ubuntu 서버 구성을 보고 베이스 AMI의 게시자, CPU 아키텍처, 검사 항목을 적어줘. AWS에서 빌드는 하지 마.”
- 태그: Packer, EC2, AMI
- 출처: [공식 SKILL.md](https://github.com/hashicorp/agent-skills/blob/main/plugins/packer/skills/aws-ami-builder/SKILL.md)

## 2. azure-image-builder

azure-arm 빌더로 단일 관리 이미지와 Azure Compute Gallery 배포용 이미지를 나눠 설계한다. 배포 지역과 이미지 버전은 별도로 확인한다.

- 예시: “테스트 환경 한 곳에서 쓸 관리 이미지와 여러 지역에서 재사용할 Gallery 이미지의 차이를 정리해줘. 구독이나 리소스는 건드리지 마.”
- 태그: Packer, Azure, 이미지 배포
- 출처: [공식 SKILL.md](https://github.com/hashicorp/agent-skills/blob/main/plugins/packer/skills/azure-image-builder/SKILL.md)

## 3. windows-builder

WinRM으로 빌드용 VM에 연결하고 PowerShell로 초기 설정을 넣는 흐름을 다룬다. 원문의 연결 예시를 그대로 운영에 적용하지 말고 인증서 검증과 네트워크 제한을 별도로 확인한다.

- 예시: “가상 Windows Server 템플릿의 업데이트, 배포 전 일반화, 빌드 실패 시 임시 VM 정리 체크리스트를 써줘. 원격 설정은 변경하지 마.”
- 태그: Windows, PowerShell, 이미지
- 출처: [공식 SKILL.md](https://github.com/hashicorp/agent-skills/blob/main/plugins/packer/skills/windows-builder/SKILL.md)

## 4. azure-verified-modules

AVM 기준에 맞는 공급자 버전, 입력 변수, 출력과 테스트·문서를 검토한다. 일반 Terraform 코드에 적용되는 규칙과 AVM 심사를 위한 요구사항을 구분한다.

- 예시: “샘플 Azure 모듈에서 공식 레지스트리 의존성, 버전 제약, 예제·테스트 누락을 표시해줘. 인증 통과 여부는 단정하지 마.”
- 태그: Terraform, Azure, 모듈 검토
- 출처: [공식 SKILL.md](https://github.com/hashicorp/agent-skills/blob/main/plugins/terraform/skills/azure-verified-modules/SKILL.md)

## 5. terraform-policy

정책 파일과 정책 테스트 파일을 작성하거나 Sentinel 규칙을 옮길 때 쓴다. 구문과 모의 리소스의 동작은 사용 중인 tfpolicy 버전에 맞춰 확인한다.

- 예시: “가상의 프로젝트에서 필수 태그가 없는 리소스를 거부하는 정책 초안과 허용·거부 예시를 만들어줘. 실제 계획이나 정책 배포는 하지 마.”
- 태그: Terraform, 정책, 테스트
- 출처: [공식 SKILL.md](https://github.com/hashicorp/agent-skills/blob/main/plugins/terraform/skills/terraform-policy/SKILL.md)

## 설치와 사용

[공식 카탈로그](https://github.com/hashicorp/agent-skills/blob/main/SKILLS.md)는 각 경로를 지정해 필요한 스킬만 설치하는 방법을 안내한다. 스킬을 추가해도 Packer·Terraform 실행 환경이나 클라우드 권한이 생기지는 않는다. 템플릿과 정책 검토는 비용이 발생하는 실제 VM 빌드나 배포와 분리한다.

## 오늘의 Top Pick: aws-ami-builder

EC2 서버를 여러 번 같은 상태로 준비해야 할 때 템플릿으로 OS와 설치 과정을 남긴다. 기존 Docker 배포가 목적이라면 모든 앱 업데이트마다 AMI를 다시 만들어야 하는지는 별도로 판단할 문제다.

## Codex에서 바로 써볼 만한 것: terraform-policy

샘플 정책에 통과와 실패 사례를 같이 작성하게 하면 규칙의 의도를 검토하기 쉽다. 운영에 적용하기 전에 실제 CLI 버전에서 테스트가 실행됐는지 확인한다.

## 관찰 메모

이미 소개한 refactor-module, terraform-style-guide, terraform-test는 제외했다. 공식 카탈로그와 원문 다섯 개를 확인했으며 스킬 설치, 클라우드 접속, 이미지 빌드 또는 정책 적용은 하지 않았다.
