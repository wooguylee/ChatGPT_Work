## 1. docker-project-foundations

Docker를 처음 붙이는 프로젝트에서 `Dockerfile`, `compose.yaml`, `.dockerignore`가 맡을 일을 나눈다. 개발용 DB를 별도 서비스로 두고 꼭 필요한 포트만 열도록 검토할 수 있다.

- 예시: “Node.js API와 PostgreSQL로 된 샘플 프로젝트에 필요한 Docker 파일 3개의 초안을 만들어줘. DB 포트는 호스트에 열지 말고, 실행은 하지 마.”
- 태그: Dockerfile, 로컬 개발, PostgreSQL
- 출처: [공식 SKILL.md](https://github.com/docker/skills/blob/main/skills/docker-project-foundations/SKILL.md)

## 2. docker-build-strategies

기존 Dockerfile의 빌드 컨텍스트, 레이어 캐시, 런타임에 남는 파일과 실행 사용자를 검토한다. 이미지 크기 문제와 소스만 수정했는데 의존성을 다시 설치하는 문제를 따로 볼 수 있다.

- 예시: “이 Node.js Dockerfile에서 소스만 바꿔도 의존성 설치가 반복되는 이유를 찾아줘. 변경 전후에 비교할 빌드 시간과 이미지 크기도 정해줘.”
- 태그: BuildKit, 캐시, 이미지 최적화
- 출처: [공식 SKILL.md](https://github.com/docker/skills/blob/main/skills/docker-build-strategies/SKILL.md)

## 3. docker-compose-patterns

Compose의 서비스 간 연결, 헬스체크, 시작 순서, 볼륨과 개발용 덮어쓰기 설정을 다룬다. 컨테이너가 시작된 것과 서비스가 요청을 받을 준비가 된 것을 구분한다.

- 예시: “예제 Compose에서 API가 PostgreSQL보다 먼저 연결을 시도하는지 확인해줘. DB 헬스체크와 API의 재시도 중 어디를 고쳐야 할지 설명해줘.”
- 태그: Compose v2, 헬스체크, 네트워크
- 출처: [공식 SKILL.md](https://github.com/docker/skills/blob/main/skills/docker-compose-patterns/SKILL.md)

## 4. docker-destructive-guardrails

컨테이너, 이미지, 볼륨, 빌드 캐시의 정리 작업을 구분하고 무엇이 없어지는지 먼저 파악한다. 다시 빌드할 수 있는 캐시와 데이터가 들어 있는 볼륨은 같은 방식으로 다루지 않는다.

- 예시: “예제 자원 목록에서 다시 만들 수 있는 것과 백업이 필요한 것을 나눠줘. 정리 명령은 실행하지 마.”
- 태그: Docker 운영, 볼륨, 변경 승인
- 출처: [공식 SKILL.md](https://github.com/docker/skills/blob/main/skills/docker-destructive-guardrails/SKILL.md)

## 5. docker-agent-config

Docker Agent의 `agent.yaml`에서 모델, 공급자, 에이전트 지시 및 도구 범위를 정의한다. 일반 컨테이너를 띄우는 Compose 스킬과는 적용 대상이 다르다.

- 예시: “가상의 문서 검토 에이전트 설정을 초안으로 작성해줘. 셸과 쓰기 도구는 붙이지 말고, 모델 이름과 작업 범위만 명확히 해줘.”
- 태그: Docker Agent, 설정 검토, 도구 권한
- 출처: [공식 SKILL.md](https://github.com/docker/skills/blob/main/skills/docker-agent-config/SKILL.md)

## Codex에서 바로 써볼 만한 것: docker-destructive-guardrails

디스크 공간을 비우기 전에 컨테이너·캐시·DB 볼륨을 나눠 보는 검토에 적합하다. 대상과 백업을 확인하지 않았다면 삭제 없이 목록과 영향만 정리한다.
