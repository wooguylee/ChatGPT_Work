## 1. mongodb-schema-design

화면과 API가 함께 읽는 데이터를 기준으로 문서 안에 포함할 필드와 별도 참조로 둘 데이터를 나눈다. 계속 커지는 배열과 잦은 조인은 별도로 점검한다.

- 예시: “샘플 문서 모델에서 본문 메타데이터와 처리 이력을 함께 둘지 비교해줘. 화면별 조회와 이력 증가량을 근거로 써줘.”
- 태그: 스키마, 문서 모델
- 출처: [공식 SKILL.md](https://github.com/mongodb/agent-skills/blob/main/plugins/mongodb-atlas/skills/mongodb-schema-design/SKILL.md)

## 2. mongodb-natural-language-querying

스키마와 예제 문서를 확인한 뒤 단순 필터·정렬은 find, 그룹 집계나 여러 변환 단계는 aggregation으로 나눈다. 원문 워크플로는 MongoDB MCP를 사용한다.

- 예시: “가상의 처리 이력에서 유형별 실패 건수를 세는 집계를 작성해줘. 샘플 스키마만 쓰고 실행하지 마.”
- 태그: 읽기 전용, 집계
- 출처: [공식 SKILL.md](https://github.com/mongodb/agent-skills/blob/main/plugins/mongodb-atlas/skills/mongodb-natural-language-querying/SKILL.md)

## 3. mongodb-query-optimizer

새 쿼리 작성보다 느린 쿼리의 실행 계획과 기존 인덱스를 보는 스킬이다. 측정 자료가 없으면 쿼리 형태에서 도출한 인덱스 후보를 실제 개선과 구분한다.

- 예시: “익명화한 실행 계획에서 스캔 비용이 큰 부분을 짚고 같은 조건에서 비교할 지표를 써줘. 인덱스는 만들지 마.”
- 태그: 실행 계획, 인덱스
- 출처: [공식 SKILL.md](https://github.com/mongodb/agent-skills/blob/main/plugins/mongodb-atlas/skills/mongodb-query-optimizer/SKILL.md)

## 4. mongodb-search-and-ai

키워드 정확도가 중요한 검색과 의미가 비슷한 문서를 찾는 검색을 구분한다. 혼합 검색은 두 방식이 실제 평가 질의에서 서로 보완할 때 검토한다.

- 예시: “샘플 OCR 문서에서 사건번호 질의와 자연어 질의를 나눠 검색 방식과 평가 기준을 제안해줘.”
- 태그: 검색, 벡터, OCR
- 출처: [공식 SKILL.md](https://github.com/mongodb/agent-skills/blob/main/plugins/mongodb-atlas/skills/mongodb-search-and-ai/SKILL.md)

## 5. mongodb-atlas-stream-processing

Atlas Stream Processing의 입력·출력, 처리기 수명 주기, 장애 진단을 다룬다. 연결 및 처리기 상태를 읽는 작업과 리소스 생성·중단을 구분한다.

- 예시: “가상의 Kafka 이벤트를 읽는 처리기에서 적체가 보일 때 입력·처리기·출력 중 어디를 먼저 확인할지 정리해줘. 새 연결은 만들지 마.”
- 태그: Atlas, 스트리밍, 운영
- 출처: [공식 SKILL.md](https://github.com/mongodb/agent-skills/blob/main/plugins/mongodb-atlas/skills/mongodb-atlas-stream-processing/SKILL.md)

## 설치와 사용

[공식 저장소](https://github.com/mongodb/agent-skills#installation)는 Codex의 플러그인 목록에서 관리형 Atlas용 `mongodb-atlas`를 찾도록 안내한다. 자체 운영 MongoDB용 `mongodb`는 별도 플러그인이다. Atlas의 실제 데이터 조회나 스트림 작업에는 연결과 알맞은 권한이 필요하다. 샘플 구조와 가짜 문서로 설계만 검토할 때는 연결하지 않아도 된다.

## 오늘의 Top Pick: mongodb-schema-design

배치 작업이 계속해서 상태를 추가한다면 이력을 배열 하나에 누적할지, 별도 문서로 둘지 조회와 증가량을 함께 보면서 결정한다.

## Codex에서 바로 써볼 만한 것: mongodb-query-optimizer

기존 쿼리, 인덱스 목록, 익명화한 실행 계획을 주고 변경 후보와 재측정 기준을 받는다. 운영에서 바로 변경할 필요는 없다.
