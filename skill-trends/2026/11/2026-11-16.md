## 1. qdrant-deployment-options

**태그:** Qdrant, 배포 설계, Edge, 운영 책임  
**난이도:** 초중급  
**출처:** [고정 SKILL.md](https://github.com/qdrant/skills/blob/f92bbe024e17a588c86ca98b9b3a7634ad81531c/skills/qdrant-deployment-options/SKILL.md)

### 무엇을 돕는가

운영을 직접 맡을지, 네트워크 왕복이 허용되는지, 프로토타입인지 운영 서비스인지부터 묻는다. Python local mode, Docker 서버, 관리형 Cloud·Hybrid Cloud, 프로세스 내부 Edge를 같은 것으로 취급하지 않고 선택 이유와 포기하는 기능을 기록하게 한다.

### 실용 예시

**합성 요청문:** “오프라인 데스크톱 검색과 여러 노드가 필요한 SaaS 검색을 비교해 줘. 운영 담당자 유무·네트워크·데이터 위치·백업 책임을 표로 작성하고 배포는 하지 마.”

**완료 기준**
- 서버 없는 local mode 테스트를 실제 서버 성능 측정으로 오인하지 않는다.
- 분산 검색이 필요한데 Edge를 선택하지 않는다.
- 관리형 선택에서도 접근 제어·애플리케이션 품질·복구 검증의 책임자를 남긴다.
- 선택하지 않은 방식의 이유와 다시 검토할 조건을 적는다.

### 적용 시 주의

[Edge quickstart](https://qdrant.tech/documentation/edge/edge-quickstart/)의 로컬 shard와 [서버 quickstart](https://qdrant.tech/documentation/quickstart/)의 서버 실행은 서로 다른 경로다. local mode와 서버의 저장 형식을 같다고 가정하지 않는다. 원문의 “Zero-Ops”는 모든 보안·품질·운영 책임이 사라진다는 뜻으로 해석하지 않는다. 지리적 요구나 관리형 서비스를 선택했다는 사실만으로 규제 준수를 선언하지 않는다.

## 2. qdrant-search-quality

**태그:** 검색 평가, ANN recall, 관련성, HNSW, RAG  
**난이도:** 중상급  
**출처:** [고정 SKILL.md](https://github.com/qdrant/skills/blob/f92bbe024e17a588c86ca98b9b3a7634ad81531c/skills/qdrant-search-quality/SKILL.md), [진단 지침](https://github.com/qdrant/skills/blob/f92bbe024e17a588c86ca98b9b3a7634ad81531c/skills/qdrant-search-quality/diagnosis/SKILL.md)

### 무엇을 돕는가

검색이 나쁘다는 증상을 먼저 분해한다. 사람이 관련성을 판단한 query–document 평가셋은 “맞는 결과인가”를 측정하고, 동일 쿼리의 exact KNN 대비 ANN 결과 겹침은 “근사 인덱스가 exact 결과를 찾는가”를 측정한다. exact도 나쁘면 데이터·임베딩·파이프라인을, exact는 좋은데 ANN이 나쁘면 인덱스를 우선 조사하는 순서다.

### 실용 예시

**합성 요청문:** “한국어 고객지원 검색에서 정답 문서가 빠지는 문제의 진단 계획을 만들어 줘. 라벨 기반 관련성과 exact 대비 ANN recall을 별도 표로 두고, 같은 필터·k·쿼리셋으로 비교해. 운영 설정은 변경하지 마.”

**완료 기준**
- 라벨을 사용한 업무 관련성과 ANN 일치율을 별개로 보고한다.
- 구성 선택에 사용한 쿼리와 최종 평가 쿼리를 분리한다.
- 지연 예산과 개선 목표를 먼저 정의하고 불확실한 차이는 미확정으로 남긴다.
- 검색 단계와 최종 답변 품질을 구분한다.

### 원문 보완

[공식 ANN recall 설명](https://qdrant.tech/documentation/tutorials-search-engineering/ann-recall/)처럼 높은 ANN 일치율 자체는 사용자에게 유용한 결과라는 증거가 아니다. 인덱스가 아직 생성되지 않아 exact scan이 수행되는지도 확인한다. hnsw_ef 증가는 지연과 함께 평가하고, m·ef_construct 변경은 재구축 비용까지 계획한다.

원문에 있는 “청킹으로 30–40% 하락”, 일률적인 “95% 초과” 목표를 모든 데이터의 보장이나 합격 기준으로 전파하지 않는다. 예시 설정·양자화 지침도 실제 데이터와 버전에 맞춰 검증한다. 이 보고서는 그런 수치를 실험으로 확인하지 않았다.

## 3. qdrant-monitoring

**태그:** 관측성, Prometheus, Grafana, 최적화, 지연  
**난이도:** 중급  
**출처:** [고정 SKILL.md](https://github.com/qdrant/skills/blob/f92bbe024e17a588c86ca98b9b3a7634ad81531c/skills/qdrant-monitoring/SKILL.md), [설정](https://github.com/qdrant/skills/blob/f92bbe024e17a588c86ca98b9b3a7634ad81531c/skills/qdrant-monitoring/setup/SKILL.md), [디버깅](https://github.com/qdrant/skills/blob/f92bbe024e17a588c86ca98b9b3a7634ad81531c/skills/qdrant-monitoring/debugging/SKILL.md)

### 무엇을 돕는가

모니터링을 처음 붙이는 작업과 이미 느려진 서비스를 조사하는 작업을 분리한다. 지표 수집·health probe·알림 계획을 만들거나 optimizer 진행 상황, 메모리, 요청 지연 순으로 증거를 확인한다. 일반 PromQL 작성법보다 Qdrant의 노드·컬렉션·최적화 상태를 무엇과 함께 읽을지가 핵심이다.

### 실용 예시

**합성 요청문:** “익명화한 3노드 지표와 컬렉션 상태를 읽고 검색 지연 원인 후보를 정리해. 각 후보를 지지·반박할 관측값, 누락된 수집 대상, 다음 읽기 전용 확인을 써 줘. 원인 확정이나 설정 변경은 하지 마.”

**완료 기준**
- 부하분산 주소 하나만 수집해 전체 노드를 봤다고 주장하지 않는다.
- 요청 지연은 평균 하나가 아니라 적절한 histogram과 분포로 검토한다.
- optimizer 오류와 단순히 오래 걸리는 작업을 구분한다.
- 지표·로그에 포함될 데이터와 외부 전송 대상을 검토한다.

### 적용 시 주의

[공식 모니터링 문서](https://qdrant.tech/documentation/ops-monitoring/monitoring/)에서 /metrics는 노드별이며 /sys_metrics는 Qdrant Cloud용이다. 노드 재시작에 따른 counter 초기화도 해석해야 한다. 메모리 사용량 증가만으로 누수를 확정하지 않고 page cache·프로세스 메모리·실제 메모리 한도와 압력을 함께 본다. 원문의 고정 비율 경보는 작업 부하별 출발점일 뿐이다. 알림 채널 연결이나 로그 외부 업로드는 이번 조사에 포함하지 않았다.

## 4. qdrant-version-upgrade

**태그:** 버전 호환, rolling upgrade, 백업, 복제, SDK  
**난이도:** 상급  
**출처:** [고정 SKILL.md](https://github.com/qdrant/skills/blob/f92bbe024e17a588c86ca98b9b3a7634ad81531c/skills/qdrant-version-upgrade/SKILL.md)

### 무엇을 돕는가

서버와 SDK 순서, 중간 minor 버전, 컬렉션별 복제 조건, 백업·회귀 기준을 하나의 실행 전 점검표로 묶는다. 목표 버전의 릴리스 노트만 읽고 여러 단계를 건너뛰는 위험을 줄이며 업그레이드 후 순위·recall·지연의 변화를 확인하게 한다.

### 실용 예시

**합성 요청문:** “합성 3노드 클러스터를 두 minor 이후 버전으로 옮기는 계획을 작성해. 한 컬렉션만 RF=1인 상황을 포함하고 중간 단계·서비스 중단 가능성·복원 시험·중단 기준을 표시해. 어떤 명령도 실행하지 마.”

**완료 기준**
- 모든 컬렉션의 복제 수와 실제 replica 상태를 확인 대상으로 둔다.
- 각 단계의 노드별 버전·건강 상태·회귀 지표를 기록한다.
- 백업 존재와 복원 가능성을 구분한다.
- 절대 점수의 완전 일치만으로 호환성을 판단하지 않는다.

### 현재 공식 순서와 안전 조건

[공식 업그레이드 문서](https://qdrant.tech/documentation/upgrades/)와 고정 원문은 **클러스터 먼저, SDK 나중** 순서다. self-hosted는 각 중간 minor의 최신 patch를 거치며 Cloud는 중간 단계를 처리한다. 무중단 rolling을 가정하려면 모든 컬렉션 RF≥2가 필요하고, 단일 노드나 RF=1에는 중단 계획이 필요하다. SDK는 클러스터와 한 minor 이내를 유지하는 안내를 따른다.

서버를 먼저 올린다고 클라이언트 검증을 뒤로 미루는 뜻은 아니다. 사전 격리 환경 테스트가 필요하다. 실제 적용 시 해당 버전의 인증·기본값 변경을 다시 확인하고 호환성 문제를 이유로 인증을 끄지 않는다. 라이브 downgrade와 스냅샷 복원도 같은 것으로 취급하지 않는다.

## 5. qdrant-multitenancy

**태그:** SaaS, 테넌트 분리, payload, shard, 검색 보안  
**난이도:** 상급  
**출처:** [고정 SKILL.md](https://github.com/qdrant/skills/blob/f92bbe024e17a588c86ca98b9b3a7634ad81531c/skills/qdrant-multitenancy/SKILL.md)

### 무엇을 돕는가

테넌트 수와 크기 편차를 기준으로 payload 분리, 전용 shard, 별도 collection의 비용·격리 특성을 비교한다. 작은 고객이 많고 큰 고객이 일부인 상황에서는 계층형 구성을 검토한다. 고객별 컬렉션을 무조건 늘리는 대신 검색 경로·스키마·리소스 편차를 함께 설계하는 지침이다.

### 실용 예시

**합성 요청문:** “고객 2,000곳 중 큰 고객 3곳이 있는 검색 SaaS의 분리 설계를 비교해 줘. 인증된 tenant와 검색 필터 연결, 다른 고객 ID를 보낸 음성 테스트, 관리용 교차 검색의 권한 경계를 포함해. 실제 데이터나 설정을 바꾸지 마.”

**완료 기준**
- tenant ID를 요청자가 임의로 지정하는 값이 아니라 검증된 권한과 연결한다.
- 검색뿐 아니라 조회·수정·삭제 등 접근 경로의 범위를 확인한다.
- 필터 누락과 다른 tenant ID 위조를 실패해야 할 테스트로 작성한다.
- 데이터 위치·백업·복제의 물리적 배치 요구를 따로 검토한다.

### 적용 시 주의

[공식 multitenancy 문서](https://qdrant.tech/documentation/manage-data/multitenancy/)는 payload·전용 shard·계층형 분리를 구분하며 tenant 필드의 keyword index 예시를 제공한다. 그러나 payload 필터는 전체 보안 체계가 아니다. 원문의 특정 point 수나 shard 수를 모든 환경의 자동 승격 임계값으로 쓰지 않는다. 기존 자동 sharding 컬렉션을 제자리에서 custom sharding으로 바꿀 수 있다고 가정하지 말고 이전 계획을 확인한다. 지역 이름을 shard key로 넣는 것만으로 실제 저장 위치가 보장되지 않는다.

## 적용 순서와 설치 안내

1. [공식 저장소 README](https://github.com/qdrant/skills/blob/f92bbe024e17a588c86ca98b9b3a7634ad81531c/README.md)와 필요한 SKILL.md·하위 문서만 먼저 검토한다. 에이전트의 지침 검색 방식과 지원 경로를 확인하고 승인된 방식으로 적용한다.
2. 배포 요구·권한·데이터 민감도를 먼저 정리한 뒤 읽기 전용 진단과 합성 평가 계획부터 시작한다.
3. 구조·인덱스·권한·버전 변경은 별도 변경 계획과 복구 절차를 통과시킨다. Skill이 실행 권한을 자동 부여하지 않는다.
