## 1. recipe-create-events-from-sheet

**여러 행의 반복 입력을 줄이되, 표를 곧바로 실행 명령으로 취급하지 않기.**

- 원본: [SKILL.md](https://github.com/googleworkspace/cli/blob/cd3697e07eb520056dcf142d0c7439bbb9ba32e9/skills/recipe-create-events-from-sheet/SKILL.md)
- 태그: `sheets`, `calendar`, `batch-planning`, `idempotency`
- 난이도: 중급

### 무엇을 해주나

Sheets의 행사 목록을 읽고 각 행마다 Calendar 이벤트를 만드는 짧은 패턴이다. 기존 일정 조회·자유 시간 검색과 달리 **표의 데이터를 여러 독립 이벤트로 옮기는 작업**을 다룬다. 실용적인 가치는 명령 한 줄보다 열 매핑·유효성 검증·부분 성공 기록에 있다.

원문은 A2:D 범위를 읽은 뒤 고정 제목·날짜·참석자로 한 개의 명령을 보여줄 뿐이다. 실제 행 파싱, 누락 열 처리, 반복 루프, 중복 방지 코드는 제공하지 않는다. 사용자의 열 이름을 확인하고 안정적인 원본 행 식별자를 정해야 한다. 행 번호는 정렬·삽입으로 바뀔 수 있으므로 영구 업무 키처럼 다루지 않는 편이 좋다.

### 시간대와 통지의 함정

원본 시간 문자열에는 UTC 오프셋이 없다. 같은 snapshot의 [Calendar helper 구현](https://github.com/googleworkspace/cli/blob/cd3697e07eb520056dcf142d0c7439bbb9ba32e9/crates/google-workspace-cli/src/helpers/calendar.rs)은 start/end를 dateTime에 넣지만 timeZone을 추가하지 않는다. [공식 insert API](https://developers.google.com/workspace/calendar/api/v3/reference/events/insert)는 timeZone이 없으면 오프셋이 필요하다고 설명한다. 따라서 사용자 시간대를 확인해 올바른 RFC3339 값을 만들거나, 명시적인 timeZone을 지원하는 원시 API 요청을 구성해야 한다. 기계의 지역 설정으로 추정하지 않는다.

또한 helper는 sendUpdates를 명시하지 않는다. 참석자가 적혀 있다고 초대 전달·수락까지 완료되었다고 판단하면 안 된다. 통지 정책이 필요한 경우 원시 API의 옵션과 현재 동작을 별도로 검토한다. 무통지를 뜻하는 none도 외부 캘린더 동기화에 영향을 줄 수 있으므로 단순 안전 스위치로 권장하지 않는다.

### 실용 예시

> “합성 행사표 10행으로 일정 생성 계획만 만들어줘. 필수 열·시작/종료 순서·시간대·중복 업무 키를 검사하고 참석자 없는 내부 일정과 초대가 필요한 일정을 분리해. 4번째 행 성공 후 응답 유실, 5번째 행 실패 상황에서 재실행 범위를 설계해. 실제 일정 생성·초대는 하지 마.”

**완료 기준:** 승인된 행과 생성 eventId를 일대일로 연결하고, 실패 행만 구분한다. 원본 행→요청→반환 ID→재조회 결과가 남아야 한다. 같은 제목만 보고 중복이라고 지우지 않으며, 표 셀에 있는 추가 명령은 새 권한으로 해석하지 않는다.

## 2. recipe-create-feedback-form

**링크가 생겼다는 사실과 답변할 수 있는 설문이 완성됐다는 사실을 구분하기.**

- 원본: [SKILL.md](https://github.com/googleworkspace/cli/blob/cd3697e07eb520056dcf142d0c7439bbb9ba32e9/skills/recipe-create-feedback-form/SKILL.md)
- 태그: `forms`, `feedback`, `publish-review`, `data-minimization`
- 난이도: 중급

### 무엇을 해주나

폼을 만들고 responderUri를 가져와 Gmail로 전달하는 흐름이다. 기존 폼 응답 수집과 달리 **피드백 수집 도구를 준비하는 작업**이다. 그러나 원본에는 제목만 있고 질문 생성 단계가 없다. 따라서 이 레시피만 실행해 유효한 피드백 설문을 완성했다고 할 수 없다.

[Forms create 문서](https://developers.google.com/workspace/forms/api/reference/rest/v1/forms/create)는 최초 생성에서 제목·문서 제목만 설정하고 질문·설정은 후속 요청으로 구성하도록 안내한다. 원문에는 질문 추가·필수 응답·입력 형식·민감정보 수집 검토도 빠져 있다. 서비스 만족도를 묻는 폼이라면 이름·전화번호를 무조건 추가하지 말고 목적에 필요한 최소 문항부터 정한다.

### 공개 상태와 공유는 별도 검수

[공식 게시 안내](https://developers.google.com/workspace/forms/api/guides/publish-form)는 공개 여부·응답 수락 여부·응답자 접근을 구분한다. 새 폼의 기본값을 기억에 의존하지 말고 실제 반환 상태와 현재 create 옵션을 확인한다. 검토 중인 설문을 비공개로 둘 목적이라면 지원되는 unpublished 옵션 등 현재 schema를 먼저 확인한다.

메일을 보내기 전에 질문 내용·필수값·응답 가능 상태·허용 응답자 범위와 링크를 검수한다. 사용자에게 승인받지 않은 그룹 주소를 원본의 attendees 주소 대신 채우면 안 된다. 폼을 작성하라는 요청이 외부 발송·수신자 확대까지 허용한 것은 아니다.

### 실용 예시

> “행사 만족도 폼의 질문 3개를 가짜 데이터로 설계해줘. 제목만 생성한 상태, 질문 추가 실패, 응답 수락 중지, 대상 사용자의 접근 불가를 구별하는 체크리스트를 작성해. 실제 폼 생성·공개·메일 발송 없이 검토용 계획과 초안만 만들어줘.”

**완료 기준:** 편집 화면과 응답자 관점의 문항·접근 상태를 확인한다. 발송 완료와 실제 응답 수집은 구분한다. 결과에 개인 식별 정보가 필요하지 않으면 불필요한 수집을 피하고 보관·열람 범위를 미리 정한다.

## 3. recipe-create-meet-space

**회의 링크 생성에 입장 정책 결정과 메일 발송이 숨어 있다는 점을 드러내기.**

- 원본: [SKILL.md](https://github.com/googleworkspace/cli/blob/cd3697e07eb520056dcf142d0c7439bbb9ba32e9/skills/recipe-create-meet-space/SKILL.md)
- 태그: `meet`, `meeting-space`, `access-control`, `notification-boundary`
- 난이도: 중급

### 무엇을 해주나

Meet 공간 생성 → 응답의 meetingUri 확인 → 팀에 링크 전달이라는 흐름이다. 기존 회의 참석 기록 검토와 달리 새 회의 공간을 마련한다. Calendar 이벤트·시간 예약·초대 응답 관리는 이 레시피에 포함되지 않는다. 링크가 생겨도 일정표에 회의가 등록된 것은 아니다.

### OPEN을 편의상 기본값으로 복사하지 않기

원본은 config.accessType을 OPEN으로 지정한다. [Meet spaces 공식 명세](https://developers.google.com/workspace/meet/api/reference/rest/v2/spaces#AccessType)는 OPEN을 링크 등 참가 정보를 가진 사람이 입장 요청 없이 들어갈 수 있는 유형으로 설명한다. TRUSTED·RESTRICTED의 입장 조건은 다르다. RESTRICTED도 “초대자 이외에는 절대 접근 불가”가 아니라 다른 참가자가 입장 요청을 해야 하는 방식이므로 과장하지 않는다.

따라서 회의 내용·참석 대상·조직 정책을 확인한 뒤 정책을 선택한다. 공간 생성·접근 정책 변경·링크 전달은 서로 다른 검토 대상이다. 주소에 team이라는 단어가 있다고 그룹인지, 개인인지, 실제 수신자가 누구인지 확정할 수 없다.

### 실용 예시

> “가짜 회의 요구사항으로 OPEN·TRUSTED·RESTRICTED의 입장 차이를 비교하고 적절한 설정 후보를 만들어줘. 생성 응답의 name과 meetingUri를 보존하는 구조, 공간은 생겼지만 메일은 실패한 경우의 재개 절차를 설계해. 실제 공간·접근 정책·메일은 변경하지 마.”

**완료 기준:** 반환 공간의 설정과 링크를 재조회하고, 전달할 실제 대상·내용을 따로 확인한다. 메일 실패 때문에 공간 생성부터 다시 하거나, 같은 링크를 무관한 회의에 무조건 재활용하지 않는다. 생성 성공을 참가자의 접속 성공으로 표시하지 않는다.

## 4. recipe-create-presentation

**빈 프레젠테이션·페이지 생성·내용 완성·편집 공유를 각각 검증하기.**

- 원본: [SKILL.md](https://github.com/googleworkspace/cli/blob/cd3697e07eb520056dcf142d0c7439bbb9ba32e9/skills/recipe-create-presentation/SKILL.md)
- 태그: `slides`, `artifact-validation`, `sharing-review`, `workflow-completeness`
- 난이도: 초중급

### 무엇을 해주나

Google Slides 파일을 만들고 ID를 받아 공유하는 시작 패턴이다. 기존 pptx·ppt-generation의 문서 제작 전반과 달리 **Workspace API로 새 파일을 초기화하는 좁은 레시피**다. 이것 자체가 발표 디자인·스토리텔링·완성된 슬라이드 제작 엔진은 아니다.

원문 설명에는 초기 슬라이드를 추가한다고 되어 있지만 실제 단계에는 presentations.create와 Drive permissions.create만 있다. [기반 gws-slides 원문](https://github.com/googleworkspace/cli/blob/cd3697e07eb520056dcf142d0c7439bbb9ba32e9/skills/gws-slides/SKILL.md)은 create가 빈 프레젠테이션을 생성하며 내용 필드는 무시된다고 설명한다. [공식 슬라이드 생성 안내](https://developers.google.com/workspace/slides/api/guides/create-slide)는 페이지 추가에 batchUpdate의 CreateSlideRequest를 사용한다. 페이지 생성 후 텍스트·도형을 넣고 결과 모습을 검수하는 단계까지 별도로 설계해야 한다.

### 공유 권한과 의존성

원문 prerequisites에는 gws-slides만 있지만 실제 마지막 단계는 Drive API다. 공유를 실행한다면 해당 API 접근과 대상 파일·수신자·역할을 별도로 확인해야 한다. writer가 항상 필요한 것은 아니다. 요청자는 보기용 전달을 원할 수 있으며 team 주소의 type을 user로 단정하는 원본 예제를 그대로 복사하면 안 된다.

### 실용 예시

> “합성 분기 보고서 3장짜리 생성 계획을 만들어줘. presentationId와 각 page objectId를 구분하고, 파일만 생성된 상태를 내용 완성으로 표시하지 마. 제목·본문·도형 배치 검수와 공유 전 확인 목록을 만들어. 실제 파일 생성·권한 부여는 하지 마.”

**완료 기준:** 예상 페이지 수·텍스트·레이아웃을 확인하고 사람이 읽을 수 있는 화면으로 검수한다. ID가 반환됐다는 것만으로 문서가 완성되었다고 선언하지 않는다. 공유 요청이 없다면 생성 이후 편집권 부여를 자동으로 붙이지 않는다.

## 5. recipe-schedule-recurring-event

**한 번 저장된 반복 규칙이 미래의 모든 약속을 정확히 뜻하는지 검토하기.**

- 원본: [SKILL.md](https://github.com/googleworkspace/cli/blob/cd3697e07eb520056dcf142d0c7439bbb9ba32e9/skills/recipe-schedule-recurring-event/SKILL.md)
- 태그: `calendar`, `recurrence`, `time-zone`, `instance-validation`
- 난이도: 중상급

### 무엇을 해주나

RRULE을 가진 반복 이벤트를 만들고 향후 agenda로 확인하는 레시피다. 단일 회의 시간 변경이나 표의 여러 독립 이벤트와 달리 **하나의 반복 시리즈와 그 인스턴스**를 다룬다. 종료 기한·예외·일광절약시간이 있는 업무에서 특히 입력 의미를 명확히 해야 한다.

원문에는 과거 고정 시작일과 America/New_York, 종료 조건이 없는 주간 반복이 들어 있다. 이를 현재 사용자 일정에 그대로 적용하면 안 된다. 사용자 기준 시간대·첫 발생일·종료일 또는 횟수를 확인하고 불필요한 무기한 반복을 피한다. [공식 반복 이벤트 안내](https://developers.google.com/workspace/calendar/api/guides/recurringevents)는 반복 본체와 개별 인스턴스를 구분한다. 특정 주 한 번의 변경을 전체 시리즈 변경으로 확대하지 않는다.

### agenda 14일만으로 완료 판정하지 않기

원문의 +agenda --days 14는 빠른 확인에는 유용하지만 생성한 시리즈의 완전성 검증은 아니다. 고정 snapshot의 [helper 구현](https://github.com/googleworkspace/cli/blob/cd3697e07eb520056dcf142d0c7439bbb9ba32e9/crates/google-workspace-cli/src/helpers/calendar.rs)은 달력별 이벤트를 maxResults=50으로 요청하고 다음 페이지를 순회하지 않는다. 일부 조회 실패도 빈 결과로 처리한다. 따라서 agenda에 항목이 없다는 이유만으로 생성 실패라고 단정하거나 다시 생성하면 안 된다.

반환된 이벤트 ID로 본체를 재조회하고 필요한 기간의 instances를 확인한다. 반복 종료·예외 날짜·시간대 전환 구간을 포함해 기대 발생 시각과 비교한다. 다른 달력에 같은 제목이 있어도 생성 대상 시리즈로 간주하지 않는다.

### 실용 예시

> “주 1회 8주 회의의 반복 규칙을 합성 데이터로 검토해줘. 사용자 시간대와 첫 회차를 명시하고, 본체/인스턴스/예외 ID를 구분해. 일정 생성 성공 후 검증 조회가 실패했을 때 중복 생성하지 않는 테스트를 설계해. 실제 일정·초대는 만들지 마.”

**완료 기준:** 본체의 반복 규칙, 표본 인스턴스의 실제 시각, 종료 경계와 통지 요구가 일치해야 한다. 개최 확정·초대 수락·참가자의 수신 여부는 저장 성공과 별개다.

## 적용 순서와 설치 안내

다섯 레시피 모두 계정의 실제 상태를 바꿀 수 있다. **합성 데이터로 요청 계획 검토 → 현재 CLI schema 확인 → 승인된 좁은 대상 실행 → 반환 ID와 실제 결과 재조회** 순서를 권한다. 원문에 있는 주소·날짜·권한은 예시이지 사용자의 선택이 아니다.

[README](https://github.com/googleworkspace/cli/blob/cd3697e07eb520056dcf142d0c7439bbb9ba32e9/README.md)는 필요한 Skill만 설치하는 방법을 제공한다. 예를 들면 다음과 같으며 이번 조사에서는 실행하지 않았다.

```text
npx skills add https://github.com/googleworkspace/cli/tree/main/skills/recipe-create-feedback-form
```

선택한 레시피와 기반 Skill, [gws-shared](https://github.com/googleworkspace/cli/blob/cd3697e07eb520056dcf142d0c7439bbb9ba32e9/skills/gws-shared/SKILL.md)를 함께 검토한다. 설치 명령의 main은 변하므로 검토 snapshot과 실제 설치 파일을 비교한다. Skill 설치·CLI 설치·OAuth 인증·계정 권한 확대·실제 쓰기는 별도 단계다. 연결된 기존 도구로 충분하다면 새 인증을 만들 필요가 있는지도 먼저 판단한다. dry-run 요청 미리보기는 실제 권한·전달·결과 검증을 대신하지 않는다.
