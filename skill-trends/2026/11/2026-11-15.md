## 1. creating-oracle-to-postgres-master-migration-plan

**태그:** .NET, 의존성 목록, 이전 계획, 프로젝트 분류  
**난이도:** 중급  
**출처:** [고정 SKILL.md](https://github.com/github/awesome-copilot/blob/8ecd5b17f02fe5fbebf35eccd1867265eded811f/skills/creating-oracle-to-postgres-master-migration-plan/SKILL.md)

### 무엇을 돕는가

솔루션의 프로젝트 목록을 얻고 Oracle 패키지·설정·타입 사용·DDL 연결을 조사한다. 이전 대상, 제외, 이전 완료 후보, 테스트 프로젝트로 나누어 후속 Agent가 읽을 일정한 형식의 MasterMigrationPlan을 만든다. 변환부터 시작해 누락을 뒤늦게 발견하는 일을 줄이는 역할이다.

### 실용 예시

**합성 요청문:** “제공한 솔루션 파일과 설정에서 Oracle 의존성을 찾아 프로젝트·근거 파일·잠정 분류·선행 의존성을 표로 작성해. 연결 문자열 값은 가리고 DB에 접속하지 마. 분류가 불확실하면 완료나 제외로 단정하지 말아 줘.”

**완료 기준**
- 모든 솔루션 프로젝트를 한 번씩 열거하고 분류의 근거를 남긴다.
- 공유 라이브러리와 호출 프로젝트의 순서를 설명한다.
- 다른 Agent에게 넘길 범위와 제외 이유가 명확하다.
- 원문의 사용자 분류 확인 단계를 건너뛰어 실제 이전을 시작하지 않는다.

### 적용 시 주의

.Postgres 복사본이 있다는 사실은 이전 성공의 증거가 아니다. 동적 SQL, 외부 구성, 공통 패키지 관리, 별도 배치 프로그램은 단순 이름 검색에서 빠질 수 있다. 외부 DDL 변환 결과가 있어도 정합성 검증까지 생략하지 않는다. 이 Skill의 표는 실행 승인이 아닌 재검토 가능한 계획이다.

## 2. creating-oracle-to-postgres-migration-integration-tests

**태그:** Oracle, 회귀 테스트, C#, seed, 의미 보존  
**난이도:** 중상급  
**출처:** [고정 SKILL.md](https://github.com/github/awesome-copilot/blob/8ecd5b17f02fe5fbebf35eccd1867265eded811f/skills/creating-oracle-to-postgres-migration-integration-tests/SKILL.md)

### 무엇을 돕는가

이전 **전** Oracle 대상 테스트를 만들고 실제 기대 동작을 기준으로 보존한다. 기존 base test와 seed 규약을 읽고, 구체적인 행·값·오류를 검증하며 빈 문자열·NULL·날짜 정밀도를 다룬다. PostgreSQL 변환 후 기대값을 임의로 바꿔 테스트를 통과시키는 접근과 다르다.

### 실용 예시

**합성 요청문:** “고객 조회 메서드에 대해 정상 ID, 없는 ID, 중복 후보, 빈 문자열, NULL의 테스트 명세를 만들어 줘. DB를 실행하지 말고 필요한 최소 seed와 예상 결과·근거를 작성해. 불명확한 기대값은 미확정으로 표시해.”

**완료 기준**
- 단순 non-null 확인 대신 seed에서 도출한 정확한 결과를 검증한다.
- 날짜는 원본 열의 정밀도와 업무 의미에 맞춰 비교한다.
- 실패와 정상 분기를 모두 포함하고 테스트 간 충돌을 피한다.
- 이 Skill은 원문상 Phase 3의 Oracle 테스트 생성용이며 PostgreSQL에 그대로 실행하는 단계가 아니다.

### 적용 시 주의

트랜잭션 rollback을 쓰더라도 운영 DB에서 안전하다는 뜻은 아니다. 별도 테스트 환경과 합성 데이터를 우선한다. 원문은 기존 업무·lookup 행을 가정하지만 그 의존성도 fixture로 명시해야 재현할 수 있다. 자동 commit, 외부 부수효과, 트리거의 영향은 별도 확인한다. 실제 실행하지 않은 명세를 통과한 테스트로 기록하지 않는다.

## 3. migrating-oracle-to-postgres-stored-procedures

**태그:** PL/SQL, PL/pgSQL, 저장 루틴, collation, DDL  
**난이도:** 상급  
**출처:** [고정 SKILL.md](https://github.com/github/awesome-copilot/blob/8ecd5b17f02fe5fbebf35eccd1867265eded811f/skills/migrating-oracle-to-postgres-stored-procedures/SKILL.md)

### 무엇을 돕는가

원본 루틴과 관련 테이블 타입을 함께 읽고 루틴별 변환 파일을 만든다. 업무 흐름을 유지하면서 정렬 규칙·타입·확장 사용을 명시적으로 검토한다. C# 호출부 변경과 DB 안의 실행 의미를 별도 산출물로 다룬다는 점이 중요하다.

### 실용 예시

**합성 요청문:** “합성 PL/SQL 조회 루틴 하나를 분석해 PostgreSQL 함수와 프로시저 중 적절한 형태를 제안해. 입력·출력 계약, 조회 0/1/여러 행, 예외, rollback, 정렬 규칙의 차이를 먼저 표로 써 줘. 변환 SQL은 초안만 만들고 실행하지 마.”

**완료 기준**
- 원본의 정상·실패 결과와 호출부 계약을 함께 유지한다.
- 단일 행 조회의 0건과 여러 건을 각각 테스트한다.
- 언어별 정렬을 무조건 바이너리 정렬로 바꾸지 않는다.
- 변환 파일 생성과 DB 적용을 분리한다.

### 원문 보완

“예외·rollback을 그대로 둔다”는 지침은 의도를 보존하라는 목표로만 해석한다. [PostgreSQL 트랜잭션 문서](https://www.postgresql.org/docs/current/plpgsql-transactions.html)는 CALL/DO의 호출 경로와 예외 블록에 따른 트랜잭션 종료 제한을 설명한다. 문장을 기계적으로 복사하면 같은 의미가 되지 않을 수 있다.

[PL/pgSQL 공식 문서](https://www.postgresql.org/docs/current/plpgsql-statements.html)에 따르면 INTO STRICT는 정확히 한 행을 요구하며 0건과 여러 건에 다른 오류를 낸다. 일반 INTO 뒤 NOT FOUND 검사만 추가하면 여러 행 문제까지 해결되는 것은 아니다. 루틴 시그니처와 이름 유지도 목적이지 모든 PL/SQL 문법의 1:1 이식을 보장하지 않는다. orafce 설치는 별도 결정이며 이번에 수행하지 않았다.

## 4. migrating-oracle-to-postgres-data-access-code

**태그:** C#, Npgsql, ADO.NET, DB provider, 매개변수  
**난이도:** 상급  
**출처:** [고정 SKILL.md](https://github.com/github/awesome-copilot/blob/8ecd5b17f02fe5fbebf35eccd1867265eded811f/skills/migrating-oracle-to-postgres-data-access-code/SKILL.md)

### 무엇을 돕는가

원본 Oracle 프로젝트를 보존하고 별도 PostgreSQL 복사본의 패키지·연결 구성·ADO.NET 타입·매개변수·루틴 호출·인라인 SQL을 체크리스트로 옮긴다. 단순 타입명 치환이 아니라 DB 반환값과 클라이언트 처리 방식의 경계를 검토하는 데 쓴다.

### 실용 예시

**합성 요청문:** “이 Repository 클래스의 Oracle 의존성을 Npgsql 전환 항목으로 분해해 줘. 함수/프로시저 호출과 refcursor 처리를 버전별로 검토하고 수정 diff 초안을 만들어. 원본 프로젝트·자격증명은 건드리지 말고 패키지 복원이나 DB 실행도 하지 마.”

**완료 기준**
- Npgsql·EF provider·.NET의 실제 버전 조합을 명시한다.
- 숫자 정밀도, 날짜의 시간 부분, NULL 처리, 결과 집합 구조를 확인한다.
- 각 호출을 반환 계약과 테스트에 연결한다.
- build 성공만으로 동작 호환성을 선언하지 않는다.

### 반드시 수정해서 사용할 부분

원문은 함수 호출에 CommandType.StoredProcedure를 유지하라고 하지만 [Npgsql 공식 문서](https://www.npgsql.org/doc/basic-usage.html)는 **7.0부터 기본적으로 프로시저를 CALL한다**고 설명한다. 함수에는 SELECT, 프로시저에는 CALL을 명시적으로 구성하고 값은 매개변수화하는 쪽을 검토한다. 기존 호환 옵션 유무도 확인한다.

원문의 SQL 치환표는 출발점이지 등가성 증명서가 아니다. ROWNUM과 정렬의 순서, NULL이 섞인 연결·분기, MERGE 조건은 개별 검증한다. [PostgreSQL 날짜 함수 문서](https://www.postgresql.org/docs/current/functions-datetime.html)에서 now()는 트랜잭션 시작 시각이다. “현재 시각” 함수를 모두 now()로 바꿔도 같은 결과라는 가정은 피한다. 연결 문자열은 비밀 저장소나 기존 구성 방식을 유지하고 예시 비밀번호를 실제 값으로 채우지 않는다.

## 5. reviewing-oracle-to-postgres-migration

**태그:** 이전 검증, 차등 테스트, refcursor, 시간대, 감사 증거  
**난이도:** 상급  
**출처:** [고정 SKILL.md](https://github.com/github/awesome-copilot/blob/8ecd5b17f02fe5fbebf35eccd1867265eded811f/skills/reviewing-oracle-to-postgres-migration/SKILL.md), [참고 목록](https://github.com/github/awesome-copilot/blob/8ecd5b17f02fe5fbebf35eccd1867265eded811f/skills/reviewing-oracle-to-postgres-migration/references/REFERENCE.md)

### 무엇을 돕는가

이전 대상마다 빈 문자열, 타입 변환, 정렬, cursor, 예외, 시간대 등의 차이가 적용되는지 확인하고 테스트와 연결한다. 계획 단계에서는 위험표, 사후 단계에서는 근거가 연결된 통과·실패·미실행 목록을 산출한다.

### 실용 예시

**합성 요청문:** “변환 SQL과 C# diff를 읽고 적용 가능한 위험 항목만 골라 원본 위치·새 위치·검증 테스트·남은 결정을 연결해. 로그가 없는 항목은 미실행으로 표시하고 실행 계획이나 테스트 통과를 지어내지 마.”

**완료 기준**
- 위험마다 적용·비적용 이유를 기록한다.
- DB 결과값뿐 아니라 오류, 정렬, 리소스 수명도 비교한다.
- 테스트 기대값을 느슨하게 바꿔 차이를 숨기지 않는다.
- 실제 로그와 명세를 구분하고 미실행 상태를 허용한다.

### 참고 문서도 검토 대상

[시간대 참고](https://github.com/github/awesome-copilot/blob/8ecd5b17f02fe5fbebf35eccd1867265eded811f/skills/reviewing-oracle-to-postgres-migration/references/oracle-to-postgres-timestamp-timezone.md)는 legacy Npgsql의 timestamptz를 Unspecified로 설명하지만 [공식 Npgsql 문서](https://www.npgsql.org/doc/types/datetime.html)는 구형/legacy 읽기를 Local, 6.0 이후 기본을 Utc로 구분한다. timestamp without time zone의 Unspecified와 혼동하면 안 된다. 출처 불명의 시각에 SpecifyKind(Utc)를 붙이는 것을 변환으로 취급하지 않는다.

[빈 문자열 참고](https://github.com/github/awesome-copilot/blob/8ecd5b17f02fe5fbebf35eccd1867265eded811f/skills/reviewing-oracle-to-postgres-migration/references/empty-strings-handling.md)의 IsNullOrEmpty assertion은 두 값을 구분할 필요가 있는 회귀 검증을 약하게 만들 수 있다. 원본 의미 보존과 새로운 업무 규칙 도입은 별도 결정이다.

[refcursor 참고](https://github.com/github/awesome-copilot/blob/8ecd5b17f02fe5fbebf35eccd1867265eded811f/skills/reviewing-oracle-to-postgres-migration/references/postgres-refcursor-handling.md)의 첫 예시는 using var reader가 아직 scope 안에 있는 동안 Commit을 호출하며 cursor 이름을 문자열에 직접 넣는다. 결과 소비 후 reader 종료 시점과 식별자 quoting을 재검토해야 한다. 원문 helper를 검증 없이 복사하지 않는다. 이는 정적 코드 검토이며 실제 장애를 재현한 결과는 아니다.

## 적용 순서와 설치 안내
