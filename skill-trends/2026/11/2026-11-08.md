## 1. expo-project-structure

**태그:** 프로젝트 구조 · Expo Router · 관심사 분리 · 서버 경계  
**난이도:** 초중급

**무엇을 돕는가**

새 Expo 앱에서 파일을 어디에 둘지 정하는 출발점이다. `src/app`에는 라우팅에 필요한 파일을 두고, 재사용 UI는 `components`, 화면에만 쓰는 UI는 `screens`, 서버 전용 보조 코드는 `server`로 구분한다. 화면이 커질 때 라우트 파일은 URL 파라미터 등 이동 관련 책임을 맡고 실제 화면 본문을 불러오게 한다. **원문은 아직 구조가 정해지지 않은 새 프로젝트 전용**이며 기존 앱을 이 모양으로 재배치하라고 하지 않는다. [고정 원문](https://github.com/expo/skills/blob/a9e5bd3fa00b4e61f632e43f85da73aee1942582/plugins/expo/skills/expo-project-structure/SKILL.md)

**사전 조건과 실용 예시**

라우터를 사용하는 신규 앱인지, 기존 구조·팀 규칙·경로 별칭이 있는지부터 확인한다. 가상의 독서 기록 앱이라면 목록과 상세 화면, 공용 책 카드, 날짜 형식 함수, 서버 조회 코드를 구분하는 작은 구조안부터 시작할 수 있다. 처음부터 모든 폴더를 채우거나 한 화면을 불필요하게 여러 층으로 쪼갤 필요는 없다.

> “새 Expo 독서 기록 앱의 폴더 구조를 제안해 줘. 라우트, 공용 책 카드, 화면 전용 컴포넌트, 날짜 함수와 테스트를 분리해. 서버 기능이 필요한지 먼저 설명하고, 기존 프로젝트가 발견되면 이동하지 말고 현재 규칙을 따라 줘. 설치나 파일 생성 전에 경로와 책임만 보여 줘.”

**완료 기준**

- 각 파일의 책임과 import 방향이 명확하고, 라우트 폴더에 일반 유틸리티·테스트가 들어가지 않는다.
- `@/*` 별칭과 실제 소스 경로가 일치한다. `app`와 `src/app`가 함께 존재하면 후자가 우선하므로 누락된 화면처럼 보이는 현상을 확인한다. 공식 문서는 SDK 55 이후 기본 템플릿에 `src`가 포함된다고 설명한다. [공식 src 안내](https://docs.expo.dev/router/reference/src-directory/)
- 서버 코드가 클라이언트에서 import되지 않는지 점검한다. 폴더 이름만 `server`로 정한다고 비밀정보가 자동 보호되는 것은 아니다.

**안전·적용 범위**

`+api.ts`는 화면이 아니라 서버 endpoint다. 모바일 바이너리에 넣는 것만으로 운영 서버가 생기지 않으며, 배포된 서버와 클라이언트의 접근 주소가 필요하다. 원문의 “app 안의 모든 파일은 route”라는 요약도 `_layout`·API handler 같은 특수 파일의 역할을 구분해서 읽는다. [공식 API Routes](https://docs.expo.dev/router/web/api-routes/)

기존 디렉터리 이동, import 일괄 수정, 서버 배포는 별도 작업으로 분리한다. 경로 정리는 사용자 데이터 접근 권한이나 운영 배포 승인을 대신하지 않는다.

## 2. expo-router

**태그:** 내비게이션 · 딥링크 · 탭 · 모달 · 버전 호환성  
**난이도:** 중급

**무엇을 돕는가**

파일 기반 URL, 동적 경로, 그룹, 탭 안의 스택, 모달·시트, 헤더를 조합하는 지침이다. 단순히 “버튼을 누르면 다음 화면”을 만드는 데 그치지 않고, 어느 탭에서 상세로 들어왔는지와 뒤로 가기 경로를 설계할 때 유용하다. 화면 스타일·애니메이션은 다른 Skill로 나누므로 이동 구조를 먼저 검토하기 좋다. [고정 원문](https://github.com/expo/skills/blob/a9e5bd3fa00b4e61f632e43f85da73aee1942582/plugins/expo/skills/expo-router/SKILL.md)

**실용 예시와 요청문**

가상의 독서 앱에 서재·검색 탭, `/books/[id]` 상세, 독서 메모 모달이 있다고 가정한다. 앱 안의 클릭뿐 아니라 앱이 종료된 상태에서 상세 링크를 여는 경우, 로그인 전에 링크가 도착하는 경우, 메모를 닫은 뒤 돌아갈 화면까지 정한다.

> “현재 Expo SDK와 라우트 트리를 읽고 서재·검색·상세·메모 모달의 이동표를 만들어 줘. 각 탭의 뒤로 가기와 직접 URL 진입을 구분하고, cold start·로그아웃·모달 닫기·연속 탭 전환 시험을 설계해. 기존 URL 변경이나 라우트 삭제가 필요하면 영향받는 링크부터 표시해 줘.”

**완료 기준**

`/`에 대응하는 화면이 있고, 유효하지 않은 책 ID와 없는 URL을 처리한다. iOS 뒤로 가기 제스처, Android 시스템 뒤로 가기, 웹 직접 URL·새로고침을 대상 플랫폼별로 확인한다. 모달을 반복해서 열고 닫아도 화면이 중첩되거나 이전 초안이 사라지지 않아야 한다. 로그인 상태 복원이 끝나기 전에 잘못 redirect하지 않는지도 확인한다. 이 항목들은 테스트 계획이며 이번에 통과한 결과가 아니다.

**현재 문서와의 차이**

- 원문 예제는 `expo-router/unstable-native-tabs`를 사용하지만 현재 공식 문서는 **SDK 58 이상은 `expo-router/native-tabs`, SDK 54~57은 기존 unstable 경로**로 구분한다. 기존 앱에 최신 예제를 무조건 붙이지 않는다. [공식 Native tabs](https://docs.expo.dev/router/advanced/native-tabs/)
- 원문의 일반적인 “특수문자를 쓰지 말라”는 문구를 파일명 전체에 기계적으로 적용하면 안 된다. `[id]`, `(group)`, `_layout`, `+not-found`는 라우터가 사용하는 문법이다. 동봉 참조와 공식 문서가 이를 명확히 설명한다. [라우트 구조 참조](https://github.com/expo/skills/blob/a9e5bd3fa00b4e61f632e43f85da73aee1942582/plugins/expo/skills/expo-router/references/route-structure.md) · [공식 표기법](https://docs.expo.dev/router/basics/notation/)
- Protected route는 클라이언트 화면 접근을 제어한다. 서버 API도 사용자·객체별 권한을 검증해야 한다. UI에서 화면이 안 보이는 것만으로 데이터 접근이 차단됐다고 결론 내리지 않는다. [공식 보호 경로](https://docs.expo.dev/router/advanced/protected/)

## 3. expo-data-fetching

**태그:** 네트워크 · 캐시 · 오프라인 · 실패 복구 · 데이터 보호  
**난이도:** 중급, 오프라인 쓰기 동기화는 중상급

**무엇을 돕는가**

API 호출, TanStack Query/SWR, 캐시, 인증, 오프라인과 화면 상태를 함께 다룬다. 특히 로딩과 빈 결과를 구분하고, 새로고침에 실패해도 기존 데이터를 유지하며, 저장 실패 시 사용자의 초안을 남기도록 하는 부분이 실용적이다. 초기 인증 상태를 읽는 동안 잘못된 화면으로 보내지 않는 것도 포함한다. [고정 원문](https://github.com/expo/skills/blob/a9e5bd3fa00b4e61f632e43f85da73aee1942582/plugins/expo/skills/expo-data-fetching/SKILL.md)

**실용 예시와 요청문**

책 목록을 받아오고 독서 메모를 저장하는 화면에 합성 응답을 준비한다. 첫 요청 지연, 정상적인 빈 목록, 401, 일시적 503, 캐시가 있는 상태의 실패, 저장 응답 유실을 각각 구분한다. 저장 버튼을 비활성화하는 것과 서버에서 중복 저장을 방지하는 것은 별개의 검증 대상이다.

> “실제 계정 없이 mock 응답으로 목록과 메모 저장 흐름을 검토해 줘. 처음 로딩·빈 목록·기존 데이터가 있는 재조회 실패·오프라인 시작을 구분하고, 저장 실패 뒤 초안과 재시도 버튼을 유지해. 요청 취소 signal 연결과 중복 저장 방지 조건을 확인하고, 실제 API 호출 없이 테스트 항목과 최소 수정안을 만들어 줘.”

**완료 기준**

- 미요청·일시중지·실패를 “데이터 없음”으로 표시하지 않는다. 캐시가 있으면 내용과 갱신 실패 안내를 함께 보여 준다.
- 화면을 떠나거나 검색어가 바뀔 때 이전 응답이 새 상태를 덮어쓰지 않는지 확인한다. 로그아웃·계정 전환 시 이전 사용자 캐시의 노출도 시험한다.
- 저장 실패 후 입력을 보존하고 재시도한다. 재시도 가능한 오류와 인증·검증 오류를 구분하며, 서버가 이미 처리했을 수 있는 쓰기는 중복 방지 계약을 먼저 확인한다.

**원문에서 반드시 보완할 부분**

1. **취소는 자동 완성이 아니다.** [동봉 참고문서](https://github.com/expo/skills/blob/a9e5bd3fa00b4e61f632e43f85da73aee1942582/plugins/expo/skills/expo-data-fetching/references/offline-and-cancellation.md)는 React Query가 unmount 시 자동 취소한다고 단순화한다. 공식 문서는 기본적으로 사용하지 않는 query의 Promise가 계속 완료될 수 있다고 설명한다. 실제 fetch를 중단하려면 query 함수가 받은 `signal`을 요청에 전달해야 한다. 취소가 서버의 이미 처리된 쓰기를 되돌리는 것도 아니다. [TanStack 취소 문서](https://tanstack.com/query/latest/docs/framework/react/guides/query-cancellation)
2. **일괄 재시도 예제는 운영 정책이 아니다.** 원문의 범용 wrapper는 HTTP 오류 종류와 method를 구분하지 않고 재시도한다. GET의 일시 오류, 401, 검증 실패, 결과가 불확실한 POST를 같은 방식으로 처리하지 않는다. TanStack의 mutation은 기본적으로 재시도하지 않으며 별도 설정이 필요하다. [공식 mutations 문서](https://tanstack.com/query/latest/docs/framework/react/guides/mutations)
3. **환경 변수는 비밀 저장소가 아니다.** `EXPO_PUBLIC_*`는 앱에 평문으로 포함되므로 비밀키를 두지 않는다. 원문은 `.env` 수정 후 개발 서버 재시작을 안내하지만 현재 문서는 CLI 재시작 없이 앱을 full reload하면 변경값을 볼 수 있다고 설명한다. 배포 번들의 환경 변경은 별도로 다룬다. [공식 환경 변수 문서](https://docs.expo.dev/guides/environment-variables/)
4. **웹 loader의 버전·보안 조건을 확인한다.** 동봉 [loader 참조](https://github.com/expo/skills/blob/a9e5bd3fa00b4e61f632e43f85da73aee1942582/plugins/expo/skills/expo-data-fetching/references/expo-router-loaders.md)는 SDK 55+의 실험 설정과 세션 캐시를 설명한다. 현재 공식 문서는 SDK 58에서 안정화되었고 재방문 시 HTTP 캐시 규칙을 사용하는 동작을 구분한다. static loader는 빌드 시 실행되므로 요청별 인증 데이터에 적합하지 않다. 반환값은 클라이언트로 전달되며 개인 데이터에는 공개 캐시를 쓰지 않는다. [공식 Data loaders](https://docs.expo.dev/router/web/data-loaders/)

loader 참조의 잔액 예제는 쿠키 유무만 표시하고 실제 인증 검증이나 반환 차단을 구현하지 않는다. **권한 검증 전에 민감한 데이터를 조회·반환하는 예제로 복사하지 않는다.** 토큰을 로그·예제 응답에 넣지 않고, 기기 저장에는 지원 플랫폼의 SecureStore 같은 보호 저장소를 검토한다. 그것도 서버 권한 검증이나 데이터 복구 정책을 대신하지 않는다. [공식 SecureStore](https://docs.expo.dev/versions/latest/sdk/securestore/)

## 4. expo-dev-client

**태그:** 개발 빌드 · 네이티브 모듈 · 실기기 QA · 개발 환경  
**난이도:** 중급

**무엇을 돕는가**

Expo Go에 포함되지 않은 네이티브 기능을 사용하는 앱을 위해 프로젝트 전용 개발 바이너리를 만들고 기기에 설치하는 흐름이다. 네이티브 모듈과 설정을 빌드에 넣은 뒤 Metro 개발 서버에 연결해 JavaScript 변경을 확인한다. `expo-dev-client`라는 이름은 이 Skill의 식별자인 동시에 라이브러리명으로도 쓰이므로 지침 설치와 앱 의존성 설치를 구분한다. 개발 빌드는 실제 앱 개발에 유용하지만 스토어 출시용 바이너리와 같은 결과물은 아니다. [고정 원문](https://github.com/expo/skills/blob/a9e5bd3fa00b4e61f632e43f85da73aee1942582/plugins/expo/skills/expo-dev-client/SKILL.md) · [공식 개발 빌드 소개](https://docs.expo.dev/develop/development-builds/introduction/)

**사전 조건과 실용 예시**

대상 플랫폼, 필요한 네이티브 라이브러리, SDK, 로컬/클라우드 빌드 방식을 먼저 정한다. 로컬 Expo CLI 경로에는 Android Studio·Xcode 같은 도구가 필요하고, EAS의 로컬 빌드 경로에는 별도의 인증·빌드 조건이 있다. [로컬 EAS 빌드](https://docs.expo.dev/build-reference/local-builds/)

> “Expo Go에 없는 네이티브 라이브러리를 넣은 가상 앱의 Android 개발 빌드 계획을 만들어 줘. 현재 SDK, 개발 프로필, 빌드 도구를 확인하고 로컬과 클라우드의 조건을 비교해. 계정 연결·과금·빌드·스토어 제출은 실행하지 말고 필요한 단계와 기기 테스트 항목만 정리해 줘.”

**완료 기준**

승인된 실행 단계에서는 지정 기기에서 앱이 시작되고, 해당 네이티브 기능이 실제로 호출되며, Metro 연결과 JS 변경 반영이 되는지 확인한다. 네이티브 코드가 바뀌면 재빌드가 필요하다는 점도 기록한다. 클라우드 빌드 성공, 파일 다운로드, 기기 설치, 기능 테스트는 서로 다른 완료 상태다. iOS Simulator용은 `ios.simulator: true` 등 전용 프로필이 필요하며 일반 기기용 `.ipa`를 그대로 설치하는 흐름으로 설명하지 않는다. [공식 Simulator 빌드](https://docs.expo.dev/build-reference/simulators/)

**원문에서 반드시 보완할 부분**

- 원문은 클라우드 빌드를 유료라고 단정하지만 현재 가격표에는 Free 플랜의 Android·iOS 빌드 할당량이 있다. 무료 할당량, 잔여 사용량, 초과 조건을 실제 계정에서 확인해야 한다. 개발용 소스가 클라우드로 올라가는 것과 무료 로컬 작업도 구분한다. [공식 가격표](https://expo.dev/pricing)
- **원문의 CLI 점검 블록에 있는 `eas update`는 CLI 업그레이드가 아니라 OTA 게시 명령이다. 버전 확인용으로 실행하지 않는다.** `eas --version`과 구분해야 한다. 또한 현재 문서의 빌드 후 자동 제출 플래그는 `--auto-submit`이며 원문의 `--submit`을 검증 없이 복사하지 않는다. [현재 CLI 참조](https://docs.expo.dev/eas/cli/)
- TestFlight 제출, 내부 배포, Simulator 설치를 한 프로필로 뭉뚱그리지 않는다. Apple 계정·서명 조건은 선택한 경로에 따라 달라진다. 개발 빌드 요청만으로 스토어 제출이나 인증서 변경까지 진행하지 않는다. [빌드 프로필 안내](https://docs.expo.dev/build/eas-json/)

## 5. expo-upgrade

**태그:** SDK 마이그레이션 · 의존성 · 호환성 · 회귀 테스트  
**난이도:** 중상급

**무엇을 돕는가**

Expo SDK 변경을 패키지 숫자 수정이 아니라 의존성 정렬, 진단, 네이티브 프로젝트 갱신, API 이전과 회귀 테스트로 나눠 다룬다. 오디오·비디오, New Architecture, React Compiler, Router import 등 참고자료가 연결되어 있어 영향 목록을 만들기 좋다. 다만 특정 시기의 버그 대응과 오래된 예제가 함께 있으므로 현재 목표 SDK의 공식 이전 가이드가 우선이다. [고정 원문](https://github.com/expo/skills/blob/a9e5bd3fa00b4e61f632e43f85da73aee1942582/plugins/expo/skills/expo-upgrade/SKILL.md)

**사전 조건과 실용 예시**

현재·목표 SDK, 패키지 매니저·잠금파일, 수동으로 고친 네이티브 코드, 라이브러리 지원 범위를 기록한다. 공식 기본 순서는 목표 Expo 버전 선택, 호환 의존성 정렬, `expo-doctor` 진단, 플랫폼별 갱신과 검증이다. 일반적으로 SDK를 단계적으로 올리도록 권장하며 특수 버그 우회는 해당 버전의 근거를 따로 확인한다. [공식 업그레이드 절차](https://docs.expo.dev/workflow/upgrading-expo-sdk-walkthrough/)

> “SDK 57의 가상 Expo Router 앱을 58로 올리는 계획을 만들어 줘. 직접 수정한 iOS·Android 코드는 보존하고 의존성·라우팅·웹 출력의 영향 목록부터 정리해. 설치·native 폴더 재생성 전에 변경 범위를 보여 주고, 성공 기준을 진단·번들·네이티브 빌드·실기기 시험으로 나눠 줘.”

**완료 기준**

미해결 진단, 변경된 잠금파일과 API, 수동 이관 파일을 남긴다. 타입 검사와 JS export 통과만으로 네이티브 기능까지 확인됐다고 하지 않는다. 로그인 후 이동, 딥링크, 앱 재시작, 뒤로 가기, 앱이 실제 사용하는 카메라·오디오 등의 권한 거절과 복구 흐름을 검증한다. SDK 57→58 Router 변경도 앱의 실제 사용 API를 기준으로 점검한다. [공식 Router 이관 문서](https://docs.expo.dev/router/migrate/sdk-57-to-58/)

**원문에서 반드시 보완할 부분**

1. **native 폴더 존재 여부만으로 관리 방식을 판정하지 않는다.** `ios/`·`android/`가 있어도 생성된 결과인지 수동 유지 코드인지 다를 수 있다. `prebuild --clean`은 네이티브 프로젝트를 다시 만들므로 수동 변경을 확인하고 보존 전략을 정하기 전에는 실행하지 않는다.
2. 동봉 [New Architecture 문서](https://github.com/expo/skills/blob/a9e5bd3fa00b4e61f632e43f85da73aee1942582/plugins/expo/skills/expo-upgrade/references/new-architecture.md)는 비활성화 설정을 제시하지만 **공식 문서는 SDK 55 이상에서 비활성화할 수 없다고 명시**한다. 최신 SDK의 의존성 문제를 `newArchEnabled: false`로 해결하라고 안내하지 않는다. [현재 공식 가이드](https://docs.expo.dev/guides/new-architecture/)
3. 원문의 SDK 56 건너뛰기·`expo@57.0.9` 이상 권고는 특정 Hermes 메모리 회귀 맥락이다. SDK 57을 현재 최신이라고 소개하거나 모든 앱에 같은 도약 경로를 적용하지 않는다. 목표 버전과 현재 릴리스 지침을 먼저 확인한다.
4. “Deprecated Packages” 표를 무조건 삭제할 목록으로 취급하지 않는다. 현재 공식 문서는 `expo-linear-gradient`를 여전히 제공하며 CSS 그라데이션을 대안으로 설명한다. 각 패키지의 실제 지원과 기능 동등성을 확인한 뒤 필요한 것만 이전한다. [현재 LinearGradient 문서](https://docs.expo.dev/versions/latest/sdk/linear-gradient/)

캐시 삭제·의존성 재설치·컴파일러 활성화를 한 번에 수행하면 회귀 원인을 좁히기 어렵다. 변경을 나눠 기준 결과와 비교하고, 필요하지 않은 기능 전환을 SDK 업그레이드에 끼워 넣지 않는다.

## 6. eas-update

**태그:** OTA · 릴리스 관리 · runtime 호환성 · 배포 검증  
**난이도:** 중상급

**무엇을 돕는가**

설치된 앱이 지원하는 JavaScript·스타일·에셋 변경을 OTA로 전달하도록 설정·게시·검증하는 지침이다. 설치된 바이너리, 업데이트, branch, channel, runtimeVersion의 차이를 설명하고 “게시했는데 바뀌지 않는다”는 문제를 순서대로 조사한다. 네이티브 코드나 SDK 변경은 새 바이너리가 필요하다. 현재 공식 문서는 서비스를 Expo Update로 표기하기도 하지만 Skill 이름과 CLI 명령은 `eas-update`·`eas`로 유지된다. [고정 원문](https://github.com/expo/skills/blob/a9e5bd3fa00b4e61f632e43f85da73aee1942582/plugins/expo/skills/eas-update/SKILL.md) · [runtime 호환성](https://docs.expo.dev/eas-update/runtime-versions/)

**사전 조건과 실용 예시**

연결된 프로젝트, 호환되는 `expo-updates`, 실제 설치 빌드와 플랫폼, channel·runtime을 확인한다. `update:configure`는 설정을 바꾸므로 실행 전후 diff를 검토하고 URL·프로젝트 ID·runtime 정책을 추측해서 채우지 않는다. SDK 55 이상은 게시할 때 EAS environment를 선택해야 한다. channel과 environment가 같은 이름이어도 각각 배포 대상과 번들에 적용할 환경 설정이라는 다른 역할이다. [공식 시작 가이드](https://docs.expo.dev/eas-update/getting-started/)

가상의 iOS preview 앱이 runtime `2.4.0`을 사용하고 검색 정렬과 문구만 바뀌었다고 가정한다. 먼저 네이티브 의존성·설정 변경이 없는지 검토한다.

> “이 변경이 현재 preview 바이너리에 OTA로 호환되는지 읽기 전용으로 검토해 줘. 프로젝트·iOS·runtime 2.4.0·preview channel과 environment를 각각 확인하고, 승인 후 사용할 게시 계획과 확인·복구 순서를 써 줘. 실제 게시나 production 채널 변경은 하지 마.”

**완료 기준**

승인된 게시 단계에서는 update 그룹, 플랫폼·runtime, channel이 연결한 branch를 확인하고 실제 설치 앱에서 수정 사항을 확인한다. 같은 channel이라는 사실만으로 호환성이 증명되지 않는다. [공식 매칭 모델](https://docs.expo.dev/eas-update/how-it-works/)

개발 빌드는 Extensions 등의 수동 열기 흐름으로 확인하고 출시형 빌드의 자동 업데이트 동작과 구분한다. 기본 출시 동작에서는 한 번의 cold start가 다운로드하고 다음 cold start가 적용할 수 있다. 앱을 백그라운드로 보내는 것과 완전히 종료하는 것도 다르다. “항상 두 번 실행해야 한다”는 규칙이 아니라 **다운로드와 적용 시점에 따라 최대 두 번 확인하는 QA 절차**로 설명한다.

**안전·실패 해석**

- 앱 설정 파일에서 channel·업데이트 URL을 바꿔도 이미 설치된 바이너리에 소급 반영되지 않는다. 서버의 channel→branch 연결 변경은 해당 channel의 여러 설치본에 영향을 줄 수 있다.
- 원인 조사 순서는 프로젝트와 게시 대상, 플랫폼·runtime, 설치 빌드의 설정, branch 연결, 다운로드·재실행 상태다. 안 보인다고 호환성 검사나 안전장치를 끄지 않는다. [공식 디버깅 가이드](https://docs.expo.dev/eas-update/debug/)
- preview 검증 뒤 production으로 옮길 때 동일 산출물 재사용과 환경변수·서명 조건을 확인한다. 다시 export한 번들은 이전에 시험한 번들과 다를 수 있다. 게시 성공은 사용자 전체의 적용·정상 동작을 증명하지 않으므로 도입률·실패 지표는 별도로 관찰한다. [공식 배포 가이드](https://docs.expo.dev/eas-update/deployment/)
- Free 플랜 지원과 무제한 무료는 다르다. 사용자 수·대역폭 등 한도, 정확한 대상과 권한을 확인한다. production 게시, channel 연결 변경, runtime 정책 변경은 각각 영향을 설명하고 승인된 범위에서만 실행한다.

## 적용 순서와 설치 안내

권장 순서는 **프로젝트·SDK 확인 → 해당 버전 문서와 Skill 대조 → 합성 입력·테스트 계획 → 승인된 좁은 범위 실행 → 실제 기기·배포 결과 확인**이다. 설치부터 시작하거나 여섯 항목을 모두 사용할 필요는 없다. 기존 앱에서 새 구조안이나 최신 SDK를 자동 적용하지 않는다.

[공식 Expo Skills 문서](https://docs.expo.dev/skills/)와 README는 Claude Code·Codex에는 plugin, 다른 호환 Agent에는 Skills CLI 경로를 안내한다. 아래는 공식 설치 명령의 예시이며 **이번 조사에서 실행하지 않았다**.

```text
# Codex 공식 marketplace의 Expo plugin
codex plugin add expo@openai-curated

# Claude Code 공식 marketplace의 Expo plugin
claude plugin install expo@claude-plugins-official
```

이 경로는 현재 marketplace 배포본을 설치하므로 이 보고서의 검토 SHA에 고정되는 것은 아니다. 설치 전에 실제 내려받는 Skill을 확인한다. 다른 Agent용 `npx skills add expo/skills` 경로는 Skill 파일만 설치하며, plugin과 기능·업데이트 방식이 같다고 가정하지 않는다. 호스트별 도구 허용·자동 발견·호환성도 별도 확인 대상이다.

**plugin은 문서만 추가하지 않는다.** 원본 [MCP 설정](https://github.com/expo/skills/blob/a9e5bd3fa00b4e61f632e43f85da73aee1942582/plugins/expo/mcp.json)은 Expo 원격 MCP 서버를 포함한다. 공식 문서는 OAuth 인증과 로컬 개발 서버 기능을 따로 설명한다. 계정 연결, 도구 권한, 데이터 전송 범위, 유료 호출 예산을 검토하고 필요한 권한만 부여한다. Skill을 읽는 데 MCP 인증이나 클라우드 빌드가 필수인 것은 아니다. [공식 MCP 안내](https://docs.expo.dev/mcp/)

각 원문에는 CLI를 통한 피드백 전송 지침도 있다. 오류를 발견했다는 이유만으로 프로젝트 코드·로그·실패 내용 등을 자동 전송하지 않는다. 외부 피드백은 보낼 내용과 승인 범위를 먼저 정한다. 이번 조사에서는 피드백을 전송하지 않았다.
