## 1. Dory1.0: 같은 가중치로 반복 연산량을 바꾸는 소형 LLM

**개발:** NVIDIA. **태그:** text-generation, English, latent-recurrent, normalized-GPT, sliding-window-attention, reasoning, tool-use, NVFP4-pretraining.

### 신규 계열의 근거

Dory는 **입력 8블록 → 공유 recurrent 20블록 → 출력 8블록**으로 구성되며, recurrent block을 다시 실행할 때 입력을 재주입한다. nGPT와 SWA/full-attention 혼합 구조를 사용한다. 기존 Nemotron 3.5 Lightning·Super VL·Bolt의 작은 크기나 단순 양자화 배포로 소개하는 것이 아니다. 핵심은 **저장된 파라미터를 공유하면서 추론 계산 깊이를 바꾸는 구조**다. 여기서 블록은 attention+MLP 묶음이며, config는 둘을 별도 항목으로 세어 16/40/16, 총 72로 표기한다. [배포 설정](https://huggingface.co/nvidia/NVIDIA-Nemotron-Labs-Dory1.0-4B-BF16/blob/main/config.json). [공식 구조 설명](https://huggingface.co/nvidia/NVIDIA-Nemotron-Labs-Dory1.0-4B-BF16), [공식 지원 구현 PR](https://github.com/vllm-project/vllm/pull/60149).

NVIDIA는 **6T tokens 사전학습 중 처음 약 4.5T를 native NVFP4, 나머지를 BF16**으로 학습한 뒤 300B tokens로 문맥을 확장했다고 설명한다. 후속 SFT·GRPO도 수행했다. 이는 개발사의 학습 보고이며, 원래 가중치 초기화의 모든 세부 이력이나 학습을 독립 재현했다는 뜻은 아니다. BF16·MXFP8·NVFP4·GGUF는 **같은 Dory1.0 한 계열**로 묶는다. [학습·배포 카드](https://huggingface.co/nvidia/NVIDIA-Nemotron-Labs-Dory1.0-4B-BF16).

### 활용 예와 실행 상태

영어 코드 함수의 오류 찾기나 문서 질의를 같은 checkpoint에서 loop 수를 바꿔 비교하는 실험에 적합한 후보다. 공식 recipe는 `n_recurrent_loops=2`, `recurrent_kv_cache_mode="per_loop"`를 기본 예로 들고, `nemotron_v3` reasoning parser와 `qwen3_coder` tool parser를 사용한다. 입력 예는 “이 Python 함수의 경계 조건 오류를 설명하고 테스트 세 개를 제안하라”이다.

**vLLM 지원 PR #60149는 조사 시 open·미병합 상태**다. 카드도 일반 배포판 대신 해당 PR 버전을 설치하도록 안내한다. 설치·가중치 실행은 이번에 하지 않았으며, HF가 자동 표시하는 일반 Transformers/vLLM snippet을 호환성 확인으로 채택하지 않았다. [현재 vLLM PR](https://github.com/vllm-project/vllm/pull/60149). llama.cpp 지원도 [draft PR #30306](https://github.com/ggml-org/llama.cpp/pull/30306) 단계다. 긴 문맥과 cache 모드는 각 구현에서 따로 검증해야 한다.

선택적 **last-loop KV cache**는 반복마다 별도 cache를 두는 비용을 줄인다. “cache overhead가 없다”는 주장을 전체 메모리·연산 비용이 없다는 의미로 확대하지 않는다. 256K는 카드의 검증 문맥 길이이며 모든 GPU·동시 요청 설정에서 보장되는 처리량이 아니다. 영어 중심 모델의 한국어 성능도 미검증이다. [실행 조건과 제한](https://huggingface.co/nvidia/NVIDIA-Nemotron-Labs-Dory1.0-4B-BF16).

## 2. ALoDLM: Qwen 초기화에서 적응형 diffusion·반복 구조로

**개발:** Amazon 연구진. **태그:** diffusion-language-model, looped-transformer, adaptive-computation, latent-refinement, text-generation, code, noncommercial-research.

### 직접 fine-tune 제외 규칙의 주요 구조 예외

**Qwen3-1.7B·Qwen3-8B에서 초기화한 파생 계보**를 명시한다. 독립 from-scratch foundation model로 소개하지 않는다. 논문은 별도 continued pretraining 없이 **5B-token 자료의 supervised conversion**을 수행했다고 설명한다. 따라서 새 이름·점수만으로 선정하지 않았다.

주요 차이는 autoregressive 답변 미세조정을 넘어 **masked diffusion + persistent latent recurrence + 학습된 halting gate**로 생성 과정이 바뀐다는 점이다. 8B는 36층을 **10층 prelude·16층 공유 recurrent core·10층 coda**로 분리하고 최대 네 번 반복한다. 1.7B는 28층 전체를 반복한다. 이미 결정된 토큰은 문맥으로 되먹임하고, 미해결 위치는 잠재 상태를 유지하며 더 계산한다. [논문 Appendix D](https://arxiv.org/html/2610.04198v1), [실제 배포 recurrence 설정](https://huggingface.co/amazon/ALoDLM-8B/blob/main/alodlm_config.json).

학습 목표는 토큰별 계산 종료 시점을 잠재변수로 두고 **conditional NELBO**를 통해 예측과 연산 배분을 함께 최적화한다. gate와 backbone을 공동학습하고 denoising·outcome credit·next-token 보조 손실을 결합한다. 이 구조·핵심 목표의 변화를 근거로 **주요 diffusion/recurrence 분기**로 인정한다. 일반 Qwen SFT·LoRA·포맷 변환 전체를 예외로 허용한다는 뜻은 아니다. [공식 학습 목표 구현 설명](https://github.com/amazon-science/ALoDLM/blob/main/docs/method.md).

### 활용 예와 비용·평가 주의

작은 수학·코드 문제에서 정확도와 토큰당 반복 연산량을 비교하는 연구 후보다. 공식 portable package를 별도 환경에 준비한 뒤 사용할 수 있는 예시는 다음과 같다.

```bash
alodlm-generate \
  --model amazon/ALoDLM-8B \
  --device cuda --precision bf16 \
  --mode entropy --q 0.5 --tau 0.4 \
  --max-new-tokens 512 \
  --prompt "Explain binary search."
```

`q`는 반복 종료 기준, `tau`는 병렬 token commitment 기준이다. 일반 Transformers에서 Qwen backbone만 로드하면 이 recurrence와 gate를 실행하지 않는다. `exit_gate.pt`와 recurrence metadata를 포함한 전용 경로가 필요하다. [공식 추론 가이드](https://github.com/amazon-science/ALoDLM/blob/main/docs/inference.md).

최적화 엔진과 portable decoder는 서로 다른 환경이다. 전자는 **A100 40GB에서 8B 경로를 확인했다는 개발사 고지**가 있지만, 이는 모든 문맥에서의 최소 VRAM 보증이 아니다. 후자는 CPU FP32도 지원하되 충분한 RAM과 느린 실행을 고려해야 한다. 첫 호출의 compilation·graph capture를 정상 상태 throughput과 섞지 않는다. [실행·측정 조건](https://github.com/amazon-science/ALoDLM/blob/main/docs/inference.md).

논문 표의 8B 평균 **80.3 대 Qwen3 78.5**는 11개 benchmark의 단순 평균인 **연구진 평가**다. 그 품질 비교의 한 pass당 단일 token commitment와, B200 throughput 비교의 병렬 commitment는 다른 설정이다. “평균 점수”를 모든 과제 우위로 바꾸거나 portable 구현에 최적화 엔진의 속도를 붙이지 않는다. [공식 결과·한계](https://github.com/amazon-science/ALoDLM). 반복 cache 구성과 첫 토큰까지의 추가 계산 때문에 짧은 답변에서는 지연이 늘 수 있고, loop를 늘린다고 항상 정답이 개선되지는 않는다.
